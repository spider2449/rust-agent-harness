# Task 347 - RAH v0.29 Scope and Authority Roadmap

Date: 2026-09-16
Status: research and product-scope decision complete
Task type: research / product scope / authority roadmap only

## Decision

Recommendation: **B. Explicit active-repository deactivation / close**

RAH v0.29 should add one host-owned Desktop workflow action that changes:

```text
active repository A
  -> no active repository
```

The admitted process-local member for A remains present and becomes inactive.
The action is not member removal, remembered-candidate deletion, repository
deletion, Git mutation, provider reload, or automatic switching.

Authority classification: **NONE**.

The existing authority model already permits zero active repositories, separates
membership from active authority, and requires withdrawal of repository-bound
state when the active context changes. v0.29 exposes that existing host-owned
withdrawal transition as an explicit human workflow. It adds no Tool, permission,
HostExplicit capability, provider, network, filesystem, index, or history
authority category.

ADR strategy: **no ADR needed**. ADR 0027 already defines process-local
membership, one-or-zero active repositories, fresh active-only composition,
switch invalidation, and the active-removal withdrawal boundary. Task 348 must
freeze the close contract against those rules without amending ADR 0027 or
combining close with active-member removal. ADR 0028 remains unchanged.

## Current released baseline

The current product boundary is:

- explicit process-local multi-repository membership;
- exactly zero or one active repository;
- explicit admission and explicit activation/switching;
- inactive-member removal completed in v0.28;
- durable descriptive remembered candidates with fresh re-admission;
- restart with zero executable repository authority;
- repository read/status/diff and bounded worktree authoring;
- separate Stage/Unstage index authority and reviewed Commit authority;
- exactly 11 HostExplicit-approved production Tools;
- host-owned Trusted Profile composition;
- local-stdio MCP and configured Process Plugin providers;
- the Codex AgentRuntime adapter; and
- a Windows-oriented Desktop workflow.

The v0.28 release theme was explicit inactive repository member removal. Its
certification proved that inactive B can be removed while active A remains
unchanged, that active removal is rejected, and that remembered candidates are
not forgotten. It did not claim GUI automation, model-selected dynamic Tool
dispatch, network isolation, linked-worktree semantics, or cross-platform live
parity.

Task 347 does not reopen or re-solve that release. It asks what useful product
capability remains after the curation loop now includes removal.

### Current implementation observations

`WorkspaceMembershipState::publish_active` can publish an active member, while
`remove` rejects that member as active. There is no corresponding production
transition that clears `active_member` while leaving the member in the map.

The Desktop command surface includes `choose_repository`,
`admit_remembered_workspace_candidate`, `activate_repository_member`, and
`remove_repository_member`. `disconnect_codex` withdraws runtime/provider
connection state but intentionally leaves the selected repository and active
membership in place. The current frontend disables switching while connected
and offers no “no active repository” action.

This leaves a normal user with two choices after working in the only active
repository: keep A selected, or remove A after first switching away. The latter
is impossible when A is the only member because active removal is correctly
forbidden. Disconnecting Codex is not equivalent to deactivating A: it does not
withdraw the repository selection or make the active-only boundary visible as
zero active repository state.

The current model therefore has the safe state already, but lacks the human
workflow that reaches it without discarding membership.

## Preserved invariants

The v0.29 decision preserves all established invariants:

- model request is not authorization;
- provider metadata cannot grant host authority;
- missing external permission fails closed;
- generic shell/process authority and generic `fs.write` remain absent;
- filesystem/worktree, index, history, and network authorities remain distinct;
- timeout, cancellation, disconnect, or removal is not rollback;
- uncertain external effects are never automatically replayed;
- process supervision is not OS sandboxing;
- Trusted Profile remains host-owned authority composition;
- remembered repository state remains descriptive;
- restart does not silently restore executable repository authority;
- path alone is not repository identity;
- at most one repository is active;
- there is no union ToolRegistry across repositories; and
- automatic admission and automatic activation remain forbidden.

## Candidate A - durable session / workflow continuity

### Product assessment

The central restart continuity problem is already partly solved. The Desktop
stores bounded completed conversation text in application-local SQLite, keeps
repository-specific namespaces, exposes a transcript, and offers explicit
Resume only after a fresh current connection. Remembered workspace candidates
and selected inactive preferences are also durable. The missing portion is
presentation-level context such as which inert candidate was last viewed, which
panel/filter was open, or a non-authoritative workflow note.

That remaining friction is real but less valuable than a missing lifecycle
action. Persisting a selected candidate or a workflow checkpoint can also make
“resume” look like repository restoration unless the UI and storage contract
remain very explicit. Current transcript persistence already has a schema,
privacy, migration, corruption, and bounded replay contract. Expanding it is
not free product continuity.

| Dimension | Rating | Explanation |
| --- | --- | --- |
| User value | Medium | Removes some restart reconstruction but does not restore executable work. |
| Frequency of likely use | Medium | Restart is normal, while the already-covered transcript is the common part. |

## Candidate B - explicit active-repository deactivation / close

### Product assessment

The current UI can admit, activate, switch, remove an inactive member, and
disconnect Codex. It cannot intentionally clear the active repository while
retaining the member. This matters when a user has finished work, wants to
review a neutral Desktop state, hands the application to another person, or
wants to ensure that no repository is currently selected before changing
context.

The safe workaround is poor. Disconnecting Codex only tears down the runtime;
it does not make repository selection absent. Switching requires another
admitted member and is intentionally blocked while connected. Removing the
only active member is correctly rejected. Thus close is a genuine ordinary
workflow capability, not another label for removal.

The action should be deliberately narrow in v0.29: the human first disconnects
Codex, then explicitly confirms Close Repository. Close is rejected while a
connection is active, connecting, or disconnecting; while a model turn or
started effect is active; or when state cannot be attributed to the active
member. This keeps provider shutdown and close as separate lifecycle actions.

### Same-dimension assessment

| Dimension | Rating | Explanation |
| --- | --- | --- |
| User value | High | Provides the missing safe zero-active end state without discarding membership. |
| Frequency of likely use | Medium-high | Finishing, pausing, handoff, privacy, and context changes are ordinary Desktop actions. |
| Product coherence after v0.28 | High | Completes the active lifecycle after inactive removal without redoing removal. |
| Existing workaround quality | Low | Disconnect is not deactivation; switch needs a second member; active removal is forbidden. |
| Authority delta | Low | NONE: host lifecycle withdrawal over existing membership/composition. |
| Security complexity | Medium | Correct invalidation and race ordering are required, but no new effect authority appears. |
| Privacy impact | Low | Presentation changes to bounded status; no new path, credential, or transcript field. |
| Persistence/restart implications | Low | Close is process-local; remembered candidates and transcript remain under existing rules. |

## Candidate C - HostExplicit `repo.create-directory`

### Product assessment

The ordinary bounded directory authority already exists. The current Tool
accepts one repository-relative path, requires an existing safe parent, rejects
reparse/nested-boundary problems, creates one ordinary directory leaf, and does
not invoke Git, create ancestors, add `.gitkeep`, stage, or commit. Git does not
track an empty directory, so a successful operation may leave status unchanged.

The Desktop registry can include this bounded Tool for an admitted repository,
but `host_kind` deliberately excludes it from HostExplicit. Promoting it would
give a human a reviewed structural-authoring route, probably as HostExplicit
#12. That solves a real scaffolding gap when a parent directory is absent, but
the existing file-creation route and ordinary bounded directory Tool cover
parts of the workflow. The reviewed route would need complete review semantics,
empty-directory post-effect proof, reparse and identity checks, uncertainty
handling, exact allowlist changes, and a Windows live effect gate.

## Candidate D - linked Git worktree support

### Product assessment

The current admission and authority model is built around an ordinary
non-bare repository with a supported `.git` directory and a canonical root.
A linked worktree commonly has a `.git` file that points to a common Git
directory, while its `HEAD`, index, and worktree administrative state are
worktree-local. Two worktrees can therefore share objects and some refs while
requiring distinct worktree-local mutation and currentness boundaries.

Path equality is not enough. Safe support would require a composite identity
for the worktree root, common Git directory, worktree administrative identity,
local HEAD/index, and Git executable; distinct alias/duplicate rules; active
switch and member semantics; and isolated Stage/Unstage/Commit behavior. This
is repository identity research, not just accepting `.git` files.

## Candidate E - network MCP / Streamable HTTP

### Product assessment

Remote MCP transport would add a networked provider boundary to a product that
currently supports local-stdio MCP and Process Plugin providers. It is not one
authority decision. The design would need to keep separate:

```text
network connection authority
!= endpoint configuration
!= credential authority
!= remote server identity
!= Tool admission
!= Tool execution permission
```

The host would need an explicit endpoint and transport policy, TLS and server
verification rules, credential storage/use rules, redirect policy, request and
response limits, cancellation/timeouts, reconnect ownership, and privacy
handling. A remote server advertising a Tool cannot grant that Tool RAH
authority. Disconnect or timeout cannot imply rollback or safe replay of an
uncertain remote effect. This is potentially valuable, but there is no current
repository-workflow evidence that makes this the next normal Desktop need.

## Candidate G - explicit Trusted Profile reload

### Product assessment

The current profile flow is host-selected and explicit. Static selection validates
provider-only profile intent without spawning; Connect freshly loads the source,
activates configured providers, merges a new registry, and publishes only after
complete success. Provider changes are therefore naturally applied by an
explicit disconnect/reconnect or a fresh selection flow.

## Why Candidate B wins now

1. It fixes a concrete ordinary action that is currently impossible: leave the
   active repository unselected while keeping it admitted.
2. It is the next coherent lifecycle boundary after v0.28 completed inactive
   member removal, but it does not redo removal or change membership curation.
3. It improves the safety explanation of Desktop: “no active repository” is an
   explicit human state, not merely an application-startup or error condition.

## v0.29 scope freeze

### In scope

- One explicit human Desktop Close/Deactivate Repository action.
- Transition of the currently active member from active to no active member,
  retaining that member in process-local membership as inactive.
- A closed no-argument action resolved only against the current host-selected
  member state; no path, repository root, Git identity, Tool name, provider
  metadata, or frontend authority fields.
- Explicit precondition that Codex is disconnected and not connecting or
  disconnecting.
- Rejection while a model turn, started HostExplicit effect, Stage/Unstage
  native effect, provider transition, or otherwise unattributable executable
  lifecycle state is active.
- Invalidation of repository-bound prepared HostExplicit state, reviewed
  Commit authorization, Stage/Unstage selectors/reservations where no effect
  has started, repository workflow/review state, repository Tool composition,
  and active conversation binding before no-active publication.
- Fresh repository-generation/active-selection currentness so old A state,
  tickets, reviews, actions, and runtime snapshots cannot act after close.
- A sanitized no-active membership/status presentation that still shows A as
  inactive and separately permits fresh explicit activation later.
- Deterministic race tests over close versus activation, admission, removal,
  Connect/Disconnect, model turns, HostExplicit, Commit, and Stage/Unstage.
- One host-driven Windows production-backend live gate over disposable real
  repositories, with no GUI-certification claim unless GUI evidence is actually
  executed and independently accepted.

### Out of scope

- Active-member removal. Close must never remove A from membership.
- Remembered-candidate deletion, editing, migration, or automatic re-admission.
- Automatic switching, automatic activation, automatic reconnection, or
  automatic provider shutdown.
- Implicit Disconnect Codex as part of Close. Human Disconnect remains a
  separate action and required precondition.
- New Tool, PermissionLevel, HostExplicit eligibility, or HostExplicit count
  change. The current production count remains exactly 11.
- `repo.create-directory` HostExplicit promotion.
- Linked Git worktrees, common-Git identity, cross-worktree operations, or
  cross-process membership.
- Network MCP, Streamable HTTP, remote credentials, endpoint policy, or
  network isolation.
- Plugin installation/download/marketplace, PluginManager, or model-controlled
  plugin lifecycle.
- Trusted Profile reload, filesystem watching, provider hot reload, or partial
  profile composition.
- Conversation schema changes, automatic conversation resume, native Codex
  thread restoration, transcript deletion, or uncertain-effect replay.
- Repository/file/directory/.git/index/HEAD/ref/history mutation, rollback,
  compensation, cleanup, or recovery claims.
- Generic shell, process, filesystem, Git, or network authority.
- GUI automation as a product authority claim.
- Cargo, dependency, permission, ADR, schema, or version changes in Task 347.

### Authority boundary

Close is a host-owned lifecycle transition over existing process-local
membership and active composition. It is not a Tool and does not pass through
the model ToolRegistry or HostExplicit dispatcher. It grants no filesystem,
worktree, index, Git, Commit, provider, network, credential, or process
authority.

The transition must use the same membership-before-lifecycle coordination
discipline as activation/removal. It must capture and validate the current
active member, then invalidate repository-bound state and publish a single
zero-active state. It must not leave a repository-bound registry or executable
repository object reachable while presenting no active repository.

The member remains in `WorkspaceMembershipState` with its original process-local
member identity. That identity is still descriptive/inert while inactive and is
not a durable authority handle. Later activation repeats current repository
identity validation and constructs fresh repository-bound composition.

### Human consent

The user explicitly selects Close Repository in the Desktop UI and confirms the
action. The UI sends a closed no-argument action; the backend resolves the
current active member under lifecycle coordination and rejects all
authority-shaped fields.

The backend owns all checks and the linearization point. Model output, provider
metadata, remembered catalog data, presentation state, and a stale frontend
selector cannot authorize close. A stale, malformed, non-active, or unknown
request fails closed with no state change.

Close is disabled in the UI when its preconditions are visibly false, but UI
state is not relied upon for authorization. The backend repeats every check.

### Persistence

Close is process-local. It does not mutate the remembered workspace catalog,
candidate labels, location hints, or last-active descriptive data except for
any explicitly approved descriptive presentation update that Task 348 proves
cannot act as an activation request. The conservative v0.29 contract should
leave the catalog bytes unchanged.

Completed transcript data remains in its existing private repository namespace.
Close clears the in-memory conversation binding/history for the active context
and may record the existing repository-context separator if the current
transcript contract requires it, but it does not delete, migrate, replay, or
automatically resume transcript data. Reopening A requires explicit activation;
using its prior transcript still requires the existing explicit Resume flow.

Restart remains unchanged: zero membership, zero active repository, zero
repository ToolRegistry, zero Commit/Stage/Unstage/HostExplicit state, zero
provider/runtime state, and no executable repository conversation context.

### Currentness

The close contract must bind its final publication to:

- the current process-local `RepositoryMemberId` and its admission generation;
- the active-selection/member relationship captured at preparation;
- the current repository generation and repository identity binding;
- lifecycle coordination state and connection generation/state;
- chat/model-turn generation and HostInvocationCoordinator state;
- repository workflow/observation generation;
- Stage/Unstage reservation token and repository binding; and
- reviewed Commit identity/currentness and HostExplicit preparation identity.

Close must advance the existing repository/active-selection currentness at the
withdrawal publication point. It must not reuse or persist an old executable
generation. A later activation of the retained A member gets fresh active
composition and currentness; an old A snapshot, action, ticket, review, or
runtime publication cannot become current by returning to the same member.

The close path must not clear an external-effect owner merely because its
binding is stale. Started or uncertain effects remain governed by their current
ownership and no-replay semantics; close is rejected while such an effect is
active or cannot be safely attributed.

### Failure semantics

- Malformed, unknown, stale, or non-active selector: bounded error, zero state
  change, zero repository/filesystem/Git/provider effect.
- No active repository: bounded no-active result, zero state change.
- Connected, connecting, or disconnecting runtime: bounded busy result; the
  user must explicitly Disconnect first; no provider teardown occurs.
- Active model turn, started HostExplicit operation, or Stage/Unstage native
  effect: bounded busy result; no cancellation or rollback is attempted.
- Pending no-effect review/preparation: invalidate it as part of the close
  transition, consume no native effect, and do not replay it after reactivation.
- Pending reviewed Commit authorization: revoke it before publication; a later
  activation requires fresh observation/review/authorization.
- Failure before the infallible withdrawal point: preserve the old active
  state and all unrelated state.
- Successful close: clear active repository-bound executable state, retain the
  member as inactive, publish no-active presentation, and emit only bounded
  descriptive status/activity.
- Cancellation, crash, disconnect, or lost response: never claim rollback or
  infer that an external effect did not happen. Close must not be used as
  uncertain-effect recovery.
- Restart: reconstruct the existing zero-authority state and never auto-close,
  auto-admit, auto-activate, reconnect, or restore a repository authority.

### Privacy

Generic activity, model-visible context, Effective Authority, error values,
test evidence, and persisted state must not disclose native paths, `.git` paths,
filesystem identities, Git executable identity, credentials, registry handles,
tickets, raw Tool input/output, or source-bearing reviews.

The dedicated human repository panel may display the existing bounded
repository label/basename and the fact that it is inactive. Close status should
say that no repository is active and that A remains admitted; it should not
expose private identity evidence. The remembered catalog and transcript retain
their existing independent privacy contracts.

### Windows live gate

Before v0.29 release, exact-source host-driven production-backend evidence must
use a fresh disposable Windows fixture and demonstrate:

1. Admit A (and optionally B), explicitly activate A, and verify the existing
   active-only composition.
2. Disconnect Codex explicitly and prove the runtime/provider state is
   withdrawn before Close is accepted.
3. Close A and prove A remains in membership as inactive while
   `active_member_id` is absent, repository selection is absent, and the
   repository-bound Tool/Commit/Stage/Unstage/HostExplicit executable state is
   absent.
4. Prove A's real repository files, `.git`, index, HEAD, refs, history, and
   sentinel bytes are unchanged; count zero Git/filesystem effects from Close.
5. Prove pending no-effect HostExplicit/Commit/workflow state cannot execute
   after Close, while a started/uncertain effect blocks Close and is not
   replayed.
6. Prove close rejects connected, connecting, active-chat, stale, malformed,
   unknown, and repeated requests with bounded zero-effect outcomes.
7. Race Close against activation, admission, inactive removal, Connect,
   HostExplicit publication, Commit authorization, and Stage/Unstage reservation
   using deterministic barriers at admission and final publication boundaries.
8. Reactivate A explicitly and prove fresh repository generation/composition;
   old close-era selectors, actions, tickets, reviews, and snapshots cannot
   execute. If B is present, prove B remains independently inactive and no
   union registry appears.
9. Prove remembered-candidate bytes and completed transcript bytes are not
   changed by Close, and restart still restores zero executable authority.
10. Prove model requests, model-selected Tool requests, MCP activation, Process
    Plugin activation, network Git, automatic activation, automatic provider
    reconnect, and automatic commit counts remain zero.
11. Record only bounded sanitized status/activity. Do not claim GUI automation,
    model-selected dynamic Tool dispatch, race-free TOCTOU, network isolation,
    OS sandboxing, rollback, cross-platform parity, or linked-worktree support.

The live gate is host-driven evidence over production Desktop/backend paths.
Fake Codex, direct state injection, helper-only membership assertions, or a
frontend screenshot alone do not establish the gate.
