## 4. Released v0.25 product and authority inventory

The released workflow is already:

~~~text
inspect repository
  -> create a local branch
  -> review and modify existing files
  -> create new files under existing safe parents
  -> delete narrow clean tracked files
  -> rename/move narrow clean tracked files
  -> Stage / Unstage through the separate repository workflow
  -> review and authorize a staged-snapshot Commit through the separate Commit control
~~~

The exact current HostExplicit-eligible production set is:

~~~text
fs.read
repo.file-info
repo.status
repo.diff
repo.diff-staged
repo.create-branch
repo.patch
repo.edit-files
repo.create-file
repo.delete-file
repo.rename-file
~~~

This is an exact host-owned allowlist. It is not inferred from
PermissionLevel::Execute, Tool registration, Effective Authority display,
provider metadata, model output, or frontend state. The following remain
outside the set:

- repo.create-directory, despite its accepted ordinary Tool foundation;
- repo.commit, because durable Git history/current-branch mutation remains a
  separate reviewed Commit workflow;
- MCP Tools, Process Plugin Tools, fixture/diagnostic Tools, unknown Tools, and
  any provider-defined Tool.

Authority layers currently remain separate:

| Layer | Current boundary | v0.25 state |
| --- | --- | --- |
| Repository observation | RAH-owned read/status/diff Tools | HostExplicit eligible |
| Worktree content | repo.patch, repo.edit-files, repo.create-file, repo.delete-file, repo.rename-file | HostExplicit eligible through capability-specific reviewed routes |
| Directory topology | repo.create-directory, ADR 0019 | Ordinary foundation only; HostExplicit-ineligible |
| Index mutation | Stage / Unstage | Separate reviewed repository workflow |
| Git history/ref | repo.commit, ADR 0016 | Separate reviewed staged-snapshot Commit workflow |
| Local branch creation | repo.create-branch, ADR 0020 | HostExplicit eligible; branch switch remains out of scope |
| External providers | local stdio MCP and configured Process Plugin adapters | Tool providers; no generic HostExplicit route |
| Trusted Profile | host-owned static authority composition | No dynamic reload/revocation redesign |
| Conversation/session state | bounded descriptive transcript and context persistence | No authority-ticket persistence or effect replay |

## 5. Concrete remaining product gaps

The local authoring primitive gap has narrowed substantially. A user can now
complete the common single-repository edit loop, including path-preserving
rename/move, without turning RAH into generic filesystem or Git authority.
The remaining gaps are different in kind:

1. A new directory leaf cannot yet be requested through the reviewed
   HostExplicit route. This blocks a new topology step, but the leaf is empty
   and Git-invisible until a separate file creation occurs.
2. Desktop treats a user workspace as one active repository context. A user
   with separate frontend/backend, service/library, or sibling repositories
   must replace the selected repository context rather than manage admitted
   repositories as independent identities in one workspace/session.
3. A generic HostExplicit Commit route is absent, but the product already has a
   reviewed staged-snapshot Commit surface. The absence is primarily a
   reachability/convenience question, not an unreviewed history primitive.
4. A multi-operation authoring bundle could reduce clicks, but existing
   operations are deliberately single-effect and non-transactional. A bundle
   would introduce partial-success and review-obscurity semantics before it
   solves a missing capability.
5. Descriptive continuity can improve, but conversation persistence already
   exists and intentionally excludes authority restoration or effect replay.
6. Network MCP, plugin lifecycle management, and live Trusted Profile reload
   are larger trust/lifecycle changes rather than ordinary next Tools.
7. Linux/macOS live certification and platform corrections would improve
   confidence, but are release/certification work and do not by themselves
   close a new user workflow gap.

## 6. Scoring method

Every score is ordinal from 1 through 5. Product columns score amount of
benefit: 1 is low and 5 is high. Exposure/cost columns score amount of risk or
cost: 1 is low and 5 is high. Proofability, deterministic-testability, and
release fit score desirability: 1 is weak and 5 is strong. The directions are
shown in the table headings so security cost is not silently combined with
product value.

Frequency scores are workflow judgments from the current product boundary,
not telemetry claims. A high score means the capability applies broadly to
real coding work; it does not claim a measured user percentage.

## 8. Candidate-by-candidate analysis

### A. HostExplicit reviewed directory creation

The existing repo.create-directory foundation and ADR 0019 already define a
narrow operation: one absent ordinary directory leaf, one existing safe parent,
one selected repository, no recursive parent creation, and no directory move or
deletion. The current policy captures repository identity, .git identity,
parent identity, and Git metadata; revalidates them; performs one native
create_dir attempt; and classifies verified success, known no-effect, or
uncertain outcome. The Tool is constructed for a selected repository, but is
not in the HostExplicit set.

Concrete workflow enabled: a user can make src/new-module, tests/fixtures, or
docs/topic when the immediate parent already exists, then separately use the
existing reviewed file-creation route to add content.

It still cannot create a multi-level hierarchy in one operation, create the
first file, stage, commit, delete/move a directory, or make an empty directory
visible to Git. It therefore does not complete a common new-module task by
itself. A subsequent file operation is required immediately in the usual case.

The capability is nevertheless a strong runner-up because it reuses ADR 0019,
adds no new underlying filesystem authority, has bounded local effects, and is
amenable to deterministic Windows alias/reparse tests. Its weakness is product
completion, not a large security delta.

### B. Multi-repository workspace support

The current Desktop model has a single selected repository and a single
repository generation. Selecting another repository replaces the binding,
clears the repository workflow/commit-review context, changes the persistence
namespace, and starts a new conversation context. That is a safe single-repo
boundary, but it makes a workspace containing several independent repositories
feel like repeated replacement of authority rather than an explicitly managed
set of repository identities.

Concrete workflow enabled: a user explicitly admits a workspace's frontend,
backend, library, or service repositories; sees each repository's status and
Effective Authority independently; chooses one as the active target; and runs
the existing bounded tools against that repository without implying authority
over any sibling. A user can then switch targets explicitly, with per-repo
currentness and Commit review preserved only where the host's fresh state still
proves it valid.

It still cannot perform a cross-repository edit, move, rename, Stage, Commit,
transaction, or shared credential/network operation. It does not make the
existing local authoring primitives more powerful; it makes them available in
one safely organized workspace. A single operation remains bound to exactly
one admitted repository.

This candidate is not a workspace-wide write permission. It is a host-owned
organizational and authority-composition boundary around existing
repository-scoped authorities. Its complexity is real: identity replacement,
privacy, nested repositories, independent generations, and stale Commit
reviews must be explicit. Those costs are lower than creating a new mutation,
network, install, durable-history, or live-profile authority plane.

### C. HostExplicit reviewed Git Commit

The current reviewed Commit workflow already binds a staged snapshot to the
exact repository, index evidence, staged tree, attached branch, expected
parent, commit policy, identity, hook/signing policy, and one-attempt result
semantics. It has separate Commit control and invalidation when relevant
worktree/index effects start.

Concrete workflow enabled by a second HostExplicit route: a Tool-reachability
caller could request the same kind of durable commit through the generic host
invocation coordinator. The user would still need the existing staged review,
message policy, currentness checks, and Commit authorization. The route would
not include Stage, push, fetch, pull, or any other Git operation.

What remains impossible is unchanged: arbitrary ref mutation, branch switch,
remote Git, and automatic Stage remain forbidden. The principal benefit is
button/route placement or model/tool reachability, while the principal cost is
a second direct route to Git objects, the current branch ref, and reflogs.
That is disproportionate to the friction removed in this milestone.

### D. Reviewed multi-operation authoring

An ordered review could describe existing edit, create, delete, rename, and,
if separately admitted, directory operations. It does not become a
transaction. Each operation has its own effect boundary, currentness, ticket,
result, and possible-effect uncertainty. After one effect starts, the
repository generation or Commit authorization may change; later preparations
may need revalidation or cancellation. A failure can leave a valid prefix and
an unknown or failed suffix, and heterogeneous effects cannot be rolled back
by RAH.

Concrete workflow enabled: fewer review screens for a known sequence. What
remains impossible: atomic all-or-nothing authoring, automatic rollback,
automatic cleanup, and safe replay after a lost result. A large review can also
obscure which operation owns which authority and make the user believe the
sequence is transactional. This is a convenience coordinator, not a missing
primitive, and is deferred.

### E. Descriptive session/workflow continuity

RAH already persists bounded descriptive conversation pairs in a repository-
namespaced context and supports explicit resume with context reconciliation.
The implementation intentionally clears or separates context when repository
or model identity changes. Drafts, selected-repository intent, and unfinished
descriptive authoring state could be improved without effect authority.

Concrete workflow enabled: return to an unfinished explanation or draft after
restart and see which repository membership/selection was last intended.
What remains impossible, deliberately: restoring a HostExplicit ticket,
serializing a retained preparation, resuming an interrupted effect, or
replaying an uncertain operation. Because the descriptive gap is narrower than
the multi-repository organizational gap, this is deferred behind the selected
foundation and must remain authority-free.

### F. Network MCP / Streamable HTTP

The current local stdio MCP adapter has bounded lifecycle, cancellation,
disconnect, result, and no-replay semantics. Streamable HTTP is a different
authority plane. It requires endpoint trust, TLS and authentication policy,
credential storage/use, redirect handling, DNS and proxy behavior, SSRF
defense, host/IP allowlists, schema/tool admission, reconnect semantics,
remote uncertain effects, cancellation/disconnect, retry/replay rules, and
privacy/exfiltration analysis.

Concrete workflow enabled: reach remote MCP servers and their tools. What
remains impossible should include no automatic approval or provider-granted
RAH authority. This is valuable for integrations but is not a safe local
workflow increment and would require a new network authority decision.

### G. Plugin lifecycle / PluginManager

Process Plugin support is configured execution and admission of an explicitly
configured child process. It is not install, discovery, update, replacement,
restart, or removal authority. A manager would need package provenance,
download/network rules, executable admission, version identity, replacement
races, process restart ownership, removal behavior, and recovery after a
failed update.

Concrete workflow enabled: install or update a provider without manual host
configuration. What remains impossible under the existing boundary is exactly
that lifecycle management. The trust and supply-chain delta is much larger
than a local authoring milestone, so it is deferred.

### H. Dynamic Trusted Profile reload

Trusted Profile is a host-owned authority-composition boundary. A live reload
would need explicit old/new profile generations, revocation of old Effective
Authority, prepared-ticket behavior, running-operation behavior, provider
shutdown/startup, stale frontend state, in-flight execution, and reconnect
semantics. A profile change cannot be treated as a convenience settings
refresh.

Concrete workflow enabled: change provider/tool composition without a manual
reconnect. What remains impossible without a new revocation contract is safe
mid-flight authority replacement. The product benefit is operational, but the
security semantics are larger than the selected v0.26 capability.

### I. Platform certification expansion

Linux/macOS live certification or platform-specific corrections could turn
current deterministic evidence and Windows host-driven evidence into broader
production confidence. They must remain distinct from feature work: a
deterministic Unix test is not Unix production live evidence, and a Windows
host-driven route is not model-selected dispatch evidence.

Concrete workflow enabled: greater confidence for an already existing route on
an additional platform. What remains impossible is any new operation. This is
important release work when selected by a milestone audit, but it does not
answer the product-gap question as strongly as multi-repository selection.

## 9. Directory creation versus the alternatives

### One reviewed directory leaf versus current reviewed file creation

| Question | One reviewed directory leaf | Current repo.create-file route |
| --- | --- | --- |
| Target | One absent directory entry | One absent file under one existing safe parent |
| Parent | Must already exist and be identity-verified | Must already exist and be identity-verified |
| Ancestors | Never created | Never created |
| Git visibility | Empty directory is not tracked | New file is Git-visible as an untracked path |
| Typical next step | A second file-create authorization | No topology step required |
| Failure residue | Empty directory may remain if later file creation fails | Create/write semantics already classify known partial/uncertain outcomes |
| Native effect | One create_dir attempt | One bounded file create/write operation |
| Currentness | Parent, repository identity, and Git metadata | Parent, repository identity, target absence, and file preimage state |
| Windows concerns | Case/alias/reparse/reserved-name path handling | Existing file-create Windows path and reparse contract |
| Product completion | Structural prerequisite only | Can create the requested artifact directly |

Directory creation is not equivalent to recursive mkdir, scaffolding,
create-file, directory deletion, or directory move. A new package or test
hierarchy may require several separate leaf operations, and every file still
requires its own review. If a later file create fails, RAH cannot remove the
empty directory as compensation; if the directory effect becomes uncertain,
it cannot retry merely because no Git change is visible.

The existing policy's Git snapshot is useful proof that the directory action
did not mutate Git metadata, but that same property means Git status cannot by
itself prove that the directory was absent after an uncertain native call.
Post-effect filesystem observation and parent identity proof remain necessary.
Windows filesystem-equivalent spellings, reparse ancestry, reserved names,
case behavior, and one-attempt semantics require capability-specific review.

### Why A is not the selected capability

Reviewed directory creation is the safest structural runner-up and should be
researched next if multi-repository research disproves the product hypothesis.
It is not the strongest v0.26 capability because it creates an empty,
non-Git-visible intermediate state and immediately requires another explicit
authorization for the artifact that users usually intend. Multi-repository
support improves access to every existing bounded authoring operation across a
real workspace while adding no new underlying mutation authority.

## 10. Multi-repository special analysis

### Hypothesis: workspace is organizational scope; repository is mutation-authority scope

The hypothesis fits the current RAH architecture if the scopes remain
strictly separate:

~~~text
Workspace
  ├─ descriptive membership / user organization
  └─ admitted Repository identities
       └─ one active host-selected repository at a time
            └─ existing repository-scoped ToolRegistry and authority composition
~~~

A workspace is not a permission granting object. A repository is not a
workspace-wide write target. The active repository is a host convenience and
selection state, not authorization by itself. The existing exact Tool
allowlist, ToolRegistry, permission gate, D2 current-definition check,
capability policy, and repository lease remain authoritative.

### Research-level state contract

The next research task should settle these types and transitions without
implementing them in Task 308:

- **Workspace identity:** a host-owned local workspace/session identity. It
  organizes admitted repositories and descriptive UI state; it grants no
  filesystem, Git, network, process, or provider authority.
- **Repository identity:** an opaque host-owned stable identity for one
  admitted canonical repository binding, with private root, Git metadata
  identity, executable identity, and current repository generation. Public
  activity and model-visible data should use bounded names or opaque IDs, not
  raw absolute paths unless the trusted user-facing surface explicitly needs
  the path.
- **Explicit admission:** each repository is selected/admitted by the trusted
  host and independently validated. No model, provider, repository content,
  sibling repository, or workspace file may admit another repository.
- **Active repository:** a convenience pointer to one admitted binding. Every
  Tool operation and HostExplicit ticket must still bind the repository ID,
  private identity, exact current registry/composition, and repository
  generation. An active pointer cannot broaden authority.
- **Independent composition:** each repository has its own repository-bound
  Tools/authorities and Effective Authority result. A shared neutral provider
  composition may exist, but it cannot turn one repository's Tool into a
  workspace-wide Tool.
- **Commit authorization:** a reviewed Commit authorization is bound to one
  repository, one staged snapshot, one attached branch/parent, and one
  repository generation. It is never transferable across repositories.
- **Tickets/currentness:** HostExplicit tickets are capability-specific,
  single-use, process-local, nonpersistent, and repository-bound. Changing or
  removing the repository invalidates currentness; there is no ticket migration
  or automatic reprepare.
- **Removal:** removing membership withdraws that repository from new
  composition and clears its descriptive active state. It must not claim to
  roll back an already-started effect. A running operation follows existing
  uncertainty/ownership rules, and later work requires fresh admission and
  observation.
- **Restart persistence:** descriptive membership or last-selection intent may
  be persisted only as inert data. Restart must revalidate repository identity
  and freshly compose authority; it must not restore a ToolRegistry,
  HostExplicit ticket, retained preparation, Commit authorization, or in-flight
  operation.
- **Nested repositories:** parent and nested repositories are distinct
  identities when explicitly admitted. A path operation must bind exactly one
  selected root; crossing a nested-repository boundary is rejected unless a
  separately admitted repository is explicitly selected. No implicit discovery
  or parent-to-child authority inheritance is allowed.
- **Cross-repository operations:** edit, create, delete, rename, directory,
  Stage, Commit, and branch operations spanning two repository identities are
  rejected. There are no cross-repository atomic transactions or shared
  tickets.
- **Privacy/path exposure:** the trusted UI may show a selected path for user
  orientation, but activity, transcript, provider input, diagnostics, and
  Effective Authority should use bounded/sanitized forms. Repository content,
  credential material, raw private identities, and authority handles do not
  become workspace metadata.

### Does it require new underlying authority?

No new mutation authority is necessary for the selection foundation. It reuses
the accepted repository-scoped authorities: observation, worktree authoring,
branch creation, index workflow, reviewed Commit control, and existing provider
composition. It does require a new host-owned organizational/composition
boundary for membership, stable identity, active selection, and per-repository
currentness. That is a reachability and scope boundary, not a generic write
permission.

The current Effective Authority surface must become per-repository
observational data. It must not become a workspace-wide union that implies a
Tool can run against every member. Likewise, one ToolRegistry instance may be
reused only if every repository-bound Tool and dispatch context is selected and
validated explicitly; otherwise the safer composition is an independently
bound registry per active repository. This is a research decision, not an
authorization to change ToolRegistry in Task 308.

## 12. Exact recommended authority boundary

The selected capability is **multi-repository workspace/repository selection
foundation**. Its exact boundary is:

~~~text
host-admitted Workspace membership
  + opaque host-owned Repository identity per admitted root
  + explicit active-repository selection
  + per-repository Effective Authority and generation/currentness
  + existing repository-bound ToolRegistry/permission/D2/lease boundaries
  + existing single-repository HostExplicit eligible set
~~~

It reuses existing mutation authorities and does not make any new Tool
HostExplicit-eligible. The new authority is only the host-owned ability to
admit, retain descriptive membership for, select, and withdraw a repository
binding. Admission is not model-selected; active selection is not generic
permission; a workspace is not a filesystem root; and a sibling repository
cannot be reached by a path supplied to a Tool bound to another repository.

If a later implementation chooses to persist membership, that persistence is
descriptive and inert. It must not serialize tickets, preparations, raw
authority handles, reviewed content, Commit authorization, provider
credentials, or a resumable effect.

| Does it create install/update authority? | No | Process Plugin remains configured execution; no manager is added |
| Does it create durable resumable authority? | No | Only inert descriptive membership may persist; tickets and preparations remain process-local and nonresumable |
| Does it create dynamic Trusted Profile authority revocation semantics? | No | Repository selection/removal uses ordinary generation/currentness invalidation; profile hot reload is deferred |
| Does it require a new generic Tool dispatch path? | No | Existing ToolRegistry, permission, D2, and authorized_tool_dispatch remain the only Tool route |

The recommendation therefore does not need a larger authority plane to justify
its product value. Its new research subject is organizational identity and
authority composition, not generic execution.

## 14. Explicit deferrals

This recommendation explicitly defers:

- HostExplicit directory creation and any change to the exact eligible set;
- HostExplicit repo.commit or any second direct durable-history route;
- Stage + Commit bundling, push, fetch, pull, remote Git, checkout, switch,
  merge, rebase, reset, stash, tags, arbitrary refs, or recovery/reset
  authority;
- heterogeneous multi-operation authoring, transactionality, rollback,
  compensation, cleanup, automatic reprepare, retry, or replay;
- workspace-wide filesystem or Git permission, cross-repository operations,
  cross-repository transactions, shared tickets, and shared Commit
  authorization;
- model/provider-selected repository admission, implicit repository selection,
  nested-repository auto-discovery, or path-based sibling traversal;
- persisted HostExplicit tickets, serialized preparations, authority
  restoration after restart, and resumable effectful work;
- Network MCP / Streamable HTTP, credential authority, redirects, proxy/DNS
  confinement, SSRF policy, and remote uncertain effects;
- PluginManager installation, download, provenance, update, replacement,
  restart, or removal authority;
- dynamic Trusted Profile reload, old/new authority revocation, provider
  hot-swap, and mid-flight profile changes; and
- platform live certification, version/dependency changes, release tagging,
  publication, or any inference-engine work as part of the scope decision.

## 15. Known nonclaims

This roadmap does not claim:

- that a workspace membership grants permission to any repository;
- that a model, provider, MCP server, Process Plugin, repository content, or
  frontend state may select or admit a repository;
- that a workspace-wide ToolRegistry or union Effective Authority is safe;
- that any operation may span repository identities or nested boundaries;
- that active-repository selection is a new mutation authority;
- that descriptive membership persistence restores authority after restart;
- that tickets, preparations, Commit authorizations, or uncertain operations
  can be serialized, resumed, replayed, rolled back, or migrated;
- that a repository removal rolls back an already-started effect;
- that a directory leaf is Git-visible or completes package/module creation;
- that a HostExplicit Commit route is selected or that Commit is missing;
- that a multi-operation review is transactional or safely rollback-capable;
- that local stdio MCP evidence proves network MCP safety;
- that configured Process Plugin support proves PluginManager safety;
- that static Trusted Profile composition proves hot-reload revocation safety;
- that deterministic Unix tests prove Linux/macOS production live behavior;
- that Windows host-driven HostExplicit evidence is model-selected dispatch;
- that frontend confirmation, PermissionLevel::Execute, Tool registration,
  Effective Authority visibility, or provider metadata creates authority;
- that timeout, cancellation, disconnect, crash, or lost response implies no
  effect or permits replay; or
- that process supervision is OS sandboxing, or that any current boundary
  proves network isolation, race-free TOCTOU, or rollback.

## 16. Minimum safe research/implementation sequence

This sequence is a gated proposal, not authorization from Task 308:

1. **Capability-specific identity research:** define workspace identity,
   repository identity, explicit admission, nested-repository handling,
   private path/identity storage, public sanitization, and membership removal.
2. **Authority-composition research:** specify active selection, per-repository
   Effective Authority, independent generations, ToolRegistry binding,
   HostExplicit ticket binding, Commit authorization binding, running-operation
   behavior, and restart behavior. Prove that the design cannot form a
   workspace-wide write permission.
3. **ADR decision:** accept a new workspace/repository identity and
   composition boundary only if the research closes the above cases. Do not
   amend mutation ADRs or ADR 0021 merely to make selection convenient.
4. **Deterministic backend foundation:** only after the ADR, implement inert
   membership and fresh host admission/currentness with no new Tool
   eligibility. Test repository isolation, nested roots, removal, stale
   generations, and privacy values under every serialized field.
5. **Desktop presentation:** expose explicit membership and active selection;
   keep Effective Authority observational and paths bounded. Do not add a
   generic Tool console or workspace-wide permission.
6. **Deterministic end-to-end gates:** run the existing sequential Cargo gates,
   multi-repository isolation tests, Commit/ticket invalidation tests,
   restart-without-authority tests, and git diff --check.
7. **Separately authorized live certification:** use fresh disposable
   repositories, prove one selected repository at a time, preserve no-replay
   behavior, and do not convert host-driven evidence into a model-selected
   claim.
8. **Milestone audit and release preparation:** verify exact eligibility,
   unchanged v0.25 identity, privacy, nonclaims, exact-head CI, and clean
   scope before any v0.26 release work.

## 18. One primary recommendation

**Recommend multi-repository workspace/repository selection foundation for RAH
v0.26.**

It is the strongest product step after the v0.25 authoring routes because it
addresses the remaining single-repository workflow bottleneck while reusing
the complete, reviewed repository-authoring set. Its authority delta is a
new host-owned organizational and authority-composition boundary, not a new
filesystem, Git, network, install, or durable-history authority. The active
repository remains explicit and singular for every operation; per-repository
identity, Effective Authority, currentness, tickets, and Commit authorization
remain independent.

The runner-up is reviewed HostExplicit creation of exactly one directory leaf
under one existing safe parent. It has the smaller implementation and
security surface, but does not complete the usual new artifact workflow and
still requires a separate repo.create-file authorization. It should be
researched if the multi-repository identity/composition evidence fails.

The next task is therefore **repository/workspace identity and
authority-composition research**, not implementation.
