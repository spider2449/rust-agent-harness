## 1. Product capability

v0.13 adds exactly one narrow model-visible capability: `repo.delete-file`.
The implementation in `crates/rah-tools/src/repository_delete_file.rs` admits
one explicit repository-relative target only when it is an eligible clean
HEAD-tracked regular file in the selected repository. It binds the request to
the host-selected repository and performs one native file deletion.

The capability does not add directory or recursive deletion, wildcard/glob
selection, arbitrary untracked deletion, rename/move, generic `fs.unlink` or
`fs.write`, `shell.exec`, generic process authority, generic Git, automatic
staging, automatic commit, or branch/ref/history/network Git authority.
The native effect is filesystem deletion, not `git rm`; the existing human
Stage/Unstage, reviewed snapshot, and separate `repo.commit` boundaries remain
in force.

## 2. Authority architecture

ADR 0017 remains faithfully implemented as a separate additive,
host-constructed `RepositoryFileDeletionPolicy`/`RepositoryFileDeletionAuthority`.
The source and composition paths preserve these distinct planes:

```text
worktree content mutation != RepositoryFileCreationPolicy
RepositoryFileDeletionPolicy != RepositoryMutationPolicy
RepositoryMutationPolicy != RepositoryCommitPolicy
PermissionLevel::Execute != any of these authorities
```

`PermissionLevel::Execute` is only the outer dispatch permission. Execute-only
access does not grant deletion. The model request, frontend state, Trusted
Profile configuration, provider metadata, Tool definition, and ToolRegistry
registration do not manufacture authority. The host constructs the opaque
authority, and composition accepts it only when its selected Git executable
and repository match the host-selected resources.

The profile implementation in `crates/rah-tools/src/trusted_profile.rs` keeps
deletion as a closed symbolic selection. The effective composer in
`crates/rah-cli/src/profile_composition.rs` registers a tool only from the
separately supplied host authority; absent or mismatched authority fails
closed. No deletion-specific bypass was added.

## 3. Exact preimage and stale-state contract

The implementation captures and revalidates, under the existing repository
mutation lease:

- canonical selected repository, Git executable, and `.git` identities;
- attached branch and exact `HEAD` observation;
- exact target logical path and file identity;
- regular-file and link/reparse/attribute eligibility;
- raw worktree bytes, requested SHA-256, and requested byte length;
- exact HEAD blob bytes and the HEAD/blob relationship;
- normal stage-0 index entry and raw index bytes; and
- relevant Git/ref state.

The immediate pre-effect revalidation compares the current path, identity,
Git state, index, and raw bytes with the captured preimage. Modified or stale
targets therefore return `precondition_failed` before the native deletion
attempt. The policy rejects unsupported path, metadata, target, index, and
repository states rather than guessing.

The Task 163 CRLF observation is important evidence, not a successful
deletion: Git considered the Windows checkout clean, but the raw worktree
bytes were 27-byte CRLF while the HEAD blob was 26-byte LF. The operation
returned `precondition_failed`; no native deletion effect occurred. This
demonstrates ADR 0017’s exact raw-byte contract failing closed as intended.

## 4. Effect and no-replay semantics

The execution sequence is:

```text
capture -> immediate independent revalidation -> one native delete attempt
         -> post-effect observation
```

The policy has one filesystem effect attempt and verifies target absence plus
repository invariants afterward. A possible effect is never automatically
retried, replayed, restored, or rolled back. Timeout, cancellation,
disconnect, crash, or lost response is not interpreted as rollback. The
deterministic uncertainty test and bridge cancellation/no-replay coverage
support this boundary.

## 5. Git/index separation

Successful deletion leaves the index unchanged and is observed as an
unstaged worktree deletion. The implementation does not invoke `git rm`,
`git add`, staging, restore, reset, checkout, or commit. It does not alter
`HEAD`, refs, or history and does not create or authorize a commit. Human
staging and the existing separately authorized `repo.commit` workflow remain
the only route to those later effects.

## 6. Trusted composition and Generic Codex Tool Bridge

The host supplies the opaque deletion authority to the normal effective
composer. `repo.delete-file` is registered through the ordinary ToolRegistry
path, with no profile-created authority and no deletion-specific dispatch
route.

The canonical public ToolName is `repo.delete-file`. Codex-compatible private
aliases remain bridge implementation details. The Task 163A correction made
aliased dynamic descriptions generically include the canonical public RAH
name, for example `RAH public tool repo.delete-file`; it did not alter
authorization or create a deletion bypass. The live run observed private alias
`rah_tool_4`. That alias is evidence for that run only and is not stable across
runs.

## 7. Desktop integration

The selected Desktop repository constructs and stores the host-created
deletion authority in the Rust-owned `DesktopRepository`. The constructor
rejects an authority that does not match the selected repository. Repository,
runtime, and generation selection remain host-owned; the frontend receives
sanitized presentation and does not hold deletion authority or a privileged
filesystem path.

Successful deletion is translated into a sanitized tool-finished activity and
refreshes repository presentation. Repository mutation invalidates the
established commit-review context according to the existing rules. Selection
and reconnect create fresh host context; stale repository or generation state
cannot reuse the old authority. No frontend schema expansion creates or
widens authority.

## 8. Deterministic validation coverage

The Tasks 160–162 implementation and integration tests provide evidence for
the cases actually present in the repository:

- clean tracked-file success, collateral-file preservation, and exactly one
  native attempt;
- missing authority and Execute-only non-authorization;
- requested digest/length mismatch, modified target, stale preimage, and
  staged/dirty target rejection;
- HEAD/index/blob consistency, unchanged raw index, and unstaged deletion
  classification;
- closed path schema, traversal/alias/metadata rejection, regular-file and
  link/reparse checks (including Windows-specific source/prefix handling where
  compiled/tested);
- post-attempt uncertainty and no replay;
- Trusted Profile closed symbolic resources, host-authority composition,
  duplicate/absent-authority failure, and fail-closed permission behavior;
- Generic Bridge canonical schema, private alias routing, bridge refusal and
  stale-precondition forwarding, exact lifecycle behavior, and duplicate or
  disconnected execution without replay; and
- Desktop selected-repository construction, authority matching, generation
  isolation, stale repository handling, refresh, review invalidation, and
  frontend authority exclusion.

These are deterministic Windows and Ubuntu/Linux validation results where the
corresponding CI or tests run. This list does not claim test cases absent from
the source, nor does it convert deterministic Linux evidence into live
certification.

## 10. Observability gap

In the successful live evidence, `tool_finished.result` was persisted as
`null`. The helper handles `ToolContent::Text`, while `repo.delete-file`
returns `ToolContent::Json`. The JSON result itself was therefore not durably
captured.

This is a non-blocking observability formatting gap, not an authority or
effect defect. The live success is independently supported by
`ToolFinished` with `is_error=false`, the exact 1/1/1 lifecycle, request
evidence, the completion marker, target absence, unchanged sentinel, unchanged
index, unchanged HEAD/refs, no replay, and successful child cleanup.

This should be recorded as technical debt for a future generic observability
cleanup task. That future task must remain generic and must not be folded into
release preparation as a v0.13 release blocker unless new evidence shows that
the underlying lifecycle or effect proof is missing.

## 11. Platform terminology and limitations

Evidence terminology for this milestone is:

- **Deterministic validation:** Windows and Ubuntu/Linux where CI/tests
  provide evidence.
- **Live-certified platform:** Windows.
- **Linux live certification:** not yet established.

The milestone preserves these limitations:

- process supervision is not OS sandboxing;
- network isolation is not claimed;
- rollback is not guaranteed;
- TOCTOU protections are bounded and revalidated, not a proof against every
  external race or privileged actor;
- Windows is live-certified, while Linux live certification is not
  established; and
- Task 120 network/transport confinement remains deferred if applicable and
  is not upgraded by deletion.

## 12. Milestone verdict

**PASS.** The audit finds no known blocking authority, preimage, index-boundary,
bridge-routing, Desktop-generation, lifecycle, or replay defect remaining for
the v0.13 bounded deletion milestone. ADR 0017 is implemented; deterministic
gates, Trusted composition, Generic Bridge integration, Desktop integration,
and the Windows live gate are complete.

### Release blockers

None identified for milestone readiness.

### Non-blocking technical debt

- Generic live evidence should decode and persist JSON `ToolContent` in
  `tool_finished.result`.
- Linux live certification remains unestablished and must not be implied by
  CI/test evidence.

### Explicitly deferred future capabilities

Rename/move, directory or recursive deletion, arbitrary untracked deletion,
generic filesystem/process/shell authority, generic Git, staging and commit
automation, branch/ref/history/network Git, network MCP/transport confinement,
OS sandboxing, rollback, and other new v0.14 capabilities remain out of scope.

The next task is **v0.13 release preparation**. It must preserve this audit,
the exact authority boundaries, the Windows-only live-certification claim, and
the documented observability debt.
