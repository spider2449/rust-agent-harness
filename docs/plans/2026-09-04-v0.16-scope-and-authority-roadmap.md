# Task 191 — RAH v0.16 Scope and Authority Roadmap

Date: 2026-09-04
Status: research complete; documentation-only roadmap
Baseline: `d2195ff541f51559c7f6847997088abc6d9fcd62` (`HEAD == origin/master`)
Released baseline: RAH v0.15.0, tag `v0.15.0`, release commit
`6b66a357cacea4b1fcf21131cbc9e72fab90d59c`

## 1. Executive recommendation

RAH v0.16 should deliver a host-owned **effective authority review** capability
in Desktop: while a runtime is disconnected or connected, the user can inspect
the effective tool inventory, each tool's authority class and source, the
selected repository binding, provider identity, and the generation/connection
state that makes the inventory usable or stale.

This is one product milestone, not a new repository primitive. It addresses a
real post-v0.15 problem: RAH can now perform a bounded source-authoring and
reviewed-commit workflow, but the user cannot clearly answer “what can this
connected runtime do right now, why is it available, and what must be
reconnected?” The host already owns the required facts in `ToolRegistry`,
Desktop repository state, connection state, and Trusted Profile composition.

The recommendation adds **no model-accessible side-effect authority**. It is a
sanitized host presentation/read capability over existing state. It does not
let the model inspect more files, execute more tools, alter policy, select a
repository, or select a provider.

The principal alternative, richer session/workflow persistence, is also
authority-free and is the strongest deferred candidate. It loses for v0.16
because the most valuable persistence foundations already exist: private
repository-scoped SQLite transcript storage, explicit bounded Resume, inactive
model preferences, migration/corruption handling, and deliberate non-persistence
of authority. The remaining persistence gap is workflow/checkpoint product
design, not basic restart recovery. Authority review has a more immediate
blocking effect on every bounded coding session and can make the existing
workflow safer without expanding its authority surface.

## 2. Post-v0.15 product baseline

The current release and source audit establish the following product:

- RAH has 12 workspace packages, version `0.15.0`, Rust edition 2024.
- RAH remains provider-neutral. `AgentRuntime`, `Tool`, `ToolRegistry`,
  `SessionStore`, and `Sandbox` are separate boundaries; Codex is an optional
  adapter.
- Desktop host selection establishes the canonical repository. Repository
  generation, connection generation, model generation, and chat/session
  generation are separate state planes. Stale publication and stale turns are
  rejected, and reconnect is required when a captured context is no longer
  current.
- The Desktop host constructs a fresh `ToolRegistry` for a connection. The
  registry currently includes bounded repository observers, `fs.read`, bounded
  worktree edit/patch, file creation, file deletion, file rename/move, one-leaf
  directory creation, and the reviewed commit Tool when their host-owned
  prerequisites are present. External MCP and Process Plugin tools are
  admitted through the same RAH-owned registry and default-deny permission
  policy.
- Stage and unstage are host actions. Staged and unstaged diffs are host-
  observed. `RepositoryCommitReview` is an opaque, in-memory, one-shot
  authorization bound to the repository, generations, identity, index/tree,
  and reviewed snapshot.
- The Codex bridge translates model requests into RAH `ToolCall` values. Codex
  does not execute or authorize RAH Tools. Codex-owned shell, file, MCP,
  network, and approval capabilities remain disabled.
- MCP is local pinned stdio only. Process Plugin is a bounded stdio adapter,
  not a lifecycle manager, installer, marketplace, or generic process surface.
- The current Desktop status presents broad rows such as runtime status,
  repository status, repository-tools status, profile status, and model
  configuration status. It does not expose a complete effective inventory or
  authority explanation to the user.

The evidence is in `README.md`, `CHANGELOG.md`, `docs/ARCHITECTURE.md`,
`docs/SECURITY.md`, `docs/RAH_V0.15_RELEASE_GATE.md`, the v0.15 post-release and
milestone audit plans, `crates/rah-desktop/src/main.rs`,
`crates/rah-desktop/src/conversation_persistence.rs`,
`crates/rah-desktop/src/desktop_preferences.rs`, and the accepted ADRs 0010
through 0019.

## 3. Is the bounded coding pipeline complete?

**Yes, materially complete for the bounded v0.15 product contract.** It is not
generic Git, generic filesystem mutation, or a transaction system. Within those
deliberate limits, the authorized workflow can currently:

| Pipeline ability | Current evidence and qualification |
| --- | --- |
| Inspect repository state | `repo.file-info`, `repo.status`, `repo.diff`, and `repo.diff-staged`; host-selected repository and fixed native Git. |
| Read source files | `fs.read`, bounded by host workspace/repository policy. |
| Edit existing tracked files | `repo.patch` and `repo.edit-files`, with exact preimages and bounded paths/content. |
| Repository-aware patch/edit | `repo.patch` is repository-aware; `repo.edit-files` is bounded multi-file edit against original snapshots. |
| Create files | `repo.create-file`, one absent validated file, separate authority. |
| Create one new directory leaf | `repo.create-directory`, one absent ordinary leaf beneath an existing validated parent. |
| Delete tracked files | `repo.delete-file`, one clean HEAD-tracked regular file, unstaged result. |
| Rename/move tracked files | `repo.rename-file`, one clean HEAD-tracked regular file to an absent destination in the same repository. |
| Stage selected changes | Host Stage action backed by bounded index mutation. |
| Unstage selected changes | Host Unstage action backed by bounded index mutation. |
| Inspect staged/unstaged diffs | Host repository snapshot and the two diff observers. |
| Obtain reviewed commit authorization | Host captures and explicitly authorizes one fresh reviewed staged snapshot. |
| Commit reviewed staged state | `repo.commit`, one ordinary commit on the already attached current branch, with message-only model input. |

The pipeline is deliberately not complete in the sense of branch switching,
rollback, transaction undo, arbitrary Git, remote Git, or automatic recovery.
Those are different authority planes and are not defects in the bounded
pipeline. The remaining ordinary-workflow friction is visibility and lifecycle:
the user must infer effective capability from several status surfaces and
cannot inspect the exact reason a tool is absent, inactive, or reconnect-bound.

### Realistic workflows

**Workflow 1 — ordinary source edit.** RAH can inspect, read, edit, stage,
review, and commit. The awkward part is not a missing mutation primitive. The
user must understand that model-visible Execute is only an outer dispatch gate,
Stage is host-owned, commit requires a fresh review authorization, and any
repository/model generation change invalidates the captured state. The current
UI does not make that complete authority path legible in one place.

**Workflow 2 — add a new module/component.** RAH can create one directory leaf,
create files, edit up to the bounded multi-file limit per call, stage, review,
and commit. Parents must be created explicitly and files separately; this is
intentional bounded behavior. The friction is call sequencing and knowing which
creation/edit authorities are active, not a need for recursive mkdir or generic
filesystem access.

**Workflow 3 — refactor structure.** RAH can create a new parent directory,
move tracked files, delete obsolete tracked files, edit references, stage,
review, and commit. Rename is deliberately one file per call, destinations must
be absent, and directories must already exist except for the one new leaf. The
workflow is therefore possible but operationally verbose. A branch switch or
bulk structural transaction would add materially new Git/history or rollback
authority and is not justified by this audit.

**Workflow 4 — recover from a bad edit.** Safe existing paths are: start a new
conversation; inspect the current file/diff; make another bounded edit with an
exact preimage; or use the host's normal review and staging controls. A
first-class restore Tool is not clearly missing. Restore-from-HEAD can be
expressed as host-authorized bounded replacement only if the existing content
mutation contract is intentionally extended to cover that preimage/source; a
separate restore primitive would duplicate content mutation semantics while
adding staged/deletion/type/symlink complexity. No current evidence shows that
restore is a larger blocker than authority visibility.

**Workflow 5 — multi-session task.** Completed conversation text survives
Desktop restart in private repository-scoped SQLite. Resume is explicit and
requires a fresh current connection; it imports bounded completed text, not a
Codex native thread or authority. Model preferences survive as inactive desired
state. Runtime, ToolRegistry, policies, commit review, child providers, and
in-flight calls do not survive. The user still reconstructs the active task
checkpoint, pending plan, tool/event history, and exact “what was approved”
state. This is a real future product gap, but it is narrower than the current
authority-explanation gap because transcript recovery already reduces the
largest re-explanation cost.

**Workflow 6 — external integration.** Today RAH can use local stdio MCP and
bounded Process Plugin providers. It cannot use remote Streamable HTTP MCP or
an arbitrary hosted external service. Remote MCP could expand the ecosystem,
but it is a NETWORK AUTHORITY milestone, not a transport-only extension. It
requires endpoint, DNS, redirect, proxy, TLS, credential, streaming, retry,
uncertainty, and server-identity policy that is not currently proven.

## 4. Remaining product/workflow gaps

The audit found these gaps, ordered by product significance rather than recent
implementation momentum:

1. **Effective authority is hard to inspect.** `AppStatus` exposes broad
   statuses, while `desktop_tool_registry` already has the concrete definitions
   and composition facts. The user cannot see the effective tool list, required
   permission, authority source, repository binding, provider identity, or
   generation/staleness explanation in a host-owned sanitized view.
2. **Workflow checkpoints are not first-class.** Transcript persistence records
   completed user/assistant pairs and context separators, but not structured
   task notes, pending work, selected next action, or a durable non-authoritative
   operation summary. This is a credible v0.17+ enhancement after its schema
   and privacy contract are designed.
3. **Provider lifecycle UX is low-level.** Process Plugin is technically
   bounded, but there is no configured-provider inventory/health/start-stop
   layer. A narrow manager could be useful, but it adds lifecycle state and
   process UX before the basic effective authority picture is visible.
4. **Remote integration is unavailable.** Network MCP is a broad new security
   category and should not be pulled into this milestone without a dedicated
   network authority design.
5. **Branch/ref workflow is unavailable.** Branch creation and switching have
   distinct and significant Git/ref/worktree effects. Current source-authoring
   tasks do not establish this as the dominant blocker.

The authority-free leverage question has a clear answer: **yes**. Authority
review UX requires no new model-accessible side-effect authority. Session
persistence and provider lifecycle UX are also possible authority-free or
authority-reusing improvements, but authority review addresses the safety and
comprehension of every existing capability immediately.

## 6. Candidate analyses

### A. Session / workflow persistence

#### Current state

`crates/rah-desktop/src/conversation_persistence.rs` already provides a private
SQLite database with schema version 1, namespaces, epochs, completed pairs,
bounded message sizes/counts, transactional writes, full SQLite synchronous
mode, a V3 JSON migration, staging, corruption quarantine, and explicit clear.
The repository namespace is an opaque SHA-256-derived key; the raw path is not
stored as the namespace. `select_namespace` adds an application-restart
separator, and `resume_previous_conversation` imports only bounded completed
text after verifying a fresh current connection and current repository/model
generations.

`desktop_preferences.rs` separately persists inactive desired model
preferences. `main.rs` constructs all runtime, repository, registry, commit
review, and generation state in memory. The accepted commit ADR explicitly
requires review authorization to be short-lived, in-memory, single-use, and
never reconstructed from SQLite.

What survives today:

| Event | Survives | Does not survive |
| --- | --- | --- |
| Desktop restart | Completed transcript presentation, repository namespace history, inactive model preferences. | Runtime, Codex thread, ToolRegistry, policies, repository selection/identity as authority, commit review, child providers, in-flight calls. |
| Runtime reconnect | Persisted transcript remains; explicit Resume can import bounded pairs into the new current context. | Old runtime/session generation, old tools, old authority, old review. |
| Repository switch | Each repository has a separate opaque namespace; old presentation is not carried across. | Old conversation model context, repository binding, mutation policies, review, runtime. |
| Process crash | Only data committed before the crash under SQLite/file persistence semantics. | In-flight turn, tool call, provider state, authority, uncommitted UI state. |
| Normal shutdown | Same completed transcript/preferences already durably written. | No special authority snapshot or in-flight replay. |

Conversation messages survive in bounded completed form. Tool/event history does
not survive as a structured audit trail; tool activity is UI/event state and
live evidence, not a resumable authority record. Selected repository identity is
not restored as authority; its namespace is a private hint keyed from the host
selection. Model preference survives only as inactive desired state. UI state,
workflow checkpoints, and pending task metadata do not have a first-class
durable schema.

#### Safe persistence design to research later

A useful v1 could persist only Desktop-owned, non-authoritative state:

- versioned schema and migration state;
- conversation transcript and bounded context separators;
- user-authored workflow notes/checkpoints with explicit size and content
  bounds;
- selected repository path/identity only as a resume hint, never as a grant;
- model preference as inactive desired state;
- optional UI preferences that contain no credentials or authority handles;
- sanitized task metadata, never raw secret-bearing Tool inputs or outputs.

On resume, the host must independently reopen and validate the repository,
derive a fresh repository identity/generation, compose a fresh ToolRegistry,
reconnect a fresh runtime, and require fresh permissions and review. A moved,
deleted, replaced, or identity-mismatched repository must become a visible stale
hint and require explicit reselection; it must never be silently rebound by
path alone. A resumed conversation can be displayed before reconnect, but Tools
must remain unusable until the fresh host context is connected and current.

Persistence must reject or revalidate `RepositoryCommitReview`, mutation
policy instances, runtime capability registries, runtime/session generations,
provider child identity, stale repository fingerprints, credentials/tokens, and
in-flight Tool authority. No uncertain Tool call may resume or replay.

The required storage contract includes one schema version, deny-unknown-field
decoding where applicable, bounded records, atomic writes, crash-consistent
commit points, migration tests, corruption quarantine/fail-closed behavior,
privacy and secret redaction, explicit user deletion/reset, and no cloud sync or
cross-device authority transfer. The current transcript implementation proves
many of these patterns but not structured workflow checkpoints.

**Rule:** “Persistence may restore context; it may not restore authority.”

This would likely require a new ADR even though it grants no model authority.
The new durable data classes, namespace/repository-hint semantics, migration,
privacy, crash consistency, and resume lifecycle are architecture-critical and
must not be inferred from the current transcript-only contract. It remains the
strongest v0.17 candidate after Task 191, not the v0.16 selection.

### B. Bounded repository restore/revert

Restore-from-HEAD, restore-from-index, and restore-from-an-explicit-reviewed
blob are different source-of-truth contracts. Each must define whether the
target is tracked, clean, staged, deleted, type-changing, linked/reparse, or
binary; whether the operation mutates worktree only or index too; and how exact
preimage and postcondition proof works. A restore effect is content mutation,
not rollback, transaction undo, or generic `git checkout`.

The current `repo.patch`/`repo.edit-files` contracts already provide bounded
host-owned content replacement with exact preimages and no replay. A user can
recover from a bad text edit by inspecting the diff and applying a bounded
replacement. `fs.read` plus `repo.create-file` can also reconstruct a new file
when the desired bytes are known. A first-class restore Tool would improve
discoverability, but it would duplicate content mutation while adding deletion,
index, mode/type, symlink, and staged/unstaged semantics. No evidence currently
proves the duplication is worth a new API or ADR.

### C. Branch/ref workflow

Branch creation without switching is ref/history mutation. Switching to an
existing branch can alter worktree and index state, conflicts, repository
context, and the meaning of a pending review. Create-and-switch combines both
planes and is not a single harmless operation. Dirty changes, detached HEAD,
unborn repositories, invalid branch names, linked worktrees, hooks/config, and
concurrent Git all require explicit contracts. Commit-review authorization must
be invalidated on branch/ref/worktree identity change, and runtime/repository
generations must be refreshed.

The smallest plausible v1 would be host-authorized creation of one validated
local branch ref without checkout, but that still creates new ref/history
authority and provides less immediate workflow value than J. `git switch` must
not be hidden behind a narrow name without acknowledging its worktree/index
effects. No network Git, merge, rebase, stash, delete, or generic Git argv is
appropriate.

### D. Network MCP / Streamable HTTP

Current MCP is a pinned local stdio adapter. Remote Streamable HTTP would be a
new NETWORK AUTHORITY milestone, not “MCP plus another transport.” A safe
design needs host-configured fixed HTTPS endpoints, URL parsing and normalized
host/domain/port identity, endpoint allowlists, explicit private/loopback/link-
local policy, DNS rebinding analysis, mandatory TLS verification, redirect and
proxy policy, host-owned credential storage, secret redaction, server identity,
request/response/stream bounds, timeouts, cancellation, reconnection, retry
rules, and side-effect uncertainty rules. A model-selected URL or generic HTTP
Tool is forbidden.

Task 120 remains historical evidence that the current provider endpoint seam
does not prove transport confinement: redirects, proxies, DNS, peer identity,
and effective destination are not claimed. That evidence is directly relevant,
not permission to skip the MCP network design. Remote MCP would require at
least one new network/security ADR, likely more than one focused design task,
and dedicated deterministic plus live evidence. Its potential leverage is high,
but its authority novelty and certification burden are too large for this
single v0.16 milestone.

### E. Process Plugin lifecycle / PluginManager

The Process Plugin adapter already validates configured executable identity,
uses bounded NDJSON stdio, clears/allowlists the child environment, isolates
working directory policy, discovers tools, and routes them through
`ToolRegistry`. The product gap is inventory and lifecycle UX, not the adapter
boundary itself.

A safe manager v1 could operate only on already host-approved, explicitly
configured providers. It could show provider id/version/executable identity,
state, health, child generation, and stale-tool state; support explicit start,
stop, and restart; shut down owned children; and rebuild a fresh registry on
provider generation changes. It must not install, download, select arbitrary
executables, choose arbitrary cwd/env, marketplace-discover, auto-update, or
automatically restart after an uncertain Tool effect. A Tool call that may have
had an external effect remains uncertain and is never replayed by lifecycle
recovery.

This is a credible later milestone and may share presentation components with
J. It loses as the sole v0.16 capability because current Desktop's first-order
uncertainty is the effective authority inventory across all providers, not only
plugin process state.

### F. Trusted Profile reload / dynamic authority

Disconnected manual reload is materially different from connected reload. The
safest shape is: validate a new host-selected profile while disconnected,
atomically compose it, then require explicit reconnect before it affects a
runtime. Connected manual reload should either be rejected or produce a
disconnected “reconnect required” state. Live reload and automatic file-watch
hot reload would need revocation, in-flight call handling, provider shutdown,
stale registry control, generation changes, commit-review invalidation, profile
identity/version, config race/symlink replacement handling, and atomic
validation-before-activation.

The current accepted profile architecture composes existing authority and
publishes a fresh registry; it does not grant dynamic authority. A disconnected
reload could fit later without a new authority category, but the lifecycle and
revocation semantics are architecture-critical. Automatic hot reload is not
appropriate for v0.16. J can present current profile/effective inventory
without changing reload semantics.

### G. Directory deletion

Git ignores empty directories. The realistic cleanup operation is normally
deleting tracked files, after which the directory ceases to be Git-visible;
empty filesystem directories are a niche local artifact. A safe directory
deletion Tool would still need an empty-only contract, ordinary-directory
identity, no recursion, no symlink/junction/reparse target, race handling for
concurrent child creation, and uncertain-effect semantics. It would remain
separate from file deletion.

The v0.15 create-directory capability does not imply a symmetric delete
requirement. No current workflow evidence makes empty-directory removal a
material blocker. It ranks last despite technical adjacency.

### H. Repository copy primitive

Copy is convenient but not necessary. A host can read a bounded source through
`fs.read` and explicitly create an absent destination through `repo.create-file`.
That path makes the source bytes visible to the workflow and preserves the
existing creation authority boundary. A native copy Tool would need source
hash/length, destination absence, byte preservation, mode/metadata policy,
link/reparse rejection, and possible-effect classification, while being a
convenience wrapper around two existing actions. It should not be added solely
to shorten a safe sequence.

### I. Deterministic workflow orchestration

Agent planning is model behavior; host orchestration is an authority and
lifecycle contract. The current `AgentRuntime`/`SessionStore` abstractions do
not establish a first-class Desktop workflow object, ordered host actions, or
checkpoint semantics. The current source does establish bounded conversation
epochs, generation checks, repository workflow state, and explicit review
lifecycle, but those are not a general workflow engine.

A workflow layer is justified only by a concrete product object such as a user-
owned task checkpoint with explicit state transitions and no implicit rollback.
It must never turn model plans into authority or replay uncertain effects. Since
Task 191 found no evidence that a general orchestrator is required to operate
the existing source pipeline, this is deferred rather than invented.

### J. Capability / authority review UX

This is the selected candidate. The host already has the facts needed to make a
useful review surface:

- `ToolRegistry::definitions()` returns a deterministic sorted inventory.
- Desktop composition knows which repository-bound authorities were present.
- `AppStatus` knows runtime, repository-tools, model, profile, and connection
  status, including reconnect-required cases.
- `ConnectionState` records the captured repository/model/connection
  generations and repository fingerprint for host diagnostics.
- Trusted Profile and external permission policies know the authority source,
  exact external identity, and assigned permission level before registration.
- Repository workflow state knows whether staged review is available and
  whether a fresh commit authorization is pending.

The missing product contract is a sanitized, host-owned presentation snapshot,
not a new Tool authorization. It should explain effective availability without
exposing raw native paths, credentials, policy internals, opaque commit handles,
or provider secrets. The snapshot must be generation-bound and treated as
advisory presentation: every actual Tool call still passes the existing host
permission/policy path.

This materially improves safe operation: before asking the model to edit, the
user can see whether repository read/edit/create/delete/rename/directory and
commit capabilities are active; whether the repository is bound; whether an
external provider is admitted; and whether reconnect is required. It also
reduces false diagnosis of “the model cannot do this” when the actual reason is
missing host composition or stale generation.

### K. Additional evidence-backed candidate

The repository does support one additional serious candidate: **provider health
diagnostics**. Current connection errors are sanitized into broad frontend
codes and `AppStatus` is intentionally coarse. A bounded diagnostic view could
show Codex baseline/source, runtime lifecycle, configured provider identity,
MCP/plugin child state, last non-secret health outcome, and stale generation
reason without probing arbitrary endpoints or exposing raw errors.

It is not selected separately because its user-facing value and safety contract
are a subset of J's effective authority/lifecycle explanation. Splitting it
would create two overlapping v0.16 milestones. Any diagnostics included in J
must remain host-owned, sanitized, non-authorizing, and explicit about whether a
result is current or stale.

## 7. Recommended v0.16 capability

### User-facing capability

Add an “Effective capabilities” view in Desktop with a refreshable host snapshot
for the current disconnected/connected state. For each effective capability,
show:

- canonical public tool/capability name;
- safe category (`repository read`, `worktree content`, `file creation`, `file
  deletion`, `file rename/move`, `directory creation`, `index`, `reviewed
  commit`, `Execute`, MCP, or Process Plugin);
- required RAH permission level;
- host source (`built-in`, configured MCP identity, configured Process Plugin
  identity, or Trusted Profile binding);
- safe availability (`active`, `inactive`, `reconnect required`, or
  `unavailable`);
- selected repository binding as a sanitized identity/presentation, not a raw
  authority handle;
- provider/runtime identity and generation labels where safe;
- a bounded reason when unavailable, such as no repository selected, missing
  host composition, disconnected runtime, stale repository generation, stale
  model generation, or review not currently authorized.

The view must distinguish effective inventory from authorization to perform a
particular call. A listed Tool is not a promise that arbitrary input succeeds;
the existing Tool schema, host policy, preconditions, and generation checks
remain authoritative.

### Likely components affected by a later implementation

No components are changed by Task 191. A later implementation would likely be
Desktop Rust presentation/state in `crates/rah-desktop/src/main.rs`, the
frontend status/presentation files, and reusable sanitized inventory types near
the host composition seam. It may need a narrow public presentation helper in
`rah-tools` only if the existing registry definitions/source metadata cannot be
adapted at the Desktop boundary. It should not require changes to
`rah-protocol`, `AgentRuntime`, Codex wire protocol, MCP transport, Process
Plugin protocol, repository policies, Cargo manifests, or accepted ADRs.

## 8. Authority impact

**No new model-accessible side-effect authority.**

The capability is host-local presentation/observation of already composed
authority. It introduces no repository read beyond existing host-selected
state, no worktree/index/ref/history mutation, no branch operation, no network
category, no generic process authority, no credential authority, and no
persistent authority. Frontend state remains presentation and cannot authorize
a Tool.

The inventory must be derived from the same host-owned composition that creates
the runtime's registry. It must not infer authority from model-visible tool
definitions, provider metadata, profile text alone, frontend controls, or
permission labels. Missing composition remains unavailable/fail-closed.

## 9. ADR decision

**No new ADR is required for the selected v0.16 capability**, provided Task 192
keeps it strictly within existing architecture. ADRs 0001–0019 already govern
the runtime, Tool/ToolRegistry extension boundary, external provider admission,
Trusted Profile composition, permission separation, repository authority, and
commit review. A sanitized Desktop read/presentation view does not alter those
decisions or create a new authority plane.

Task 192 should still produce a focused implementation contract and review the
relevant ADRs before code changes. If the design expands into durable
workflow/checkpoint persistence, dynamic profile reload, network diagnostics,
or lifecycle controls that start/stop providers, that expanded work must stop
and receive its own authority/architecture decision rather than being smuggled
into J.

## 10. Smallest safe v1 contract

The next implementation research task should treat the following as normative
boundaries:

1. The host builds one immutable inventory snapshot from the currently effective
   `ToolRegistry` and host composition state.
2. The snapshot is presentation-only. It exposes no callable authority handle,
   raw policy object, repository path selected by model input, credential,
   executable path, raw native error, or private provider metadata.
3. Tool names and categories come from host-registered RAH definitions and
   explicit host source metadata. Provider descriptions cannot grant or upgrade
   authority.
4. Repository binding is represented by a safe display identity and current
   generation/state. Raw paths and sensitive fingerprints are not exposed
   unless an existing Desktop presentation contract already permits them.
5. Connected inventory includes captured repository/model/connection generations
   and reports stale/reconnect-required state. A disconnected inventory may
   describe configured/inactive capabilities but must not call providers or
   construct authority merely to display them.
6. Commit review is represented only as a safe state such as “review available,”
   “authorized for one current review,” or “unavailable.” The review object,
   selector, index digest, and authorization handle never cross the frontend
   boundary and are never persisted.
7. External MCP/Process Plugin entries show only exact host-approved identity,
   admitted tool name, assigned permission, lifecycle/generation state, and
   sanitized failure state. Unknown or unassigned tools remain absent.
8. Refresh is a new host observation, not a policy mutation, profile reload,
   runtime reconnect, provider restart, or authority grant.
9. Every reason string is an allowlisted sanitized enum/message. Raw OS, Git,
   process, transport, credential, and provider errors remain private.
10. Inventory visibility never changes the existing dispatch gate, policy,
    precondition, lease, uncertainty, no-replay, or reviewed-commit rules.

## 11. Security/lifecycle model

The lifecycle is:

```text
host composition -> effective registry + source metadata
                  -> immutable sanitized inventory snapshot
                  -> Desktop presentation only

repository/model/profile/runtime change
                  -> generation change or reconnect-required state
                  -> old snapshot becomes stale
                  -> fresh host composition is required
```

No capability snapshot survives a process restart as authority. If a future
session persistence feature stores a displayed inventory for continuity, it
must be clearly marked historical and rederived before any current claim.

Provider child identity and runtime connection identity remain lifecycle-owned.
The inventory must not keep children alive, restart them, or imply that a
provider is healthy merely because it was previously composed. A disconnected
view can show configured/inactive state from trusted host configuration, but it
must not activate providers as a side effect of viewing the page.

The selected repository remains host-owned. A repository switch increments the
repository generation, clears/rebuilds repository workflow state, invalidates
commit review, and makes the prior inventory stale. Model configuration changes
retain the existing Apply/reconnect lifecycle. Disconnect destroys the active
runtime/registry relationship; reconnect creates a fresh one. No old Tool call,
review, or uncertain external effect is replayed.

## 12. Deterministic validation strategy

Task 191 does not implement tests. The eventual deterministic plan should prove:

- inventory is derived from host composition, not model/provider metadata;
- deterministic sorting, stable categories, and allowlisted reason codes;
- repository-present and repository-absent inventories;
- each existing repository authority present/absent according to its actual
  host construction, including commit review availability versus Tool presence;
- Execute remains separate from repository mutation authorities;
- MCP and Process Plugin tools are default-deny and only appear with exact host
  assignments;
- stale repository/model/connection generations produce reconnect-required or
  stale presentation and never grant a call;
- disconnect/reconnect and repository switch replace snapshots without leaking
  old repository/provider identity;
- raw paths, credentials, policy internals, child environment, native errors,
  opaque review handles, and sensitive fingerprints never cross the sanitized
  presentation boundary;
- a presentation refresh causes no Tool execution, provider start, network
  request, repository mutation, index mutation, commit, or profile reload;
- property/failure tests cover absent composition, duplicate tools, malformed
  metadata, provider crash, and unavailable runtime without optimistic display;
- existing repository mutation, commit, uncertainty, and no-replay tests remain
  unchanged and continue to prove their own authority contracts.

## 13. Windows live-validation strategy

The capability is mostly local Desktop lifecycle/presentation, so live evidence
must validate the Desktop state transitions rather than force a model mutation
fixture.

Using the certified Windows Codex baseline `codex-cli 0.149.0` and its complete
companion code-mode host, a future live task should:

1. start from a clean pinned baseline and a disposable repository outside the
   checkout;
2. launch Desktop disconnected and capture the sanitized inactive inventory;
3. select the disposable repository and verify repository-bound capabilities
   are shown as configured/inactive before connection, without provider or Tool
   execution;
4. connect Codex and verify a fresh inventory shows the current runtime,
   repository, and connection generations and the effective bounded Tool set;
5. exercise only an already-authorized harmless bounded observation or fixture
   if needed to correlate displayed inventory with actual registry dispatch;
6. change repository or model configuration and verify the old inventory is
   stale/reconnect-required and no old authority is usable;
7. disconnect/reconnect and verify a new inventory is composed, with no replay,
   old review authorization, or stale provider identity;
8. record only sanitized inventory categories, lifecycle states, generation
   relationships, certified Codex version, and explicit PASS markers.

The live task must not claim Linux live certification. Ubuntu/Linux deterministic
tests remain established evidence, while Windows remains the live-certified
platform. No network, remote MCP, plugin installation, arbitrary executable,
or repository mutation beyond the smallest separately authorized correlation
fixture belongs in this gate.

## 15. Alternatives deferred

**Session/workflow persistence (A).** Strongest authority-free alternative and
recommended immediately after J once structured checkpoints, privacy, migration,
and stale-hint semantics are designed. Basic transcript recovery already
exists, so it is not the highest current blocker.

**PluginManager (E).** Useful over already-approved configured providers, but
provider lifecycle should not precede a clear effective authority view.

**Provider health diagnostics (K).** Folded into J where it explains current
availability; a separate health milestone would overlap.

**Restore (B).** Defer until a concrete recovery workflow demonstrates that
bounded read/edit/create/delete behavior cannot safely meet the need. Do not
duplicate content mutation authority for convenience.

**Branch/ref workflow (C).** Requires new ref/history authority; create and
switch must be researched separately. No current evidence makes it the next
highest-value safe increment.

**Network MCP (D).** Potentially the largest ecosystem opportunity, but it is a
new NETWORK AUTHORITY milestone with a dedicated security surface and live
certification burden. Task 120's unproven transport confinement remains
relevant.

**Profile reload (F).** Disconnected reload plus reconnect may be viable later;
live/hot reload has revocation and stale-runtime risks.

**Directory deletion (G).** Empty directories are not Git-tracked and the
workflow blocker is not demonstrated; create/delete symmetry is insufficient.

**Copy (H).** Existing bounded `fs.read` plus `repo.create-file` covers the safe
product outcome without another authority API.

**Workflow orchestration (I).** No general engine should be created without a
concrete host-owned checkpoint/state-transition requirement.
