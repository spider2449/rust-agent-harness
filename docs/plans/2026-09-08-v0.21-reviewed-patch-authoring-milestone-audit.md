## Milestone definition

The selected v0.21 milestone is **HostExplicit Reviewed Single-File Patch
Authoring**. It is the narrow human route selected by Task 245 and specified
by Tasks 246 and 247: one connected-current Desktop user supplies an H1
repository-relative path, literal expected old text, and literal replacement
text; the host derives the security bindings, prepares an exact bounded review,
requires an explicit confirmation, and reaches the existing bounded
`repo.patch` authority.

The milestone does not add a generic authoring plane. It does not make the
model select or authorize the operation, does not stage or commit automatically,
and does not broaden any other authoring capability.

## Product capability audit

The released-next product path is complete and coherent:

```text
inspect
  -> typed human patch Prepare
  -> exact in-memory review
  -> ticket-only Confirm
  -> existing repo.patch
  -> inspect diff
  -> existing Stage / Unstage
  -> existing reviewed Commit
```

The roadmap defines this as `inspect -> reviewed exact repo.patch -> diff ->
Stage -> reviewed Commit` (Task 245). The frontend renders the backend
Effective Authority descriptor and creates only typed forms. `repo.patch`
creates the H1 Prepare form; the subsequent diff, Stage, and reviewed Commit
surfaces remain separate existing Desktop actions.

There is no `fs.write`, arbitrary JSON console, shell shortcut, generic Git
shortcut, automatic Stage, or automatic Commit in this path. The existing
`repo.patch` Tool is reached through `ToolRegistry` only after the host checks;
its underlying native replacement remains governed by ADR 0012. The review is
display-only and is never passed to `git apply` or another diff executor.

## Authority audit

The authority relationship is preserved exactly:

- ADR 0012 remains the sole underlying `repo.patch` worktree-content mutation
  authority. It owns repository admission, exact preimage checks, bounded
  postimage construction, one native replacement attempt, postimage proof, and
  conservative uncertainty.
- ADR 0021 remains the general HostExplicit boundary. It owns connected-current
  selection, current definition and permission checks, D2 admission,
  coordinator exclusion, ticket principles, and Desktop-private provenance.
- ADR 0022 adds only the reviewed H1 human workflow around the existing
  capability. It does not create a second write policy or generic mutation
  authority.

The current code agrees with the ADRs. `RepositoryWorktreePatchTool` retains a
private `RepositoryWorktreeMutationPolicy`; `RepositoryPatchPreparer` is not a
Tool and has no replacement or Tool-execution method. The neutral
`authorize_tool_dispatch` primitive compares the complete current
`ToolDefinition`, checks current permission membership, and only then permits
the ordinary registry call. No provider metadata, frontend state, model text,
or `PermissionLevel::Execute` alone grants authority.

## Preparation and review audit

`RepositoryPatchPreparer` lives in `crates/rah-tools` and is constructed from
the host-fixed Git executable and selected repository. It reuses the shared
patch policy primitives for candidate capture, tracked/clean repository
admission, UTF-8/BOM handling, literal uniqueness and overlap checks,
postimage construction, and existing bounds.

Preparation accepts only `RepositoryPatchPreparationRequest` with `path`,
`expected_old_text`, and `replacement_text`. It derives the canonical legacy
ToolInput, preimage SHA-256 and byte length, postimage SHA-256 and byte length,
review identity, and opaque identity evidence. `prepare` performs no Tool
execution, temporary-file write, target replacement, index operation, Stage,
Commit, ref operation, provider operation, or model lifecycle.

The shared preparer has no mutation API. Its `revalidate` method is also
non-effectful and compares the preparer, repository, Git, target, exact
preimage, postimage, review, and review identity. The deterministic tests cover
zero replacement attempts and absence of patch temporary artifacts across
preparation and revalidation paths.

The review is R4 and complete for all mutation-relevant changed material. It
contains the operation, relative path, one replacement, exact changed byte
range, complete escaped old text, complete escaped replacement text, BOM state,
preimage/postimage EOF state, hashes and lengths, intended effect, explicit
non-effects, and an unchanged-context statement. CR, LF, TAB, controls, format
characters, zero-width/bidi characters, trailing spaces, BOM, and final-newline
state are represented safely and deterministically. There is no normalization
or executable unified-diff interpretation.

The changed-material, review, and prepared-representation bounds are measured
after escaping. If the complete changed content cannot fit, preparation returns
`review_too_large` and creates no ticket. Patch activity events contain no
review or source text; full source material is limited to bounded process-local
prepared state and the local review presentation, not generic activity,
conversation persistence, or evidence logs.

## Revalidation and dispatch audit

The effective Confirm order is:

```text
ticket/currentness
  -> shared RepositoryPatchPreparer::revalidate
  -> authorize_tool_dispatch
  -> HostExplicit Started
  -> authorized_tool_dispatch
  -> ToolRegistry
  -> existing repo.patch / ADR 0012 policy
```

The Desktop takes and consumes the prepared ticket first. It then checks the
current generation tuple, composition identity, repository identity, current
definition, allowed permissions, and retained preparer identity. Patch Confirm
calls shared preparer revalidation before D2 admission. Any stale or malformed
pre-start state finishes the coordinator and returns before `Started`.

Only after that does it invalidate the old reviewed-commit authorization,
emit private `host_explicit` `Started`, and spawn the owned execution. The
owned execution uses `authorized_tool_dispatch`, which repeats the complete
definition and permission admission immediately before ordinary registry
execution. Raw registry execution is not treated as complete authorization.

The exact HostExplicit eligible set is seven, as implemented by
`host_kind` and tested by `host_allowlist_is_exact`:

1. `fs.read`
2. `repo.file-info`
3. `repo.status`
4. `repo.diff`
5. `repo.diff-staged`
6. `repo.create-branch`
7. `repo.patch`

The following remain ineligible: `repo.create-file`, `repo.edit-files`,
`repo.delete-file`, `repo.rename-file`, `repo.create-directory`,
`repo.commit`, and all external MCP/Process Plugin Tools. The host classifier
does not infer eligibility from visibility, effect class, permission, or
provider metadata.

## Result and uncertainty audit

The shared strict classifier accepts only one JSON content item containing
exactly `status`, `changed`, `uncertain`, and `reason`, with the current
producer's exact combinations. It rejects missing, extra, wrong-type,
unknown, contradictory, multi-content, and text forms.

Desktop maps `ChangedVerified` to completed, known precondition/replacement
failure to ToolError, and malformed, uncertain, or post-start ToolError to
`PossibleEffectUnknown`. It never infers success from observing changed file
contents. Repository refresh and commit-review invalidation are applied only
when the captured repository context remains current.

The existing mutation policy has one native replacement call in the effectful
path and no retry, replay, rollback, restore-preimage, compensation, or
automatic second confirmation. Pre-start stale rejection is a known zero-Tool,
zero-replacement boundary. Post-start malformed, contradictory, lost, or
errored results remain conservative.

## Reviewed-authorization audit

Prepare preserves an existing reviewed-commit authorization and does not arm or
manufacture one. Once effectful patch Confirm passes the pre-start gates and
reaches the mutation boundary, the old pending reviewed authorization is
cleared conservatively.

Successful patch handling refreshes the repository workflow. The refresh may
produce a fresh `ReadyToAuthorize` staged review, but this is presentation and
review state only: the underlying one-shot authorization is not automatically
re-authorized. The live gate explicitly checked that the old authorization was
invalidated, the new selector and commit review were fresh, and no pending
underlying authorization remained. This is the correct documented meaning of
"authorization is revoked": the old authorization is revoked; a fresh manual
review and explicit authorization may be performed afterward.

## Coordinator correction audit

Task 251A corrected the production async Prepare defect narrowly. The prior
path entered `HostPrepared(preparing)` with `begin_prepare`, then incorrectly
called the synchronous `prepare(ticket)`, which requires `Idle` and therefore
always returned `Busy`.

The corrected path is:

```text
begin_prepare
  -> transient HostPrepared(preparing)
  -> finalize_prepare
  -> HostPrepared(ticket)
```

`finalize_prepare` requires exactly the transient reservation, no existing
ticket, stores the ticket, clears the `preparing` flag, and remains
`HostPrepared`. Shared preparation failure calls `abort_prepare` and returns
to `Idle`. Direct branch Prepare retains its separate synchronous path.

The correction does not weaken concurrency exclusion: model turns, reads, a
second Prepare, and Confirm remain excluded while the reservation is active.
Deterministic tests cover reservation exclusion, finalize success and failure,
abort behavior, exact-once ticket consumption, direct branch behavior, failed
patch preparation cleanup, and unchanged HostExplicit provenance/conversation.

## Frontend audit

The frontend consumes `effectiveTools[].hostInvocation` from the backend. It
does not assign eligibility, permission, effect class, authority category, or
Tool names. It renders the typed H1 fields only: path, expected old text, and
replacement text.

The review uses `textContent`, including `<pre>.textContent` for escaped old
and replacement material. The activity renderer does not copy patch review or
source material into generic activity. Confirm and Cancel both send only
`{ request: { ticketId } }`; the ticket is opaque to the frontend. Escape and
dialog dismissal cancel the backend ticket. An in-memory action guard disables
both buttons before the asynchronous call and prevents double action. No
generic JSON console or persistent review store is present.

## Security and privacy audit

The milestone preserves HostExplicit/model separation: host activity is private
`host_explicit`, with no fabricated model request, model Tool lifecycle, chat
message, or ToolOutput injection. Human input cannot provide hashes, lengths,
ToolDefinition, permission, ToolName, raw ToolInput JSON, native paths, or
repository identity. The host binds those values to the current selected
composition and repository.

Review source content is bounded and escaped for the local review only. Full
old/new source text is not copied into generic activity, conversation SQLite,
conversation replay, or live-evidence JSONL. Terminal metadata is bounded and
redacted. Confirm cannot refresh, rewrite hashes, reprepare automatically,
retry, replay, or execute against the latest file.
