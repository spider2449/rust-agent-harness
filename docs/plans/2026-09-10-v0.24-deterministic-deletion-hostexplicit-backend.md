## Backend contract

The production HostExplicit set is exactly these ten names:

```text
fs.read
repo.file-info
repo.status
repo.diff
repo.diff-staged
repo.create-branch
repo.patch
repo.edit-files
repo.create-file
repo.delete-file
```

Deletion is admitted only for a selected repository with host-granted
`RepositoryFileDeletionAuthority`, an exact current `repo.delete-file` Tool,
and a successfully constructed retained `RepositoryDeleteFilePreparer`.
Provider metadata, Execute permission, Tool presence alone, prefixes, and
categories do not create eligibility. Rename, directory creation, Commit,
providers, fixtures, and unknown Tools remain ineligible.

The backend request is the closed typed `{path}` DTO. Prepare reconstructs the
unchanged three-field ordinary Tool input from the preparer and returns the
complete `RepositoryDeleteFileReview` only in the direct
`PreparedDeleteFileResponse`. Generic Prepared and Started activity carries a
distinct non-authority activity ID, no ticket, no review, and no raw Tool
payload. Prepare is zero-effect and issues no ticket on any bounded failure.

The retained ticket payload owns the shared preparation and the exact retained
preparer. Confirm consumes the ticket, verifies generations, composition and
repository identity, exact ToolDefinition and permission membership, retained
preparer identity, and shared deletion revalidation before D2. Only after D2
does it invalidate reviewed repository-bound Commit authorization, emit
HostExplicit Started, and dispatch through the current
`authorized_tool_dispatch -> ToolRegistry -> repo.delete-file` path. Cancel,
Prepare, and all pre-Started rejection paths preserve Commit authorization.

## Independent deletion classification

The shared preparer now exposes reviewed-only non-mutating proof methods. The
known-no-effect proof requires the same preparer/resource identity, exact
target FileIdentity and link count, source bytes/hash/length, parent binding,
HEAD/blob/index relationship, raw index, and protected Git fingerprint.
Same-byte replacement with a different FileIdentity fails this proof.

The deleted-verified proof requires the same resource/preparer binding, a
protected root and exact retained parent identity, specifically confirmed
`NotFound` target absence, no same-name or case-equivalent entry, unchanged
raw index, and unchanged protected HEAD/tree/blob/branch/refs state. A generic
metadata failure, visible delete-pending path, replacement, or contradictory
observation is uncertain. The reviewed route performs one native Tool attempt
and one immediate proof pass: no polling, second delete, retry, cleanup,
restore, replay, or rollback.

The Desktop parser accepts only the ordinary five statuses with their exact
key/type/path/error shapes. It combines structural output with independent
proof and maps proof-insufficient or malformed results to status-only
`uncertain` and `possible_effect_unknown`. Valid terminal results are
status-only in generic activity. Descriptive refresh runs only for effect or
possible-effect outcomes and never upgrades uncertainty or recreates
authority.

## Task 283 correction — deterministic backend evidence

The first Task 283 commit was functionally correct and passed source review,
but its deterministic Desktop coverage stopped at the underlying deletion
registry/tool and isolated parser/proof tests. It did not exercise the new
deletion-specific HostExplicit Prepare/Confirm orchestration through the
production backend helpers. This correction preserves that implementation and
closes only the evidence gap.

The correction adds these deletion-specific deterministic tests in
`crates/rah-desktop/src/main.rs`:

- `deletion_host_prepare_path_is_zero_effect_complete_and_private` drives the
  shared production Prepare helper from typed `{path}`, verifies the current
  exact definition, retained preparer, non-effectful preflight, complete direct
  review, redacted Prepared activity, unchanged target identity/bytes, index,
  HEAD, branch, refs, pending reviewed Commit authorization, and zero Tool
  executions.
- `deletion_hostexplicit_ticket_boundaries_use_real_preparation` uses real
  deletion preparations to prove activity IDs, wrong tickets, expiry, Cancel,
  duplicate Confirm, and coordinator Idle behavior cannot execute the Tool.
- `deletion_hostexplicit_rejects_stale_before_started_for_git_and_desktop_drift`
  covers same-byte identity replacement, staged/index drift, and a generation
  drift; every rejection is before Started with zero Tool executions and no
  automatic reprepare.
- `deletion_hostexplicit_proof_coupling_requires_independent_postcondition`
  covers structurally valid `deleted_verified` with confirmed absence,
  `deleted_verified` while present, valid `known_no_effect` with the exact
  intact target, and same-byte recreation; proof-insufficient cases map to
  `possible_effect_unknown` and status-only `uncertain`.
- `deletion_hostexplicit_success_dispatches_once_and_invalidates_commit_review`
  drives the real deletion Tool through the shared production dispatch helper
  without a model/runtime turn. It proves one Tool dispatch, verified absence,
  one unstaged deletion, unchanged index/HEAD/branch/refs, reviewed Commit
  invalidation at Started, status-only `deleted_verified`, and coordinator Idle.
- `deletion_hostexplicit_post_started_failures_are_uncertain_without_replay`
  covers a Tool/runtime error and a second-stage
  `AuthorizedDispatchError::Rejected` after Started; both are status-only
  `uncertain`/`possible_effect_unknown`, leak no raw failure data, and do not
  dispatch again.

The production-only refactor extracts the deletion Prepare orchestration,
deletion structural-output-plus-independent-proof classification, and shared
Confirm currentness/D2 validation helpers used by the Tauri command path and
the deterministic tests. Native deletion remains only in the existing
`repo.delete-file` Tool. Ordinary deletion schema/status/1 MiB/binary behavior,
the exact ten-tool HostExplicit set, ADR 0017/0021/0025, and all frontend
behavior remain unchanged. No connected-current destructive certification,
model execution, MCP/Process Plugin execution, frontend deletion UI, or Task
284 work was started.
