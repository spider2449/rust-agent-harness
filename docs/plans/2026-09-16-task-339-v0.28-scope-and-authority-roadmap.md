# Task 339 — RAH v0.28 Scope and Authority Roadmap

Date: 2026-09-16
Status: Research and product-scope decision only
Baseline: 65707878edcb262c5bf66c83709fad4bc072b5a0
Task type: Documentation-only roadmap; no Rust, frontend, schema, Cargo,
dependency, permission, or ADR change

## Decision

Recommendation: A — explicit process-local removal of an inactive repository member

RAH v0.28 should complete the released multi-repository lifecycle with one
host-owned action: a user may remove an admitted repository that is currently
inactive. Removing the active member is rejected while it is active. The user
can first explicitly activate another admitted member, then remove the former
member.

This is the smallest capability that removes an ordinary Desktop friction point
without introducing a new executable authority category. Its authority-delta
classification is NONE: ADR 0027, the existing host-owned membership identity,
active-only composition, and currentness rules are sufficient. The private
WorkspaceMembershipState::remove primitive already rejects removal of the
active member and removes an inactive member from process-local state. The
missing work is a closed host action, lifecycle integration, presentation, and
evidence.

This is not remembered-candidate deletion:

    forget remembered candidate != remove process-local repository member

Member removal changes only process-local membership and reachability. It does
not delete repository files, mutate Git, delete a remembered candidate, restore
or remove durable conversation text, shut down the active provider/runtime, or
create a model-facing repository selector.

Direct active-member removal is out of scope. If a later product decision
requires one-click withdrawal of the active repository, that is an
authority-withdrawal lifecycle design and must return as separate research and
ADR work.

## Product friction after v0.27

The released product admits several repositories, activates one, switches
explicitly, and remembers descriptive candidates across restart. It still has
an incomplete in-process curation loop:

1. A user can admit a repository accidentally or temporarily.
2. It remains a process-local member after it is no longer useful.
3. There is no user-facing way to remove that inactive member.
4. The workaround is restart, which also discards every other process-local
   member and active workflow state.

This is ordinary usage friction for changing repository pairs or short-lived
workspaces. It is more immediate than linked worktrees, network MCP, or plugin
discovery, which serve narrower or advanced workflows. It is also more
product-specific than GUI automation, which is valuable infrastructure but not
an end-user capability.

The v0.28 product objective is:

> Users can explicitly curate the current process-local repository set without
> turning remembered descriptions into executable authority or adding generic
> mutation authority.

## Non-negotiable boundaries

The recommendation preserves:

- model request is not authorization;
- provider metadata cannot create host authority;
- missing explicit external permission fails closed;
- no generic shell, process, fs.write, or network authority;
- worktree, index, history, and network Git authorities remain distinct;
- timeout, cancellation, disconnect, crash, or lost response is not rollback;
- uncertain effects are never replayed;
- process supervision is not OS sandboxing;
- Trusted Profile remains a trusted-host composition boundary;
- restart restores zero executable repository authority;
- remembered path is not repository identity;
- automatic admission and activation remain forbidden;
- remembered persistence remains descriptive only;
- HostExplicit remains an exact host-owned allowlist of 11 tools;
- inactive members remain inert and do not own executable ToolRegistries;
- no repository-qualified model Tool input or model-selected repository route.

## Current implementation observations

ADR 0027 already defines the relevant lifecycle:

- admission creates a fresh process-local RepositoryMemberId and private
  repository identity evidence;
- exactly zero or one repository is active;
- active composition is fresh and repository-bound;
- switching withdraws old active executable state;
- inactive removal removes future reachability without unnecessarily
  invalidating unrelated active authority;
- active removal is an authority-withdrawal lifecycle concern;
- removal during a started effect cannot roll back or prove no effect;
- restart creates a new process-local authority context.

The current source already has the lower-level operation:

- WorkspaceMembershipState::remove accepts a member ID;
- it returns no member when the target is active;
- it advances membership generation for inactive removal;
- it removes only the selected member from the process-local map.

The Desktop command surface exposes remembered-candidate management, membership
presentation, admission, and activation, but no public member-removal command.
Activation failure cleanup calls the private removal primitive, confirming that
removal is needed for lifecycle rollback but is not yet a supported user
capability.

The remembered catalog is separate. Candidate deletion mutates only the bounded
durable descriptive catalog; it does not call repository deletion, membership
removal, activation, provider teardown, or Git. A v0.28 member removal leaves
the remembered candidate unchanged and permits later explicit fresh admission.

Completed conversation text already has application-local SQLite persistence
under an opaque repository namespace, and explicit resume is display-only after
a fresh current connection. That existing continuity reduces the current value
of broad durable session restoration. Removal must not turn conversation,
runtime, or provider state into restart authority.

## Candidate A — explicit inactive-member removal

### Contract

The closed host-owned operation is:

    typed human member selector
      -> validate current opaque process-local identity
      -> require target exists and is inactive
      -> require no target-bound effect is running
      -> remove target and invalidate target reachability
      -> publish sanitized membership presentation

The request contains only the current bounded selector. It does not accept a
path, repository root, Git identity, Tool input, provider identity, or
frontend-supplied authority metadata.

Removal must remove only the target member, make its selector unusable, and
invalidate any prepared state bound to that member. It must preserve an
unrelated active member's repository, current ToolRegistry, provider/runtime,
active conversation, Commit authorization, and Stage/Unstage state. Repository
files, .git, index, HEAD, refs, and history remain unchanged. The remembered
candidate remains unchanged. Re-admission later receives a fresh member ID.

Attempting to remove the active member returns a bounded active/busy result with
no effect. It does not switch, disconnect, clear conversation, revoke active
workflow state, or partially withdraw composition. A later explicit switch can
make it inactive, after which removal is a separate action.

## Candidate D — linked Git worktrees

directory, and ADR 0027 does not claim linked-worktree support. A linked
worktree commonly has a .git file pointing into a common Git directory, while

Safe support is not path equality. RAH would need a composite identity for the
common Git directory and worktree administrative identity, worktree-local root

## Why A wins now

1. It fixes a visible everyday gap in the feature released by v0.26/v0.27.
2. It uses existing process-local identity and accepted ADR 0027 lifecycle
   rules instead of creating a new authority category.
3. It has no durable schema, dependency, provider, model, network, or Git
   mutation impact.
4. It is reversible and easy to explain: remove an inactive inert member; switch
   before removal if active.
5. A bounded host-driven Windows scenario can prove the transition and preserve
   the active repository.

Alternatives wait for evidence: B for continuity pain beyond current transcript
and candidate persistence; C for reviewed structural authoring demand; D for a
worktree-heavy user cohort and identity ADR; E for a concrete remote MCP need
and trust design; F for repeated plugin-operability pain; G for frequent
intentional profile changes. H may proceed as enabling infrastructure but does
not replace the product objective.

## v0.28 scope freeze

### In scope

- Host-owned Desktop removal of one explicitly selected inactive
  process-local member.
- Closed bounded selector input; no path or repository identity input.
- Fail-closed malformed, unknown, stale, duplicate, and alias handling.
- Explicit active-member rejection with no state change.
- Lifecycle coordination with model turns, HostExplicit effects, Commit review,
  Stage/Unstage, and provider/runtime transitions.
- Target-bound currentness/reachability invalidation while preserving unrelated
  active authority.
- Sanitized presentation with no native paths, identities, tickets, handles,
  or raw errors.
- Fresh re-admission after removal with a new RepositoryMemberId.
- Deterministic tests and one host-driven Windows production live gate.

### Explicitly out of scope

Active removal; automatic switching; any repository/file/directory/.git/index/
HEAD/ref/history mutation; remembered-candidate deletion or update; durable
conversation deletion; automatic resume, provider reconnect, profile reload, or
runtime restoration; linked worktrees; network MCP; PluginManager discovery or
installation; model-controlled plugin lifecycle; Trusted Profile hot reload;
HostExplicit repo.create-directory; generic shell/process/filesystem/network
authority; model-selected repository routing; and GUI automation as a product
authority claim.

No Cargo, dependency, schema, permission, production/test/frontend, or ADR
change is part of Task 339.

### Authority boundary

No authority category is added. The host reuses the current process-local
RepositoryMemberId, private RepositoryAdmissionIdentity, one-active-repository
composition, lifecycle coordination, currentness, and opaque selector
presentation. Removal is a membership reachability transition, not repository
mutation, filesystem authority, Git authority, Tool authority, provider
authority, network authority, or HostExplicit capability.

### Human consent

The user explicitly chooses Remove for one displayed inactive member. The
frontend submits only the selector. Rust resolves it against current host state
and performs all checks. Model/provider output, remembered data, and frontend
state cannot authorize removal.

### Persistence

Removal is process-local. The remembered candidate is unchanged. Restart loads
only descriptive state and restores zero repository membership, active
repository, ToolRegistry, provider/runtime, Commit/Stage/Unstage, HostExplicit,
and executable conversation authority.

Durable conversation text is not deleted. Any in-memory binding for a removed
member is no longer selectable; later use requires fresh admission, activation,
currentness, and existing explicit display-only resume rules.

### Failure semantics

- Unknown or malformed selector: bounded failure; no state change.
- Active selector: bounded active/busy failure; no state change.
- Stale identity/currentness or lifecycle transition: no removal and no retry.
- Valid inactive removal: remove only that member and publish a fresh sanitized
  snapshot.
- A started effect is never rolled back or replayed; removal is rejected while
  lifecycle ownership requires it.
- Crash/restart reconstructs no executable membership or authority.
- Later admission of the same path is fresh and cannot revive the old member or
  prepared state.

### Mandatory Windows live gate

Use a fresh disposable fixture and exact candidate SHA. The production Desktop
backend route must demonstrate:

1. Admit distinct A and B, activate A, and verify active-only composition.
2. Remove inactive B and prove B is absent and A's repository, ToolRegistry,
   provider/runtime, conversation binding, Commit review, and Stage/Unstage
   state are unchanged.
3. Attempt removal of active A and prove bounded rejection with zero
   repository/filesystem/Git effect and no provider teardown.
4. Attempt malformed/unknown/stale selectors and prove zero effect.
5. Re-admit B and prove a fresh member identity.
6. Prove the remembered catalog is unchanged and restart restores zero
   executable repository authority.
7. Prove zero model requests/model-selected Tool dispatch, MCP activation,
   Process Plugin activation, network Git, automatic activation, automatic
   commit, and HostExplicit allowlist change.
8. Record only bounded status/activity without native paths, filesystem IDs,
   authority handles, tickets, or source-bearing data.

The gate is host-driven production evidence. It must not claim GUI automation,
model-selected dynamic Tool dispatch, race-free TOCTOU, network isolation,
rollback, OS sandboxing, or cross-platform live parity.

## ADR strategy and implementation sequence

Task 340 requires no new ADR for the inactive-only scope. ADR 0027 already
contains the accepted removal boundary and ADR 0028 remains unchanged. Task 340
should produce an implementation-ready contract and acceptance matrix. If
research discovers that active removal, cross-process removal, durable member
removal, or a new authority category is necessary, stop and return to ADR
research rather than expanding silently.

1. Task 340 — inactive-member removal contract and lifecycle acceptance.
   Freeze selector, active rejection, lock/order, currentness, conversation/
   provider effects, privacy, remembered-candidate isolation, and tests.
2. Task 341 — Desktop host removal foundation.
   Add the host command/backend transition around the existing private primitive.
3. Task 342 — Desktop presentation and hardening.
   Add UI/status mapping, race handling, conversation binding cleanup, and tests.
4. Task 343 — independent audit and Windows live certification.
   Audit the route, run the disposable A/B fixture, and record nonclaims.
5. Task 344 — v0.28 milestone audit, release preparation, and publication.
