# Task 356 — RAH v0.30 Scope and Authority Roadmap

Date: 2026-09-18
Status: **RECOMMENDATION — READY FOR TASK 357 CONTRACT RESEARCH**
Task type: research and product scope only

## Recommendation

**Recommendation: Linked Git worktree membership.**

The concrete friction is that RAH Desktop rejects an existing linked worktree
when the user selects it. The user cannot use RAH's repository workflow against
a second local branch working tree that shares the original repository's Git
history. The current workaround is a separate clone or use of another tool.
That workaround loses the immediate shared local branch/ref workflow that is
the reason to use a linked worktree.

This matters after v0.29 because the active-repository lifecycle is now complete:
RAH already supports explicit membership, one active repository, switching,
zero-active Close, inactive removal, and fresh admission after restart. The next
useful repository workflow is to let a user select another real Git working
tree without treating shared history as if it were an independent repository.
This improves the normal Desktop/chat repository workflow directly; it is not
primarily an internal cleanup.

The cost is acceptable only as an explicitly bounded identity and authority
extension. A linked worktree has its own working root, private Git directory,
HEAD, and index, while it shares common repository state such as objects and
ordinary refs. Root path or shared common-directory identity alone cannot
identify the executable target. Each admitted worktree must remain a distinct
repository target with its own worktree identity and currentness, while shared
Git state remains a separately observed relationship. That is a **new
authority category** and needs an additive ADR before implementation.

The strongest alternative is HostExplicit repo.create-directory. Its underlying
bounded Tool and Desktop registration already exist; users can request it
through the ordinary Tool route when the configured authority and permission
allow it. The unmet part is a direct human-reviewed HostExplicit route. That is
useful for scaffolding, but adds reviewed UX to an operation users can already
perform and creates a twelfth reviewed route. Its normal-use workaround is
better than the linked-worktree workaround, so it should wait.

Adjacent capabilities that remain excluded from v0.30 are HostExplicit
repo.create-directory, remote/network MCP, Process Plugin management or
installation, Trusted Profile hot reload, durable restoration of repository
membership or executable state, automatic worktree discovery, Git worktree
creation/removal/pruning, multiple simultaneously active repositories, and
GUI automation infrastructure.

## v0.29 baseline confirmed

The release gate, live certification, current source, architecture/security
documents, and accepted ADR 0027/0028 establish this baseline:

- Explicit process-local multi-repository membership, one active repository,
  valid zero-active state, switching, active Close, inactive removal, and
  fresh restart readmission from descriptive candidates.
- Repository observation and bounded worktree authoring, separate Stage and
  Unstage index effects, and separately reviewed Commit authority.
- Exactly 11 HostExplicit-approved Tools. The set remains:
  fs.read, repo.file-info, repo.status, repo.diff, repo.diff-staged,
  repo.create-branch, repo.patch, repo.edit-files, repo.create-file,
  repo.delete-file, and repo.rename-file.
- Trusted Profile is host-owned composition. Local stdio MCP and Process
  Plugin providers remain profile-configured. Codex remains an optional
  AgentRuntime adapter.
- Membership and executable composition are process-local. Restart restores
  no RepositoryMemberId, active repository, repository ToolRegistry, Commit
  authority, Stage/Unstage state, HostExplicit ticket, runtime connection, or
  provider activation.
- Remembered candidates and completed transcripts are descriptive/private
  data. Admission, validation, activation, provider connection, and transcript
  resume remain explicit steps.
- Currentness uses fresh repository identity and generations. Reactivation
  cannot revive a stale prepared action.

The Windows v0.29 gate was host-driven production-backend certification.
GUI automation was NOT EXECUTED. The certified Codex baseline is 0.149.0.
Model-selected dynamic Tool dispatch, Linux/macOS live parity, race-free TOCTOU,
network isolation, rollback, and OS sandboxing remain nonclaims.

requests, supports JSON or request-scoped SSE replies, treats stream closure as

## Candidate conclusions and evidence quality

### A. HostExplicit repo.create-directory

**What the user cannot do today:** invoke directory creation directly through
the human-reviewed HostExplicit panel. This is not a general inability to
create a directory. Desktop composition registers RepositoryDirectoryCreationTool
when a repository is active. It creates one empty ordinary directory beneath
an already existing validated parent, checks repository and parent identity,
rejects nested repository/reparse boundaries, snapshots Git metadata, and
classifies uncertain effects without replay.

**Frequency and workaround:** scaffolding directories is a normal editing
pattern (**inference: medium frequency**). The ordinary bounded Tool is a
substantial workaround (**production code and current user-facing Tool
composition**); repo.create-file also covers a file below an existing parent.
An empty directory alone is not represented by Git, so a user normally creates
a file afterward.

**Evidence:** production code, deterministic tests in
repository_create_directory.rs, current HostExplicit allowlist tests, and
released Security/Architecture documentation. User frequency is inference.

**Conclusion:** **NARROW EXTENSION** of existing bounded directory-creation
authority if exposed through a capability-specific review path. It is a strong
alternative, but its unmet user action is narrower than the linked-worktree
admission failure. Do not infer that repo.create-file creates missing parent
directories; its policy requires an existing validated parent. The ordinary
directory Tool creates one leaf beneath an already-existing safe parent; deeper
structures require one creation at a time. Git does not track an empty
directory. The existing policy checks parent and repository identity, rejects
symlink/reparse/nested-repository traversal, and conservatively reports an
uncertain native effect without retry or rollback. A HostExplicit route would
need a relative-path review and separate Prepare/Confirm consent.

### B. Durable session/workflow continuity

**What the user cannot do today:** restore executable repository selection,
membership, provider connection, and model context automatically after restart.
That deliberate restriction remains required. For the ordinary continuity case,
the Desktop already persists bounded completed conversation pairs, exposes
transcript presentation, offers an explicit resume action only after a current
connection exists, stores an ApplicationRestarted separator, and has a
remembered-candidate catalog for fresh readmission.

The resume route requires an idle chat, connected current repository/model/
profile/connection generations, empty current conversation history, bounded
replay, and explicit invocation. This reduces the need to manually reconstruct
the transcript while preserving zero authority on restart.

**Evidence:** production code in conversation_persistence.rs,
remembered_workspace.rs, and main.rs; deterministic persistence/restart tests;
ADR 0027 and ADR 0028. The assertion that the remaining extra presentation
state is lower value is product judgment, not usage telemetry.

**Conclusion:** **NONE** for authority classification. Additional descriptive
workflow notes or presentation preferences could use existing safe principles,
with explicit bounds, clear/delete behavior, and privacy review. The already
supported safe material is user-labelled remembered candidates, opt-in
location hints, ordered candidate presentation, completed transcript pairs
and their descriptive repository namespace, plus a visible restart separator.
It is not an authorization object. The central continuity case is already
covered; do not silently restore a selected member, active repository, runtime,
ToolRegistry, Commit, Stage/Unstage, generation, or ticket.

### C. Linked Git worktree membership

**What the user cannot do today:** select and use a linked working tree as a
distinct Desktop repository member. RepositoryAdmissionIdentity currently
accepts a supported .git directory and rejects non-directory .git metadata;
Commit explicitly reports linked worktrees and .git indirection unsupported.
Current worktree mutation/index code also assumes ordinary .git directory
paths, and deterministic tests explicitly reject linked .git-file layouts.

**Git semantics:** a linked worktree’s top-level .git is a gitfile pointing to a
private per-worktree Git directory. The private directory supplies that
worktree’s HEAD and index; a common directory supplies shared objects and most
refs. This means:

- Main and linked worktrees under one common directory are **distinct
  repository authority targets**. They have different roots and private
  gitdirs, with independently bound HEAD, index, and worktree state (HEAD
  values may coincide).
- They are related targets sharing repository history and some refs. They must
  not be deduplicated by common-dir identity, admitted as a union, or treated
  as independent clones.
- Stage and Unstage bind to the selected worktree's index and root.
- Reviewed Commit binds to the selected worktree's HEAD, index, branch/ref
  semantics, private gitdir, and validated common repository relationship.
  A commit changes shared history/ref state. Other members must freshly
  revalidate shared state before any later operation.
- Close, switch, and inactive removal change RAH membership/composition only.
  They do not remove, prune, lock, or mutate Git worktrees.
- Two members may share one Git common directory while only one remains
  active. Same-worktree aliases are one candidate; a second path to the same
  private worktree identity is a duplicate. Nested repository boundaries,
  submodules, arbitrary gitfiles, and unrecognized private/common-dir
  relationships remain rejected unless Task 357 proves a narrower safe rule.

**User value and workaround:** developers who use multiple worktrees can switch
local branch contexts without creating and synchronizing another clone
(**inference: medium frequency among Git users; high value for affected users**).
A separate clone or external Git client is possible but loses the shared local
worktree/index and branch-ref workflow (**inference: poor-medium workaround**).

**Evidence:** production identity/commit checks, mutation policies, released
ADR 0027 nonclaim, deterministic rejection tests, current explicit folder
selection behavior, and official Git repository-layout documentation. The
potential frequency is inference because the repository has no usage telemetry.

**Conclusion:** **NEW AUTHORITY CATEGORY**: validated linked-worktree target
identity plus its relationship to shared Git common state. Add an ADR rather
than amend ADR 0027 or 0028. Preserve their existing rules for one active
member, no union registry, descriptive-only persistence, fresh readmission,
and currentness invalidation.

### D. Network MCP / Streamable HTTP

**What the user cannot do today:** configure an MCP server by remote HTTP
endpoint; current MCP integration is local stdio and a host-selected child
executable. Remote MCP might remove local installation/proxy setup and reach
hosted services, but this is an integration capability, not the next core
repository workflow.

The authority model would have to separate endpoint configuration, connection
authority, TLS/server identity, credential authority, remote Tool identity and
admission, RAH permission, Tool execution, redirects, reconnect, and external
effect uncertainty. HTTPS transport and valid server identity would be
necessary but would not establish network isolation. Tools remain individually
host-admitted and permission checked; advertised names/schemas cannot grant
authority. Restart may retain only inert endpoint/profile intent, not live
connection, OAuth state, access/refresh token, permission, or Tool admission.

**Evidence:** production stdio-only profile/provider code, current MCP
2026-07-28 primary specifications, and current user-facing profile composition.
Expected value/frequency are inference. Current protocol facts are linked above.

A future Trusted Profile representation would need a closed endpoint/transport
record distinct from remote server identity and user-selected authorization.
Credential material or refresh tokens need a host-owned secure store keyed to
the validated resource origin; they must not be copied into profile JSON,
conversation history, Tool schemas, or general preferences. Redirects must not
silently change the trusted origin; reject cross-origin redirects and re-check
TLS identity on reconnect. Apply bounded connect/request timeouts and
cancellation, but do not automatically replay a Tool call after a timeout or
disconnect. Remote tools/list changes require fresh host admission and
permission matching; server advertisement itself grants nothing. Restart
restores only inert endpoint intent, never a connection, token, session, or
admitted Tool set.

**Conclusion:** **NEW AUTHORITY CATEGORY**. Defer until a concrete remote-service
need outweighs OAuth, credential storage, endpoint/redirect, privacy, timeout,
cancellation, reconnect, dynamic Tool-set, and external uncertain-effect
costs.

### E. PluginManager / Process Plugin lifecycle UX

**What the user cannot do today:** inspect, pause, restart, or check one
configured Process Plugin from Desktop without cycling the complete connected
provider composition. The current host composes fixed profile-selected plugins
on Connect and owns their shutdown on Disconnect. There is no individual
inventory/status/restart UI or model-controlled lifecycle.

The candidate surface would be limited to inventory, enable/disable intent,
start/stop, health/status, explicit restart, and protocol/version compatibility
for exact already-configured executables. Installation, download, arbitrary
executable discovery, and Tool permission/admission remain separate.

**Workaround:** Disconnect and Connect rebuilds the configured profile. This
is coarse but retains existing fixed executable selection and provider
admission. A management panel would not install plugins, discover executables,
download code, change Tool authority, or make process supervision an OS
sandbox.

**Evidence:** production provider-composition and Process Plugin lifecycle
code, deterministic adapter lifecycle tests, and current UI commands. Usage
frequency is inference.

**Conclusion:** **NARROW EXTENSION** of existing host-owned, fixed-profile
provider lifecycle. Defer because it primarily improves provider operations,
has a useful reconnect workaround, and creates Windows process-lifecycle
certification work without advancing repository authoring.

### F. Explicit Trusted Profile reload

**What the user cannot do today:** atomically replace a connected provider
composition with a changed profile file without Disconnect/Connect.
Current Connect fresh-loads the selected source, validates it, and composes
providers; Desktop already exposes profile choose/restore/clear operations
subject to its lifecycle guards.

**Workaround:** explicitly Disconnect, choose or restore the intended profile,
then Connect again. This causes fresh source loading and provider composition.
There is no default automatic file watcher or hot reload.

**Evidence:** production profile-selection and provider activation paths,
deterministic profile-composition tests, and current Desktop controls.
Frequency/value of profile editing is inference.

**Conclusion:** **NARROW EXTENSION**. Defer because the current reconnect
workflow is serviceable and live reload adds atomic withdrawal, in-flight Tool,
provider cleanup, conversation/session, repository currentness, prepared
HostExplicit, and sanitized-error questions.

### G. Windows GUI automation / certification infrastructure

**What the user cannot do today:** RAH has not certified real mouse/keyboard/
accessibility confirmation and stale-confirmation behavior with GUI automation.
The release evidence does not claim that it did.

That infrastructure could exercise confirmation-flow regressions,
keyboard/accessibility behavior, permission UX, stale-confirmation races, and
release confidence, and could shorten later manual gates. It remains release
infrastructure rather than an end-user product capability.

**Workaround:** deterministic frontend behavior tests plus the host-driven
production-backend live gate. This leaves the GUI claim open but preserves
precise evidence boundaries.

**Evidence:** v0.29 live certification and release gate explicitly say GUI
automation was NOT EXECUTED; checked-in frontend tests exercise state and
render behavior without driving a real Desktop. The idea that UI automation
will shorten future gates is inference.

**Conclusion:** **NONE**. Defer as infrastructure. Do not turn an honest
nonclaim into a product objective. The seven Task 352 storage-only roots are a
non-blocking historical cleanup limitation and provide no independent reason
to choose this work.

### H. Repository/session workflow grouping

**What the user cannot do today:** no material missing grouping action was
found. ADR 0027 defines a descriptive workspace container, and ADR 0028 plus
remembered_workspace.rs implements one durable ordered catalog of labelled
candidate members with explicit add/update/reorder/delete actions.

The catalog stores no executable membership, repository identity, authority,
or runtime state. A last-active candidate remains a presentation hint.

**Evidence:** production catalog module and UI commands, deterministic schema/
catalog/restart tests, and released ADR 0027/0028.

**Conclusion:** **NONE**; **Unnecessary / already covered**. Do not add another
workspace-grouping concept or turn candidate grouping into persistent
membership.

## Product sequencing check

Linked worktree support makes the next normal workflow materially better for
users who keep multiple local branch working trees. The existing folder-picker
path currently rejects that workflow; full clones impose extra synchronization
and do not share the local index/HEAD/ref behavior that linked worktrees
provide. The usage estimate is medium and inferred, so Task 357 must validate
the user-facing workflow framing, but the production refusal and workaround
cost are directly evidenced.

The recommendation is not to normalize every Git layout for architectural
completeness. The selected boundary is limited to existing, host-selected
linked worktrees and the correct identity binding for existing repository
operations. Git worktree lifecycle management, branch switching, parallel
active repositories, and shared ambient Git access add no value required for
this workflow and stay excluded.

## Recommendation scope freeze

### Product behavior

A user can explicitly select an existing main or linked Git worktree in
Desktop, admit each selected worktree as a distinct process-local repository
member, and use the existing repository workflow on the selected active
worktree. Members sharing one common Git directory remain separate targets;
only one may be active at a time.

### In scope

- Host validation and fresh admission of an explicitly selected linked
  worktree whose .git file, private gitdir, and common-dir relationship can be
  proven using fixed native Git invocations and bounded filesystem identity
  checks.
- Distinct process-local member identities for distinct worktree roots/private
  gitdirs, including a main worktree and one or more recognized linked
  worktrees sharing a common Git directory.
- Existing read/status/diff, bounded worktree authoring, Stage, Unstage, and
  reviewed Commit operating on the selected worktree's actual root, HEAD,
  index, private Git directory, and validated shared ref state.
- Duplicate and alias rejection for one worktree; separate members for
  distinct validated worktrees; one active member; no union ToolRegistry.
- Existing activate, switch, Close, inactive-removal, fresh currentness, and
  HostExplicit behavior applied to the selected worktree. HostExplicit stays
  at exactly 11 names.
- Deterministic Git fixtures for multiple linked worktrees and independent
  per-worktree indexes/HEADs plus shared ref effects.

### Out of scope

- Creating, removing, pruning, locking, unlocking, moving, or automatically
  discovering Git worktrees.
- Arbitrary .git files, submodules, nested repositories, bare repositories,
  git submodules, linked-worktree roots nested under another admitted root, or
  unsupported/ambiguous common-dir relationships.
- More than one active repository, a union registry, parallel per-repository
  model dispatch, cross-worktree Tools, or provider-selected repository
  routing.
- Generic Git, shell, process, filesystem, network, branch-switch, fetch,
  pull, push, or remote authority.
- Persisted RepositoryMemberId, active repository, private/common Git
  identity, repository generation, ToolRegistry, Commit authorization,
  Stage/Unstage selector, HostExplicit ticket, or runtime/provider connection.
- HostExplicit repo.create-directory, network MCP, PluginManager, profile
  reload, or GUI automation.

### Authority

Add a **NEW AUTHORITY CATEGORY** for the identity of one selected worktree and
its validated relationship to shared Git common state. The authority target is
the specific working tree/private gitdir pair, not the common directory alone.
Common-dir identity is private relationship evidence used to detect sharing
and stale shared state; it is not an executable root and cannot authorize
another worktree.

Existing permission levels and capability policies remain in force. No
PermissionLevel is added. No provider or model input can select a worktree
identity. Existing Stage/Unstage and reviewed Commit authorities stay separate.

### Human consent

The human explicitly selects each working-tree root with the existing Desktop
folder picker or an equivalent host-owned path-selection action. The host
validates and admits it. The human explicitly activates/switches to one member.
Existing Stage/Unstage controls and reviewed Commit consent remain unchanged.
No inferred sibling worktree, common-dir scan, model request, provider
metadata, remembered hint, or Git output automatically adds or activates a
member.

### Persistence

Only the existing remembered-candidate descriptive record may persist: its
opaque candidate ID, user label, order, and explicitly opted-in location hint.
Do not persist the .git file contents, private gitdir identity, common-dir
identity, per-worktree HEAD/index, RepositoryMemberId, active member, Tool
composition, permissions, HostExplicit state, Commit authorization,
Stage/Unstage state, provider connection, or runtime.

Restart leaves zero repository members and no active repository. A remembered
linked-worktree candidate requires explicit fresh admission, complete current
identity validation, a new RepositoryMemberId, and explicit activation.
Existing ADR 0028 schema remains unchanged unless Task 357 demonstrates a
strictly necessary descriptive field; do not persist authority to avoid an
admission check.

### Currentness and identity

Task 357 must define opaque, non-serialized currentness over at least:

- canonical working-tree root and root filesystem identity;
- accepted top-level .git directory or gitfile identity and exact validated
  relationship;
- Git-resolved private gitdir and common dir, their filesystem identities,
  repository-format and ordinary-worktree classification;
- per-worktree HEAD and index locations/identities/state;
- shared refs/HEAD semantics and relevant Git executable identity;
- workspace membership, active-selection, repository, model, profile,
  connection, and composition generations already required by ADR 0027; and
- capability-specific target/path/preparation identity.

A changed or replaced root, gitfile, private gitdir, common dir, Git executable,
HEAD/index binding, shared ref state, active member, or composition makes the
affected preparation stale. Reactivation creates fresh currentness; it never
revives an old HostExplicit preparation, Commit authorization, or index
reservation. Common-dir identity alone never establishes continuity or
duplicate identity between sibling worktrees.

### External effects

Repository observation and bounded content changes target the selected active
worktree. Stage and Unstage target that worktree's index only. Reviewed Commit
uses that worktree's reviewed index and HEAD and may update a ref shared with
the other linked worktrees. Any later operation in a sibling must validate
current shared state before use. Close, switching, or member removal does not
change Git worktree registration, refs, index, files, or common metadata.

The host continues to use fixed Git programs and argument vectors with
explicit working directory, environment, output bounds, timeout, and owned
lifecycle. No shell interpolation or generic process authority is introduced.

### Cancellation and uncertainty

Timeout, cancellation, disconnect, process failure, or a lost response is not
rollback and does not prove no effect. Do not retry, replay, delete, prune,
compensate, or restore an uncertain external effect. If shared Git state or
the selected worktree cannot be proven current after an attempt, preserve the
uncertain result and require fresh observation/admission as appropriate.
Process supervision is not OS sandboxing.

### Privacy

Canonical roots, raw .git file contents, private gitdir/common-dir paths,
filesystem IDs, and shared ref snapshots remain host-private evidence. Desktop
presentation uses the existing bounded label/name DTOs. User review shows only
necessary repository-relative paths and bounded effect facts. Do not put
absolute paths, filesystem identities, raw Git metadata, tokens, or authority
handles into Tool input, provider metadata, chat text, generic activity, or
unbounded errors.

### Windows live gate

Release-blocking Windows evidence must use the exact production source SHA,
clean required checkpoint, and a fresh disposable Git fixture with one main
worktree and at least two linked worktrees sharing one common Git directory.
The gate must prove:

1. Explicit admission distinguishes the main and linked worktrees, assigns
   fresh member IDs, and rejects duplicate/alias, nested, submodule, malformed
   gitfile, replaced-private-dir, replaced-common-dir, and reparse cases before
   effects.
2. Switching and zero-active Close/removal preserve the one-active rule,
   invalidate stale worktree-bound state, and do not run git worktree remove,
   prune, branch switch, or cleanup.
3. Reads and bounded authoring resolve against the selected working root.
   Stage/Unstage change only the selected worktree's index.
4. Reviewed Commit proof names and validates the selected worktree's HEAD,
   index, attached branch/ref, common repository state, and postcondition.
   Changes through a sibling or external Git process stale prepared state and
   cannot be rebound to the currently active member.
5. Before/after captures distinguish each worktree's HEAD/index from the
   shared common refs/objects and show that only the requested intended effect
   occurred. Any uncertain effect is not retried or cleaned up.
6. Provider, model, HostExplicit count, permission, runtime, and network
   assertions remain within their recorded scope; emit exactly
   RAH_V030_LINKED_WORKTREE_LIVE_OK only after all checks pass.

The release-blocking gate is host-driven production-backend evidence, not GUI
automation or model-selected dynamic Tool evidence. No failed/uncertain fixture
may be reused for a later effectful attempt.

### Cross-platform claim

The release may claim Windows live behavior only for the exact certified
production source and tested operations. Deterministic tests and compilation on
other targets support only those executed checks; they do not establish Linux
or macOS live Desktop parity, filesystem race freedom, network isolation, OS
sandboxing, rollback, or universal Git-layout support.
