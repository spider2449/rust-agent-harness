## 4. Dynamic Tool contract and current-source check

Current source is consistent with the required separation:

1. With the experimental API enabled, `rah-runtime-codex` initializes the
   app-server with `experimentalApi: true` and accepts the version-pinned
   dynamic Tool request shape.
2. The bridge snapshots definitions from the host-supplied RAH
   `ToolRegistry`, translates unusable public names to private aliases, and
   advertises the resulting dynamic Tools for the thread.
3. A dynamic request is resolved against that snapshot and is admitted through
   RAH permission policy and authorized dispatch before the current
   `ToolRegistry` executes it.
4. RAH emits `ToolRequested`, `ToolStarted`, and `ToolFinished` only for an
   actual RAH Tool lifecycle. A completed assistant message without those
   events is not a Tool call.
5. The captured Codex 0.149.0 schema fixture and deterministic bridge tests
   cover the experimental API, dynamic definitions, aliases, request
   correlation, replay handling, permission denial, currentness, and
   ToolRegistry dispatch.

Task 323’s deterministic evidence separately establishes v0.26 admission,
activation, active-only composition, stale-currentness rejection, Stage and
Unstage reservation/effect invariants, Connect/Disconnect lifecycle
coordination, provider isolation, and the exact 11-name HostExplicit set.

Therefore the missing evidence is model selection. Tool registration,
current-host composition, and the underlying authorization route are not
missing based on the current source and deterministic evidence. If a future
source review contradicts this contract, the disposition must be blocked and
reopened; the current source does not create that condition.

## 5. Model selection is not authorization

The assurance claims must remain separate:

| Assurance plane | Question | Owner | Evidence type |
| --- | --- | --- | --- |
| Host-owned RAH authority/effect correctness | Does the host compose the correct bounded authority and produce only the permitted repository effect? | RAH host, policy, Tool, ToolRegistry, native effect proof | Deterministic and host-driven live evidence |
| Codex runtime connection/lifecycle correctness | Does the certified Codex process connect, publish current state, reject unsafe lifecycle transitions, disconnect, and clean up? | RAH Desktop/runtime lifecycle | Deterministic and real process/lifecycle evidence |
| Model-selected dynamic Tool dispatch | Does the tested model choose an advertised RAH dynamic Tool and complete the request/response lifecycle? | External model/runtime behavior plus RAH bridge | Real model event evidence |

Model output and provider metadata are untrusted requests. A
`ToolRequested` event is not authorization; it is only an input to RAH’s
host-owned checks. Conversely, a model that does not request an advertised
Tool does not prove that host authority, policy, or effect handling is broken.

Model selection quality is a product/runtime behavior concern. Host
authorization correctness is a security boundary. One must not be used as
proof for the other. This is especially important here because v0.26’s actual
authority boundary is host-owned admission and activation of one active
repository, followed by a fresh active-only Desktop composition.

## 6. Option A — Keep original model-driven Task 324 blocked

Option A waits for the exact approved combination—Codex 0.149.0, the recorded
SHA, `gpt-5.6-terra`, medium reasoning, and the restricted live gate—to
produce a model-selected dynamic Tool lifecycle, then reruns the original
model-driven A/B/A certification.

Its security value is narrow. A successful run would add end-to-end evidence
that this particular external model/runtime combination can select a Tool;
it would not add authority to RAH or prove that the host would reject an
unauthorized request. The host’s authorization and effect correctness must
still be checked independently.

Its product value is real but bounded: it would document current user-path
compatibility for this exact model and gate. Its determinism is low because
the observed behavior depends on external service and model policy. Waiting
can become retry-until-pass sampling, especially after a completed ordinary
turn has already shown that the runtime can connect and receive model output.

This option delays the v0.26 milestone, risks indefinite blocking on behavior
outside RAH, and does not produce new evidence about host authority. It is not
selected as the v0.26 certification disposition.

## 7. Option B — Host-driven two-repository Windows live certification

Option B certifies the actual v0.26 host-owned authority/effect plane through
the production Desktop paths without requiring model Tool selection. It still
uses the real certified Codex binary to prove Connect, currentness, connected
lifecycle behavior, switch rejection, Disconnect, process reaping, and
cleanup. Repository reads and Stage/Unstage effects are invoked by the host
through the real active Desktop ToolRegistry/production dispatch path.

The certification target is:

```text
human admits A and B
 -> inert membership
 -> activate A
 -> fresh active-only DesktopRepository/ToolRegistry
 -> host-driven fs.read of repo-marker.txt from A
 -> real Codex Connect and current Connected publication
 -> B activation while Connected is rejected with RepositoryBusy
 -> real Disconnect and process reap
 -> activate B
 -> stale A Stage action is rejected
 -> fresh active-only B registry
 -> host-driven fs.read of the same relative marker from B
 -> real B Stage effect
 -> real B Unstage effect
 -> activate A
 -> fresh active-only A registry
 -> host-driven read proves A again
 -> fresh host state restores zero membership authority
 -> bounded cleanup
```

This directly tests the milestone’s security boundary: A and B are admitted
by the host; only one is active; inactive members do not supply executable
authority; switching withdraws old composition; stale A state cannot act on B;
and real filesystem/Git effects are bound to B only when B is active. The Codex
process remains meaningful to certify because connection publication and
lifecycle exclusion are host/runtime guarantees, not model-selection claims.

Option B is sufficient for v0.26 release preparation when combined with Task
323 deterministic evidence, provided release preparation preserves the
separate model-dispatch nonclaim. It is not sufficient to claim that
`gpt-5.6-terra` currently selects RAH Tools under the restricted gate.

The required host-driven success claim is exactly:

> **WINDOWS HOST-DRIVEN MULTI-REPOSITORY AUTHORITY/EFFECT CERTIFICATION
> PASSED**

The required nonclaim is exactly:

> **MODEL-SELECTED DYNAMIC TOOL DISPATCH NOT ESTABLISHED UNDER THE APPROVED
> GPT-5.6-TERRA LIVE GATE.**

The multi-repository milestone changes the live effect target, not the
authority principle. It makes A/B isolation, active-only composition,
currentness, and lifecycle coordination the relevant live proof. It does not
make model selection an inseparable security invariant because the model
cannot admit, activate, or compose a repository and cannot grant Stage,
Unstage, Commit, or HostExplicit authority.

## 8. Option C — Change certification model

Option C would keep Codex 0.149.0 but use another supported model, such as
GPT-5.5, solely to seek model-selected dynamic Tool dispatch. No such probe is
run in Task 324-B.

A different model producing Tool calls would establish only that the other
model works with the bridge under the tested configuration. It would not prove
that `gpt-5.6-terra` works, and it would not prove the shipped/default user
path unless the product deliberately adopts the other model as its supported
baseline. That would require separate model-baseline research covering model
identity, recommended/default configuration, compatibility, repeatability,
and release wording.

Option C risks converting certification into retry-until-pass model sampling
and would expand the immutable certification identity. The multi-repository
milestone supplies no reason to change the model baseline: its security value
is host-owned active-only authority, not model behavior. Option C is rejected
for this task. If later desired, it must be a dedicated model-certification
baseline research task; it cannot be a disguised Task 324 rerun.

## 9. Option D — Block v0.26 indefinitely on model selection

Option D makes a model-selected `ToolRequested` / `ToolStarted` /
`ToolFinished` lifecycle mandatory for release even after complete deterministic
and host-driven proof.

That is inconsistent with RAH’s role and accepted boundaries. RAH is not an
inference engine. Model request is never authorization. The host owns
authority composition, and the dynamic bridge is an adapter into the
RAH-owned ToolRegistry. Task 229B rejected indefinite prompt/model sampling;
Task 229C then certified the real Windows Desktop authority/effect path while
preserving the explicit model-dispatch limitation.

Option D would add no host-authority evidence, would make release timing
depend indefinitely on external nondeterministic model policy, and would not
solve or improve the external behavior. It would make a generic product/runtime
limitation a false security gate for a host-owned multi-repository feature.
Option D is rejected.

## 10. Security-invalid rescue strategies

The following are explicitly rejected and are not authorized by this
decision:

| Proposed rescue | Disposition |
| --- | --- |
| Generic Codex-owned shell authority | Reject; creates an unrelated execution surface and does not prove RAH Tool authorization. |
| Generic Codex-owned filesystem mutation | Reject; bypasses the bounded RAH repository authority model. |
| Enable `code_mode_host` merely to make GPT-5.6 invoke something | Reject; code-mode host is a Codex-owned execution surface intentionally disabled by the gate. |
| Browser, network, or computer-use authority | Reject; unrelated authority expansion and ambient-effect risk. |
| Add `shell.exec` or `process.exec` | Reject; generic process authority is outside scope and prohibited by accepted policy. |
| Weaken RAH Tool permissions | Reject; permission weakening cannot repair model selection and would damage the security boundary. |
| Make model selection grant authority | Reject; directly violates “model request is not authorization.” |
| Inject Tool calls manually and label them model-driven | Reject; false evidence. A host-driven call must be reported as host-driven. |
| Replay prompts until Tool selection happens | Reject; retry-until-pass sampling and unsafe repetition of effectful paths. |
| Silently upgrade Codex CLI | Reject; baseline migration requires separate research and certification. |
| Silently change the model | Reject; model identity is part of the tested product/runtime claim. |
| Use an unverified Codex binary | Reject; violates the immutable executable baseline. |
| Accept prose-only marker output as a Tool call | Reject; only the complete RAH Tool lifecycle and Tool result establish a Tool call. |

If GPT-5.6 currently prefers a code-mode route, that is an external
model/runtime compatibility limitation. It is not permission to broaden RAH’s
authority boundary.

## 11. Product impact

The limitation does not make v0.26’s multi-repository feature incoherent.

- The host can safely admit repositories without model dispatch because
  admission is a human/host operation.
- The host can activate A or B and compose only the active repository without
  model authority.
- Stage/Unstage and reviewed HostExplicit authorities remain host-controlled
  and can be exercised independently of model Tool selection.
- Codex Connect/Disconnect remains meaningful because it tests process
  ownership, currentness, lifecycle exclusion, reaping, and the prohibition on
  switching while Connected; it need not include a model turn to prove those
  invariants.
- The limitation is not specific to multi-repository identity. It is a generic
  RAH Tool Bridge usage limitation under the tested external
  model/runtime/gate combination.
- Blocking v0.26 would not repair the external model behavior. It would only
  defer host-owned feature evidence and keep the two assurance planes
  conflated.

The honest product statement is that a host-driven v0.26 certification does
not establish that GPT-5.6 Terra currently chooses RAH dynamic Tools under the
approved restricted ChatGPT-auth live gate. Users must not be promised current
model-selected Tool dispatch on the basis of this certification.

## 14. ADR impact

ADR 0027 requires no change. This task decides how to classify evidence; it
does not redesign workspace identity, admission, active selection,
currentness, or authority composition.

The existing accepted principles already cover the distinction needed here:

- model output and provider metadata cannot grant authority;
- the host owns permission and authority composition;
- active-only composition is the executable boundary;
- the RAH `ToolRegistry` remains the dispatch authority; and
- Codex dynamic Tools are untrusted requests through an adapter boundary.

HostExplicit eligibility.

## 15. Strong recommendation

**Recommendation B — USE HOST-DRIVEN WINDOWS TWO-REPOSITORY CERTIFICATION.**

This is the strongest disposition because Task 323 already establishes the
deterministic bridge and authority invariants; Task 324-A proves the block is
at the external model-selection layer; the model is not an authority source;
Task 229B selected the same policy; Task 229C established its real Windows
Desktop effect precedent; and the host-driven route directly tests the
security and product boundary that v0.26 introduces.

Recommendation B does not weaken the restricted gate or convert a host call
into a model call. It preserves the model-dispatch limitation as a separate,
visible nonclaim.
