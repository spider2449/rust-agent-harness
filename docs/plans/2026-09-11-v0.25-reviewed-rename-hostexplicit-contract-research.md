# Task 291 — RAH v0.25 Reviewed File Rename/Move HostExplicit Contract Research

## Scope and verdict

This document is research and contract definition only. It does not implement
Rust, change the frontend, change tests, create or edit an ADR, change
HostExplicit eligibility, change a Tool schema or result vocabulary, change
Cargo metadata, run destructive or live rename certification, create a tag or
release, or begin the next task.

The proposed reviewed route is intentionally narrower than the ordinary
`repo.rename-file` capability. It is a human/host route around the existing
Tool, not a new filesystem authority. The route is not ready for ADR 0026
decision because the current ordinary rename policy has material conformance
gaps against accepted ADR 0018. Those gaps must be hardened and independently
reviewed before a HostExplicit contract can safely rely on the Tool's ordinary
effect and status claims.

## Fixed authority boundary

The contract must preserve this separation:

```text
ADR 0018 RepositoryFileRenamePolicy
  = sole underlying rename/move mutation authority

ADR 0021
  = generic HostExplicit coordinator/currentness/ticket/D2/provenance boundary

future ADR 0026
  = reviewed human rename/move HostExplicit boundary
```

None of the following creates rename authority: model output, human
confirmation, frontend state, `PermissionLevel::Execute`, Tool registration,
Tool presence, Effective Authority display, Trusted Profile metadata, provider
metadata, MCP, Process Plugin, or an activity ID.

If later accepted, the reviewed route must still execute only through:

```text
authorized_tool_dispatch
 -> current ToolRegistry
 -> existing repo.rename-file
 -> ADR 0018 RepositoryFileRenamePolicy
```

Desktop must not directly rename a filesystem path.

### Hardening classification

The rows marked “Yes” are category A decisions: ordinary
`repo.rename-file` must be hardened before HostExplicit exposure. This is not a
broadening of ADR 0018 authority. It is bringing the implementation into the
accepted ADR 0018 compliance envelope.

The ignored-but-absent destination decision is category B: ADR 0018's
ordinary destination rule is about absence of an object and does not require a
Git ignore policy, but the reviewed route must reject an ignored absent
destination as a narrower human contract. This prevents the expected
worktree result from being silently hidden by ignore rules. The reviewed
preparer must check the current Git ignore/exclude result and issue no ticket
for an ignored destination.

## Existing ordinary Tool contract

The current ordinary Tool is:

```text
name       = repo.rename-file
permission = Execute
```

Its closed input schema, from
`crates/rah-tools/src/repository_rename_file.rs:75-82`, is exactly:

```json
{
  "source_path": "src/old.rs",
  "destination_path": "src/new.rs",
  "expected_source_file_sha256": "<64 lowercase hexadecimal characters>",
  "expected_source_file_byte_length": 123
}
```

The schema requires exactly those four properties, rejects additional
properties, declares a 1024-character path maximum, and limits the expected
source length to 1 MiB. The parser's safe logical-path check applies the
1024-byte bound (`value.len() <= 1024`) and rejects NUL, separators, traversal,
aliases, and unsupported components. The ordinary Tool reads the source and
derives/validates the actual hash and byte length internally; the model-supplied
values are preconditions, not authority.

The current emitted `ToolOutput` always has exactly one JSON content item. Its
current shapes from `result()` are:

| Status | Current JSON content | `is_error` |
| --- | --- | --- |
| `renamed_verified` | `{"status":"renamed_verified","uncertain":false,"path":"<logical destination>"}` | `false` |
| `known_no_effect` | `{"status":"known_no_effect","uncertain":false}` | `true` |
| `invalid_input` | `{"status":"invalid_input","uncertain":false}` | `true` |
| `precondition_failed` | `{"status":"precondition_failed","uncertain":false}` | `true` |
| `uncertain` | `{"status":"uncertain","uncertain":true}` | `true` |

The optional logical `path` is currently emitted only for
`renamed_verified`; the current ordinary Tool emits no `path` for the other
four statuses. The future route must not modify this schema, these five status
names, or these shapes. It may strictly validate them and then apply the
stronger independent reviewed-route proof below.

## Exact human Prepare DTO

The future human request is one closed object:

```json
{
  "source_path": "src/old.rs",
  "destination_path": "src/new.rs"
}
```

The canonical serialized request is UTF-8 JSON with no insignificant
whitespace, exactly the two fields in the shown order, no unknown fields, no
duplicate fields, and no NUL. Its serialized size is bounded at **8192 bytes
inclusive**, measured after JSON serialization and before parsing into host
state. Each logical path is 1 through 1024 UTF-8 bytes inclusive. The request
bound remains useful because JSON escaping can expand a path beyond its raw
UTF-8 length.

The human supplies no SHA-256, byte length, FileIdentity, repository root,
native path, Git executable, HEAD/tree/blob/index/ref identity, parent
identity, permission, authority, Tool name, Tool input/output, overwrite or
replace flag, temporary path, copy/delete fallback, retry/replay/restore
control, Stage, Unstage, or Commit instruction, provider/model/runtime/profile
selection, activity ID, or ticket.

Prepare derives the exact unchanged ordinary Tool input from protected source
bytes:

```json
{
  "source_path": "src/old.rs",
  "destination_path": "src/new.rs",
  "expected_source_file_sha256": "<host-derived lowercase SHA-256>",
  "expected_source_file_byte_length": 123
}
```

The host, not the frontend or model, constructs this input.

## Reviewed source-content representation and exact bounds

### Selected v1 answer: strict UTF-8 complete escaped source

The reviewed route selects option A: strict UTF-8, no NUL, at most 65,536 raw
bytes, with a complete deterministic escaped source representation. Option B
(complete binary representation) is deferred. Option C (digest/length/path
without a complete source representation) is rejected: the released reviewed
authoring model requires a human-visible complete preimage for an effectful
review, and rename has a destructive path effect even though it preserves
bytes.

This is intentionally narrower than ordinary ADR 0018. Ordinary
`repo.rename-file` remains a 1 MiB, binary-capable Tool. HostExplicit reviewed
rename is restricted to source/test/config/document-style content that a human
can inspect completely. A binary or non-UTF-8 source remains available only to
the ordinary route, subject to ordinary ADR 0018 compliance.

The exact inclusive bounds are:

| Representation | Bound |
| --- | ---: |
| Serialized human request | 8,192 bytes |
| Each logical path | 1–1,024 UTF-8 bytes |
| Reviewed source raw bytes | 0–65,536 bytes |
| Source content | strict UTF-8; NUL rejected |
| Complete serialized review | 262,144 bytes |
| Retained private preparation | 524,288 bytes |

The complete review uses deterministic ASCII-safe escaping. CR, LF, TAB,
quotes, slash where required, C0 controls, DEL, bidi/zero-width/format
characters, and non-ASCII scalars use fixed escapes. Spaces, including
trailing spaces, remain explicit. BOM, newline style, final-newline state,
tabs, controls, bidi, zero-width, and format-character facts are stated
separately. There is no normalization, newline conversion, BOM insertion or
removal, truncation, ellipsis, hidden collapsed region, digest-only review,
hex/base64 substitute, or partial preview.

The 65,536-byte raw bound does not guarantee that every eligible source fits
the serialized review bound: escaping can expand the representation. Prepare
must reject with no ticket when the complete escaped review exceeds 262,144
bytes. The retained 524,288-byte bound covers raw protected bytes, the complete
review, canonical input, raw index/fingerprint material, and bounded metadata;
the total retained representation is measured, and overflow also fails before
ticket issuance.

## Exact source eligibility

Prepare admits exactly one source that is:

- one existing ordinary regular file beneath the selected canonical repository;
- one safe repository-relative logical path with no alias ambiguity;
- cleanly tracked by current `HEAD`;
- represented by exactly one normal stage-0 index entry;
- whose index mode/object entry exactly agrees with the corresponding HEAD tree
  entry;
- whose worktree bytes exactly equal the HEAD blob;
- whose supported mode is exactly `100644` or `100755`, with worktree/index
  mode drift rejected;
- captured with a protected `FileIdentity` and link count exactly one;
- reached only through safe ordinary parent ancestry with no symlink, junction,
  mount-like redirection, Windows reparse point, or nested-repository alias;
- in a supported ordinary non-bare repository state;
- strict UTF-8, NUL-free, and no larger than 65,536 raw bytes; and
- representable in the complete review and retained-preparation bounds.

The source path must be rejected for missing, directory, special, symlink,
junction, reparse, hard-link-ambiguous, untracked, intent-to-add,
staged, conflicted, unmerged, sparse/skip-worktree-ambiguous, submodule or
gitlink state. It must also be rejected for a bare repository, linked
worktree, detached or unborn HEAD, alternate or malformed index, nested
repository, unsafe path alias, or active merge, rebase, cherry-pick, revert,
sequencer, or bisect state.

These are not all currently proven by the rename source. The index object
comparison, worktree/index mode agreement, active-operation rejection, and
other gaps are ordinary hardening prerequisites, not assumptions that the
future Desktop layer may silently supply.

## Exact destination eligibility

Destination admission is independent from source admission. The destination
must be:

- exactly one safe logical repository-relative path in the same selected
  canonical repository;
- distinct from the source under the supported path identity model;
- beneath an already existing ordinary parent;
- reached through a parent chain whose identities are captured and revalidated;
- free of a worktree file, directory, link, reparse point, special object, or
  alias-equivalent object;
- absent from the current HEAD tree;
- absent from every current index stage, including intent-to-add;
- not tracked-but-worktree-missing, untracked, or otherwise Git-visible;
- not ignored by the current Git exclude/ignore rules, even when no object is
  present; and
- on a supported same-volume/filesystem relationship with the source.

An ignored-but-absent destination is explicitly rejected by the reviewed route.
The reason is product-visible: the expected destination could become a hidden
ignored worktree result, making a human-reviewed structural move harder to
observe and audit. This is a reviewed-route narrowing, not an ordinary Tool
schema change.

The destination is rejected for missing parent, parent replacement, path
escape, repository metadata or nested repository targeting, directory or
special entry, source alias, Windows case-equivalent entry, trailing-dot/space
alias, Unicode normalization ambiguity, reparse/link substitution, overwrite,
replace, swap, or any other absence uncertainty. `Foo.rs -> foo.rs` is always
rejected on Windows. No temporary-name workaround is permitted.

## Same-directory and cross-directory scope

V1 supports exactly one regular-file operation in one selected repository:

- same-directory file rename; or
- same-repository cross-directory file move when the destination parent already
  exists and the supported same-volume/filesystem proof passes.

V1 excludes directory or recursive movement, cross-repository movement,
cross-volume fallback, parent creation, copy plus delete, overwrite/replace,
swap, multiple sources, wildcard/glob selection, and any temporary-name
sequence. It does not update imports or references, edit file content, or
perform repository-aware refactoring.

## Zero-effect Prepare

Prepare is strictly non-effectful:

```text
0 Tool executions
0 native rename attempts
0 source mutation
0 destination creation
0 index mutation
0 HEAD/ref/history mutation
0 Stage
0 Unstage
0 Commit
0 model or runtime Tool lifecycle
0 MCP execution
0 Process Plugin execution
0 temporary repository mutation artifact
0 durable authority persistence
```

Bounded host reads, hashing, Git observation, identity inspection, content
escaping, review construction, retained private preparation, and an opaque
ticket are allowed. Prepare must not call `Tool::execute`, a ToolRegistry, a
native rename, `git mv`, a shell/process move, or any recovery path. Prepare
failure issues no ticket and does not invalidate an existing reviewed Commit
authorization.

## Retained private preparation

The process-local in-memory preparation must retain enough protected state to
reconstruct and revalidate the unchanged ordinary Tool request without trusting
the frontend. It must include, at minimum:

- canonical selected repository/root/`.git` identities;
- canonical Git executable path and Git executable identity;
- source and destination logical paths;
- source native path and destination native path, private only;
- source `FileIdentity` and link count;
- source parent identity and destination parent identity, plus safe parent-chain
  identity evidence;
- exact protected source bytes, SHA-256, byte length, and mode;
- source HEAD/tree/blob entry and exact source index stage/object/mode state;
- destination worktree absence evidence, destination HEAD absence, every-index-
  stage absence, intent-to-add result, ignored/excluded result, and alias rules;
- same-volume/filesystem evidence;
- raw index fingerprint or collision-resistant equivalent;
- HEAD, attached branch, protected refs fingerprint, and supported Git-state
  markers;
- repository, runtime, profile, model, connection, registry, composition, and
  generation identities;
- exact ordinary `ToolDefinition`;
- explicit current permission membership and policy identity;
- canonical `ToolInput` and `ToolCall`;
- retained capability-specific preparer identity; and
- complete review identity and the complete review size accounting.

This state is bounded by 524,288 bytes, in memory only, and is never accepted
back from the frontend or placed in generic activity, logs, URLs, telemetry,
provider metadata, persistence, or a restart-resume path.

## Ticket and currentness contract

The ticket reuses ADR 0021 and ADR 0025 semantics. It is RAH-generated,
opaque, process-local, in-memory, capability-specific, single-use,
nonpersistent, nonresumable, and bound to the exact preparation/currentness
tuple. It expires at the exact boundary:

```text
elapsed < 300 seconds: valid
elapsed >= 300 seconds: expired
```

Confirm and Cancel receive only:

```json
{"ticketId":"..."}
```

`ticket_id != activity_id`. An activity ID cannot Confirm or Cancel. Wrong,
malformed, duplicate, expired, cancelled, or activity-ID tickets execute
nothing. There is no automatic reprepare or replacement ticket.

Before `Started`, stale or cancelled rejection has zero Tool executions and
zero native rename attempts, and preserves reviewed Commit authorization. Once
`Started` is reached, the reviewed Commit authorization has already been
invalidated even if dispatch, runtime, or result observation later becomes
uncertain.

Confirm must reject any drift in:

- source bytes/hash/length;
- source `FileIdentity`, link count, source parent, or parent chain;
- destination appearance, alias state, ignored state, or destination parent;
- destination HEAD/index/all-stage absence;
- source index stage/object/mode relationship;
- HEAD, attached branch, protected refs, or active Git-operation markers;
- repository root, `.git`, Git executable, or selected repository identity;
- same-volume/filesystem assumption;
- runtime, profile, model, connection, repository, registry, composition, or
  generation identity;
- exact ToolDefinition or explicit permission membership;
- retained preparer identity; or
- complete review identity/canonical ToolInput.

Hash and length equality alone are never sufficient currentness because a
same-byte replacement can have a different filesystem identity.

## Confirm ordering, D2, and Commit authorization

The exact production ordering is:

```text
consume ticket
 -> connected-current / generation / repository checks
 -> retained rename-preparer identity
 -> capability-specific source/destination revalidation
 -> exact current ToolDefinition
 -> exact permission membership
 -> D2 authorize_tool_dispatch
 -> invalidate repository-bound reviewed Commit authorization
 -> HostExplicit Started
 -> authorized_tool_dispatch
 -> current ToolRegistry
 -> existing repo.rename-file
 -> ADR 0018
 -> strict result classification and independent proof
 -> descriptive refresh
```

There is no post-Started D2. Desktop never directly invokes a Tool or native
rename outside the current registry path. A stale, cancelled, or D2-rejected
ticket fails before `Started`; it produces no Tool or native effect and does
not invalidate Commit authorization merely because the ticket was consumed.

Prepare, Cancel, and pre-Started failure do not invalidate a reviewed Commit
authorization. Immediately before `Started`, the backend invalidates all
repository-bound reviewed Commit authorization. This remains true for a later
success, known no effect, malformed output, dispatch failure, runtime failure,
or uncertain result. Refresh is descriptive only; it does not Stage, Unstage,
Commit, authorize a newer snapshot, issue a replacement ticket, or replay the
move.

## Native effect semantics and platform scope

ADR 0018's one-effect model is retained exactly:

```text
Windows:   MoveFileExW(source, destination, flags=0)
Linux:     renameat2(..., RENAME_NOREPLACE)
other Unix: fail closed; no supported no-replace primitive is implemented
```

The current source confirms these branches at
`repository_rename_file.rs:466-516`. The operation has exactly one native
no-replace rename/move attempt. It does not call `git mv`, a shell/process move,
generic filesystem rename authority, copy-plus-delete, a temporary name, a
second attempt, or rollback/compensation.

The route must not claim universal rename atomicity, universal durability, or
universal file-identity proof. Windows is the separately authorized live
certification platform. Deterministic Linux evidence does not establish Linux
live certification, and Windows live certification does not establish macOS
or other-Unix live parity. Other Unix currently fails closed rather than
claiming a supported native rename.

The ordinary and reviewed routes must establish same-volume/filesystem
compatibility before the effect where the platform identity model supports it:
on Linux, compatible device/mount evidence; on Windows, compatible volume
identity and the supported `MoveFileExW` semantics. If the relationship cannot
be established safely, Prepare/Confirm fails closed before the native attempt.

## Independent reviewed-route postcondition proof

The HostExplicit route must not trust Tool status alone. It performs the
capability-specific proof against the retained preparation under the
repository mutation lease.

### `renamed_verified`

The route accepts `renamed_verified` only when all of the following hold:

- the Tool produced exactly one JSON item with the current exact shape,
  `is_error == false`, `status == "renamed_verified"`, `uncertain == false`,
  and `path` exactly equal to the prepared logical destination;
- the source path's immediate observation is specifically `NotFound`, not
  `AccessDenied`, sharing failure, generic I/O failure, or an observer error;
- source parent and its protected safe ancestry remain the same identities;
- no same-name or case-equivalent source replacement is present;
- destination is present as one ordinary regular file, with no link/reparse or
  special-object substitution;
- destination parent and its protected safe ancestry remain the same
  identities;
- destination bytes exactly equal the protected source bytes and hash/length;
- destination `FileIdentity` corresponds to the protected source identity on
  supported Windows/Linux semantics, with link count still exactly one;
- no destination alias-equivalent replacement is present;
- raw index, HEAD, attached branch, protected refs, root, `.git`, and Git
  executable identities remain unchanged; and
- no contradictory or failed observation exists.

A generic source metadata error is not source absence. If any required proof is
missing, the route classifies the result as `uncertain`.

### `known_no_effect`

The route accepts `known_no_effect` only when all of the following hold:

- the Tool produced exactly one JSON item with the current exact shape,
  `is_error == true`, `status == "known_no_effect"`, and `uncertain == false`;
- source remains an ordinary regular file with the exact original
  `FileIdentity`, same link count, same source parent/ancestry, and no reparse
  or alias substitution;
- source bytes, SHA-256, and byte length remain exactly the prepared preimage;
- destination is specifically absent (`NotFound`) and has no alias-equivalent,
  case-equivalent, reparse, or special-object replacement;
- destination parent identity and source parent identity remain unchanged;
- protected raw index/fingerprint, HEAD/tree/blob, attached branch, protected
  refs, repository/root/`.git`/Git identities, and supported Git state remain
  unchanged; and
- no contradictory observation exists.

A same-byte replacement with a different identity is not known no effect. A
native error alone is not known no effect.

### `uncertain`

The route must use `uncertain` for any state that cannot safely prove one of the
two classes above, including observer/access/sharing/I/O failure, source
missing without attributable destination identity, destination appearing
without identity/provenance, source and destination both visible, both absent,
case-equivalent replacement, parent replacement, contradictory Git state,
reparse/link substitution, dispatch/runtime failure after `Started`, or a lost
result. No rollback, move-back compensation, retry, replay, or recovery journal
is allowed.

## Strict Tool-result classification

The accepted underlying output remains exactly one JSON content item with the
current ordinary shapes. The HostExplicit route adds independent proof:

| Underlying condition | Required independent check | HostActivity state | Generic result |
| --- | --- | --- | --- |
| `renamed_verified` with exact valid output | Independent verified-move proof passes | `tool_completed` | `{"status":"renamed_verified"}` |
| `renamed_verified` with exact output but proof fails | Any required postcondition is unproven or contradictory | `possible_effect_unknown` | `{"status":"uncertain"}` |
| `known_no_effect` with exact valid output | Independent identity-equal intact proof passes | `tool_error` | `{"status":"known_no_effect"}` |
| `known_no_effect` with exact output but proof fails | Original state is not identity-proven intact | `possible_effect_unknown` | `{"status":"uncertain"}` |
| `invalid_input` with exact current shape | No effect is represented by the ordinary Tool contract | `tool_error` | `{"status":"invalid_input"}` |
| `precondition_failed` with exact current shape | Pre-effect ordinary Tool refusal is structurally valid | `tool_error` | `{"status":"precondition_failed"}` |
| `uncertain` with exact current shape | Possible effect remains possible | `possible_effect_unknown` | `{"status":"uncertain"}` |
| malformed/contradictory ToolOutput | Never upgrade a malformed result | `possible_effect_unknown` | `{"status":"uncertain"}` |
| dispatch/runtime failure after `Started` | Post-start effect cannot be ruled out | `possible_effect_unknown` | `{"status":"uncertain"}` |

Unexpected fields, wrong types, wrong `is_error`, wrong `uncertain`, a path on a
status that does not emit one, or a path mismatch on `renamed_verified` is
malformed and becomes `uncertain`. Pre-Started lifecycle rejection remains a
HostExplicit rejection distinct from the five Tool statuses. Generic activity
and persistence remain status-only; raw ToolOutput is never forwarded.

## Git meaning after a verified move

The native worktree operation leaves the index, HEAD, branch, refs, and history
unchanged. Before a human stages the result, Git may display a deletion plus an
untracked destination. Git may later apply rename-detection heuristics, but the
reviewed contract does not promise a specific porcelain rename presentation.

There is no automatic Stage, Unstage, Commit, `git mv`, import rewrite, or
reference rewrite. Stage/Unstage and reviewed Commit remain separate ADR 0010
and ADR 0016 authorities.

## Privacy, frontend, and model/provider boundary

The direct Prepare response may contain only the intended human review data:
the opaque ticket ID, complete escaped source representation, logical paths,
source-derived hash/length/content facts, and sanitized review facts. Generic
Prepared, Started, terminal activity, persistence, telemetry, URLs, logs, and
conversation state must exclude actual values of the ticket, complete or
partial source, source sentinel, escaped source, SHA-256, byte length, raw Tool
input/output, native paths, FileIdentity, raw index, private parent/root/.git/
Git identities, complete review, and retained preparation.

The frontend may hold the direct review and ticket ephemerally for the active
interaction. It must not place them in transcript, `localStorage`,
`sessionStorage`, preferences, URLs, or ordinary logs. The frontend sends only
the typed two-path Prepare DTO and ticket-only Confirm/Cancel; it computes no
hashes, identities, Tool JSON, proof, permission, or authority.

The route is human/host initiated. It does not establish model-selected
HostExplicit rename, provider-selected rename, MCP HostExplicit rename,
Process Plugin HostExplicit rename, generic invoke-any-tool, or model-created
rename tickets. A connected runtime does not justify fake model lifecycle
events; the route emits no synthetic model ToolRequested/Started/Finished turn,
does not inject ToolOutput into model context, and does not auto-continue the
model.

## ADR 0018 implementation conformance prerequisites

This is the required hardening decision, not implementation work performed by
Task 291.

### Before ADR 0026 acceptance

Create a separately authorized ordinary-policy hardening task that:

1. proves destination absence from worktree, HEAD tree, every index stage,
   intent-to-add, tracked-but-worktree-missing state, aliases, and special
   objects;
2. compares the source stage-0 index object/mode with the HEAD tree object/mode
   and rejects staged, sparse, skip-worktree, intent-to-add, and conflict states;
3. rejects merge, rebase, cherry-pick, revert, sequencer, bisect, and other
   unsupported Git operation markers;
4. captures and compares source parent identity as well as destination parent
   identity and safe parent chains;
5. makes `known_no_effect` require exact source identity, link count, parent,
   bytes/hash/length, destination-specific absence, and protected Git state;
6. distinguishes specifically confirmed `NotFound` from access, sharing,
   observer, and generic I/O errors for source absence;
7. requires destination identity correspondence with the prepared source on
   supported Windows/Linux identity models;
8. proves supported same-volume/filesystem compatibility before the native
   attempt and rejects unsupported relationships before effect;
9. hardens post-effect alias/case/reparse/link/replacement observation; and
10. records the exact fail-closed behavior for unsupported non-Linux Unix
    without claiming a supported native primitive.

This task must preserve the existing Tool name, four-field schema, five status
names, one-attempt effect model, and authority boundary. It is compliance
hardening, not an ADR 0018 authority expansion. It must be deterministic and
must not run live/destructive certification as part of the hardening task.

### Before shared HostExplicit preparation

The ordinary hardening task must pass focused deterministic evidence and an
independent review must confirm that the ordinary Tool no longer makes the
conformance gaps above. Only then may a shared rename preparer bind the
unchanged Tool input and reuse the ordinary policy. The preparer still needs
the stronger reviewed-only ignored-destination rule, complete source review,
and independent postcondition proof described here.

### Before Desktop backend integration and live certification

After ADR 0026 is accepted, the shared preparer and Desktop backend must add
the typed DTO, complete review, private preparation, ticket/currentness,
Confirm ordering, D2, Commit invalidation, strict result parser, and
independent proof. Deterministic fault, privacy, alias/case, destination race,
same-volume, postcondition, no-replay, and generation tests must pass before a
fresh separately authorized Windows live gate. Task 291 performs none of these
changes or tests.

## Proposed ADR 0026 decision package

Provisional title:

```text
ADR 0026 — HostExplicit Reviewed Repository File Rename/Move Boundary
```

ADR 0026 should accept or reject, as one coherent package, the following:

- **Human DTO:** closed `{source_path, destination_path}` only; canonical
  serialized request at most 8192 bytes; host-derived ordinary ToolInput.
- **Review bounds/representation:** strict UTF-8, NUL-free source at most
  65,536 raw bytes; complete deterministic escaped source; complete serialized
  review at most 262,144 bytes; retained private preparation at most 524,288
  bytes; no preview, truncation, ellipsis, or digest-only authorization.
- **Source eligibility:** one clean HEAD-tracked regular file, exact stage-0
  index/HEAD relationship, supported mode, identity/link count, safe ancestry,
  supported Git state, and review-content bounds.
- **Destination eligibility:** one absent safe logical path with existing safe
  parent; absent from worktree/HEAD/all index stages/intent-to-add; not ignored
  for this reviewed route; same repository; supported same-volume proof; no
  overwrite, alias, reparse, or case-only Windows rename.
- **Scope:** same-directory rename and same-repository cross-directory move of
  one regular file only; no directory/recursive movement or parent creation.
- **Prepare:** strictly zero Tool/native/filesystem/index/HEAD/ref/Stage/
  Unstage/Commit/model/MCP/Process Plugin effects and no Commit invalidation.
- **Private state:** all required canonical identities, source/destination
  identities and parents, bytes/hash/length, Git/index/HEAD/ref state,
  same-volume evidence, exact Tool definition/permission/registry/generations,
  preparer identity, review identity, and canonical ToolInput remain in-memory
  only.
- **Ticket:** RAH-generated, opaque, process-local, in-memory, capability-
  specific, single-use, nonpersistent, nonresumable, currentness-bound,
  expires at `elapsed >= 300` seconds, and is distinct from activity ID.
- **Confirm:** consume ticket, perform currentness and capability-specific
  revalidation, check exact ToolDefinition and permission, D2, invalidate
  reviewed Commit authorization, emit Started, then dispatch once through
  `authorized_tool_dispatch` and the current ToolRegistry to `repo.rename-file`.
- **D2 boundary:** D2 is before Started and before any effect; there is no
  post-Started D2 and no Desktop direct rename.
- **Commit interaction:** Prepare/cancel/pre-Started stale rejection preserves
  Commit authorization; reaching Started invalidates it before dispatch,
  including eventual uncertain outcomes.
- **Native effect:** exactly one Windows `MoveFileExW(flags=0)` or Linux
  `renameat2(RENAME_NOREPLACE)` attempt; other Unix fails closed; no fallback,
  retry, replay, rollback, or compensation.
- **Five statuses:** preserve exactly `renamed_verified`, `known_no_effect`,
  `invalid_input`, `precondition_failed`, and `uncertain`, with current exact
  ordinary Tool JSON shapes and strict route-side validation.
- **Independent proof:** status alone never establishes success or no effect;
  verified move requires specific source `NotFound`, unchanged parents/Git
  state, exact destination preimage, supported source-to-destination identity,
  link/reparse/alias safety, and no contradiction; known no effect requires
  identity-equal intact source and specific destination absence.
- **Privacy:** only direct Prepare may contain the complete review/ticket and
  source-derived facts; generic activity and persistence are status-only and
  contain no source/private/identity/Tool values.
- **Frontend:** presentation and typed input only; ephemeral direct review is
  not authority and no sensitive review/ticket persistence is allowed.
- **Model/provider exclusions:** no model-selected, provider-selected, MCP, or
  Process Plugin HostExplicit rename and no generic invoke-any-tool route.
- **Platform/nonclaims:** no universal atomicity/durability/identity claim,
  no Linux/macOS live parity from Windows evidence, and no race-free TOCTOU,
  OS sandbox, or network-isolation claim.

ADR 0026 must not redefine ADR 0018's underlying effect authority. Acceptance
must not itself change the HostExplicit allowlist.
