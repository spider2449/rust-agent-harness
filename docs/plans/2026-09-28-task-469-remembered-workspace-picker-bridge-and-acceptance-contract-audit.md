## Exact picker path and error

In `frontend/index.html`, the Remembered Workspaces `#remembered-catalog` action leads through `installRememberedWorkspaceHandlers` in `frontend/status.js`: `edit-location` calls `openRememberedEditor`; its Choose Location click calls `pickRememberedLocation(dialog)`. `initializeDesktop` obtains `dialog` from `window.__TAURI__` and passes it to the handler. `pickRememberedLocation` requires `typeof dialog?.open === "function"`, then awaits `dialog.open({ directory: true, multiple: false, title: "Choose remembered workspace location" })`. A string result is returned to the click handler. This is the Tauri dialog plugin's `open` command, not the Rust `choose_repository` command. Its native implementation belongs to `tauri-plugin-dialog`; `main.rs` installs the plugin with `.plugin(tauri_plugin_dialog::init())`. It is not listed in the application's `generate_handler!` because plugin commands are registered by the plugin.

The exact displayed text comes from `errorMessage` in `frontend/status.js`: any error value not in its message map falls back to `Desktop frontend unavailable`. The editor click catches the picker rejection and passes it to `showRememberedError`. By contrast, absence of `dialog.open` throws `remembered_catalog_request_invalid`, which has its own mapped message (`That remembered workspace request is invalid.`). Thus Task 468's message came **after attempting** `dialog.open`, assuming the observed editor source and binary were equivalent as Task 467 established. It does not identify the underlying rejection. The frontend's boot availability predicate is separate: `waitForTauriApi` polls up to 20 times at 100 ms for `window.__TAURI__?.core?.invoke` and `window.__TAURI__?.event?.listen`. It does not check the dialog plugin. The Tauri configuration sets `withGlobalTauri: true`; Tauri installs the global in its WebView before frontend initialization. `Desktop UI ready` after `loadStatus` establishes the core bridge was present, not that dialog invocation was authorized.

## Existing post-selection contract

After a successful selection, `openRememberedEditor` puts the path in its local `selectedLocation`, sets `locationChanged`, checks `Save a location hint`, enables Clear Location, and shows `New location selected — save to remember it`. It does not display the raw path in the editor. Save sends `locationHint: selectedLocation` to `update_remembered_workspace_candidate` (or `remember_workspace_candidate` for a new entry). Before Save the path exists only in local editor state; Cancel discards it. After Save and catalog refresh, the entry shows `Location saved — hidden`. The catalog's `Show Location` action invokes `reveal_remembered_workspace_location`; the returned `location` is rendered in `.remembered-location`, and `Hide Location` hides it again. Reopen the editor shows `Saved location — hidden`. Thus an exact selected path is inspectable through the existing catalog action after persistence.

Task 458 described the entry editor extending beyond its content area and clipping the **left side of Choose Location**; Task 459 repeated that precise observation. It did not establish clipping of the selection status, Reveal/Show Location, or sibling controls. The corrected live gate should select the intended long path through the Remembered Workspaces editor, observe the selection status and Choose Location within the dialog without left-edge clipping at normal and narrow widths, Save, reopen to confirm the saved-location state, and use catalog Show Location to compare the revealed exact path with the intended fixture. This verifies selection and persistence without inventing a path-valued editor control. Keep the separate repository chooser smoke gate separate.

**UI classification: U1 — EXACT PATH ALREADY INSPECTABLE**, after Save through Show Location. Direct path display inside the editor is not part of the existing contract.
