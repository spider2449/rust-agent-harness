## 4. Architecture reconstruction

The current implementation matches ADR 0027:

~~~
explicit human admission
  -> WorkspaceMembershipState
  -> inert private member record
  -> opaque process-local selector
  -> fresh DesktopRepository for the selected member
  -> fresh active-only ToolRegistry/composition
  -> existing repository-bound Tools, policies, tickets, index, and Commit
~~~

WorkspaceMembershipState is descriptive and organizational. It is not a
filesystem authority, Git authority, ToolRegistry, provider, or model authority.
Only the current DesktopRepository supplies executable repository context.
There is one active member or zero active during setup/transition; there is no
parallel active composition and no union registry.

## 5. Membership and admission audit

WorkspaceMembershipState, RepositoryMemberId, InertRepositoryMember, and
RepositoryAdmissionIdentity are present in the expected host-private layers.
An inert member retains only its opaque ID, admission generation, private root,
private display-path evidence, and private admission identity. It contains no
DesktopRepository, ToolRegistry, provider, runtime, workflow, Commit
control/capability, HostExplicit ticket, or index reservation.

Admission is initiated by the host's folder picker. The model, provider,
repository contents, automatic discovery, and frontend authority metadata do
not admit a repository. Fresh admission captures and revalidates canonical
root, filesystem identity, supported .git form and identity, Git executable
identity, ordinary worktree classification, and ambiguous ancestry/reparse
protections. Path spelling is not identity.

Same/alias-equivalent membership is rejected as RepositoryAlreadyMember.
Nested co-membership is rejected as RepositoryNestedMembershipConflict.
There is no silent focus change, automatic discovery, or model/provider
selection route. A fresh WorkspaceMembershipState starts empty after restart.

## 6. Nested-boundary audit

RepositoryNestedBoundaryPolicy remains separate from Git-agnostic
WorkspacePolicy. Existing-target and creation-parent validation reject any
target ancestry that crosses a descendant repository marker. Whole-repository
observation rejects a nested marker before Git observation can cross it.

The current policy is wired through the applicable repository-bound read,
mutation, Stage/Unstage, Commit snapshot, and HostExplicit preparation paths,
including fs.read, repo.file-info, repo.status, repo.diff, repo.diff-staged,
repo.patch, repo.edit-files, repo.create-file, repo.delete-file,
repo.rename-file, repository directory creation, Stage, Unstage, and Commit
target/snapshot validation. The real nested repository integration test rejects
A's observation of B before observation.

Windows compares the marker name ASCII case-insensitively, so .git, .GIT,
.Git, and equivalent spellings are treated as the same nested marker. Unix
keeps exact .git semantics. This is deterministic platform behavior; no
live case-sensitive NTFS certification is claimed. Nested membership rejection
does not replace path-level nested .git isolation.

## 7. Activation transaction audit

Activation captures the target member, admission generation, identity, current
active member, and repository generation; revalidates identity before
construction and again at the final gate; constructs a fresh repository; then
acquires membership and lifecycle coordination for the final synchronous
commit. The final fallible target check occurs before Commit revocation and
destructive invalidation.

After the commit point, only infallible publication occurs: prepared
HostExplicit state is cleared, old Commit capability and workflow are cleared,
the new repository/member/generation are published, persistence namespace is
selected, and a fresh conversation is started. No normal fallible validation
occurs after invalidation begins.

Failed or stale activation preserves the current active repository, workflow,
Commit authorization, HostPrepared state, conversation, persistence namespace,
and generation. Concurrent B/C activation from A has one winner; a loser
cannot clear or reset the winner. Successful real switching increments the
repository generation once. Already-active activation is a no-op with no
reconstruction, generation churn, revocation, workflow reset, conversation
reset, or provider activation.

## 8. Lifecycle and currentness audit

The effective lifecycle participants are coordinated by the host-owned
lifecycle_coordination mutex, with membership admission/activation additionally
serialized by membership_coordination. The audited writers include activation,
Connect publication, Disconnect, model configuration/reset, Commit identity,
reviewed Commit authorization, and Stage/Unstage reservation begin/finalization.
No blocking standard mutex guard is held across an async .await.

Connect captures and final publication compare repository, model, Trusted
Profile, connection, and Commit identity generations. Stale identity or model
state cannot publish the old composition, provider owner, or Commit capability.
Identity/profile changes make an existing connected composition stale or
reconnect-required according to the current design.

Disconnect first withdraws current runtime/Commit/provider state under lifecycle
coordination, performs async cleanup after releasing blocking guards, and then
publishes NotConnected or a bounded error. It does not migrate a connected
runtime between repositories.

## 9. Commit audit

The reviewed Commit path is still human review bound and remains outside
HostExplicit. Desktop production uses the two-phase flow: capture current
repository/model/identity/workflow and exact control, synchronously supersede
old pending authorization, asynchronously prepare a private candidate, then
reacquire lifecycle coordination, recheck currentness/control/review identity,
and install once into the shared pending slot.

Prepared authorization is private, opaque, non-serializable, bound to its
originating RepositoryCommitControl, one-shot, and non-installable into
another control. Busy installation publishes no partial workflow state and no
candidate queue exists. Production call-site search found no bypass of this
two-phase Desktop flow; the only direct authorize_reviewed_snapshot call is
test-only.

Switching, model changes, identity changes, Disconnect, and index reservations
invalidate or block stale Commit authorization. A stale A candidate cannot
re-arm after B wins. Inactive members hold no Commit control or capability.

## 10. Stage/Unstage and index reservation audit

Stage and Unstage remain separate host index authority. Action selectors are
observation- and repository-generation-bound. begin_repository_index_effect
acquires lifecycle coordination before consuming the action and installing one
opaque process-local reservation containing token, repository generation,
active-member binding, action kind, and the exact repository Arc.

The reservation is installed before the async native effect. It blocks or
safely orders activation, Disconnect, model changes/reset, Commit identity,
reviewed authorization, and Connect admission/final publication. No lifecycle
guard crosses Tool execution or refresh awaits. Completion retains the
reservation through terminal effect classification and captured-repository
refresh, and only the matching token can clear it. A stale completion cannot
clear a newer reservation.

Known failure and uncertain effect remain distinct. There is one attempt, no
automatic retry/replay, and no rollback claim. Refresh remains explicitly bound
to the captured repository and generation, so A cannot publish its workflow
into B.

## 11. Connect/Disconnect audit

begin_connect checks lifecycle state and an active index reservation before
entering Connecting. publish_connected_provider_state repeats the index
reservation check under the same lifecycle exclusion before publishing
provider ownership, Connected state, composition, permissions, or Commit
capability.

Task 321-I now exercises the real reservation-start path and the real final
publication function. The three focused tests prove Stage admission rejection,
Unstage admission rejection, and real Stage reservation rejection at real
Connected publication. They also prove matching five-generation pending state,
no Commit/provider/composition publication, returned runtime ownership,
reservation preservation, real completion, and fresh Connect admission.

Stale A publication is shut down and mapped to bounded RepositoryBusy or
reconnect-required errors. No stale runtime or provider owner remains stored.
The pending Commit candidate is dropped rather than installed. There is no
connected runtime migration between repositories.

## 12. Provider and model isolation

Trusted Profile remains global, host-owned composition intent. Inactive members
do not activate, clone, or retain providers. Provider metadata cannot admit or
select repositories and cannot grant repository authority. Failed/stale
publication returns pending runtime/provider ownership through the existing
cleanup path.

Model configuration and reset are lifecycle writers. Generation changes prevent
old Connect or Commit candidates from publishing. Model output and conversation
text contain no repository selector, repository ID, workspace selector, or
switching path. There is no provider-selected or model-selected repository.

## 13. ToolRegistry and Effective Authority audit

All Desktop registry construction is for the current active repository only.
Connect constructs a fresh first-party registry and merges only the current
provider composition. There is no union registry, inactive registry, or
per-member executable cache. A→B→A rebuilds current authority rather than
reviving an old executable object.

Effective Authority describes only the current active composition. Inactive
membership contributes no permission union. Public snapshots and errors do not
expose registry internals, native paths, filesystem IDs, provider credentials,
tickets, or reservation tokens.

## 15. Conversation, persistence, and removal audit

Successful switching selects the new repository namespace and starts a fresh
in-memory conversation. Transcript persistence is descriptive session data,
not repository authority; a stored transcript does not restore a member,
active repository, runtime, registry, Commit authority, HostExplicit ticket, or
index reservation. A fresh process has zero executable multi-repository
membership authority.

The source persists no membership, active member, member ID, admission
identity/generation, repository generation, ToolRegistry, Commit authorization,
HostExplicit ticket, index reservation, pending Connect publication, or provider
ownership. Existing model preferences and transcript persistence remain
separate boundaries.

There is no user-facing member-removal IPC or UI. The private remove helper is
used only for admission rollback after a newly admitted member fails activation
and by test fixtures; it is not a product removal surface. Persistence and
removal are explicitly deferred by Task 322 and are not milestone blockers.

## 16. Privacy and error contract

Membership presentation exposes only bounded opaque selector, safe basename,
active state, availability, and membership generation. It does not expose
canonical root, filesystem identity, .git identity, Git executable identity,
admission generation, registry internals, credentials, tickets, or reservation
tokens.

Malformed, unknown, stale, duplicate, nested, and busy selectors map to closed
FrontendError classifications. Repository and lifecycle failures are
bounded; raw Git stderr and native paths are not returned. Activity remains
status-only and does not carry review source content, tickets, or authority
objects.

## 17. Windows-specific audit

Admission canonicalizes the repository root and validates reparse/symlink
ancestry, .git form, filesystem identity, and Git executable identity. Alias
and case-equivalent duplicate handling is identity-based rather than spelling
based. Native paths remain private.

The nested policy treats Windows .GIT markers ASCII case-insensitively and
Unix markers exactly. Deterministic tests cover the platform contract. This
audit does not claim race-free filesystem identity, live case-sensitive NTFS
behavior, or Linux/macOS live parity.

## 20. Uncertainty and no-replay audit

Project-wide mutation semantics remain one attempt with conservative result
classification. Timeout, cancellation, disconnect, crash, or lost response
does not imply rollback. Uncertain external effects are not automatically
replayed. Stage, Unstage, Commit, and HostExplicit mutation paths do not add
retry or compensation. Switching does not attempt rollback of an external Git
or filesystem effect.

No milestone code claims transactional Git/filesystem rollback, network
isolation, or recovery from an uncertain native effect.

## 21. Public contract, frontend, and Tauri audit

The intended public additions are limited to Desktop membership presentation
and activation IPC. The presentation uses bounded member lists, opaque
selectors, active indication, and an explicit Activate action. The backend
performs all admission, identity, currentness, and authority decisions. The UI
has no removal control, no absolute native path, no optimistic authority
switch, and no persisted-membership claim.

No unexpected Tool name/schema, PermissionLevel variant, provider protocol
field, Trusted Profile schema field, mutation status, or generic authority API
was added. repo.commit remains governed by its existing Commit policy and is
not HostExplicit.

The default Tauri capability enables only the narrow named Desktop commands,
including membership listing and activation. No wildcard filesystem capability,
generic invoke scope, or generic command capability was introduced.
