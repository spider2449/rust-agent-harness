## 3. Task 427 no-feature result

Task 427 closed live Trusted Profile recomposition with:

> NO FEATURE — DISCONNECT / CONNECT REMAINS THE CLOSED TRUSTED PROFILE RECOMPOSITION BOUNDARY

Connect rereads the host-selected profile and creates a fresh provider
composition, registry, runtime, and Codex thread. Disconnect shuts down the
runtime and its provider activation. For unchanged repository/model context,
Desktop retains the host conversation and can replay it into a new thread.
Live replacement would add overlapping provider ownership, late-call and
currentness races, and thread-snapshot problems. No evidence showed that users
hit these problems often enough to justify that complexity. Task 429 does not
reopen or route this candidate to implementation.

## 4. Task 428 no-feature result

Task 428 closed a reviewed HostExplicit route for `repo.create-directory`:

> NO FEATURE — ORDINARY `repo.create-directory` REMAINS SUFFICIENT

The existing ordinary Tool is bounded and Windows-live-certified. A person can
also create a directory in an OS/editor. A HostExplicit route is technically
possible but would add a twelfth host-invocable effect, a capability-specific
review contract, and Windows certification. No material workflow need was
established. Task 429 does not reopen or route this candidate to implementation.

## 5. Current released product workflow

The source-supported repository loop remains:

```text
host admits/selects one active repository
  -> repo.list: bounded direct-child browse of tracked structure
  -> repo.search: bounded literal path/text search over tracked, present files
  -> fs.read / repo.file-info and repository status/diff inspection
  -> existing authoring Tools
  -> Stage / Unstage and reviewed Commit
```

`repo.list` and `repo.search` use the host-selected repository observer. Their
inventory is tracked-only, their results are bounded, and neither is
HostExplicit. Authoring, Stage/Unstage, and reviewed Commit remain separate
operations. Empty-directory creation remains an ordinary Tool operation with
no marker, index, ref, or history effect.

The provider lifecycle remains explicit: host selects a provider-only Trusted
Profile while disconnected; Connect reloads and activates its configured
providers; the active registry is composed for a fresh runtime/thread;
Disconnect withdraws the runtime and shuts down its provider activation.
Effective Authority reports configured provider/capability counts, effective
Tools, unavailable capabilities, and connection/currentness state. The
presentation does not provide per-child process health. Model settings,
remembered workspace descriptions, conversation transcript/new/resume controls,
and effective authority inspection already have host-owned Desktop workflows.
No source/workflow record reviewed here establishes a new blocker in those
areas.

## 8. User-blocker evidence

The evidence bar is not met for a product milestone:

* Provider recovery does not require application restart in the observed
  lifecycle: an idle user can Disconnect and Connect again. This shuts down the
  current runtime/provider owner, rereads the profile, and creates a fresh
  runtime/thread. Repository/model settings and host conversation remain when
  their context is unchanged. No evidence shows this recovery is frequent,
  loses work, or costs more than a possible convenience step.
* Configured provider counts, expected capability counts, effective Tools,
  unavailable capabilities, and generic connection/currentness are already in
  the authority/status presentation. Per-child process liveness is not exposed,
  but no user decision requiring it was evidenced.
* Literal search and tracked structure browsing have just been established as
  bounded discovery operations. No observed case demonstrates common files are
  missed or forces unsafe/manual repeated work.
* Untracked discovery, worktree mutation, remote MCP, and union registries
  would increase authority substantially without a demonstrated blocker.

These are findings about the available evidence. They do not assert that future
users cannot report a blocker.

## 11. Product versus maintenance distinction

No product candidate clears the demonstrated-blocker bar. Maintenance work can
still be more important than starting a speculative v0.33 feature. The
Codex-baseline compatibility task is a real evidence gap but is not urgent for
the currently released product: exact `codex-cli 0.149.0` is now locally
available and its manifest/binary verifies; the adapter remains pinned and the
release preserves the inference nonclaim. Recertification must not silently
change the pin or pretend nondeterministic model selection is deterministic.

The Tauri permission-generation discrepancy has a concrete, still-open
authorization-surface inventory mismatch affecting three registered
HostExplicit prepare handlers. It deserves a bounded audit before additional
product work because the audit can establish whether current command callers
and generated permissions/capabilities agree. Existing evidence says Task 408
found it outside the `repo.list` path; that does not establish exploitability,
frontend reachability, or release blockage. Task 429 does not fix or widen it.

## 12. Maintenance-priority assessment

Recommend exactly one next task:

> **Task 430 — Tauri Command Permission-Generation Discrepancy Audit**

The bounded audit should reconcile the 47 registered invoke handlers against
the 44 generated permission/capability entries, starting with the known missing
names `host_prepare_repo_edit_files`, `host_prepare_repo_create_file`, and
`host_prepare_repo_delete_file`. It should inspect the actual Tauri build-time
generation, default capability, frontend invoke callers, and relevant tests;
classify each mismatch as intentionally unreachable, missing by defect, or
stale generated inventory; then recommend the smallest separately authorized
correction. It must preserve the exact HostExplicit set and distinguish
Tauri IPC permission from RAH Tool/HostExplicit authorization. It must not
assume the result is a security vulnerability, add permissions preemptively,
or change product authority in the audit phase.

This priority is based on a concrete mismatch at an existing command boundary,
not on a belief that every mismatch is exploitable. If the audit proves the
inventory difference intentional and no runtime effect exists, close it with
evidence and reassess maintenance priorities afterward.

## 13. HostExplicit implications

HostExplicit remains exactly 11. `repo.create-directory` is still ineligible;
neither search candidate becomes HostExplicit. Provider restart/status are
host control-plane concerns and must not become model-selectable Tools by
convenience. The three Tauri permission-generation names concern IPC command
reachability for existing HostExplicit preparation handlers; resolving that
inventory does not itself add or remove a HostExplicit kind. No permission is
changed in Task 429.

## 14. Provider/profile implications

Disconnect/Connect remains the closed profile recomposition boundary. The
ordinary reconnect path replaces the whole runtime/provider activation and
creates a fresh Codex thread; it preserves the host transcript and unchanged
repository/model context, but does not preserve the old Codex thread. There is
no evidence that one extra explicit lifecycle action or that lack of per-child
health is a material blocker. A future provider restart would need to prove
per-provider ownership and fresh-thread semantics rather than reuse the word
“restart” to imply in-place thread recovery.

Configured/effective counts and unavailable capability states are host-derived
and already sanitized for presentation. Any future diagnostics must continue
to exclude raw stderr, executable paths, environment values, credentials, and
private provider metadata.

## 15. Repository/Git implications

Keep the tracked-only, selected-active-worktree browse/search boundary. Do not
add untracked/ignored inventory, fuzzy/regex modes, or new search result
disclosure on the basis of framework comparisons or presumed convenience.
Keep Stage/Unstage, reviewed Commit, filesystem mutation, and shared worktree
metadata effects separate. No current evidence justifies worktree lifecycle
commands or changes to zero-or-one active repository composition.

## 16. Network implications

Keep MCP local stdio and Process Plugin boundaries as currently configured.
Do not add Streamable HTTP, endpoint selection, OAuth, proxy, or network
authority as a reaction to the rejection of narrower candidates. No current
workflow evidence offsets the new endpoint, credential, SSRF, remote-effect,
reconnect, and replay/cancellation contract required.

## 17. Deterministic testability

The narrower search/status candidates are technically testable: bounded regex
engine semantics, fuzzy scoring/ties, sanitized status derivation, and
provider lifecycle fault points can be deterministic. Deterministic
testability does not establish user value. Provider restart races need barriers
and fake actors; process effects need separate platform evidence. Worktree,
network, and union-registry tests cannot replace live proof of OS/Git/network
identity and routing behavior. No test suite is run for this research task.

For Task 430, the primary evidence should be a source-to-generated-inventory
matrix and actual command reachability/capability-path analysis. Any proposed
permission change should receive focused deterministic frontend/build
verification in its own authorized task.

## 18. Windows certification cost

No new product live certification is warranted. A status-only view has no
process effect; actual provider restart would require Windows child identity,
single-owner, shutdown/reaping, and production Desktop-route evidence, with
separate Linux/macOS evidence for those claims. Regex/fuzzy search can reuse
the observer boundary but still require a Windows production gate if shipped.
Untracked discovery and worktree lifecycle require substantial Windows path,
ignore, reparse, locking, and shared-metadata evidence. Network MCP requires
endpoint/TLS/proxy/DNS certification and cross-platform review. Union registries
would need end-to-end routing assurance across active workspaces.

Task 430 is an audit, not a live certification task. It should not launch the
app or mutate permissions merely to explore a hypothetical repair.

## 19. Architecture disruption

Provider restart is the least disruptive remaining product candidate, but it
still modifies provider lifecycle/currentness and requires a fresh runtime
thread or a separately proven bridge reset. Regex/fuzzy search fit an existing
read-only Tool seam but add semantics without proven leverage. Provider status
is mostly already present. Untracked discovery changes disclosure policy;
worktree commands mutate shared repository state; network MCP adds a new
transport trust boundary; union registries conflict with ADR 0027. None is a
sound primary milestone on current evidence.

The selected maintenance audit is bounded to current Tauri generation and
command reachability. Its result may recommend a separate correction, but it
does not authorize one.

## 20. Final outcome B

**NO v0.33 PRODUCT CAPABILITY SELECTED — PERFORM MAINTENANCE BEFORE REASSESSMENT.**

No remaining product capability has both demonstrated user value and a
sufficiently closed authority contract. The maintenance audit of Tauri
permission-generation coverage should precede any renewed feature selection.
The decision does not mean a broader candidate wins because the narrow ones
were rejected; authority cost and product evidence were evaluated separately.
