## Authority audit

No new authority class was introduced. `PermissionLevel` remains the existing
closed enum. The audit found no new generic filesystem, generic process/shell,
provider-granted, model-selected profile, frontend, or automatic effective
authority path.

The relevant boundaries remain:

- Trusted Profile selection and preference persistence are host-owned intent.
- `ToolRegistry` remains the external capability boundary.
- Profile/provider metadata is translated at the adapter edge and cannot grant
  or escalate RAH permission.
- Frontend buttons invoke host commands and render sanitized DTOs; they do not
  compose or grant authority.
- The model receives no profile path or profile-control Tool.
- Connect composes a fresh registry only after host-side source validation and
  provider admission.

ADR 0011 remains sufficient. Persistence lifecycle state does not need an ADR;
no ADR is created by Task 218.

## Preference security audit

`desktop-preferences.json` v3 is a closed, bounded preference document. The
audit confirmed:

- the remembered path is non-authoritative data, not a profile or authority
  cache;
- v1 and v2 compatibility remains intact, while the Trusted Profile field is
  accepted only in v3;
- unknown fields and duplicate fields fail closed;
- total preference size and remembered path length are bounded;
- startup performs lexical/syntactic path checks only;
- startup does not read the Trusted Profile source, canonicalize it, validate
  its contents, or spawn a provider;
- source contents and effective metadata are never cached as authority;
- the existing atomic writer is reused;
- model, identity, and profile preference fields preserve one another;
- failed writes preserve both prior disk state and prior in-memory state;
- Forget removes only `trusted_profile`, preserving unrelated model and
  identity fields.

The writer is canonical and ordered, and cleanup only removes owned temporary
preference files. No persistence path can become an authority restoration path
without an explicit fresh Restore/Connect action.

## Restore / Forget / Clear semantics

The four host actions remain independent:

| Action | Required behavior | Audited result |
| --- | --- | --- |
| Choose | Static validation, persist selected source, publish selected intent, increment profile generation once, spawn zero providers | PASS; no spawn in deterministic/live evidence |
| Restore | Read remembered path, fresh static validation, publish selected intent, increment generation once, spawn zero providers, do not rewrite on success | PASS; invalid Restore preserves prior selection/preference |
| Forget | Remove preference only; generation, selected intent, runtime, and active provider composition unchanged; allowed while connected and idle | PASS; live connected Forget preserved `connected_current` and both providers |
| Clear Selection | Process-local selection only; remembered preference retained; disconnected-only; generation changes only when an actual selection existed | PASS; deterministic exact-generation test |

No cross-effect was found: Restore does not Connect, Forget does not stop
providers, and Clear Selection does not delete the remembered path.

## Activation-boundary audit

`DesktopProviderActivation::activate` fresh-loads the exact selected source
through `load_for_activation`, reapplies the provider-only rule, derives
permissions and external descriptors from that current profile, and then calls
the shared composer. It does not trust Restore-time effective metadata.

Deterministic tests prove that a valid profile changed between selection and
activation is admitted using current bytes, and that invalid or missing changed
profiles fail before provider publication. A post-Connect source edit does not
hot reload the active composition; a later activation loads the new source.

The source boundary continues to reject, where the current contract requires:
relative and lexical alias paths, UNC paths, device/verbatim paths, ADS forms,
non-regular files, symlinks, junctions, and Windows reparse topology. Profile
persistence stores no canonicalized or source-derived authority identity.

## Generation/currentness audit

The four-generation tuple is:

```text
[repository_generation, model_generation,
 profile_generation, connection_generation]
```

It participates in:

- pending connected-publication acceptance and stale cleanup;
- connected state and Effective Authority Currentness;
- pre-chat dispatch and the running chat path;
- reconnect/resume admission;
- repository/workflow currentness where connection-bound authority is needed.

The profile generation is retained in `ConnectionState::Connected`, checked in
the Effective Authority snapshot, and compared in stale publication and chat
dispatch. A profile mismatch therefore cannot remain Current. No security-
relevant path was found that uses only repository/model generations where the
profile generation is required.

The general application status helpers intentionally expose model and
repository status separately; their profile status is independently derived
from the connected profile generation and provider owner. This is presentation
decomposition, not an authority bypass.

## Provider lifecycle audit

There is one Desktop activation owner per connection. `DesktopProviderActivation`
owns every admitted MCP and Process Plugin provider until explicit disconnect,
hard recovery, failed publication, or application shutdown.

The implementation and tests cover:

- stale publication cleanup of both runtime and provider activation;
- final registry merge failure cleanup;
- runtime construction failure cleanup;
- duplicate owner rejection;
- normal disconnect and application-exit cleanup;
- provider shutdown without replay, automatic restart, or forced global process
  termination.

Task 217 live evidence observed, for both MCP and Process Plugin:

```text
spawn -> shutdown -> exit
```

The successful connected phase had one `spawn` per provider, and normal
Disconnect produced the shutdown/exit sequence. Executable rename after
shutdown succeeded, confirming unlock. The implementation matches the claim.

## Effective Authority audit

Effective external metadata is derived at Connect-time from the freshly loaded
profile and admitted provider composition. Configured metadata may remain in
the inert Restore snapshot, but it cannot override effective Tool names,
permission, provider type, or registry admission.

The final composition checks descriptor/name/permission/provider classification
matches and rejects unmatched or unclassified Tools. External Tools remain
`repositoryBound=false`. That flag is a classification value, not proof that a
provider has no ambient repository or host effect.

The resumed live run showed `Current`, the connected runtime, and sanitized MCP
and Process Plugin entries with the expected permissions. No stale configured
metadata was used as effective metadata.

## Privacy/redaction audit

The raw Trusted Profile path is confined to private desktop preferences and
host-only Rust state. It is absent from `TrustedProfilePresentation`,
`EffectiveAuthoritySnapshot`, Tool definitions, Codex prompts, conversation
persistence, activity UI, normal live/public evidence, provider metadata, and
dynamic Tool identity.

Profile errors are collapsed to bounded frontend errors and do not include the
path. Provider descriptors use sanitized provider labels and public RAH Tool
names. The live evidence deliberately redacts fixture paths and executable
paths.

## Codex baseline-management audit

The repaired baseline workflow is coherent across
`scripts/codex-baseline.ps1`, `scripts/test-codex-baseline.ps1`, and
`docs/CODEX_BASELINE_MANAGEMENT.md`:

- repair is explicit host-only maintenance and is not run at startup or
  Connect;
- exact semantic version and complete native source pair are required;
- both executables are validated as native Windows x64 PE files and hashed;
- a fresh v2 directory is staged and verified before replacement;
- replacement uses bounded same-volume staging/backup moves;
- valid differing destinations are never replaced;
- failed replacement attempts preserve or attempt bounded restoration of the
  old destination;
- no force process termination, manifest-only fake upgrade, legacy v1
  acceptance, code-mode-host reconstruction, or PATH fallback from an invalid
  present baseline is allowed.

The deterministic matrix covers absent, valid/idempotent, legacy v1, missing
host, malformed manifest, wrong source version, non-PE source, invalid host,
staged failure, first/second move failure, differing valid baseline refusal,
and corrupted destination repair. It passed locally.
