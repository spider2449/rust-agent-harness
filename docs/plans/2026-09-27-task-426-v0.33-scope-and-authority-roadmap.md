# Task 426 — RAH v0.33 Scope and Authority Roadmap

Date: 2026-09-27
Status: **RECOMMENDATION — NO PRODUCT CAPABILITY SELECTED; AUTHORITY RESEARCH REQUIRED**
Task type: current-source product-scope and authority analysis only

## Decision

Task 426 does **not** select a v0.33 primary product capability. The current
source confirms several real extensions, but it does not establish a normal-use
blocker whose smallest useful contract is both sufficiently closed and
understood. The most promising operational candidate is live Trusted Profile
recomposition. It requires a focused authority and lifecycle contract before
we can say whether it is a safe product capability or merely a more complex
way to do the already-supported Disconnect / Connect workflow.

The recommended next task is:

> **Task 427 — Trusted Profile Live Recomposition Authority Research**

Task 427 remains research/design only. It should decide whether an explicit,
user-triggered in-session profile recompose is valuable and can be made
fail-closed across existing provider, registry, runtime, and conversation
lifecycle boundaries. It must compare that proposal with the existing
Disconnect / Connect path and may conclude that no feature is warranted. It
must not implement Rust, edit the profile format, add persistence, change
provider trust, add a network transport, or authorize a v0.33 implementation.

This is Recommendation B because the meaningful candidates either require
unresolved authority/currentness work or do not currently show enough user
leverage to justify a milestone. Version cadence is not a reason to widen
authority.

## Frozen v0.32 product and authority baseline

v0.32 added bounded repository structure browse through `repo.list`. Its
released contract is:

```text
authority       = ReadOnly / RepositoryObservation
permission      = Execute
binding         = repository_bound=true
repository      = host-selected active repository only
inventory       = tracked Git paths only
projection      = direct children only
directories     = synthesized from tracked paths
contents        = never read
ordering        = deterministic repository-relative
result          = bounded
consistency     = best_effort
HostExplicit    = ineligible
```

The v0.31 `repo.search` contract remains closed to `path | text`, tracked
currently-present files, literal case-sensitive host-side matching, and the
host-selected active worktree. It has no empty-query inventory mode. The
current production HostExplicit set remains exactly:

```text
fs.read
repo.file-info
repo.status
repo.diff
repo.diff-staged
repo.create-branch
repo.patch
repo.edit-files
repo.create-file
repo.delete-file
repo.rename-file
```

Neither `repo.list`, `repo.search`, `repo.create-directory`, `repo.commit`,
nor provider-defined Tools are HostExplicit eligible. Task 426 proposes no
change to this set.

The architecture remains host-owned membership and activation, zero or one
active admitted repository, active-only executable repository composition,
no union ToolRegistry, no model/provider repository selector, separate
linked-worktree member identity despite shared Git state, and zero executable
repository authority after restart. Observation, worktree mutation, index
mutation, ref mutation, and reviewed history mutation remain separate.

## Current product workflows from source

### Repository path

The current normal workflow is:

```text
host admits/selects active repository
  -> repo.list bounded tracked structure browse
  -> repo.search bounded tracked path/text discovery
  -> fs.read / repo.file-info known-path inspection
  -> existing authoring Tools
  -> Stage / Unstage / reviewed Commit workflow
```

Production composition in `crates/rah-desktop/src/main.rs` constructs the
first-party registry for the host-selected repository. `crates/rah-tools/src/repository_list.rs`
and `repository_search.rs` use the shared observer boundary; both require a
repository identity selected outside model input. `crates/rah-desktop/src/effective_authority.rs`
classifies both as `ReadOnly / RepositoryObservation`; `host_invocation.rs`
omits both from `host_kind`.

The directory-creation Tool already exists in
`crates/rah-tools/src/repository_create_directory.rs`. It is a bounded
repository-bound `PermissionLevel::Execute` operation classified as
`RepositoryDirectoryCreation`; it creates one ordinary empty directory and
does not write a marker, stage content, or modify Git index/HEAD/refs. Because
Git does not track an empty directory, that filesystem effect can leave Git
status clean. It is deliberately absent from the HostExplicit coordinator.

### Profile and provider path

`crates/rah-tools/src/trusted_profile.rs` parses the static profile and
`crates/rah-desktop/src/trusted_profile_selection.rs` retains a host-selected
source path plus sanitized configured counts/descriptors. Selection is allowed
while disconnected; changing/choosing a profile while connected is rejected.
The retained path is not an already-running composition.

On each `connect_codex` call, `crates/rah-desktop/src/provider_composition.rs`
calls `load_for_activation`, re-reads the selected profile, applies the
provider-only rule, and invokes the shared composer. The resulting MCP and
Process Plugin adapters are owned by one `DesktopProviderActivation`. Their
tools are merged with first-party tools before the Codex runtime is connected.
Duplicate tool names fail closed. Profile/provider metadata does not assign
permission. The connected state captures repository, model, profile,
connection, and identity generations; stale publication is rejected.

`disconnect_codex` requires an idle chat and no prepared/running HostExplicit
invocation, withdraws the connection, shuts down the runtime, and then shuts
down the provider activation. Thus a user can apply changed profile contents
by disconnecting and reconnecting; Connect rereads the selected source. The
source does not show a safe live replacement of providers and the active
ToolRegistry while the Codex runtime/thread is already connected.

### Desktop lifecycle and Codex bridge

Repository selection/switching, remembered descriptive workspace state,
Trusted Profile selection/preferences, Connect/Disconnect, conversation
transcript lifecycle, and effective authority/currentness presentation are
host-owned Desktop operations in `crates/rah-desktop/src/main.rs`,
`remembered_workspace.rs`, `desktop_preferences.rs`, and
`crates/rah-desktop/frontend/status.js`. Remembered workspace state is not
executable authority. Repository selection and profile selection are blocked
or constrained around active chat/connection states; authority snapshots
compare captured generations with current state.

The Codex runtime is an adapter. `crates/rah-runtime-codex/src/bridge.rs`
translates dynamic Tool requests through the supplied RAH registry; runtime
approval requests are not approved, and Codex-owned tools remain unsupported.
The adapter pins `codex-cli 0.149.0` and its captured app-server schema
contract. The v0.32 release gate preserves the nonclaim that Windows live
symlink behavior and real model-selected dynamic Tool inference were not
certified for v0.32.

### Criteria synthesis

* **Product leverage and frequency:** the source proves that folder creation,
  profile composition, provider child lifecycle, and repository discovery
  exist; it does not prove a frequency or severity of the remaining gaps.
  Profile hot recomposition has the clearest operational benefit, but
  Disconnect / Connect already rereads the profile and recreates providers.
* **Workflow continuity:** profile recomposition fits provider lifecycle best;
  directory creation fits authoring but is already available as an ordinary
  Tool; search variants extend a recently closed workflow without showing a
  concrete miss; other candidates introduce a new category or rewrite.
* **Authority and security:** only bounded profile replacement or
  HostExplicit directory creation could plausibly stay near existing
  authority. The former has unresolved generation and owner handoff; the
  latter has a reviewed-effect visibility problem and expands HostExplicit.
  Network MCP, untracked discovery, semantic indexing, worktree lifecycle,
  and union registries entail much larger boundaries.
* **Currentness and testability:** candidate B has the densest currentness
  surface. Deterministic tests can prove local transitions but cannot alone
  certify the real Windows provider-process and Codex connection lifecycle.
  Candidate A is more deterministic, but its user-visible and Git-review
  semantics are not compelling enough from current evidence.
* **Windows, cross-platform, and dependency cost:** no selected candidate
  removes platform obligations. Live provider lifecycle, filesystem effects,
  and Git behavior need Windows evidence; Linux/macOS parity cannot be
  inferred from Windows. Network and semantic candidates add the highest
  external/dependency cost; profile recomposition and directory routing do
  not appear to require a new crate.
* **Architectural disruption and closure:** a narrow in-session profile
  contract might be possible, but current source does not settle Codex thread
  replacement or old-provider retirement. HostExplicit directory creation
  has a smaller code surface but expands a deliberately exact reviewed route
  set. No candidate yet has both a proven product blocker and a frozen small
  contract.

## Required authority research: Task 427

Task 427 should answer whether **explicit live Trusted Profile
recomposition** is a user-facing capability worth adding, or whether the
existing disconnected Connect path is the right closed lifecycle. It should
inspect the same current source and answer at minimum:

1. What user-visible state indicates the selected source changed, and what
   explicit human action authorizes loading those changed bytes?
2. Does applying a profile require an idle chat, runtime disconnect, fresh
   Codex thread, or conversation transition? Can an existing thread hold a
   stale tool snapshot after registry replacement?
3. What happens to in-flight calls and pending provider requests during
   replacement? Define no-replay behavior for uncertain calls.
4. Can the new provider set be completely validated and started before the
   old set is withdrawn? If yes, what prevents simultaneous duplicate
   external effects or duplicate public names? If no, specify the fail-closed
   disconnected interval.
5. How are old adapters shut down and reaped on success, activation failure,
   cancellation, timeout, or disconnect failure? No detached children or
   implicit automatic restart.
6. Which repository, model, profile, connection, identity, and composition
   generations must be current at activation and publication? How does a
   changed file between preview and activation behave?
7. Does the user review profile identity/counts only, or a privacy-safe
   configuration-change summary? Executable paths, credentials, environment,
   and provider private metadata remain undisclosed unless a separately
   authorized UX contract requires otherwise.
8. Is there any persistence/schema change? Default assumption: none; restart
   continues to restore no executable repository authority and no running
   provider process.
9. Does the candidate remain `External` provider authority assigned only by
   the host-owned selected Trusted Profile? Does any changed profile add
   process, network, credential, repository, or Tool permission beyond the
   exact user-selected profile? Any such expansion requires separate
   authority research.
10. Define deterministic fake-provider tests, fault injection, independent
    audit, Windows live lifecycle evidence, and separate Linux/macOS claims.
11. Compare the useful in-session behavior with the simpler explicit
    Disconnect / Connect route and state a no-feature outcome if no material
    workflow benefit is demonstrated.

Task 427 should end with one of: a closed implementation-contract
recommendation for a later separately authorized implementation task, or a
no-selection conclusion. It is not an implementation task.

## Authority, security, and privacy conclusions

This task proposes no runtime authority change. It does not add a Tool,
permission level, provider identity, profile trust, model route, repository
selector, filesystem observation, mutation effect, network path, executable,
credential, persistence, or Git capability.

For future profile recomposition research, do not infer that calling
`DesktopProviderActivation::activate` again is safe replacement. Current
activation creates a new provider composition; existing activation owns
provider children until `shutdown`; currentness snapshots are bound to the
connected publication; and the Codex bridge snapshots tool definitions for a
thread. The handoff and disclosure contract is unresolved. No automatic
Trusted Profile reload is authorized.

All v0.32 nonclaims remain intact:

* no arbitrary filesystem enumeration, untracked/ignored discovery, or
  recursive repository dump;
* no generic shell, generic Git, or model-selected repository/worktree;
* no network MCP, credentials, or OAuth expansion;
* no Git worktree add/remove/prune/move/repair/lock/unlock lifecycle;
* no simultaneous active repositories or union ToolRegistry;
* no persistent executable repository authority;
* no general Windows symlink certification beyond recorded evidence;
* no race-free TOCTOU, rollback, or replay guarantee;
* no OS sandboxing or network isolation claim;
* no automatic Trusted Profile reload and no HostExplicit #12.

## Product work versus maintenance and evidence

These remain separate from a v0.33 primary capability:

* **Hardening / technical debt:** Tauri permission-generation discrepancy
  (47 invoke handlers versus 44 generated entries), duplicated fixture
  portability patterns, intermittent Git timing families, documentation
  organization, CI portability, and test runtime cost. Each needs its own
  bounded task and evidence; this roadmap fixes none of them.
* **Compatibility / certification:** refresh the pinned Codex baseline only
  under a dedicated compatibility task; certify current model-selected
  dynamic Tool inference only when the exact supported binary is available;
  gather Linux/macOS evidence separately. These tasks do not become product
  scope solely to advance a version.
