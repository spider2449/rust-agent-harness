The relevant accepted decisions were also read before making a recommendation:
ADRs 0003, 0007, 0008, 0009, 0010, 0011, 0012, 0013, 0014, 0015, 0016, 0017,
0018, 0019, 0020, 0021, 0022, and 0023. They preserve the following facts:

1. RAH orchestrates inference providers; it is not an inference engine.
2. Model output, provider metadata, Tool visibility, frontend state, and
   `PermissionLevel` are requests or dispatch classifications, never authority.
3. `Tool` and `ToolRegistry` remain the provider-neutral capability boundary.
4. HostExplicit is a separate connected-current human/backend dispatch plane.
   It shares D2 and registry dispatch but does not create the underlying
   capability authority.
5. Trusted Profile remains host-owned composition. It may select symbolic
   resources and compose authority already constructed by the host; it cannot
   manufacture or widen repository authority.
6. Worktree content mutation, absent-path creation, deletion, rename/move,
   directory creation, Git index mutation, and Git history/ref mutation are
   separate authority families.
7. Timeout, cancellation, disconnect, crash, or a lost response does not imply
   no effect or rollback. An uncertain effect is never automatically replayed.
8. There is no generic shell, process, filesystem, Git, network, rollback,
   race-free TOCTOU, OS-sandbox, or network-isolation claim.

## v0.22 product checkpoint

A connected-current Desktop human can now safely use the released workflow to:

- inspect repository status, file information, worktree diff, and staged diff;
- read bounded file content;
- create one local branch through the reviewed HostExplicit route;
- prepare and review one bounded single-file `repo.patch`;
- prepare and review one bounded multi-file `repo.edit-files` change-set;
- confirm those authoring changes through the opaque ticket/currentness/D2 route;
- inspect the resulting worktree and staged diffs;
- use the established Stage and Unstage paths; and
- use the separate reviewed Commit workflow for Git index/history mutation.

The authoring flow remains deliberately split:

```text
typed human request
 -> zero-effect Prepare
 -> complete backend-derived review
 -> opaque process-local ticket
 -> currentness revalidation and D2
 -> HostExplicit Started
 -> authorized_tool_dispatch
 -> ToolRegistry
 -> existing narrow Tool authority
 -> strict result classification and descriptive refresh
```

The ordinary authoring workflow is still awkward or impossible when it needs:

- a new repository file;
- deletion of an existing file;
- a rename or move;
- a directory needed before a new file can be created;
- one reviewed workflow that combines structural operations with content edits;
- durable descriptive workflow state without confusing it with resumable authority;
- a provider-specific HostExplicit operation; or
- production live assurance on platforms other than the current Windows target.

These are gaps, not a reason to combine unlike authority families. In
particular, a UI grouping such as “file operations” does not prove that
creation, deletion, rename, and directory creation share preconditions,
review material, or failure semantics.

## Structural-authoring question

Yes: after v0.22 existing-file editing, safely creating a new repository file is
the highest-value remaining authoring gap. It is the smallest operation that
lets a normal author add a source, test, configuration, documentation, or other
bounded file without requiring an out-of-band editor. It is also the candidate
with the strongest current evidence:

- ADR 0013 already accepts a narrow one-file create-new authority;
- the authority is implemented and has deterministic tests;
- the Tool is already closed to `{path, content}` and bounded;
- the target is absent from HEAD, index, and worktree;
- exclusive create-new/no-clobber semantics already exist;
- existing parent validation, Git preservation, untracked-state behavior, and
  partial/uncertain outcomes are already explicit; and
- the v0.22 reviewed HostExplicit pattern can be reused without widening it to
  generic filesystem writing.

The milestone should select only **HostExplicit Reviewed New-File Authoring**.
It should not bundle create, delete, rename, and directory operations. Their
semantics differ materially:

- creation reviews complete new content and proves absence before the effect;
- deletion reviews destructive preimage material and privacy-sensitive content;
- rename reviews two path identities and a no-clobber destination; and
- directory creation has no content preimage and may remain invisible to Git.

Bundling them would make one release responsible for multiple independent
currentness, review, Windows-native, and uncertain-effect contracts.

## Selected capability and authority boundary

### Selected capability

**HostExplicit Reviewed New-File Authoring** — a connected-current Desktop
human may prepare, inspect, and explicitly confirm creation of exactly one
bounded new repository-relative UTF-8 regular file through the existing
`repo.create-file` Tool.

### No new underlying authority

ADR 0013 remains the underlying creation authority. A future capability-specific
ADR is likely required before implementation because the human review contract
for an absent path and complete new content is materially different from ADR
0022's existing-file patch and ADR 0023's existing-file multi-edit review.
That ADR would define only the reviewed HostExplicit workflow around
`repo.create-file`; it would not amend ADR 0013, ADR 0021, or the v0.22
architecture. Task 268 accepts no ADR and changes no eligibility.

The exact new boundary required is:

```text
closed typed human {path, content}
 -> zero-effect host Prepare for repo.create-file
 -> complete backend-derived new-file review
 -> opaque single-use process-local ticket
 -> shared creation-specific revalidation/currentness
 -> D2 complete-definition and permission check
 -> HostExplicit Started
 -> authorized_tool_dispatch
 -> ToolRegistry
 -> existing repo.create-file / ADR 0013
 -> strict result classification and descriptive refresh
```

The route must remain Desktop-private HostExplicit provenance. It must not
create model Tool lifecycle events, inject the review into conversation, accept
arbitrary Tool JSON, or bypass the ordinary registry.

### Closed human input

The human Prepare DTO should contain only:

```json
{"path":"src/new_module.rs","content":"...complete UTF-8 content..."}
```

Unknown fields must fail closed. The human must not provide a repository root,
native path, executable, Git arguments, authority fields, permission,
provider/model metadata, expected hashes, parent identity, file mode, retry
control, or execution order. The host derives those values.

The existing implementation bounds the logical path to 1024 UTF-8 bytes, the
content to 256 KiB, and the serialized request to 320 KiB, rejects NUL content,
and accepts only the existing closed path language. The reviewed route must
retain or narrow those limits; it must not silently increase them.

### Host-derived preparation state

Prepare must derive and bind, without an effectful Tool call or repository
temporary file:

- connected-current selected repository, canonical root, Git executable, and
  repository/runtime/profile/connection generations;
- canonical logical path and stable path identity;
- immediate parent identity and every validated parent component;
- target absence as every filesystem object, including file, directory, link,
  reparse point, special entry, and case/alias-equivalent name where the
  supported Windows identity model can detect it;
- hard-link concerns: a proven absent target cannot be an existing hard link,
  but parent identity and native target acquisition still require conservative
  identity checks; no race-free or comprehensive hard-link claim is allowed;
- ordinary parent type, containment, non-link/non-reparse status, and nested
  repository or metadata exclusion;
- absence from HEAD and every index form, including intent-to-add and unmerged
  entries, plus ignore and submodule/sparse admission;
- strict UTF-8 content bytes, byte length, SHA-256, BOM and newline/final-EOF
  facts, control/bidi/zero-width/format markers, and regular non-executable
  file-mode/attribute policy;
- the exact existing `repo.create-file` ToolDefinition and canonical ToolInput;
- protected HEAD, refs, index, repository identity, and unrelated sentinel
  observations;
- expected current permission membership and Effective Authority identity; and
- a review identity and the retained capability-specific preparer binding.

Prepare must prove zero Tool calls, zero native create attempts, zero
repository mutations, zero index/HEAD/ref/history changes, zero provider or
model lifecycle activity, and zero persistent authority writes. If the complete
review cannot be bounded and understood, it returns `review_too_large` and
issues no ticket.

### Complete review representation

The review must show every mutation-relevant value needed for a human to
understand the exact create-new effect:

- operation name and one target ordinal;
- logical repository-relative path and path bounds;
- target absence proof and the stable absence/alias identity observation;
- immediate parent logical path, type, identity, and containment proof;
- Git tracked-state facts: absent from HEAD and index, expected untracked state
  after creation, and no Stage/Commit effect;
- complete new-file content in deterministic escaped display form, including
  all content and not merely a preview;
- exact raw byte length and SHA-256 derived by the host;
- BOM, CR/LF/final-newline, whitespace, control, bidi, zero-width, and format
  character representation where applicable;
- regular-file mode/attribute policy and the absence of executable, ACL, owner,
  or caller-selected permission changes;
- intended effect: one exclusive create-new file in the existing parent;
- protected non-effects: no overwrite, append, directory creation, delete,
  rename, index, HEAD, branch, ref, history, Stage, Unstage, Commit, provider,
  model, shell, or process effect; and
- explicit warning that native create is the effect boundary and that partial
  or uncertain content is not rolled back.

Escaping is display-only and must not normalize or change bytes. No
mutation-relevant content may be clipped, ellipsized, hidden behind an editor,
or redacted while remaining confirmable. Unchanged repository context may be
omitted only when the review states that it was omitted. Complete content or
complete review that exceeds bounded local limits fails closed.

### Ticket, currentness, and dispatch

The ticket must follow the v0.22 pattern: RAH-generated, opaque,
capability-specific, process-local, in-memory, nonserializable as durable
authority, single-use, exact-change/currentness-bound, and valid for the
inclusive five-minute TTL. Restart, disconnect, cancellation, expiry,
recomposition, generation drift, or stale repository state invalidates it.

Confirm accepts exactly `{ticketId}`. It must not accept a path, content, hash,
Tool JSON, parent identity, permission, provider, repository, or authority
value from the frontend. Before `Started`, the host atomically consumes the
ticket, revalidates the retained creation plan and all target/parent/absence/Git
observations, checks the complete current ToolDefinition and current permission
membership through D2, and then calls `authorized_tool_dispatch` into the
current `ToolRegistry`.

One confirmed ticket permits at most one `repo.create-file` Tool execution and
one native create attempt. A duplicate or stale confirmation cannot be
reprepared automatically. There is no direct filesystem call from a Desktop
command, no direct `Tool::execute`, no generic registry shortcut, no generic
Tool-name-plus-JSON console, and no model/runtime substitution.

### Failure semantics

The host must preserve the existing creation semantics rather than collapse
them into success/failure:

| Phase/result | Required classification | Required behavior |
| --- | --- | --- |
| Invalid DTO/path/content or unsafe precondition | known no effect | No Tool/native attempt; no ticket on Prepare failure |
| Target/parent/Git/currentness drift before native create | known no effect | Fail closed; do not rewrite expected state or retry |
| Exclusive create reports target collision and fresh observation proves no RAH effect | known no effect | Preserve the external target; no overwrite or retry |
| Native write leaves a provable partial new file | partial effect | Report only the proven partial file state; retain it; no delete, cleanup, continuation, or replay |
| Exact regular file/content/Git postconditions are verified | known verified effect | Report one created file and refresh descriptively |
| Lost return, timeout, cancellation after possible create, identity contradiction, or failed post-observation | uncertain effect | Do not infer absence, do not retry, and do not roll back |

The existing Tool vocabulary (`ok`, `precondition_failed`,
`create_failed_known`, `write_failed_known`, and `uncertain`) may remain
Tool-private, but the HostExplicit contract must map it to a bounded human
result that distinguishes known no effect, verified creation, partial effect,
and uncertainty. The route must not manufacture a verified result from a file
appearing at the target after a lost response.

### Privacy

Task 263's value-level privacy lesson carries forward. The authority ticket and
HostExplicit activity ID are distinct values. The ticket must never enter
generic activity, conversation persistence, transcript replay, logs, telemetry,
or live evidence, including under another field such as `invocationId`.

Complete new-file content is source-bearing review material. It may exist only
in bounded process-local pending state and the local review DTO needed for the
human. Generic activity and persistence may retain only bounded redacted
metadata: operation kind, relative or opaque target label, byte length, review
identity, result class, effect state, currentness identity, and boolean
lifecycle counts. They must exclude the content, raw ToolInput/output, ticket,
absolute/native paths, parent implementation details, temporary names,
credentials, provider output, and content-bearing errors.

The review must not be copied into generic conversation context or persisted as
an authority-bearing “plan.” Descriptive workflow text may be persisted only if
it is clearly non-authoritative and cannot Confirm, recreate a ticket, or select
new trusted bindings.

### Stage, Unstage, Commit, and refresh

The selected capability is worktree-only. It must not Stage, Unstage, Commit,
alter HEAD, create refs, or alter history. A verified new file appears as an
untracked worktree file; `repo.file-info` and `repo.status` can observe it, while
ordinary Git diff may not show untracked content. The host-derived review hash,
length, and post-observation are therefore important and must not be replaced
by a diff-only claim.

Any effectful start invalidates stale reviewed Commit authorization for the
repository, including verified, partial, and uncertain outcomes. A descriptive
refresh may show status/file information and may produce a new review state, but
it must not auto-stage, auto-commit, reissue the create ticket, or authorize a
new Commit. Human Stage/Unstage and the existing reviewed Commit workflow remain
separate.

## Candidate research

### A. Reviewed HostExplicit `repo.create-file`

This is the selected candidate. Its concrete user value is direct, reviewed
creation of a missing source/test/configuration/documentation file. The
underlying authority is sufficient: ADR 0013 already defines one bounded
UTF-8 regular file, existing parent only, absent from HEAD/index/worktree,
exclusive no-clobber creation, unchanged Git state, bounded content, and no
replay after possible effect.

The missing boundary is a capability-specific `CreateFilePreparer` and typed
Desktop workflow around the existing Tool. The route must add parent identity
and complete target-absence/currentness binding to the review; it must not turn
the Tool into `fs.write`, permit arbitrary absolute paths, or compose delete,
rename, directory creation, Stage, or Commit.

The review burden is high but bounded because the operation has one target and
complete new content. The Windows live burden is meaningful: prove root and
existing-parent path handling, CREATE_NEW/no-clobber behavior, reparse and alias
rejection, regular-file verification, untracked state, unchanged index/HEAD/
refs, no duplicate attempt, privacy, and partial/uncertain no-replay behavior.
Those are narrower and less destructive than deletion or two-path rename.

### B. Reviewed HostExplicit `repo.delete-file`

Deletion has clear value for removing a tracked obsolete file, and ADR 0017
plus the underlying Tool are strong. It requires a destructive preimage review:
the human must see the exact path, source identity, HEAD/index/worktree
identity, content hash and length, tracked-clean admission, and the exact
non-restoration warning. Complete deleted content or a sufficiently complete
destructive representation must be bounded; hashes alone cannot hide material
that the human needs to understand.

The operation must reject dirty/staged/untracked/link/reparse/hard-link or
ambiguous targets and hold the index unchanged. Windows open handles can delay
name disappearance; after the one native delete attempt, uncertainty is real.
There is no automatic restore, retry, or cleanup. It is valuable, but its
privacy and destructive-review burden is higher than creating a new file, so it
is not the v0.23 selection.

### C. Reviewed HostExplicit `repo.rename-file`

Rename would remove a common authoring gap, but it has two independently
reviewed paths: source identity and destination absence/parent identity. The
review must show source bytes/hash/length and Git identity, destination path and
absence proof, both parents, no-clobber semantics, and that the native effect is
rename rather than copy/delete. It must reject destination aliases, case-only
Windows ambiguity, missing/replaced parents, cross-volume behavior, and any
`git mv` or copy/delete fallback.

ADR 0018 and the Tool already enforce a one-attempt native no-replace operation
with `renamed_verified`, `known_no_effect`, and `uncertain` outcomes. However,
two-path currentness and post-effect ambiguity make this a larger one-release
workflow than new-file creation. It remains a strong later candidate, not v0.23.

### D. Reviewed HostExplicit directory creation

The underlying ADR 0019 Tool and authority are present and narrowly bounded to
one leaf under an already-existing ordinary parent. Its standalone value is
limited: Git does not track empty directories, `git status` may remain clean,
and the capability does not create a file or implicit parent. A directory can
remain after a later file operation fails, so a combined workflow would need
cross-operation partial-effect semantics.

A future HostExplicit route could review path, parent identity, target absence,
fixed platform mode/attribute policy, Git non-effects, and the absence of marker
files. It should remain separate from file creation. It is not enough product
value for the v0.23 milestone by itself.

### E. Structural change-set / combined authoring plan

The current `repo.edit-files` authority edits existing tracked files only. A
change-set such as “create a new file and edit two existing files” would combine
ADR 0013's create-new commit point with ADR 0014's non-atomic multi-file
replacement and distinct result taxonomy. “Rename plus edits” adds two-path
identity and no-replace semantics as well.

No current single authority, review model, operation ordering contract, or
cross-operation effect classifier proves that this orchestration is safe. A
descriptive plan may later help users organize work, but an executable plan
would be an authority-bearing orchestration layer. It is premature for one
release and is rejected for v0.23.

### F. HostExplicit `repo.commit`

The product already has a separate reviewed Commit workflow based on ADR 0016,
staged-snapshot review, commit identity, exact index/currentness checks, and
one-shot history mutation. Adding a duplicate generic HostExplicit Commit path
would create a second route to durable history/ref authority and blur the
worktree -> Stage/Unstage -> reviewed Commit separation.

There is no demonstrated deficiency that requires a duplicate route. Keep
`repo.commit` HostExplicit-ineligible and improve the existing workflow only in
a separately scoped task if evidence identifies a real gap.

### G. Descriptive session/workflow persistence

Current conversation persistence is descriptive conversation state with
repository/model boundaries and resume handling. It is not a persistence layer
for HostExplicit authority. The current ticket is intentionally process-local,
single-use, nonserializable, and invalidated by restart, disconnect, and
currentness drift.

Persisting a non-authority plan or user-facing checklist could be safe if it
contains no ticket, raw authority binding, trusted path, source-bearing review,
or implicit Confirm capability. Persisting resumable tickets or authority must
be presumed unsafe: repository content, parent identity, ToolDefinition,
permission, profile, and currentness can all change. This is not the highest
value next capability and is not v0.23 scope.

### H. MCP / Process Plugin HostExplicit

Current MCP and Process Plugin adapters preserve the Tool boundary, expected
schemas, permissions, lifecycle ownership, and provider failure handling. They
do not provide a generic semantic effect contract suitable for HostExplicit.
The v0.22 host classifier rejects non-built-in/non-repository-host sources as
`ProviderNotSupported`.

A future provider-specific HostExplicit operation could be considered only for
one named contract whose effect, input, review, identity, lifecycle, privacy,
and uncertainty semantics are host-understood. Arbitrary provider schemas or
generic Tool JSON must remain rejected. No provider-specific contract has
stronger current evidence than new-file authoring, so this is deferred.

### I. Network MCP / Streamable HTTP

The accepted provider boundary covers a bounded model-provider endpoint, not a
network MCP Tool plane. Current MCP composition is local stdio-oriented and ADR
0011 explicitly defers Streamable HTTP/network MCP. A network MCP milestone
would need a separate endpoint, TLS and server-identity contract; credential
handling; proxy and DNS behavior; redirect policy; connection lifecycle;
external side-effect and no-replay semantics; and deterministic/live tests.

Those concerns are not transport-only. They add remote effect and data-routing
authority, with no current network-isolation claim. This is not v0.23.

### J. Trusted Profile explicit reload

An explicit host-driven reload/recomposition could be useful operationally, but
it is not the next missing authoring capability. It must remain distinct from
automatic file-watcher or hot-reload authority changes. A future explicit
reload would need to invalidate old composition, registry, generation, and
HostExplicit tickets before publishing a new host-selected composition, with
no provider metadata self-enablement.

ADR 0011 already defers automatic reload and current product evidence does not
show explicit reload as the principal v0.23 user gap. It is deferred.

### K. Plugin lifecycle / PluginManager

The current Process Plugin adapter supervises an explicitly configured process;
it is not a PluginManager. Install, update, discovery, trust, replacement,
package verification, executable provenance, rollback, and Windows packaging
would each add authority and lifecycle surfaces.

No current product evidence shows that install/update management is a better
next milestone than a missing repository authoring operation. PluginManager is
deferred.

### L. Cross-platform production certification

Linux/macOS production certification is valuable assurance, but it is not a
new user capability and cannot fill the demonstrated new-file authoring gap.
The current evidence deliberately distinguishes deterministic CI/platform tests
from connected-current Windows production certification. v0.23 should use
Windows as the live target for the selected capability; broader platform parity
can remain a separately budgeted assurance milestone.

## Why the alternatives lose

The decisive comparison is not abstract architectural elegance. v0.22 already
proves reviewed edits to existing files, while the current code already proves
an underlying bounded create-new authority. New-file authoring therefore adds a
direct user capability at the smallest authority delta: one absent path, one
complete content value, one parent, one native create attempt, and no Git index
or history effect.

Deletion is more destructive and privacy-sensitive. Rename is a two-path
operation with a larger Windows identity/collision surface. Directory creation
has weaker standalone value because Git does not track an empty directory.
Combining the operations creates a new orchestration authority before each
individual HostExplicit route has a proven reviewed contract. Commit is already
separate and complete enough for its purpose. Persistence, providers, network,
plugins, reload, and cross-platform certification do not address the immediate
new-file authoring gap and each introduces a larger lifecycle or assurance
surface.

## Proposed v0.23 task sequence

These are proposed future tasks only. None is started by Task 268.

   product checkpoint, candidate matrix, authority boundary, exclusions, and
   evidence limitations.
2. **Task 269 — reviewed HostExplicit new-file contract research.** Reconfirm
   ADR 0013 behavior and specify closed input, absent-path/parent identity,
   complete content review, UTF-8/BOM/newline bounds, file attributes,
   tracked/untracked semantics, exact privacy surfaces, and all result classes.
3. **Task 270 — capability-specific ADR, if accepted by a separately authorized
   task.** Add only the reviewed `repo.create-file` HostExplicit boundary around
   ADR 0013 and ADR 0021. Do not amend existing authority or add a wildcard
   allowlist. This ADR is not accepted in Task 268.
4. **Task 271 — shared non-effectful creation preparation and revalidation.**
   Build a host-bound preparer that performs zero Tool/native effects, derives
   exact review state, retains the same host-selected repository/Git identity,
   and revalidates target absence, parent identity, Git state, ToolDefinition,
   permission, composition, and generations. No Desktop UX or eligibility yet.
5. **Task 272 — deterministic backend HostExplicit contract.** Add the
   capability-specific typed ticket route using Prepare -> bounded review ->
   opaque ticket -> revalidation -> D2 -> Started -> authorized dispatch ->
   ToolRegistry -> existing Tool. Keep the exact existing eight-name allowlist
   until the complete implementation gate is separately authorized.
6. **Task 273 — typed Desktop review workflow.** Add only the closed `{path,
   content}` human form and complete safe review rendering. Do not expose raw
   Tool JSON, authority fields, hashes as caller input, generic editors, or
   content-bearing activity/persistence.
7. **Task 274 — deterministic fault, result, and privacy hardening.** Prove
   zero-effect Prepare, target/parent/absence races, CREATE_NEW collision,
   partial write, lost post-observation, stale currentness, D2-before-Started,
   exactly-once dispatch, ticket/activity separation, source privacy, reviewed
   Commit invalidation, and no retry/replay/rollback/cleanup.
8. **Task 275 — Windows connected-current live certification.** Use a fresh
   disposable Windows repository and the production Desktop backend, with one
   new file under an existing parent. Prove one Prepare with zero Tool/native
   attempts, one ticket-only Confirm, one Tool/native create attempt, complete
   postimage and untracked observations, unchanged index/HEAD/refs/sentinel,
   no model lifecycle, MCP, or Process Plugin activity, and the required
   redacted live marker. A failed or uncertain run stops; it is not retried on

9. **Task 276 — v0.23 milestone audit.** Audit the exact allowlist, authority
   separation, complete review, privacy, result semantics, Windows evidence,
   Stage/Commit separation, and nonclaims. Do not convert host-driven evidence

## Final decision

**SELECTED v0.23 MILESTONE: HostExplicit Reviewed New-File Authoring (`repo.create-file`)**

The authority decision is to add, in a future separately authorized sequence, a
capability-specific reviewed human/backend workflow around the already-accepted
and already-bounded ADR 0013 `repo.create-file` authority. The workflow must
accept only a closed typed path and complete UTF-8 content, derive parent and
target absence identities plus all Git/currentness/Tool bindings in the host,
show a complete bounded review, use a process-local opaque single-use ticket,
revalidate before D2 and `Started`, dispatch only through `authorized_tool_dispatch`
and `ToolRegistry`, preserve known-no-effect/verified/partial/uncertain results,
and leave Stage, Unstage, Commit, model authority, provider authority, and
generic filesystem authority unchanged. A new capability-specific ADR is likely
required before implementation, but Task 268 accepts none and changes no
allowlist. The Windows connected-current live target is one fresh disposable
new-file creation under an existing validated parent with exactly one native
attempt and full privacy/currentness/non-effect evidence.
