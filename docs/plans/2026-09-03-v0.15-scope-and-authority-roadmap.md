# Task 180 — RAH v0.15 Scope and Authority Roadmap

Research date: 2026-09-03
Task type: research, roadmap, and documentation only
Baseline: `HEAD == origin/master == 5655dd9e3ec0f312455865f8529954b006c394a4`

## 1. Executive recommendation

RAH v0.15 should deliver one bounded user-facing capability:

> `repo.create-directory`: create exactly one absent ordinary directory at a
> validated repository-relative path whose immediate parent already exists.

This is the highest-value next step because v0.14 now completes the ordinary
single-file reorganization case, while `repo.create-file` still cannot create a
new module or test directory. This closes that concrete source-authoring gap
with a small, reviewable authority increase. It does not attempt to solve Git
branches, restore, persistence, network integration, or provider management in
the same milestone.

The recommendation is conditional on a dedicated authority/design task proving
the Windows reparse, symlink, path-identity, and uncertain-effect contract. A
new accepted ADR is required before implementation because directory creation
is a new structural worktree mutation plane. It must not be inferred from
ADR 0013 file creation or ADR 0018 file rename/move.

## 2. Post-v0.14 product baseline

The release record identifies v0.14.0 as released, with immutable release
commit `52506521bdf838784dd45bb54df2d6bcff8bcd08`, annotated tag `v0.14.0`,
and tag object `9193423e96dd0cda2fd8f5ed5619ab2b58483acc`.

The current product surface, confirmed in `README.md`, `CHANGELOG.md`,
`docs/ARCHITECTURE.md`, `docs/SECURITY.md`, the v0.14 audit, and the
accepted ADRs, includes:

| Area | Actual bounded capability |
|---|---|
| Read and observation | `fs.read`; `repo.file-info`, `repo.status`, `repo.diff`, and `repo.diff-staged`; host-selected executable, repository, and bounded output. |
| Existing-file authoring | `repo.patch` for one existing strict-UTF-8 tracked file with one or up to sixteen exact replacements; `repo.edit-files` for one through four existing files, exact preimages, deterministic order, and no automatic staging. |
| File creation | `repo.create-file`, one absent UTF-8 file per call, exclusive/no-overwrite, repository-relative, with an existing real parent; it does not create directories. Documented bounds are a 1024-byte path, 256 KiB content, and 320 KiB serialized request. |
| File deletion | `repo.delete-file`, one clean HEAD-tracked regular file with exact authorized HEAD preimage; it leaves an unstaged deletion and does not mutate the index or history. |
| File rename/move | `repo.rename-file`, one clean HEAD-tracked regular file, same-directory or same-repository cross-directory, to an absent destination under an existing parent; one native no-replace operation; no copy-delete fallback. |
| Index | Host-owned `host.git.stage` and `host.git.unstage`, separate ADR 0010 index authority, narrow tracked-file operations; model Execute permission does not itself grant index authority. |
| Reviewed commit | `repo.commit`, message-only, one ordinary commit from one fresh host-reviewed staged snapshot on the current attached branch under ADR 0016; no automatic staging, branch/ref input, amend, merge, rebase, reset, or network Git. |
| Execute | Bounded host capabilities such as `host.cargo.version` and fixed Git observers; fixed executable, argv, cwd/environment, output, and timeout policies. This is not generic shell or process authority. |
| External providers | Local pinned MCP stdio and bounded Process Plugin stdio adapters, both ordinary RAH `Tool` implementations routed through `ToolRegistry`; neither provider metadata nor child process grants authority. |
| Composition and Desktop | Host-owned Trusted Static Profile composition, Generic Codex Tool Bridge, selected-repository binding, runtime/repository generations, refresh, and stale-context rejection. Windows is live-certified for the released Codex 0.149.0 path; Ubuntu/Linux has deterministic test/CI evidence only. |
| Persistence | Private repository-scoped SQLite completed-conversation text and explicit Resume display/context replay. Resume happens after a fresh connection and restores no repository, runtime, tool, model, or mutation authority. |

The v0.14 audit records successful deterministic and Windows live evidence for
rename, including one request/start/finish lifecycle, exact destination bytes,
unchanged index/HEAD/refs, and no replay. It also records that Linux live
certification is not established.

The realistic bounded coding loop is already:

```text
inspect -> edit/create/delete/move files -> inspect diff -> human stage/unstage
-> host-observed staged review -> fresh reviewed commit authorization -> commit
```

For an existing repository layout, RAH can complete the requested source-code
change sequence without generic shell, generic filesystem, or generic Git
authority. The remaining direct blocker is structural setup: when a new nested
directory is needed, `repo.create-file` requires the parent to exist, and
neither rename nor the existing tools can create that directory.

## 3. Remaining workflow gaps

The evidence does not support describing RAH as unable to do source-code work
after v0.14. It can edit existing files, create files in existing directories,
delete or move eligible tracked files, stage selected changes through host
actions, review staged state, and commit one reviewed snapshot.

The main product gap is completeness at the repository-layout boundary:

- A new nested module, test fixture, or source package directory cannot be
  created by the model-facing bounded tools.
- A user must pre-create every parent directory outside the RAH workflow.
- Recursive directory creation would be a materially larger operation because
  it combines multiple path effects and makes partial-effect accounting harder.

There are larger workflow gaps, but they are not equally good v0.15 targets.
Restore adds destructive replacement semantics; branch switching adds ref and
worktree state transitions; persistence beyond transcript replay adds
stale-state and authority-lifecycle questions; network MCP adds network and
credential risk; PluginManager adds process lifecycle ownership; and profile
reload changes the effective live authority set.

A documentation consistency issue was found: the current `README.md` still
uses release-preparation wording near its v0.14 heading, while the changelog and
release gate record v0.14.0 as released. The v0.14 audit classified this as
release-facing documentation drift, not an implementation or security blocker.
It is not silently corrected in Task 180.

No additional candidate beyond A–G is selected. Repository copy and richer
inspection would either duplicate existing bounded observation or introduce
another structural mutation; repository evidence does not establish either as
a higher-value blocker than directory creation.

## 5. Candidate analyses

### A. Bounded repository directory creation

`repo.create-file` requires an existing real parent, rejects links/reparse
traversal and unsupported repository targets, creates one file, and explicitly
does not create directories. `repo.rename-file` likewise requires an existing
destination parent and excludes directory movement. Directory creation through
a narrow RAH tool is currently impossible.

The smallest useful contract is one absent ordinary directory per operation,
with one already-existing ordinary parent. The path remains a logical
repository-relative path, with the existing metadata, nested-repository,
symlink, junction, reparse, traversal, alias, and Windows reserved-name
protections applied. Preexisting final paths should fail closed rather than
become idempotent success unless dedicated research proves a narrower rule.

The v1 contract should not create missing ancestors. Recursive `mkdir -p`
semantics would authorize an unbounded number of directory effects, complicate
partial success and cleanup, and make a model-selected path more powerful than
the file-creation contract. Empty directories also have no Git tree identity by
themselves: Git does not track an empty directory, so the product value is to
enable a later bounded file creation, not to create a Git-visible change alone.

This candidate has a real new authority despite its small implementation shape:
file creation does not automatically imply directory creation. A directory can
contain future files, alter traversal and collision behavior, and enable a
larger structural workflow. The authority must be host-created, opaque, and
separate from `RepositoryFileCreationPolicy`, `RepositoryFileRenamePolicy`,
deletion, content mutation, index, and commit policies.

### B. Bounded repository restore/revert primitive

Restore is not transaction rollback. It would be a new worktree mutation that
replaces or recreates a path from a specifically selected known source, such as
HEAD, the index, or an exact reviewed blob. The design must distinguish HEAD
versus index source semantics, dirty-file refusal, deletion restoration,
staged-change interaction, file-type and symlink transitions, and
post-effect uncertainty.

A safe shape would require host-bound source and destination identities, exact
preimage/postimage conditions, a single native effect or a strictly bounded
fixed primitive, immediate revalidation, and no retry after a possible effect.
It must never become `git checkout`, `git reset`, generic restore, or a
rollback promise. Its value is real for iterative work, but its destructive
replacement semantics are more complex than directory creation.

### C. Repository branch/workspace workflow

Inspecting the current branch is already part of host observation and commit
preconditions. Creating a branch without checking it out is materially narrower
than switching: it changes a ref but not the worktree. Even so, it is durable
repository ref mutation and is outside ADR 0016’s one current-branch commit
authority.

Switching or create-and-switch is a larger action. It can change worktree files,
index state, conflicts, sparse/worktree behavior, runtime repository generation,
and the meaning of pending reviewed state. Neither should be modeled as generic
Git argv. Branch creation alone could be researched separately, but it is not
the current source-authoring blocker.

### D. Session/workflow persistence

RAH already persists bounded completed conversation text in private,
repository-scoped SQLite namespaces and supports explicit Resume after a fresh
connection. The schema is versioned and corruption handling fails closed. The
current design intentionally does not persist or restore reviewed commit
authorization, runtime authority, provider credentials, repository selection,
or a native Codex thread.

A useful next persistence feature could store non-authoritative workflow
checkpoints, such as a user-visible task label, display filters, or bounded event
history. It must revalidate repository identity and generation, discard or
invalidate stale runtime state, never serialize authority objects or secrets,
and handle corruption and migration. This is valuable for long tasks but does
not unblock the common repository change that directory creation does.

### E. Network MCP / Streamable HTTP

The current MCP adapter is pinned local stdio. Streamable HTTP would add remote
tool integration, but protocol support is not network authorization. A safe
design would need host-owned endpoint admission, authentication and credential
ownership, TLS verification, redirect and proxy rules, DNS/address-rebinding
handling, request/response bounds, cancellation and timeout, reconnect/retry
semantics, uncertain external effects, and profile allowlisting.

ADR 0015 endpoint work does not prove transport confinement, and the repository
does not claim network isolation. This is a distinct security milestone, not a
follow-on to local stdio MCP.

### F. PluginManager / plugin lifecycle

The current Process Plugin adapter validates a host-selected executable, uses
bounded NDJSON stdio, minimizes the child environment, owns an isolated working
directory, and exposes admitted tools through `ToolRegistry`. A narrow manager
could inventory configured plugins and report state without installing anything.

Starting, stopping, health checks, and restart policy still create lifecycle
authority over external processes. Installation, download, arbitrary executable
selection, and automatic restart are materially broader and remain out of
scope. A manager must not automatically retry after a provider call with an
uncertain external effect. The current product has enough provider capability
for local integration tests, so this is not the next coding blocker.

### G. Trusted Profile reload / dynamic authority

`TrustedStaticProfile::load` loads one explicitly selected profile without
search or reload. Current composition builds a fresh registry and requires the
host to supply effective authority. This static lifetime is a security feature:
the model cannot silently gain tools while connected.

Manual reload could be useful operationally, but it changes the effective tool
set while a runtime/session may be connected. A safe design needs atomic
composition, profile and authority generations, revocation semantics, in-flight
call handling, stale-result rejection, provider cleanup, and an explicit
reconnect boundary. File watching adds another trigger and should not be the
first version. This is high authority complexity with little direct leverage.

## 6. Recommended v0.15 capability

The smallest safe v1 is:

- public tool name: `repo.create-directory`;
- one explicitly named logical repository-relative directory path;
- exactly one absent final directory entry;
- one existing, validated ordinary immediate parent;
- selected canonical repository and runtime/repository generation fixed by the
  host;
- no file content input and no recursive ancestor creation;
- no overwrite, replacement, delete, rename, copy, or directory move;
- no automatic staging, index mutation, commit, ref/history mutation, or
  network operation;
- result states distinguishing invalid input, precondition failure, verified
  creation, known no-effect, and uncertain possible effect.

The operation should be useful as the first step before subsequent
`repo.create-file` calls. Because Git ignores empty directories, a successful
directory creation alone may leave no Git diff; the Tool result must state that
fact rather than imply a tracked repository change.

## 7. Authority boundary

A new authority is required: a private, host-owned
`RepositoryDirectoryCreationPolicy` (name provisional until the authority
research task). It grants only one native creation effect for one absent
ordinary directory under one existing ordinary parent in one host-selected
repository.

It does not grant generic filesystem or directory creation, recursive parent
creation, file creation, content writing, append, replacement, deletion,
rename, copy, symlink/junction/reparse/mount/special-file creation, repository
selection, model-selected absolute paths, Git index/staging/commit/branch/ref/
history/checkout/reset, shell, generic process, network, MCP, credential, or
provider authority. It grants no rollback, transaction, durability, or replay
guarantee.

`PermissionLevel::Execute` remains only an outer dispatch permission. A model
request, provider metadata, Tool definition, frontend state, or Trusted Profile
entry cannot manufacture the authority. Trusted Profile integration, if
accepted later, composes an already host-created authority into a fresh
registry; it does not widen the policy.

ADR 0013 and ADR 0018 remain unchanged. A new ADR is required because directory
creation has distinct path identity, preexisting-path, reparse, concurrency,
and possible-effect semantics. Create file plus rename/delete is not a valid
authority-composition shortcut.

## 8. Security model

The authority research must bind canonical repository identity and root,
repository/runtime generation, exact logical path, immediate parent identity,
repository metadata exclusion, nested-repository boundary, and final-entry
absence. It must validate the path again immediately before the effect.
Windows case/alias equivalence, trailing dot/space behavior, reserved names,
and reparse ancestry must fail closed when identity cannot be proven.

The native effect must be one host-selected directory-creation attempt with no
replacement behavior. There is no recursive fallback and no cleanup attempt
after an effect may have occurred. Timeout, cancellation, disconnect, crash,
observer failure, or contradictory postcondition does not imply rollback and
must not be replayed automatically. If post-observation cannot prove the
directory state, the result is `uncertain`.

The shared per-repository mutation lease should serialize this operation with
existing RAH-owned worktree mutation operations, while acknowledging that the
lease does not exclude external processes. The policy should verify that HEAD,
branch, index, refs, and unrelated protected state were not intentionally
mutated. A successful empty-directory effect may be invisible to Git; that is a
product semantic, not a reason to invoke Git.

## 9. Proposed deterministic validation strategy

Future implementation work should prove, without live credentials or internet:

1. exact closed schema, logical path bounds, traversal and metadata rejection;
2. successful one-directory creation with an existing parent;
3. missing-parent refusal and preexisting file/directory refusal;
4. symlink, junction/reparse, nested repository, special-entry, alias, and
   Windows reserved-name refusal where the platform supports the fixture;
5. rejection of a second target, wildcard, absolute, drive-relative, and
   recursive-tree request;
6. repository identity and generation change refusal;
7. parent replacement/identity race refusal;
8. one-attempt behavior and no retry after possible effect;
9. verified postconditions and conservative uncertain results;
10. unchanged file contents, index, HEAD, attached branch, refs, and no Git
    mutation;
11. ToolRegistry permission and missing-authority refusal;
12. Trusted Profile composition and Generic Codex Bridge canonical schema,
    redacted inventory, dispatch, duplicate delivery, cancellation, and
    response translation; and
13. Desktop selected-repository binding, refresh, generation invalidation, and
    reconnect behavior.

The test plan must distinguish deterministic Windows and Ubuntu/Linux evidence
from any later live certification. It must not claim empty-directory Git
tracking or transaction rollback.

## 10. Proposed Windows live-validation strategy

Do not perform live validation in Task 180. A later live task should pin the
certified `codex-cli 0.149.0` pair and a clean exact release-derived baseline,
use a disposable repository outside the checkout, and authorize one smallest
example: create one nested directory under an existing parent, then prove the
directory exists, no file was supplied or changed, Git index/HEAD/refs are
unchanged, and the lifecycle is exactly one request/start/finish where the
evidence contract requires it.

The live run should capture the canonical public tool advertisement, exact
bounded request, structured result, marker, parseable JSONL, and absence of
replay. Windows is the live-certified platform. Ubuntu/Linux should be described
as deterministic validation unless separately authorized live certification is
actually completed.

## 11. Explicit v0.15 non-goals

- recursive directory-tree creation or `mkdir -p`;
- directory deletion, directory rename/move, copy, or cross-volume behavior;
- file overwrite, restore, rollback, transaction, or recovery journal;
- untracked/dirty/special-file mutation;
- generic filesystem, shell, process, or Git authority;
- automatic staging, commit, branch/ref/history mutation, checkout, switch,
  reset, clean, stash, merge, rebase, fetch, pull, push, or network Git;
- network MCP or Streamable HTTP;
- PluginManager installation, download, arbitrary executable selection,
  automatic restart, or uncertain-effect replay;
- profile editing, discovery, watching, hot reload, or silent authority
  changes in a live runtime;
- persistence of credentials, authority objects, reviewed commit authorization,
  native Codex threads, or stale runtime state;
- version, dependency, accepted-ADR, release-tag, or release-metadata changes
  in the roadmap task itself; and
- Linux live-certification claims.

- Task 183 — implement the private core policy and deterministic fixture tests.
- Task 184 — integrate host composition, Trusted Profile admission,

- Task 185 — harden cross-platform deterministic tests, evidence redaction, and

  Codex pair and disposable fixture.

If Task 181 finds that safe one-directory creation cannot be proven on the
supported path model, stop this sequence and select a different researched
milestone; do not broaden it into recursive creation.

## 13. Release recommendation

An eventual v0.15 release should require:

- an accepted new ADR with explicit non-goals and no changes to ADRs 0010–0018;
- deterministic core, policy, bridge, composition, and Desktop tests covering
  all preconditions, races, identity checks, outcomes, and no-replay rules;
- evidence that no generic filesystem, process, shell, Git, network, or profile
  authority was added;
- exact canonical Tool advertisement and redacted observability;
- clean release-derived baseline and unchanged release tag;
- Windows live evidence using the exact certified Codex 0.149.0 executable pair,
  one bounded effect, exact postconditions, and no replay;
- Ubuntu/Linux deterministic test/CI evidence recorded without a Linux live
  certification claim;
- `cargo fmt --check`, `cargo check --workspace`, `cargo test --workspace`,
  `cargo clippy --workspace --all-targets --all-features -- -D warnings`, and
  `git diff --check` passing in the release task; and
- exact-head CI PASS for the final release commit before publication.

## 14. Alternatives deferred

Restore is deferred because its destructive replacement and source-baseline
choices need a dedicated authority model. Branch creation may be lower risk
than switching, but both are durable ref work and neither blocks current local
coding; switching is additionally a worktree/generation operation. Session
workflow persistence is valuable but transcript persistence already exists and
safe checkpoints require a separate schema/lifecycle review.

Network MCP is deferred because it is a network security milestone, not merely
an adapter transport. PluginManager is deferred because lifecycle ownership is
more than the current configured-provider adapter. Trusted Profile reload is
deferred because dynamic authority must not silently alter a connected model’s
effective capabilities. Directory creation is therefore the single selected
v0.15 milestone: it has the clearest current workflow blocker and the smallest
credible authority expansion.
