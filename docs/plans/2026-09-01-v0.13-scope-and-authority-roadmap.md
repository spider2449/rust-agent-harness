# Task 157 — RAH v0.13 Scope and Authority Roadmap

**Research and roadmap only.**

## Decision

**RECOMMENDATION: Bounded Repository Structural Authoring, beginning with
tracked-file deletion.**

**NEW AUTHORITY REQUIRED: YES.** The next milestone must establish a distinct,
host-owned deletion authority before any implementation begins. The expected
research output is a proposed additive **ADR 0017 — Bounded Repository File
Deletion Authority**; its final title and exact contract are deliberately left
to Task 158.

v0.13 should not reinterpret or broaden ADR 0010, ADR 0011, ADR 0012, ADR
0013, ADR 0014, or ADR 0016. In particular:

```text
RepositoryWorktreeMutationPolicy
    != RepositoryFileCreationPolicy
    != RepositoryFileDeletionPolicy
    != RepositoryMutationPolicy
    != RepositoryCommitPolicy
```

`PermissionLevel::Execute` may be an outer dispatch gate if that remains
consistent with the existing architecture. It is not deletion authority.
Trusted Profile may compose an already-approved deletion capability into a
fresh `ToolRegistry` under ADR 0011, but the profile itself cannot manufacture
the authority.

remain documented observability gaps, not claims this roadmap upgrades.

## Product question

v0.12 demonstrates that RAH can perform the bounded local edit, review, and
commit workflow. The v0.13 question is therefore:

> What remaining capability most materially limits an ordinary local coding
> workflow, and what is the smallest additional host-owned authority needed to
> remove that limitation?

The assessment prefers capabilities that strengthen the certified local
repository workflow without introducing generic filesystem, process, Git,
credential, remote-ref, or network authority.

## Selected scope: one bounded deletion

The first product capability should allow the model to request deletion of one
explicit repository file through a narrow host-owned Tool, bound to the selected
symbolic repository and the current runtime/generation. Its intended workflow
composition is:

```text
model requests bounded deletion
-> Rust authority validation
-> one native deletion attempt
-> repository state observation
-> Desktop repository refresh
-> human Stage/Unstage
-> staged review
-> human Authorize
-> existing repo.commit
```

Deletion neither stages nor commits. The existing human Stage / Review /
Authorize boundary remains unchanged. It must not become generic filesystem
authority, generic Git, or an implied deletion-plus-commit workflow.

Deletion closes a material ordinary-coding gap: obsolete modules, tests,
configuration, adapters, and dead source cannot currently be removed through
the bounded workflow. It is the smallest remaining structural mutation.

### Why rename/move follows deletion

Rename/move is not deletion with improved UI. It combines removal of a source
pathname with allocation of a destination pathname, parent and collision rules,
partial-effect semantics, Windows case-only rename handling, and stronger
source/destination identity revalidation. It must not be implemented by
composing independent creation and deletion calls. After deletion receives
deterministic and Windows live evidence, separate research should decide whether
a native single-operation primitive has sufficiently strong containment,
identity, collision, and post-observation semantics.

## Conservative deletion research direction

Task 157 does not fix a Tool ABI. Task 158 should begin from a conservative
one-file contract: delete exactly one existing, HEAD-tracked regular file only
when its identity and expected source state are freshly validated. The preferred
initial source-state rule is a clean HEAD-tracked regular file, or an
equivalently strict expected-preimage rule. A file containing unreviewed human
work must fail closed rather than be silently discarded.

The Task 158 research contract must assess all of the following:

- repository-relative target only, bound to the selected repository and current
  runtime/generation;
- no absolute or repository-escaping path, `.git`/metadata target, wildcard,
  glob, directory, recursive deletion, or generic arbitrary filesystem target;
- no symlink, junction, reparse-point, alias, or submodule-boundary traversal;
- no staging, branch/ref/history mutation, model-selected Git argv, or commit
  authority;
- strict HEAD/index/worktree eligibility and preimage/staleness protection;
- immediate pre-effect revalidation and an explicit deletion commit point;
- exactly one native deletion attempt, with deterministic post-effect
  observation and bounded/redacted results;
- a result taxonomy that distinguishes known refusal/no effect, verified effect,
  known failure, and uncertain effect as justified by the researched primitive;
- no automatic retry, replay, rollback, or recovery assumption after a possible
  effect;
- preservation of unrelated user work; and
- native Windows unlink behavior, file-type restrictions, race limits, and
  review/refresh invalidation consequences.

The resulting authority must explain the exact preimage identity mechanism,
Windows native unlink semantics, post-effect verification, uncertainty rules,
and deterministic test requirements. It must preserve the shared mutation lease
and fail closed if external changes or unsupported identity observations prevent
proving the authorized outcome.

## Explicitly deferred authority

### Verification execution

Build/test/verification has high utility, but it is not repository read
authority. Build scripts and tests can execute repository-controlled code,
spawn children, mutate files, access environment state, and potentially use the
network. RAH presently claims neither OS sandboxing nor network isolation.

A future verification capability needs separate research for closed executable
identities, fixed and bounded argv, cwd/environment policy,
repository-code-execution consequences, resource limits, supervision, network
expectations, and uncertain-effect handling. v0.13 must not obtain this
functionality through `shell.exec`, `process.exec`, or model-selected commands.

### Remote Git and publication

Branch switching/creation, push, fetch, pull, remote ref mutation, credentials,
and pull-request publication remain outside the initial v0.13 scope.
`repo.commit` remains ADR 0016's message-only, reviewed, one-shot operation.
A successful local commit does not imply authority to publish it. Publication
needs its own research for remote identity, network/credential authority,
remote-ref mutation, and uncertain external effects.

### Other non-goals

The initial v0.13 scope excludes generic filesystem writing, generic
shell/process execution, generic Git, automatic staging, automatic commit
authorization, binary staged-content authorization, branch/ref/history
management, remote Git publication, credential management, network MCP
completion, profile hot reload, OS sandbox claims, network-isolation claims,
rollback guarantees, directory/recursive deletion, and rename/move
implementation.

## Validation direction

Windows remains the first live-certification platform unless equivalent new
platform evidence is gathered. Future live deletion validation must durably
persist the exact Tool label and `ToolRequested` / `ToolStarted` /
`ToolFinished` counts that any milestone claims. This is a forward-looking
observability requirement; it does not retroactively repair the Task 151 gaps.

Deterministic validation must cover stale-state rejection, repository identity
change, aliases and reparse/symlink cases, submodule boundaries, failure before
and after the deletion commit point, no replay after possible effects,
unrelated-work preservation, cleanup, and exact repository observations.
Normal workspace tests must remain offline and credential-free.

## Recommended milestone sequence

```text
Task 157 — v0.13 scope and authority roadmap (research only)
-> Task 158 — bounded repository file deletion authority research (research only)
-> proposed ADR 0017 / reviewed exact deletion contract
-> narrow deterministic implementation
-> Trusted Profile / Generic Tool Bridge composition
-> Desktop bounded-authoring integration
-> deterministic hardening
-> Windows live Codex validation
-> milestone audit
-> release preparation
```

Do not begin deletion implementation until the authority contract has been
reviewed and accepted. Do not broaden the milestone into rename, generic
filesystem mutation, generic process execution, or remote Git because deletion
proves successful.

## Expected next task

**Task 158 — Bounded Repository File Deletion Authority Research**

Task 158 is research only. It must define the smallest safe host-owned
authority for deletion of one repository file, including source-state
eligibility, repository/path identity, preimage/staleness protection, native
Windows effect semantics, deletion commit point, post-effect verification,
failure/uncertainty taxonomy, no-replay rules, Trusted Profile composition,
Desktop refresh/review interactions, deterministic tests, and the proposed ADR
0017 boundary. It must not implement Rust or product changes.

## Task 157 boundaries

This task adds only this roadmap. It does not create ADR 0017, change accepted
ADRs, add a Tool, alter Trusted Profile/Generic Tool Bridge/Desktop behavior,
change production code, dependencies, version, release tag, certified Codex
