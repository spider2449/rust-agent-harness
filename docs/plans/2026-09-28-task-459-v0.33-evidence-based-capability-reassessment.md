## 2. Observation A — repository selection while Chat appeared ready

### Source trace

The relevant source is `crates/rah-desktop/src/main.rs` and
`crates/rah-desktop/frontend/status.js`:

- Backend connection state is `ConnectionState::{NotConnected, Connecting,
  Connected, Disconnecting, Error}` (`main.rs`, `ConnectionState`). Chat
  state is separately `ChatState::{Idle, Running, CancelRequested}`.
- `send_chat` reserves `ChatState::Running` in `DesktopAppState::start_chat`.
  On normal completion, the backend claims the terminal result, commits the
  assistant response, emits `ChatEvent::Completed`, then exits the event loop
  and calls `finish_claimed_chat`, which clears the active chat and sets
  `ChatState::Idle` (`main.rs`, `start_chat`, `run_chat`,
  `finish_claimed_chat`). Failure and cancellation also emit terminal events
  and subsequently finish the claimed chat unless uncertain repository
  effects require retaining model ownership.
- For each runtime execution, `rah-runtime-codex` starts a Codex thread and
  turn, records their provider IDs with a RAH `SessionId`, and accepts
  notifications only for that matching thread/turn (`runtime.rs`,
  `thread/start`, `turn/start`, `event_stream`). A matching
  `turn/completed` first clears the provider session's active-turn ID, then
  maps the provider status to RAH `Completed`, `Cancelled`, or `Failed`.
  Desktop separately tracks `ActiveChat { generation, runtime, session_id,
  terminal }`; its `ChatState` remains `Running` until Desktop finishes
  terminal publication. Provider turn completion, Desktop terminal ownership,
  and frontend ready presentation are therefore distinct state sources.
- The frontend's “Chat ready” text is computed from the published connection
  status and its local `chatRunning` flag. A terminal `chat_event` sets
  `chatRunning = false` and reloads status (`status.js`, `loadStatus`,
  `handleChatEvent`). It does not read backend `ChatState` directly.
- `choose_repository` and repository-member activation both require
  `repository_selection_allowed(ChatState::Idle)` **and**
  `repository_selection_allowed_for_connection`. The latter permits only
  `NotConnected` or `Error`; it rejects `Connecting`, `Connected`, and
  `Disconnecting` with `FrontendError::RepositoryBusy` (`main.rs`,
  `choose_repository`, `capture_activation_transaction`,
  `repository_selection_allowed*`). The host invocation coordinator also
  rejects a `ModelTurn` or `HostRunning` operation.
- On the frontend, the active-member activation control is blocked when the
  connection is `connected`. The separate “Choose repository” button is
  disabled for connecting/disconnecting or local `chatRunning`, but **not**
  for `connected` (`status.js`, `loadStatus`,
  `updateRepositoryMembershipControls`). The Rust command still rejects it.
- The `repository_busy` message is “Repository selection is unavailable while
  chat is running” (`status.js`, `errorMessage`). The same backend error is
  used for an active chat and for a connected runtime, so that message does
  not identify which guard rejected the request.

### Reconstructed lifecycle and contradiction

The intended repository-selection path is:

```text
NotConnected -> Connecting -> Connected
Connected + ChatState::Idle -> repository selection rejected by connection guard
Connected + normal turn -> ChatState::Running
terminal event -> frontend may show Chat ready
backend terminal cleanup -> ChatState::Idle
Connected + ChatState::Idle -> repository selection still rejected by connection guard
Disconnect -> Disconnecting -> NotConnected
NotConnected + ChatState::Idle -> repository selection/switch allowed
Connect -> Connecting -> Connected with the selected repository composition
```

Thus **yes**, Chat can display “Chat ready” while repository selection is
unavailable. The ordinary, stable combination is a connected runtime with
`ChatState::Idle`: “Chat ready” describes whether another chat turn can be
sent, while repository selection additionally requires the runtime to be
disconnected. The chooser remains clickable in that state and its generic
error incorrectly attributes the rejection to a running chat.

There is also a source-level post-terminal interval in which the frontend can
receive `Completed` before `finish_claimed_chat` changes backend chat state to
`Idle`. Cleanup follows an asynchronous uncertain-effect check, and the code
can retain model ownership when an external repository effect is uncertain;
in that path backend `ChatState` can remain non-idle after the UI has changed
to Chat ready. Task 458 preserved no command/result timing or backend-state
trace proving that this path occurred. It is not needed to explain why the
connected-state guard rejects repository selection.

### Disconnect and Connect

`disconnect_codex` checks that `ChatState` is already `Idle`; it returns
`ChatAlreadyRunning` otherwise. It then shuts down the connected runtime and
provider activation and publishes `ConnectionState::NotConnected`. It does
not clear or reset chat state. `connect_codex` constructs and publishes a
fresh runtime composition from the currently selected repository and current
configuration. Therefore a successful Disconnect followed by repository
selection and Connect matches the existing lifecycle contract. It is not
evidence that reconnect repairs a stale chat flag, nor that a provider restart
capability is missing.

Task 458 did not preserve enough event-level detail to prove which exact guard
returned the particular rejection. Source establishes, however, that the
connected-state guard is expected by design and that the frontend affordance
and error text misrepresent it. Normal switching is already supported for one
active repository at a time and requires the runtime to be disconnected
(ADR 0027; Task 322; current `choose_repository` and activation guards).

**Observation A classification: UI DEFECT; A3 — INTENTIONAL LIFECYCLE
CONTRACT; USER EXPERIENCE DEFECT.** The incident does not prove an existing
chat-currentness bug or a missing switching capability. The concrete
maintenance defect is the enabled chooser and misleading `repository_busy`
message while connected. A bounded reproduction using existing
instrumentation can record connected status, the Chat-ready UI, chooser
result, successful Disconnect, and chooser result while disconnected. A
successful Disconnect itself checks backend `ChatState::Idle`, but frontend
status does not expose that state at the earlier chooser attempt and
`repository_busy` does not identify its guard. No live reproduction was run
and no instrumentation was added. Exact transient-currentness proof would
require a separate narrowly scoped diagnostic task.

## 3. Observation B — Remembered Workspaces location control clipping

Task 458 records that the location editor extended past its content area and
clipped the left side of its “Choose Location” control. The source presents
the remembered entry form as a grid with padding and gaps; the containing
status card is capped at `min(100%, 42rem)` inside a centered `main` with
viewport padding. The remembered form has no explicit fixed width or
`overflow: hidden` rule, and its button is start-aligned. The location label
uses `overflow-wrap: anywhere`.

The constrained card width and nested padding leave limited content width on
narrow viewports; default intrinsic sizing for form controls and differences
in viewport/font rendering could contribute. Source inspection alone does
not establish which factor caused the recorded clipping. Task 458's normal-UI
observation is sufficient to classify the visible presentation failure, but
it did not retain viewport dimensions or computed layout to localize its CSS
mechanism.

**Observation B classification: UI DEFECT.** This is a presentation defect in
the existing descriptive Remembered Workspaces UI. Remembered entries remain
descriptive and confer no repository authority (ADR 0028). No authority or
product capability change is indicated.
