## Canonical gate mechanics

Entry point and bounded reproduction command: `& .\scripts\windows-desktop-test-gate.ps1` from this checkout, with default parameters. The script resolves the repository root from its own path, defaults its target to `target\windows-desktop-gate`, and assigns that absolute path to both `CARGO_TARGET_DIR` and `RAH_TEST_TARGET_DIR` during the run. It builds `rah-mcp-echo-server` and `rah-plugin-echo` with `cargo build -p rah-tools-mcp --bin rah-mcp-echo-server -p rah-tools-plugin --bin rah-plugin-echo`, verifies both executables in the target's `debug` directory, then launches ordinary parallel `cargo test -p rah-desktop --bin rah-desktop -- --nocapture`.

Each command is a `Diagnostics.Process` with explicit repository cwd, redirected stdout and stderr, and asynchronous copies to separate log files. The launcher synchronously calls `WaitForExit(600000)` on its **Cargo process**, not on a stream or the test binary. On normal exit it waits for both copies, returns the Cargo exit code, and records `PASS` or `TEST_FAILURE`. Helper build failure is `HELPER_BUILD_FAILURE`; a missing helper is `HELPER_MISSING`. Each stage has its own default 10-minute watchdog. On timeout, the script snapshots the Cargo PID's descendant tree (plus named processes outside that tree), calls `taskkill.exe /PID <Cargo PID> /T /F`, waits up to 30 seconds for Cargo, and would return `WATCHDOG_TIMEOUT`/124 with a null stage exit code. The script does not record a launched PID separately in `status.json`; the process snapshot identifies the root when a timeout occurs. Cleanup has no explicit exit-code classification or process-already-gone handling. A terminating PowerShell error in cleanup reaches the outer catch and records `HARNESS_ERROR`/70; this can mask the intended timeout disposition. A normal test exit never invokes `taskkill`.
