# Task 212 — RAH v0.18 Scope and Authority Roadmap

## Result

explicitly host-selected Trusted Profile source path across Desktop restarts,
restore it only as inert configured intent, and require a fresh explicit
Connect/reconnect operation before any provider is activated or any effective

**ADR:** not required. This is a lifecycle and host-preference change inside

hot reload, model-visible profile selection, credential persistence, or a
branch/Git milestone. Task 212 authorizes no implementation and does not start

## Remaining product gaps

The remaining gaps are intentionally different authority planes:

1. Desktop does not remember the selected Trusted Profile source path. The
   useful safe subset is inert preference restoration, not authority restore.
2. A bounded local branch/ref workflow is absent. Creating a branch, switching
   branches, and creating-and-switching have different effects.
3. Directory subtree rename/move and directory deletion are absent; neither is
   a safe generalization of file rename or file deletion.
4. Stage/Unstage are host-owned by design. Making them model-visible would
   remove an intentional human review boundary.
5. Profile hot reload and dynamic provider replacement are absent and require
   revocation/currentness semantics beyond static selection.
6. Network MCP/Streamable HTTP, credentials/OAuth, and provider installation or
   update are absent and are materially broader authority features.
7. Task 120 remote llama.cpp successful-generation/transport-confinement proof
   remains **DEFERRED / NOT VALIDATED**.
8. Linux live certification for existing live-provider behavior is absent;
   deterministic Linux CI evidence is not the same claim.
9. The known Windows Git foreign-owner diagnostic fixture remains technical
   debt, not a demonstrated v0.17 product defect.
10. Task 207's model-selected external Tool execution limitation remains an
    external evidence gap. Repeating the same 0/0/0 experiment or upgrading
    Codex without new evidence is not a product milestone.

## Authority baseline

The accepted architecture keeps these planes separate:

```text
observation
  != bounded worktree content mutation
  != file creation/deletion/rename
  != directory creation
  != index mutation
  != reviewed commit/history mutation
  != branch/ref mutation
  != checkout/HEAD/worktree transition
  != remote/network Git
```

ADR 0011 makes a Trusted Profile a host-owned composition boundary. A profile
can describe already host-approved capability composition; it cannot create
authority from model output, provider metadata, a Tool definition, a frontend
button, or `PermissionLevel::Execute`. Existing ADRs 0012–0019 deliberately
make worktree content, file creation, multi-file edit, commit, deletion,
rename, and directory creation separate. ADR 0016 explicitly rejects branch
creation and switching as part of reviewed commit authority.

Every existing mutation follows the same security shape: host-selected
repository and executable, fixed argument policy, bounded input/output,
repository identity and generation checks, a shared RAH mutation lease where
applicable, immediate revalidation, sanitized results, and no automatic
replay after a possible effect. Timeout, cancellation, disconnect, crash, or a
lost response never implies rollback.

For the selected milestone, the new state is only a persisted host preference.
The following must remain distinct after restart:

```text
remembered profile path
  != statically validated selection
  != effective provider composition
  != runtime-advertised Tool set
  != current executable/provider session
  != per-operation authorization
```

## Candidate analyses

### A. Bounded branch creation / switch workflow

The three A variants must not be collapsed into “Git permission”. RAH has no
branch or checkout Tool today; the absence is confirmed by the `rah-tools`
exports and by ADR 0016's explicit exclusions.

**A1 — create branch only.** This would create exactly one new ordinary local
branch under `refs/heads/`, pointing to one host-captured exact current commit,
without changing `HEAD`, the current branch, the index, or worktree files. A
dirty worktree need not be rejected merely because this effect does not read
or change dirty content; the UI must say that the branch starts at `HEAD` and
does not absorb uncommitted changes. For a conservative first contract, reject
bare repositories, linked-worktree ambiguity, special merge/rebase/sequencer
states, detached `HEAD`, and unborn `HEAD`. A valid ordinary attached branch
and an existing commit are required.

The branch name must be host-validated as one logical branch name and then
bound to exactly `refs/heads/<name>`. Reject empty names, path traversal and
`.`/`..` components, `..`, control characters, `@{}`, leading `-`, trailing
dot/space, unsupported Git ref syntax, tags, remotes, arbitrary namespaces,
and names that collide with any existing ref. There is no overwrite, force,
rename, delete, tracking configuration, remote operation, or model-selected
start point. Namespace collisions fail before the one native attempt.

The host must capture the selected repository identity, repository generation,
current attached branch, exact current commit, target absence, and the
relevant refs/index/`HEAD` observations. It must revalidate immediately before
one fixed native ref-creation attempt. Verified success means the new local ref
points to the captured commit, current `HEAD` and worktree/index state remain
unchanged, all pre-existing refs remain unchanged, and any expected new reflog
state is classified as part of the bounded effect. A timeout or ambiguous
native result is uncertain; RAH must observe, never retry, delete, or roll back
the new ref automatically.

This is a useful but incomplete branch workflow. It gives the host a safe
“prepare a branch here” operation while avoiding checkout. It does not switch
the active worktree, and therefore does not claim that future model edits are
on the new branch. It is technically feasible on Windows and Linux with a
fixed native Git argument vector or an equivalent narrowly constrained native
primitive, but it is not the selected v0.18 milestone because it introduces a
new persistent ref authority for only a preparatory step.

**A2 — switch to existing branch.** This is a different authority:
`RepositoryCheckoutOrBranchSwitchPolicy`. It changes symbolic `HEAD`, the
worktree materialization, and possibly the index. The first useful contract
would need a host-selected existing `refs/heads` branch, no branch creation,
no detached target, no remote/ref guessing, no linked worktrees, no sparse or
special Git state, a clean index and clean worktree including untracked-file
policy, and a no-overwrite/no-conflict checkout operation. Detached or unborn
current state should fail closed in v1. A no-op switch to the current branch
must be classified explicitly rather than treated as a hidden effect.

After a successful switch, repository context is still the same root but
branch identity and worktree content context have changed. The host must
invalidate repository-bound action selectors and reviewed commit
authorization, refresh the repository snapshot, and require a fresh runtime
publication/reconnect. Existing conversation persistence is keyed by the
repository context fingerprint, not a branch namespace; A2 therefore needs a
branch-aware conversation namespace or a deliberate “no Resume across branch
switch” rule before it can be product-complete. Provider composition would
need to be torn down or marked stale and rebuilt on explicit reconnect.

Windows and Linux can test a narrow clean checkout, but native checkout has a
larger partial-effect and filesystem race surface than A1. A timeout after
checkout may leave `HEAD` changed, files changed, locks present, or the result
ambiguous. No rollback or automatic switch-back is allowed. A2 is valuable and
should be researched separately, but is not a one-release follow-on to inert
profile persistence.

**A3 — create-and-switch.** A3 combines two distinct effects: creating a new
ref and changing `HEAD`/the worktree to it. It needs both authority classes,
two effect manifests, conflict rules, and explicit semantics when ref creation
succeeds but checkout does not. It must not compensate by deleting the new
branch or switching back after uncertainty. It is therefore not a shortcut
for A1 or A2 and is deferred beyond v0.18.

The model should not own any A variant directly in the selected roadmap. A
future host-only UI workflow may be considered first. `PermissionLevel::Execute`,
`repo.commit`, Stage/Unstage, file or directory mutation, Trusted Profile
selection, provider metadata, and runtime advertisement do not imply branch
creation or checkout authority. If A1 is later selected, it requires a new ADR
and a new narrow policy; A2 would require a separate ADR/policy, not reuse A1.

### B. Bounded directory rename / move

Directory movement is a new structural tree mutation, not an extension of
`RepositoryFileRenamePolicy`. A defensible candidate would move one clean,
HEAD-tracked subtree to an absent destination beneath an existing ordinary
parent, with no overwrite and no symlink, junction, mount, or Windows reparse
traversal. Source and destination parents must be distinct validated ordinary
directories as appropriate, and cross-volume movement must fail before effect.

The host would need a deterministic preimage manifest of every entry, type,
relative path, identity, and relevant Git/index/tree state. It must decide what
to do with untracked children, ignored files, empty directories, nested Git
repositories, submodules/gitlinks, and reparse points. The safe v1 answer is
to reject any subtree containing untracked/ignored children, nested repository
or submodule boundaries, unsupported entry types, or an empty/untracked-only
tree whose Git meaning cannot be stated. A native directory rename can be one
same-volume effect, but that does not make cross-volume or partial observation
reversible, and a per-file fallback would be a materially different multi-
effect authority.

The operation would require its own authority, a new ADR, repository
generation/currentness checks, review invalidation, bounded postimage
verification, and no rollback/replay. It has real refactor value but a broad
TOCTOU and partial-effect surface on both platforms. Existing file rename,
directory creation, deletion, Execute, and commit authority do not imply it.
Defer it.

### C. Bounded directory deletion

Git does not track empty directories. Empty ordinary directory deletion has
some narrow value as cleanup, but it is destructive and largely invisible to
Git status/diff. It would still be a new `RepositoryDirectoryDeletionPolicy`
because directory creation and file deletion do not imply it. It must reject
non-empty targets, links, junctions, reparse points, nested repositories,
submodules, and aliases, and make exactly one native removal attempt with
conservative uncertainty.

Clean tracked-subtree deletion is more useful but must account for every
tracked and untracked child, directory identity, path count, index/tree
preimage, and native recursive-effect failure mode. Recursive deletion is
explicitly rejected: it would approach generic recursive filesystem removal,
has high destructive breadth, and cannot provide rollback. Neither variant
beats the selected restart UX for v0.18. Empty-directory deletion is LATER;
tracked-subtree deletion is a later research item, and generic recursive
deletion is REJECT FOR NOW.

### D. Model-visible Stage / Unstage

Desktop already has host-owned Stage/Unstage actions backed by the existing
index-mutation policy. They use host-bound targets, fixed Git arguments, a
shared repository lease, pre/post snapshots, and generation-aware ephemeral
action IDs. The model-visible Tool set does not need this convenience to
complete the existing workflow because the human review step is intentional.

Making staging model-visible would not merely add a button. It would transfer
selection of staging scope and timing into an untrusted model request, affect
partial staging, deletion/rename staging, index locking, and the exact staged
snapshot later eligible for reviewed commit. It would need a new model-facing
index authority contract or a security decision to widen ADR 0010. It would
also make provider composition and Tool advertisement part of a sensitive
review boundary. The model cannot be allowed to manufacture reviewed commit
authorization by staging and then supplying a commit message.

The correct v0.18 disposition is **KEEP STAGE/UNSTAGE HUMAN-OWNED**. Host
frontend actions may continue to present and invoke them; the frontend is not
authority. Provider metadata, Execute, `repo.commit`, and Trusted Profile
composition do not grant model staging authority.

### E. Trusted Profile persistence / auto-restore

This is the selected gap because v0.17 shipped the valuable Desktop external
provider composition path but deliberately leaves profile selection process-
local. The narrow safe feature is:

- persist only an explicit host preference identifying the selected profile
  source path, in a closed app-owned preference record;
- on startup, restore at most an inert remembered/configured presentation;
- optionally perform only bounded static source validation, which is already
  non-spawning, while treating missing, replaced, malformed, or inaccessible
  sources as stale/unavailable inert state;
- never persist a loaded `TrustedStaticProfile`, provider child, ToolRegistry,
  credentials, tokens, live endpoint session, authority object, reviewed
  commit authorization, or runtime connection;
- require an explicit host Connect/reconnect to reload the current profile from
  disk, resolve current resources, activate providers, compose a fresh
  registry, and publish Tools; and
- clear the preference on explicit clear, with failed persistence reported as
  a bounded host warning rather than silently changing authority.

This is missing today, has no new authority breadth, and can be tested without
Codex, paid credentials, a live provider, internet, or GPU. It is reversible
preference state. Stale executable/profile identity is handled by explicit
fresh validation at Connect; startup must not turn a remembered path into
effective authority. No profile hot reload is implied.

The profile generation must distinguish a restored inert selection from a
freshly selected or changed profile. A profile file replacement, stale source,
or explicit clear must invalidate the configured selection and any dependent
effective/advertised/current state. A successful explicit Connect still owns
provider activation and fresh publication. No reviewed commit authorization is
restored. This uses the existing Trusted Profile boundary and requires no ADR.

### F. Trusted Profile hot reload / dynamic authority

Hot reload is substantially different from persistence. Watching a profile
file while Desktop runs creates dynamic authority replacement, possible
provider revocation, partial provider activation, stale Tool snapshots, and
concurrency with running model turns. The design would need a source-change
generation, atomic replacement of effective registry and provider ownership,
revocation of old runtime advertisement, explicit behavior for in-flight Tool
calls, failure handling for partial replacement, and fresh currentness checks.

Observation of a changed file could be a safe informational feature, but
automatic activation or replacement is not. Profile persistence must not be
combined with hot reload. Hot reload needs a new authority/lifecycle ADR and
is LATER.

### G. Network MCP / Streamable HTTP

Network MCP would add endpoint, DNS, proxy, redirect, TLS peer identity,
origin/effective destination, OAuth/token, credential storage, streaming,
body/response limits, reconnect/retry, and uncertain external-effect rules.
The existing ADR 0015 bounded model-provider endpoint authority does not prove
network MCP destination confinement and must not be cited as such. RAH must
not claim network isolation.

This has ecosystem value but is a broad network authority milestone with high
external nondeterminism and weak live-certification independence. It is not a
transport-only extension of local stdio MCP and does not fit with the selected
preference milestone. LATER, with a dedicated authority/security research
task and ADR if pursued.

### H. Process Plugin manager / install / update

The current Process Plugin path activates a host-selected local executable and
owns its bounded lifecycle. Discovery, download, install, update, version
pinning, signature/hash verification, binary placement, replacement, and
rollback/recovery would create a materially broader supply-chain and local
filesystem authority. Installing an executable is not equivalent to executing
an already host-selected executable.

The manager would need durable lifecycle state, interrupted-install semantics,
identity and signature policy, safe destination rules, update authorization,
child replacement, and platform-specific executable handling. Provider
metadata cannot request or grant installation. This is REJECT FOR NOW as a
v0.18 milestone and must not be smuggled into profile persistence.

### I. Task 120 / remote llama validation

Task 120 remains a longstanding validation/security-debt item. It asks whether
remote llama.cpp generation and transport behavior can be validated; it does
not by itself provide a new user-facing RAH capability. Existing endpoint
configuration is bounded at the input surface, but that does not prove
redirect, proxy, DNS, peer identity, or effective-destination confinement.

Revisiting it would require actual supported remote generation evidence,
careful distinction between readiness and generation, and no unsupported
network-isolation claim. It depends on an external server/model and is not a
deterministic local milestone. Classify as TECH-DEBT / LATER, not v0.18.

### J. Cross-platform live certification

Linux deterministic CI is valuable and should continue to exercise RAH-owned
contracts. It is not Linux live Codex/provider certification. Actual live
provider certification additionally needs a supported runtime/model path,
credentials or fixture policy, complete lifecycle evidence, and platform
cleanup proof. Windows remains the project’s later live-certified platform;
Linux live external-provider certification is not established.

Linux live parity can improve assurance for selected v0.18 preference behavior
only as a release validation item, but it does not create a user-facing
milestone or new authority. LATER.

### K. Windows Git fixture hardening

The known failure at
`crates/rah-desktop/src/main.rs:6438`,
`tests::hardened_git_environment_requires_host_pinned_safe_directory_for_foreign_owner_diagnostic`,
is a pre-existing Windows/Git foreign-owner diagnostic fixture portability
issue. Task 208 recorded focused reproduction and the authoritative exact-head
CI was green; no v0.17 production regression was found.

It should become a focused maintenance task that states its supported Git and
environment assumptions, or replaces the fixture with a stable equivalent. It
has no product authority or profile interaction and is TECH-DEBT, not the v0.18
milestone.

### L. Codex dynamic Tool-selection limitation

Task 207B already compared the certified `0.149.0` baseline with
`gpt-5.6-terra` and `gpt-5.6-sol`, and research-only `0.153.4` with Terra.
The tested combinations remained `0/0/0`; no host exact/required Tool forcing,
relevant protocol incompatibility, or RAH defect was found. The hardened gate
correctly failed closed at `ToolRequested=0`.

There is no new evidence in Task 212. Do not choose “upgrade Codex”, do not
repeat the same failed selection experiment, and do not weaken the hidden
nonce/lifecycle gate. Re-certification is permitted only after a supported
production path supplies new positive evidence. REJECT FOR NOW as a v0.18
milestone; preserve the external limitation verbatim.

## Selected v0.18 milestone

RAH v0.18 should deliver **inert Trusted Profile selection persistence and
explicit restore** for Desktop.

The user-facing behavior is:

```text
explicit host profile selection
  -> persist only bounded preference/path intent
  -> restart
  -> show remembered configured/inert state
  -> explicit host Connect
  -> reload and validate current source
  -> activate providers and compose fresh effective registry
  -> advertise only the fresh current publication
```

At every earlier point, no provider executable is started and no provider Tool
is usable. If the source path is missing, changed, replaced, invalid, or
unreadable, the restored state is stale/unavailable and fails closed. The user
must explicitly reselect or correct it. A successful profile reload still
does not connect by itself.

The milestone does not remember “active providers”. It remembers a host
preference that can be used to present or statically validate the next
explicit selection. The effective composition is always reconstructed from
current disk contents and current host resource identity.

## Why this beats the alternatives

This milestone closes the most immediate post-v0.17 friction: the feature that
v0.17 just made useful must not require the user to rediscover the same profile
path after every application restart. It improves usability for MCP and
Process Plugin users without relying on model behavior, external provider
execution, or a live network.

A1 branch creation is narrower than branch switching but leaves the user on the
old branch and introduces a persistent ref authority for a preparatory step.
A2/A3 provide more Git value but require worktree/currentness/conversation
semantics that do not fit one small release. Directory tree and Stage/Unstage
changes carry greater mutation or review risk. Hot reload and network/plugin
management are lifecycle or external-authority expansions. Linux live parity,
Task 120, the Windows fixture, and the Codex limitation improve assurance or
resolve external evidence but do not close a comparable product workflow.

The selected feature is independently certifiable on both platforms with a
small deterministic state machine and does not make any unsupported live
provider-execution claim.

## Required authority boundary

No new authority is required. The existing authority boundary remains:

```text
Trusted Profile preference
  -> inert configured host state
  -> explicit host composition
  -> provider-specific admission/lifecycle policy
  -> fresh ToolRegistry
  -> runtime advertisement
```

The preference is not an authority object and cannot be used as one. Existing
authorities that explicitly do **not** imply profile persistence or activation
are:

- `PermissionLevel::Execute` and all existing Tools;
- repository observation, worktree/file/directory mutation, index mutation, and
  reviewed commit authority;
- local MCP or Process Plugin execution authority;
- the Codex runtime or dynamic Tool advertisement;
- frontend state and UI selection;
- provider metadata, provider identity, or a remembered path; and
- conversation persistence or Resume.

No new policy, Tool, public protocol field, or capability is authorized by
Task 212. If implementation discovers that path persistence would implicitly
restore effective authority, the selected scope is violated and work must
stop for a new authority decision.

## Model / host / frontend ownership

| Plane | v0.18 ownership and contract |
| --- | --- |
| Host-only | Preference storage location, closed schema, source path handling, source identity/staleness checks, profile generation, static validation, provider activation, registry construction, provider cleanup, and currentness. |
| Frontend host action | User explicitly chooses, reselects, clears, or Connects. The UI may display remembered/stale/inert state and warnings, but cannot grant, activate, or compose authority. |
| Model-visible Tool request | None. The model cannot select a profile, persist one, activate providers, or request profile reload. |
| Trusted Profile | Remains a host-owned composition input for current explicit activation. The persisted preference is not a profile capability declaration and does not widen the schema. |
| Runtime advertisement | No advertisement occurs for an inert remembered selection. Only a fresh successful composition may be advertised, and currentness still requires repository/model/profile/connection/publication generation agreement. |
| Per-operation authorization | Explicit Connect/reconnect is the host operation that may activate current provider composition. Any later Tool call still passes normal ToolRegistry and host policy checks. |

## Security invariants

The implementation sequence must preserve all of the following:

- Configured, Effective, Advertised, and Current remain distinct.
- Remembered path state never restores a provider child, ToolRegistry, runtime,
  credential, token, endpoint session, or reviewed authorization.
- Startup is non-spawning. Profile source validation remains bounded and
  static; provider activation occurs only during explicit Connect/reconnect.
- A missing, stale, replaced, malformed, or inaccessible profile fails closed.
- Current profile contents and executable/provider identities are revalidated
  at explicit activation. A path string is not an identity proof.
- Provider metadata cannot grant or escalate permission. The model cannot
  create or activate a profile. Frontend presentation is not authority.
- No profile watcher, background reload, automatic reconnect, automatic
  provider restart, or model-facing profile selection is introduced.
- Repository selection remains host-owned and canonical. Profile persistence
  cannot select or replace the Desktop repository.
- Conversation Resume never restores profile/provider/runtime authority.
- Failed persistence is not treated as a successful preference update, and a
  preference write cannot partially publish effective authority.
- Provider shutdown remains owned and explicit. Uncertain external effects are
  not replayed or represented as rolled back.
- No OS sandbox, network isolation, rollback, or absence of ambient provider
  effects is claimed.

## Deterministic validation strategy

The selected milestone needs deterministic tests, not a live model. Tests must
cover:

1. Empty/default startup has no remembered profile and no provider activation.
2. Explicit selection persists only the closed preference record and loads it
   after a simulated restart.
3. Startup restoration performs zero provider executable spawns, zero provider
   handshakes, zero ToolRegistry external publication, and zero runtime
   advertisement.
4. A remembered existing profile is presented as configured/inert and requires
   explicit Connect before effective composition.
5. Missing, unreadable, malformed, replaced, and stale source files produce a
   bounded stale/unavailable state and no activation.
6. Explicit Connect reloads current source contents, rejects stale resource or
   executable identity, and publishes only an all-or-nothing fresh registry.
7. Clear removes the preference and invalidates the profile generation; it
   cannot leave an old effective provider composition current.
8. Profile selection changes and reconnects use fresh generations and never
   revive old provider children or old proxy Tools.
9. Restart never restores conversation, repository, model, Tool, provider,
   commit, or index authority merely because a profile path was remembered.
10. Preference storage has bounded size, closed fields, duplicate/unknown-key
    rejection, atomic write behavior, cleanup of temporary files, and bounded
    failure warnings consistent with existing Desktop preferences.

Tests should use the existing provider fixtures and spawn counters, not paid
credentials, a live model, internet, or GPU. The test contract must assert
that no provider process starts before explicit Connect.

## Live-validation strategy

No live model or provider execution is required to certify the selected
milestone. Optional Desktop manual/live validation may demonstrate that a user
can restart, see an inert remembered profile, and explicitly Connect, but it
must not claim model-selected external Tool execution. Any provider lifecycle
evidence remains subject to Task 207's hidden nonce and complete lifecycle gate.

The release gate should record deterministic startup/no-spawn and explicit-
Connect evidence first. A live model completion, an advertised Tool, or a
provider marker alone is not evidence that a provider Tool executed.

## Cross-platform considerations

The preference path and record must use the existing app-owned Desktop storage
policy, bounded UTF-8 serialization, closed schema, atomic replacement, and
platform-safe path handling. A path is host configuration, not model input.

Windows must preserve the existing absolute-path, link/junction/reparse,
profile-source identity, executable identity, and cleanup rules. The known
foreign-owner Git fixture is unrelated to this preference milestone and stays
separate.

Linux should receive deterministic persistence, malformed/stale-source, and
no-spawn tests. Those tests are not Linux live Codex/provider certification.
No platform-specific provider activation or network claim is added. If a path
identity behavior cannot be proven consistently on a platform, startup should
retain inert stale state and require explicit re-selection.
