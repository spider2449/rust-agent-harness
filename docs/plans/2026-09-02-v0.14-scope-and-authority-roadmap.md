# Task 168 — RAH v0.14 Scope and Authority Roadmap

**Research and roadmap only.** This document selects a candidate v0.14
capability. It does not authorize Rust, Cargo, dependency, version, ADR
implementation, authority, Trusted Profile, Generic Tool Bridge, Desktop, or
live-validation changes.

## Decision

**RECOMMENDATION: bounded repository rename/move of one tracked file.**

**NEW AUTHORITY REQUIRED: YES, subject to dedicated research and an accepted
ADR.** Rename/move is a persistent structural worktree effect with two bound
pathnames and a distinct collision, identity, and uncertain-effect contract.
It must not be obtained by composing `repo.delete-file` and
`repo.create-file`, or by broadening any existing mutation, Execute, index,
Git, filesystem, or process authority.

The recommended v0.14 headline is deliberately narrower than a general
refactoring engine: one explicit source file to one explicit destination file
in the selected repository, with host-owned exact source preimage and
destination nonexistence bindings, no implicit staging, and no commit.

## Current product and authority state

RAH can read repository/workspace files, perform bounded content edits, create
one bounded repository file, edit a bounded set of existing files, delete one
eligible clean HEAD-tracked file, inspect status/diffs, stage and unstage
through separate host-owned authority, and perform a separately reviewed
repository commit. These capabilities compose through the host-owned Trusted
Profile and the ordinary `ToolRegistry`/Generic Codex Tool Bridge path. The
Desktop selected-repository workflow binds repository context and refreshes
host-owned state after authoring.

The authority planes remain separate:

```text
observation
  != worktree content replacement
  != file creation
  != multi-file content editing
  != file deletion
  != index mutation
  != commit/history mutation
```

`PermissionLevel::Execute` is only an outer dispatch gate. Model requests,
provider metadata, Tool descriptions, frontend state, and Trusted Profile
configuration cannot create authority. MCP and Process Plugin providers adapt
into `Tool`; they do not own RAH authorization. The Generic Codex Tool Bridge
translates and dispatches registered capabilities but cannot broaden them.

The v0.13 live deletion evidence is strong product evidence: one public
`repo.delete-file` request/start/finish, verified target deletion, unchanged
sentinel/index/HEAD/refs/history, no replay, and the certified Windows marker.
The CRLF/raw-byte attempt correctly failed closed. Its evidence helper still
has non-blocking technical debt: `tool_finished.result` can be `null` when a
JSON ToolContent result is not captured.

## Unresolved product gaps

The bounded local authoring loop still lacks a structural operation for moving
an existing file while preserving its content and review boundary. This
blocks ordinary rename-driven work such as module reorganization, source-file
renames, test moves, and configuration path changes. A user can approximate a
move as create plus delete, but that loses the semantic one-operation contract,
requires a second path authority, and creates an unsafe opportunity for
partial or mismatched content handling.

Other gaps remain intentionally outside this decision: configured provider
install/enable/update lifecycle, remote MCP/Streamable HTTP, durable
workflow-state improvements, dynamic profile reload, bounded directory
creation, broad repository-aware refactoring, and observability cleanup.

### Rejected pressure toward generic authority

Generic `fs.rename`, generic `fs.write`/`fs.unlink`, generic shell/process
execution, model-selected Git commands, automatic staging, and automatic
commit are not candidates. They would collapse distinct authority planes and
would contradict the accepted architecture and ADR contracts. A
repository-aware refactoring engine is also not a safe shortcut: bundling
multiple content mutations and a move would create a transaction and rollback
expectation that RAH does not currently claim.

## Recommended capability boundary

The follow-on research should test whether the following v1 contract is both
useful and provable; it is not yet an authorization to implement it.

- Exactly one explicit logical repository-relative source and one explicit
  logical repository-relative destination.
- Both paths bind to the host-selected canonical repository and current
  runtime/generation. Native paths, absolute paths, traversal, globs,
  metadata, aliases, unsupported normalization, and repository escapes fail
  closed.
- The source is one eligible clean HEAD-tracked regular file with an exact
  host-captured preimage, including the relevant HEAD/index/worktree identity,
  raw bytes, SHA-256, and byte length.
- The destination is freshly proven absent and its parent chain is validated
  as the intended real directory beneath the repository. Existing files,
  directories, links, junctions, reparse points, nested repositories,
  submodules, and ambiguous aliases fail closed.
- The operation is one host-authorized native move attempt. It does not call
  generic filesystem APIs through a model-facing surface, invoke Git, stage,
  alter the index, commit, alter refs/history, or publish remotely.
- The contract must explicitly classify pre-effect refusal, known no effect,
  verified move, known failure, and uncertain outcome. After the native effect
  commit point, timeout, cancellation, disconnect, crash, or lost observation
  is not interpreted as rollback and must never trigger automatic retry or
  replay.

This boundary needs dedicated research before naming a tool. The research must
resolve whether a single native rename operation can provide adequate
post-observation on both platforms, how source/destination identity is
revalidated under the shared repository mutation lease, and what partial
effects are possible if the destination parent or filesystem crosses an
unsupported boundary.

## Security and authority analysis

Rename/move is a new persistent worktree authority because it removes one
directory entry and allocates another. It is not deletion plus creation: two
independent calls cannot prove that the destination contains the exact source
preimage or that a gap between calls is safe. It must not reuse
`RepositoryFileDeletionPolicy`, `RepositoryFileCreationPolicy`,
`RepositoryWorktreeMutationPolicy`, `RepositoryMultiFileMutationPolicy`,
`RepositoryMutationPolicy`, or `RepositoryCommitPolicy` as a grant.

The host must own source/destination canonicalization, repository and Git
identity, runtime/generation binding, exact preimage capture, destination
nonexistence, final revalidation, effect attempt, and postcondition
observation. Trusted Profile may later compose only an already-constructed
rename authority through a closed symbolic binding. It may not select raw
paths, create the authority, relax its limits, revive it after restart, or
combine it with deletion/creation to manufacture a move.

Main failure and security cases include stale source bytes, source replacement,
destination creation or collision, parent replacement, path traversal,
`.git`/metadata targeting, symlinks, junctions, Windows reparse points,
hard-link ambiguity, case-equivalent aliases, submodule/nested-repository
boundaries, detached/unborn or unsupported Git states, external edits, native
sharing failures, and an observer that cannot prove the final state. The
operation must preserve unrelated work and retain uncertainty rather than
claim rollback. A later attempt requires fresh host observation and new
authorization.

## Platform and integration implications

Windows has the highest immediate proof burden. Research must cover native
handle/path identity, reparse-point rejection, Unicode normalization and
case-only rename behavior, same-directory versus cross-directory moves, open
handles/sharing violations, and exact post-effect disappearance/appearance.
Case-only rename must not be treated as a harmless string change: the source
and destination may be case-equivalent under Windows while Git records a
case-sensitive logical path. The initial scope should either define a tested
two-step native case-only procedure with one effect contract or refuse it;
silently relying on checkout configuration is insufficient.

Ubuntu/Linux deterministic tests should cover the same logical contract,
symlinks, inode replacement, collision, and uncertain observation paths.
Windows remains the only live-certification target for the eventual milestone;
Linux live certification is not established. No transport confinement, OS
sandbox, network isolation, or race-free guarantee should be claimed.

Desktop integration should remain selected-repository and Rust-owned: after a
verified move it refreshes repository observations and invalidates stale
presentation/review state as appropriate. Human Stage/Unstage and the existing
one-shot reviewed `repo.commit` boundary remain unchanged. Persistence must
not restore move authorization or an in-flight effect.

Generic Bridge integration should use the ordinary ToolRegistry route and a
canonical public name, with any Codex alias private and run-specific. Bridge
lifecycle evidence must capture the canonical request and sanitized result,
including JSON content, but observability repair remains separate from the
authority decision. MCP and Process Plugin status remains composition-only:
neither provider type receives rename authority from its metadata.

## Explicitly deferred alternatives

- Provider/plugin installation, update, executable replacement, enable/disable
  persistence, and marketplace/discovery management. A management-only
  restart/reconnect slice may be researched later, but it must not become
  model-controlled installation or generic process authority.
- Network MCP and Streamable HTTP until Task 120's endpoint, redirect, proxy,
  DNS, TLS/peer identity, credential, SSRF, reconnect/retry, and uncertain
  request questions have a separately accepted confinement decision. Task 120
  remains **DEFERRED / NOT VALIDATED**.
- Durable workflow authorization, commit review, deletion, edit, staging, or
  move replay. Display restoration is not authority restoration.
- Dynamic profile reload until generation/revocation and active-call behavior
  can be proven without stale capability use.
- Directory creation, recursive operations, arbitrary untracked moves, branch
  or ref mutation, remote Git, credentials, generic Git, generic filesystem,
  shell/process execution, and OS/network sandbox claims.
- A multi-file rename-aware refactoring primitive. It may be reconsidered only
  after the single-move contract has evidence and a separate compound
  authority research decision.
- The `ToolContent::Json` evidence capture fix as a small non-blocking cleanup;
  it should be scheduled independently and must not define the v0.14 product
  headline.

## Proposed task sequence

```text
Task 168 — v0.14 scope and authority roadmap (this document)
-> dedicated bounded repository rename/move authority research
-> proposed ADR for the exact one-source/one-destination contract
-> reviewed ADR acceptance
-> narrow deterministic implementation
-> deterministic hardening, including Windows case-only and reparse cases
-> Trusted Profile composition
-> Generic Codex Tool Bridge integration and evidence correction where scoped
-> Desktop selected-repository integration and refresh/invalidation
-> Windows live validation using certified codex-cli 0.149.0
-> v0.14 milestone audit
-> release preparation
```

Each arrow is a separate authorization boundary. No implementation should
start merely because this roadmap recommends the capability. If research
cannot establish a safe, deterministic single-operation contract, v0.14
should remain docs/research-only or select a smaller non-authority improvement
rather than broaden existing authorities.
