# v0.5 scope and authority roadmap plan

Status: Completed research; no implementation authorized
Date: 2026-08-22

## Scope

Define the recommended RAH v0.5 product/security scope after v0.4.0 without changing Rust code, Cargo manifests, protocol DTOs, permissions, profile fields, accepted ADR status, Codex baseline, or release version.

## Method

1. Preserve the released v0.4.0 authority-composition baseline and inspect ADRs 0010 and 0011, release/security documentation, and current relevant policy/session source.
2. Inventory existing None, Read, Execute, index-mutation, and trusted-profile composition authority classes separately from deferred worktree, history, network, lifecycle, and isolation classes.
3. Compare safe worktree mutation, commit, repository-aware editing, session persistence, network MCP, plugin lifecycle, and profile reload by product value, fit, risk, complexity, testability, Windows reliability, authority delta, network/credential dependency, and release scope.
4. Decide one primary product direction; compare write and patch forms; keep restore, index, and history authority separate.
5. Define the required ADR, crate placement, sequencing, deterministic/live verification expectations, Windows evidence, technical debt, and deferrals.

## Decision

Recommend v0.5 focus on a new private repository-worktree content-mutation policy and a bounded conditional text-editing capability, provisionally called `repo.patch`. It is more useful for the coding workflow than destructive Git restore and more controllable than generic `fs.write`.

The new authority requires a new ADR before implementation. It belongs in `rah-tools`, must not broaden ADR 0010's index-only `RepositoryMutationPolicy`, and must be hardened before trusted-profile composition. Commit/history, network MCP, plugin lifecycle, hot reload, generic process authority, and rollback guarantees remain deferred.
