## 2. Established architecture that remains fixed

The following architecture is a fixed input to the v0.27 decision:

- RAH remains an orchestration and harness system, not an inference engine.
- Codex remains an optional `AgentRuntime` adapter.
- `Tool` and `ToolRegistry` remain the single RAH extension boundary.
- Built-ins, MCP providers, and Process Plugin providers adapt into RAH-owned
  Tools; providers do not own RAH authorization.
- Trusted Profile remains a trusted host authority-composition boundary.
- Model output, provider metadata, Tool definitions, Tool inputs, and
  frontend state are untrusted requests or presentation data, never
  authorization.
- Missing explicit external permission fails closed. Execute permission is
  not generic filesystem, shell, process, Git, network, or credential
  authority.
- Repository authorities remain separate: observation, bounded worktree
  mutation, index mutation, and reviewed commit/history mutation.
- Timeout, cancellation, disconnect, crash, or lost response does not prove
  that an external effect did not occur. Uncertain effects are not replayed.
- Process supervision is not an OS sandbox claim, and no network-isolation or
  rollback guarantee is implied.

v0.26's accepted ADR 0027 composition is also fixed:

```text
explicit human repository admission
  -> process-local descriptive membership
  -> zero or one explicit active repository
  -> fresh active-only DesktopRepository and ToolRegistry
  -> existing repository-bound Tools, policies, tickets, index, and Commit
     authorities
```

There is no union registry, parallel active repository authority,
model-selected repository, provider-selected repository, workspace-wide
mutation route, or cross-repository Tool input. A repository switch withdraws
old currentness and requires fresh composition. Restart restores zero
repository authority.

## 3. v0.26 product gaps and nonclaims

### Established product value

v0.26 now provides one coherent Desktop workflow: a human can admit A and B
within one process, keep B inert, explicitly switch A to B and back, and use
only the active repository's fresh composition. The Windows host-driven
authority/effect plane and real Codex process lifecycle passed Task 324-C-R4.

### Product gaps

Two deliberate management gaps remain:

1. Repository membership is process-local, so a restart loses the A/B catalog
   and requires fresh admission.
2. There is no member-removal control. An unwanted inactive member remains in
   the process-local catalog until it is removed by a future feature or the
   process ends.

The restart cost is medium product pain for users who repeatedly work across
the same repositories. Removal is low-to-medium product pain and is not
repository deletion: it would mutate only host membership state. Neither gap
prevents the released A/B workflow.

### Required nonclaim

```text
MODEL-SELECTED DYNAMIC TOOL DISPATCH NOT ESTABLISHED UNDER THE APPROVED GPT-5.6-TERRA LIVE GATE.
```

Task 324-A proved that a real approved Codex/model turn could complete while
producing zero RAH dynamic Tool lifecycle. Task 324-B correctly classified
that as an external/generic model-selection block, not an authorization or
RAH Tool-bridge failure. Task 324-C-R4 proved the host-driven route instead;
it did not convert the missing model-selected behavior into a PASS.

Other retained nonclaims are no persisted authority restoration, no active
parallel repositories, no cross-repository mutation, no generic shell or
process authority, no automatic Git history operation, no network Git, no
rollback/replay guarantee, and no OS sandbox or network-isolation claim.

## 4. Candidate A analysis - Codex dynamic Tool compatibility / runtime baseline refresh

### User problem and value

The core agent workflow is more useful when the model can select an advertised
RAH Tool and receive its result without a host-only workaround. This is a
high-value product problem in principle and would occur in many agent turns
if the path were reliable. It is visible in v0.26 evidence, but only as a
nonclaim: the approved live combination did not produce a dynamic Tool call.

Today the safe workaround is host-driven invocation through the real
active-only Desktop ToolRegistry and deterministic fake-transport bridge
coverage. That workaround proved authority and effects, but it does not give
the model the intended model-to-RAH Tool usability.

### Current official protocol comparison

The current [official Codex App Server documentation](https://developers.openai.com/codex/app-server)
describes:

- bidirectional JSON-RPC 2.0-style communication over default stdio JSONL;
- one `initialize` request followed by `initialized`;
- an `experimentalApi` capability gate for experimental fields and methods;
- `dynamicTools` on `thread/start` as an experimental field;
- the model-selected lifecycle `item/started` with a `dynamicToolCall`, then
  server request `item/tool/call`, client content response, and
  `item/completed`; and
- current `thread/resume` behavior that restores persisted dynamic tools when
  new definitions are not supplied.

The released RAH adapter and its captured `0.149.0` contract already do the
following for bridge mode: opt into `experimentalApi`, snapshot the
host-supplied registry at thread creation, translate incompatible public
names to private aliases, parse and correlate `item/tool/call`, and route the
request through RAH permission/policy/currentness checks before dispatch.
The local deterministic tests cover the captured dynamic definitions,
request correlation, denial, replay, cancellation, and registry dispatch.

The comparison establishes protocol continuity at the conceptual boundary;
it does not establish wire-schema identity across versions. The current
documentation's added resume persistence is not evidence that `0.149.0`
should be changed, nor does it explain why the approved model selected zero
Tools. No concrete adapter defect, deprecated field, removed API, or required
new authority was found in this research. A future version could still
change schemas or lifecycle details and must be checked against generated
schemas before adoption.

### Tractability verdict

Candidate A is not currently a tractable RAH-owned release capability. The
remaining failure is model/runtime/service behavior unless a later controlled
comparison identifies a concrete supported protocol mismatch. RAH cannot
guarantee that an untrusted model chooses a Tool, and repeated prompts until
one call occurs would be certification by luck. A newer installed Codex
(`0.154.0` was present in the ambient environment) is not the certified
baseline and was not used.

If later research finds a documented compatibility correction, it can be
implemented without new RAH authority: model requests remain untrusted,
ToolRegistry dispatch and host policy remain mandatory, and existing
repository/currentness and capability-specific checks remain unchanged. If
the result depends only on model routing or account/service availability,
RAH must report the limitation rather than promise a product guarantee.

### Compatibility shortcuts explicitly rejected

Candidate A cannot be made tractable by enabling generic shell, generic
process execution, Codex-owned filesystem mutation, `code_mode_host`, browser
or computer-use authority, model-selected executable/argv/cwd/env, weaker
permissions, or a different model chosen because it happened to call a Tool
in one sample. Those are different authority surfaces and do not repair
dynamic RAH Tool compatibility.

### Boundary classification

| Dimension | Candidate A |
| --- | --- |
| New executable authority | No, if it is protocol compatibility only |
| New durable trust source | No |
| Cross-process authority | No |
| Network authority | No new RAH authority; upstream service remains an external dependency |
| Credential boundary | No new RAH boundary |
| New mutation class | No |
| New lifecycle owner | No, existing adapter ownership remains sufficient |
| New currentness generation/domain | No, existing thread/turn/registry/currentness applies |
| New Tool schema | No, existing RAH definitions are translated at the adapter edge |
| New PermissionLevel | No |
| New Trusted Profile semantics | No |
| HostExplicit eligibility | No; remains exactly 11 |
| ADR impact | No for a pure correction; possibly additive research if upstream changes the contract |

## 5. Candidate B analysis - durable remembered multi-repository workspace

### User problem and value

Candidate B removes the most visible cost of the released multi-repository
workflow: repeated admission of the same A/B set after every Desktop restart.
The problem is frequent for users with stable repository pairs and is directly
visible in the v0.26 product shape. It improves Desktop continuity and
workspace management while preserving the primary agent workflow. It has a
simple safe workaround today - fresh admission - but that workaround is
repetitive rather than protective.

The release theme is coherent: remembered workspace candidates make the new
multi-repository Desktop workflow durable without making it executable across
restart. The feature must not silently become automatic repository authority.

### Safe conceptual contract

```text
persist bounded descriptive candidate
  -> restart
  -> candidate visible but inert
  -> explicit human fresh re-admission
  -> fresh root/.git/Git identity verification
  -> new process-local member identity and generation
  -> explicit activation
  -> fresh active-only authority composition
```

Persisted data may contain a closed schema version, an opaque descriptive
workspace ID, bounded display/user labels, ordering, an optional
privacy-approved location hint, availability state, and an optional
last-active descriptive hint. It must never persist or reconstruct a
`DesktopRepository`, `ToolRegistry`, provider/runtime state, HostExplicit
ticket or preparation, Commit authorization, Stage/Unstage action, live
generation as currentness, filesystem/.git/Git identity proof, credentials,
or uncertain-effect continuation.

Automatic startup re-admission remains forbidden. A remembered path is a
private location hint, not proof of repository identity and not consent to
compose authority. Fresh human admission must revalidate canonical root,
root filesystem identity, supported `.git` form and identity, Git executable
identity, ordinary-worktree status, nested boundaries, alias/duplicate rules,
and all applicable policy. Successful re-admission creates a new
process-local member identity and fresh generations.

### Storage, privacy, and reconciliation requirements

The design phase must define:

- a closed, versioned, size-bounded schema and unknown-field behavior;
- whether absolute/native paths are opt-in, how they are displayed, and how
  they are protected under the normal user-account at-rest boundary;
- atomic write ordering, temporary-file handling, synchronization, corruption
  quarantine, truncation behavior, and migration policy;
- startup reconciliation for moved/deleted/replaced roots, changed `.git`,
  changed Git executable, case-equivalent aliases, duplicate candidates,
  changed nested relationships, removable/offline media, and inaccessible
  locations;
- privacy tests that scan serialized values, errors, generic activity,
  model-visible state, and Effective Authority for sentinel paths, `.git`
  identities, filesystem IDs, credentials, and authority handles; and
- bounded UI outcomes such as remembered, unavailable, stale, or fresh
  admission required, without automatic recovery or effect replay.

The existing preferences and transcript stores must not be reused by
assumption. Their schemas and authority semantics are different. Candidate B
needs a dedicated storage/reconciliation owner and a dedicated authority
decision before implementation.

### Boundary classification

| Dimension | Candidate B |
| --- | --- |
| New executable authority | No, under inert remembered-candidate semantics |
| New durable trust source | Yes, but descriptive/private and fail-closed |
| Cross-process authority | No; restart creates zero authority and fresh admission |
| Network authority | No |
| Credential boundary | No; credentials are explicitly excluded |
| New mutation class | No repository/Git mutation; only host catalog persistence |
| New lifecycle owner | Yes, bounded storage and startup-reconciliation ownership |
| New currentness generation/domain | No new live authority domain; restart/admission epochs must be re-created fresh |
| New Tool schema | No |
| New PermissionLevel | No |
| New Trusted Profile semantics | No |
| HostExplicit eligibility | No; remains exactly 11 |
| ADR impact | Additive persistence/restart authority ADR or explicit amendment before implementation |

## 6. Candidate C analysis - explicit repository member removal

### User problem and value

Removal would let a user curate an accidental or obsolete inactive member
without restarting Desktop. It is low-to-medium frequency and low-to-medium
pain. It improves management UX, not core agent execution. v0.26 evidence
shows the absence of the control, but does not show that it blocks the A/B
workflow.

### Smallest safe scope

The only v0.27-sized version is inactive-member removal:

```text
explicit host request with opaque member selector
  -> resolve current process-local member under membership coordination
  -> reject stale/unknown/active selector
  -> remove only the inactive descriptive record
  -> advance membership generation
  -> allow later fresh admission with a new member identity
```

It must not accept a path as authority, delete repository contents, mutate
Git, affect the active repository, or use frontend membership state as the
decision. Active removal should be rejected while active and require an
explicit switch away first. Direct active removal is a different feature: it
would need atomic withdrawal of runtime/provider state, registry, conversation
namespace, HostExplicit preparations, Commit authorization, Stage/Unstage
actions, connection state, and all races with model turns, Connect,
Disconnect, activation, and index-effect reservations. A Started effect is
never rolled back or replayed.

### Boundary classification

| Dimension | Candidate C, inactive-only |
| --- | --- |
| New executable authority | No |
| New durable trust source | No |
| Cross-process authority | No |
| Network authority | No |
| Credential boundary | No |
| New mutation class | No; membership catalog only |
| New lifecycle owner | No new external owner; a membership transaction writer is required |
| New currentness generation/domain | No new domain; membership generation advances |
| New Tool schema | No |
| New PermissionLevel | No |
| New Trusted Profile semantics | No |
| HostExplicit eligibility | No; remains exactly 11 |
| ADR impact | Existing ADR 0027 is conceptually sufficient for inactive-only; active removal requires new research/design |

## 7. Candidate D analysis - durable session / conversation continuity

### User problem and value

Candidate D would make Desktop feel less disposable by restoring descriptive
conversation transcript, UI history, and an active-repository hint. It can
help users resume reasoning and reduce reorientation cost, with medium-to-high
value for long-running work. It is less directly tied to multi-repository
authority than Candidate B and partially overlaps the existing repository-
scoped conversation/transcript design.

The safe version restores context only. It must not resume a Codex runtime,
reconnect a provider, restore a ToolRegistry, rearm a ticket, revive Commit or
Stage/Unstage state, or treat a transcript's repository hint as fresh
admission. A descriptive transcript can be displayed or offered as context
only after the host has made the current repository and conversation
namespace decision.

## 8. Candidate E analysis - MCP Streamable HTTP / network MCP

### User problem and value

Network MCP would expand the provider ecosystem beyond configured local stdio
servers and could connect RAH to remote services. Its potential ecosystem
value is high, but it is not required for the primary v0.26 agent workflow.
Frequency depends on external integrations and is not established by v0.26
evidence. A local configured MCP provider remains the safe current option.

### Required trust boundary

This is not a transport-string feature. It introduces a network endpoint and
credential trust boundary that must define endpoint admission, TLS and server
identity, authentication/secret handling, redirects, DNS/IP changes,
proxy behavior, SSRF and local-network restrictions, request/response bounds,
timeouts, cancellation, reconnect, schema/tool-set changes after reconnect,
and uncertain remote side effects. Remote tool metadata cannot self-authorize,
and a disconnect cannot imply rollback or permit replay.

The design must also distinguish network authority from existing model
provider endpoint configuration. No generic outbound networking may be added
incidentally.

| New mutation class | Potentially remote side effects; RAH must admit and bound them explicitly |
| New lifecycle owner | Yes, network session/reconnect/identity owner |

## 9. Candidate F analysis - PluginManager / plugin lifecycle

### User problem and value

A manager could make Process Plugin discovery and lifecycle easier for users:
install, start, restart, update, remove, and recover configured plugins. It
could improve ecosystem usability, but current Process Plugin is deliberately
an explicitly configured hardened provider. No v0.26 evidence shows that
installation or marketplace management blocks agent usefulness.

### Required trust boundary

Installation is not process supervision. A manager would need separate
authority for source/download, provenance and signature verification, install
location, persistent configuration, version/update policy, binary identity,
restart/crash recovery, removal, and rollback semantics. Plugin metadata must
not grant its own permissions or repository access. A downloaded executable
would remain a new trusted program even if its process is supervised.

## 10. Candidate G analysis - Trusted Profile reload / dynamic authority

### User problem and value

Hot reload could reduce friction when a host administrator changes a Trusted
Profile or provider configuration. The value is operational and intermittent,
not a demonstrated block in v0.26. A controlled explicit reconnect or restart
is a workable current path.

### Required trust boundary

Reload is an authority-composition writer. The host, never a model or
provider, would need to define who initiates it, atomic replacement, profile
generation/currentness, current model turns, HostExplicit preparations,
Commit authorization, Stage/Unstage actions, registry/provider replacement,
credentials, partial startup, failure rollback of configuration state, old
provider teardown, and uncertain effects. A filesystem watcher cannot
automatically grant authority. A provider cannot request its own authority
reload.

## 11. Candidate H analysis - new HostExplicit commit or directory workflow

Candidate H contains two different proposals and must not be treated as one
generic HostExplicit expansion.

### H1 - HostExplicit `repo.commit`

`repo.commit` already has a separate reviewed repository-bound authority. It
is intentionally not HostExplicit-eligible. Making it eligible would extend a
human reviewed history mutation into a new invocation workflow, including
exact staged-snapshot review, branch/parent identity, commit identity, hooks,
native Git effect, uncertain outcome, and postcondition handling. The
existing Tool and PermissionLevel do not make this eligible by default.

User value is real for users who want a single reviewed host action, but the
history effect is high consequence and the current staged-review workflow is
the safe workaround. It would be a new HostExplicit eligibility and
lifecycle decision, not a count increase.

### H2 - HostExplicit `repo.create-directory`

`repo.create-directory` is already a separate bounded directory policy but is
not HostExplicit-eligible. The effect is structurally smaller than Commit,
but Git does not track empty directories, so user value is low and the
workflow is peripheral. The existing host action remains the workaround.

| New credential boundary | No beyond commit identity/hooks policy | No |
| New mutation class | HostExplicit history mutation is a new workflow boundary | HostExplicit structural worktree mutation is a new workflow boundary |
| New lifecycle owner | Yes, review/effect ownership | Yes, review/effect ownership |

## 14. External-dependency analysis

### Candidate A dependency split

Candidate A has four separable owners:

1. **RAH-owned adapter compatibility:** exact generated schema validation,
   version-pinned translation, experimental capability opt-in, request
   correlation, aliasing, cancellation, policy checks, and dispatch.
2. **Codex CLI/app-server behavior:** whether the certified executable accepts
   and advertises the supplied dynamic definitions and emits the documented
   request lifecycle.
3. **Model behavior:** whether the selected model chooses an advertised Tool
   in a particular context.
4. **Service/account capability:** authentication, routing, rollout, model
   availability, and upstream service behavior.

Task 324-A/B evidence establishes only that the approved combination completed
ordinary turns without selecting an RAH dynamic Tool. It does not identify
which of owners 2-4 caused the missing selection, and it does not establish a
RAH production defect. Current official documentation confirms that the
dynamic path is still experimental and supported as a documented protocol
shape, but does not guarantee model selection or account availability.

Therefore:

- a documented protocol mismatch would be a tractable compatibility
  maintenance task with no new RAH authority;
- a model/service/account limitation is not a RAH milestone guarantee;
- a different model or ambient newer Codex producing one Tool call is not
  certification evidence for the current supported baseline; and
- no repeated model probes are authorized or useful for Task 328.

### Candidate B dependency split

Candidate B is predominantly RAH-owned. The external dependencies are
Windows filesystem/path semantics and normal user-account storage behavior,
both of which can be bounded with deterministic fixtures and focused Windows
live evidence. It does not require a live model, paid credentials, remote
service, provider installation, or a new model baseline.

## 16. One strong recommendation

### Recommendation B - durable remembered multi-repository workspace

RAH v0.27 should make multi-repository Desktop membership rememberable as
bounded descriptive candidates while preserving fresh explicit admission and
active-only executable composition.

The release promise should be:

> RAH Desktop remembers which repositories the user may want to work with,
> but restart never restores repository authority. The user freshly admits a
> candidate, RAH freshly verifies its identity and boundaries, and the user
> explicitly activates it before any repository-bound authority exists.

B beats A because A's remaining product failure is not currently attributable
to a safe RAH-owned compatibility correction. It beats C because removal is
curation after admission, while persistence reduces recurring friction in the
released workflow. It beats D because D overlaps sensitive transcript
continuity and does not reopen the repository workspace without B-like
admission semantics. It beats E, F, and G because those introduce materially
larger network, program-installation, or authority-composition trust surfaces.
It beats H because neither a new HostExplicit history effect nor a low-value
empty-directory effect is required to make the multi-repository product more
useful.

### Smallest required boundary

The smallest boundary is a host-owned, closed, privacy-reviewed, descriptive
remembered-candidate store with explicit fresh re-admission. It must be
strictly below executable authority:

```text
remembered candidate != admitted member != active repository authority
```

No Tool, model, provider, profile, frontend field, persisted path, or startup
scan may bypass that separation.

## 17. ADR impact

Candidate B fits the active-only composition and descriptive membership model
of ADR 0027. It does not require an amendment to the one-active-repository,
fresh-composition, nested-boundary, HostExplicit, Commit, or Stage/Unstage
rules.

Before implementation, B requires an additive persistence/restart authority
ADR or a formally reviewed amendment that fixes:

- remembered-candidate schema and storage lifetime;
- path/privacy and at-rest handling;
- corruption, migration, atomicity, and bounded failure behavior;
- explicit fresh admission and no automatic startup re-admission;
- identity changes, moved/replaced roots, aliases, nested relationships, and
  unavailable storage; and
- the rule that no persisted value is reusable authority/currentness proof.

Task 328 does not modify ADR 0027 or create that ADR. Candidate A would need
no ADR for a pure adapter correction, but a changed upstream contract would
require dedicated compatibility research first. Candidates E, F, G, and H
would require new authority/security decisions before implementation.

## 18. Explicit deferrals

The following remain outside v0.27 unless separately authorized by new
evidence and scope:

- model-selected dynamic Tool certification by repeated prompting or luck;
- silent Codex baseline migration, model substitution, or pin changes;
- automatic repository re-admission or authority restoration at startup;
- active member removal; the first removal design, if later selected, is
  inactive-only and requires switching away first;
- durable runtime/provider/tool/registry/Commit/Stage/Unstage restoration;
- generic `fs.write`, generic shell/process execution, and model-selected
  executable/argv/cwd/env;
- workspace-wide filesystem authority, parallel active repositories, and
  cross-repository mutation;
- automatic Git history operations, network Git, rollback/replay guarantees,
  OS sandbox claims, and network-isolation claims;
- network MCP / Streamable HTTP;
- PluginManager installation, download, update, or marketplace authority;
- Trusted Profile hot reload or filesystem-watcher authority; and
- HostExplicit `repo.commit` or `repo.create-directory` expansion.

Candidate D transcript continuity is also deferred as a co-equal theme. A
small descriptive UI hint may be considered only if it is necessary to make
B understandable and is separately kept outside authority; it is not part of
this recommendation.

## 19. v0.27 milestone definition

The v0.27 milestone is READY only when all of the following are true in
design, implementation, deterministic evidence, and bounded Windows
certification:

1. A closed, versioned, size-bounded remembered-candidate schema is defined.
2. Persisted records contain only descriptive candidate data and any
   explicitly approved private location hint.
3. Startup displays remembered candidates as inert; it does not admit,
   validate into authority, activate, connect, compose, spawn, advertise, or
   restore providers/runtime state.
4. Explicit fresh admission performs current root, `.git`, Git executable,
   nested-boundary, alias, duplicate, and repository-policy validation.
5. Fresh admission creates a new process-local member identity and fresh
   generations; persisted generations and identity proofs are never reused.
6. Explicit activation creates exactly one fresh active repository composition;
   inactive remembered candidates contribute no executable registry or
   authority.
7. Moved, deleted, replaced, aliased, nested, unavailable, malformed,
   truncated, and corrupt candidates fail closed with bounded descriptive
   outcomes.
8. Atomic persistence and corruption quarantine do not silently lose the
   authority boundary or restore stale state.
9. Privacy tests scan actual sentinel values across storage, errors, generic
   activity, model-visible state, provider metadata, and Effective Authority.
10. Existing v0.26 switch, HostExplicit, Commit, Stage/Unstage, provider,
    runtime, and nested-boundary invariants remain unchanged.
11. No new Tool, PermissionLevel, HostExplicit eligibility, network authority,
    provider authority, or Codex baseline is introduced.

The milestone does not claim automatic startup re-admission, persisted
authority, currentness continuity, or model-selected dynamic Tool dispatch.
