## Existing authority and current behavior

### Underlying ADR 0013 authority

ADR 0013 is the existing underlying authority. It authorizes one host-bound,
exclusive create-new attempt for one bounded UTF-8 regular file at one
validated repository-relative path. It is distinct from existing-file content
replacement, directory creation, deletion, rename, index mutation, and
history/ref mutation.

The existing authority does not authorize or imply:

- generic `fs.write` or generic path-write authority;
- overwrite, append, or replacement of an existing path;
- parent or directory creation;
- delete, rename, or move;
- chmod, executable-bit selection, ACL selection, or permission changes;
- binary-file creation;
- Git add, Stage, Unstage, index, Commit, history, branch, or ref mutation;
- shell, process, provider, MCP, network, or arbitrary workspace authority;
- transactions, rollback, crash-atomic complete-content creation, or replay.

`PermissionLevel::Execute` is only an outer dispatch classification. Trusted
Profile composition selects symbolic host resources and constructs the
host-owned policy; it cannot manufacture authority. The Generic Tool Bridge
continues to use the ordinary ToolRegistry, permission, alias, deduplication,
cancellation, and no-replay behavior.

### Current production Tool

`crates/rah-tools/src/repository_create_file.rs` currently provides
`RepositoryFileCreationTool` with:

- public name `repo.create-file`;
- `PermissionLevel::Execute`;
- a closed Tool schema containing exactly string fields `path` and `content`;
- host-owned absolute canonical repository root and Git executable;
- a repository-scoped mutation lease;
- path, content, and serialized-request bounds;
- Git HEAD/index/ignore/submodule/sparse observations;
- path-based parent checks followed by native parent opening;
- one native create-new attempt;
- exact-content verification for `ok`;
- retained-prefix verification for `write_failed_known`; and
- no cleanup, automatic retry, Stage, Commit, or replay.

`crates/rah-tools/src/native_repository_create.rs` currently provides the
platform primitive. Unix opens existing parents with directory descriptors,
`openat`, `O_DIRECTORY`, `O_NOFOLLOW`, `O_CREAT | O_EXCL`, and requested mode
`0o600`. Windows opens parents relative to handles with reparse rejection and
uses `NtCreateFile` with `FILE_CREATE` and `FILE_NON_DIRECTORY_FILE`; this is
the current semantic equivalent of Windows `CREATE_NEW` for the final target.
The retained native parent handle prevents a pathname replacement of the
parent from redirecting the create operation in the tested race.

The focused tests and integration tests prove ordinary successful creation,
empty content, exact UTF-8 bytes, root-level and nested existing parents,
request bounds, invalid path forms, existing targets, ignored targets,
submodules, sparse checkout, intent-to-add, conflict index stages, target
races, partial-write retention, post-create uncertainty, composition, Execute
permission denial, private aliases, one bridge execution, and unchanged Git
metadata.

The prior live certification is evidence for the ordinary Trusted Profile /
Generic Tool Bridge and Codex route, not for the new Desktop HostExplicit
route. It proved one fresh Windows repository creation with exact content and
hash, untracked status, unchanged index/HEAD/refs/sentinel, one native create,
and no replay. It did not prove a human Prepare / Review / ticket-only Confirm
route.

### Current HostExplicit boundary

The current production HostExplicit allowlist is exactly:

```text
fs.read
repo.file-info
repo.status
repo.diff
repo.diff-staged
repo.create-branch
repo.patch
repo.edit-files
```

`repo.create-file` is registered in the ordinary Desktop repository registry
and classified descriptively in Effective Authority, but `host_kind` does not
accept it. There is currently no create-file HostExplicit kind, typed
preparer, review DTO, or ticket route. This research does not add any of
those.

ADR 0021 supplies the reusable HostExplicit coordinator, connected-current
composition check, exact complete `ToolDefinition` and permission D2 check,
opaque process-local ticket principles, Desktop-private provenance, and
`authorized_tool_dispatch` path. ADR 0022 supplies the single-file
`repo.patch` reviewed workflow precedent. ADR 0023 supplies the multi-file
reviewed workflow precedent. Neither ADR makes `repo.create-file` eligible.

The current `PreparedHostInvocation` retains a ticket ID, a separate activity
ID, Tool name, expected definition, ToolCall, registry, allowed permissions,
four host generations, repository fingerprint, composition identity, and a
capability-specific payload for patch or multi-file preparation. The future
create-file payload must add the creation-specific preparation and preparer
identity; it must not use generic Tool JSON or a generic filesystem preview.

### Material current-source discrepancies

The accepted ADR 0013 and core contract are the required semantic target, but
the current low-level implementation does not itself contain every binding
needed for a reviewed route. These discrepancies are recorded rather than
silently treated as solved:

1. `PreState` currently retains the target path, raw HEAD output, raw refs
   output, and raw index bytes, but not explicit reviewed parent identities,
   target negative-identity evidence, ignore/submodule/sparse observations,
   content review identity, or a capability-specific preparer binding.
2. The current policy performs fresh path checks and then opens a native parent
   handle, but it does not expose a stable parent identity record for review or
   compare an explicit retained identity at every reviewed boundary. The
   native handle is a private effect binding, not a complete HostExplicit
   review contract.
3. `symlink_metadata(&target).is_ok()` distinguishes successful metadata from
   an observed entry, but an arbitrary metadata error is treated as if the
   target were absent for that check. A reviewed route must classify inability
   to prove absence as a failed precondition, not absence.
4. The current Tool maps a generic native create error to
   `create_failed_known`, and the current Windows native function maps every
   failed `NtCreateFile` status to `AlreadyExists`. Those mappings are not
   sufficient to prove known no effect for permission, I/O, namespace, or
   unknown native outcomes.
5. The current post-success and known-partial checks verify path observations,
   regular type, link/reparse status, bytes, and Git metadata, but do not
   retain an explicit target identity proving that the observed file is the
   file created by this invocation. A reviewed route must require that
   attribution before `ok` or `write_failed_known`.
6. The current parser rejects reserved device names, but a reviewed Windows
   route should reject trailing-dot/space components as a workflow admission
   rule rather than depending on Windows alias behavior. This is a narrowing
   of the reviewed route, not a change to the underlying ADR.

These are implementation acceptance prerequisites for the future ADR and
implementation tasks. Task 269 makes no source correction.

## Closed human Prepare DTO

The human request is exactly:

```text
RepositoryCreateFilePrepare {
    path: String,
    content: String,
}
```

Its JSON representation is:

```json
{
  "path": "src/new_module.rs",
  "content": "complete UTF-8 content"
}
```

The DTO must use a closed deserialization contract equivalent to
`deny_unknown_fields`. Exactly two fields are accepted. Unknown fields,
missing fields, duplicate fields if rejected by the selected deserializer,
wrong types, and non-object input fail closed and issue no ticket.

The human supplies only `path` and `content`. The human does not supply a
repository root, native path, parent path as an authority, Git executable,
hash, byte length, file mode, permissions, ToolName, ToolInput, provider or
model metadata, permission, authority fields, expected target identity, retry
control, temporary path, ordering, Stage/Commit intent, or execution control.

The exact ToolInput is host-reconstructed from the validated DTO and contains
only the existing `repo.create-file` fields:

```json
{
  "path": "host-validated-logical-path",
  "content": "host-retained-exact-content"
}
```

The frontend cannot replace the host-reconstructed ToolInput after review.
Confirm cannot resubmit either field.

## Exact request and content bounds

The reviewed route retains the existing ADR 0013 limits and may narrow them,
but may not increase them without a later decision:

| Value | Exact bound or rule |
| --- | --- |
| Logical `path` | 1 through 1024 UTF-8 bytes, inclusive |
| `content` | 0 through 262144 UTF-8 bytes, inclusive |
| NUL | U+0000 is rejected in content and path |
| Serialized canonical request | at most 327680 bytes, inclusive |
| File count | exactly one |
| Encoding | exact UTF-8 bytes represented by the accepted Rust `String` |
| Empty content | allowed; creates an empty regular file if `ok` |
| BOM | U+FEFF, when supplied, is literal content and is preserved |
| Newlines | CR, LF, and CRLF are preserved exactly |
| Normalization | none |
| Template expansion | none |
| Append or overwrite | none |

The serialized request bound is measured over the exact canonical JSON request
used by the existing Tool parser, including JSON escaping. It is not a license
to add preparation metadata to the human DTO.

### Review-size decision

The maximum serialized complete local review is **262144 bytes (256 KiB),
inclusive**, measured after deterministic safe escaping and including all
review metadata. The process-local retained reviewed representation must fit
within the existing 512 KiB ticket-storage ceiling, but the review itself is
intentionally capped at the established 256 KiB complete-review precedent.

This bound is compatible with the current Desktop reviewed-authoring
transport precedent and keeps complete source-bearing review below the
process-local ticket ceiling. It also deliberately means that some valid
256 KiB Tool contents will not be eligible for HostExplicit review: escaping,
path, hashes, warnings, and schema metadata can make the complete review too
large. If the complete escaped content or complete serialized review exceeds
262144 bytes, Prepare returns `review_too_large` and issues no ticket.

There is no preview, truncation, ellipsis, collapsed mutation-relevant region,
or hidden editor that can still be confirmed. A review is either complete
within the bound or not authorizable.

## Logical path language

The accepted logical path is repository-relative and uses `/` separators.
Every component must be nonempty and `Component::Normal` after parsing.
The following are rejected before a ticket exists as invalid input/target:

- empty path;
- `.`, `..`, or any dot-navigation component;
- repeated separators or a trailing separator;
- NUL or backslash;
- colon or ADS/alternate-stream syntax;
- leading slash or any absolute path;
- drive-qualified or drive-relative path;
- UNC, verbatim, long-path, device, or namespace path;
- any component equal to `.git`, case-insensitively;
- Windows reserved device names `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`,
  and `LPT1`–`LPT9`, including extension and trailing-dot/space aliases; and
- any component ending in `.` or space for the reviewed Windows route.

The final trailing-dot/space rule is a reviewed-route safety restriction. It
prevents a human review from displaying one logical name while Windows
acquires another normalized name. It does not create a new authority or amend
ADR 0013.

Unicode path text is opaque UTF-8. The reviewed route performs no Unicode
normalization or case folding. It does not turn a visually similar path into
another path. Native filesystem identity and the conservative Windows alias
check govern admission. A target that is case-equivalent or otherwise
alias-equivalent to an existing Windows entry is not absent and is rejected
before authorization. Native or absolute paths are never shown in the review,
generic activity, transcript, logs, or errors.

## Parent identity and containment contract

The host derives the immediate parent by removing the final component from the
validated logical path. For a root-level path, the canonical repository root
is the parent. The human cannot select or create the parent.

Prepare must prove and retain privately:

1. the selected non-bare repository’s canonical root identity;
2. the immediate parent logical repository-relative path;
3. the canonical/native identity of the root and every traversed parent
   component, using the platform identity mechanism available to the native
   implementation;
4. ordinary-directory type for every component;
5. containment below the canonical root;
6. no symlink, junction, reparse point, mount-like redirect, or special entry
   from root through the immediate parent;
7. the parent’s existence before Prepare completes; and
8. nested Git metadata and submodule admission for every ancestor.

The parent must already exist. Missing parent is a failed precondition. No
parent creation, implicit `mkdir`, temporary parent, fallback root, or
authority-bearing parent input is permitted.

The native binding must retain a safe parent descriptor or handle through the
final create attempt. On Unix this is the existing descriptor-relative
`openat`/`O_NOFOLLOW` direction. On Windows this is the existing handle-relative
walk with reparse rejection. The reviewed route must compare retained parent
identity with immediate pre-effect observations and must reject drift before
Tool execution. A handle or descriptor is private and is not a frontend review
field.

Parent identity is not a race-free guarantee. External editors, Git, sync
software, antivirus, other processes, and privileged actors can race the
observations. The contract only requires conservative revalidation and the
native exclusive commit point; it makes no race-free TOCTOU claim.

## Target-absence and currentness contract

### Prepare absence admission

The host must observe the target as absent from every relevant namespace before
constructing the review. Absence means all of the following are true:

- no regular file at the exact logical target;
- no directory at the target;
- no symlink or broken symlink entry;
- no junction or other reparse entry;
- no special filesystem entry;
- no case-equivalent or trailing-dot/space-equivalent Windows name;
- no `HEAD` tree entry;
- no index entry at any stage;
- no intent-to-add entry;
- no unmerged/conflict index entry;
- no ignored target;
- no target that enters or aliases a submodule boundary; and
- no unsupported sparse-checkout or sparse-index state that makes absence
  ambiguous.

The host must distinguish “not present” from “metadata could not be read.” An
access, I/O, sharing, namespace, or identity error is not proof of absence.
Prepare fails closed and does not issue a ticket when absence cannot be proved.

The negative target observation is retained as a private absence binding, not
as a claim that an absent file has a file identity. The binding includes the
exact logical final component, parent identities, root identity, filesystem
observation result, Windows alias/case admission result where applicable,
HEAD/index/ignore/submodule/sparse observations, current generations, and
review identity.

### Confirm-time absence revalidation

Immediately before D2 and HostExplicit `Started`, while the repository lease
and native parent binding are active, the host revalidates:

- selected repository and Git executable identity;
- root, every parent component, ordinary type, containment, and no-link/no-
  reparse facts;
- exact target absence and case/alias absence;
- HEAD absence and every index-form absence;
- ignore, submodule, and sparse admission;
- the retained review, content bytes, content digest, and canonical ToolInput;
- the complete current ToolDefinition and current permission membership; and
- the current composition, Effective Authority, and all relevant generations.

Any drift fails before Tool execution. The host does not rewrite the review,
refresh the expected absence, issue a replacement ticket, or retry.

The final native create-new operation is the exclusive name-acquisition commit
point. No Prepare or path check can make absence race-free. A target collision
at that point must not overwrite or replace the external entry.

## Git-state contract

The reviewed route retains ADR 0013’s Git requirements:

- target absent from `HEAD`;
- target absent from the complete index, including intent-to-add and all
  unmerged stages;
- ignored target rejected;
- paths entering submodules rejected;
- unsupported sparse checkout or sparse-index state rejected;
- `.git` and linked-worktree administration rejected;
- raw index bytes unchanged;
- `HEAD` and symbolic `HEAD` unchanged;
- branch and refs unchanged;
- no automatic Git command that stages or commits the target;
- unrelated pre-existing dirty worktree state may remain admissible where ADR
  0013 permits it; and
- unrelated existing state remains protected by the existing scoped operation,
  private before/after observations, and future deterministic/live sentinels.

After a successful effect, the expected Git state is exactly one new untracked
regular file. RAH does not run `git add`, Stage, Unstage, Commit, or any ref or
history operation. The new file is not automatically included in a commit.
An ordinary worktree `git diff` need not show untracked content, so status,
file-info, and host-owned exact hash/length verification are required.

The human review should communicate that pre-existing unrelated changes may
remain and that the operation intentionally does not alter them. It should not
copy unrelated source, sentinel content, full status text, or native paths into
generic activity, transcripts, logs, or telemetry.

## Exact content and review representation

The review must show complete mutation-relevant content in a deterministic
escaped display. The display is not an alternate input and cannot be edited to
change the pending bytes.

The required display grammar is ASCII-safe and deterministic:

- CR is shown as `\\r`;
- LF is shown as `\\n`;
- TAB is shown as `\\t`;
- U+0020 space is shown as `\\u{20}`, including trailing spaces;
- backslash and quote are escaped deterministically;
- U+0001–U+001F other than rejected NUL, DEL, and other control/format
  characters are shown as `\\u{HEX}`;
- bidi controls, zero-width characters, and all other Unicode format
  characters are shown as `\\u{HEX}`;
- U+FEFF is shown as `BOM U+FEFF (literal content; preserved)` or an
  equivalent fixed escape with the same unambiguous semantics; and
- non-ASCII characters are shown by fixed `\\u{HEX}` code-point escapes so
  visually ambiguous glyphs cannot conceal a different scalar value.

The actual content remains the exact UTF-8 bytes from the human DTO. Escaping
does not normalize, decode-and-reencode differently, remove a BOM, transform
newlines, trim whitespace, expand templates, or prettify text. The review
explicitly states whether the content is empty, contains a BOM, contains CR,
LF, or CRLF, has a final newline, has tabs or trailing spaces, and contains
control, bidi, zero-width, format, or other escaped characters. The host also
derives the exact byte length and lowercase SHA-256 over the bytes that the
existing Tool will receive.

No mutation-relevant source is clipped, ellipsized, hidden, or redacted while
the ticket remains confirmable. If complete safe escaping exceeds the review
bound, Prepare returns `review_too_large` and no ticket exists.

## File attributes and platform semantics

The reviewed semantic is one ordinary regular file with no caller-selected
mode or permission change.

On Windows:

- native creation is regular-file creation through the handle-relative
  create-new primitive;
- no executable-bit claim is made;
- inherited ACLs are operating-system behavior;
- neither human nor model selects ACLs, owners, attributes, or permissions; and
- antivirus, sharing, open-handle, and external process interference remain
  possible native outcomes and are classified conservatively.

On Unix:

- the native request uses the intended non-executable `0o600` mode;
- the process umask may affect the final mode according to operating-system
  semantics;
- RAH does not add chmod authority or let the human select a mode; and
- directory-descriptor traversal and `O_NOFOLLOW` are the required current
  hardening direction, without a race-free general filesystem claim.

## Zero-effect Prepare guarantee

Successful Prepare creates a complete local review and exactly one pending
opaque ticket. It performs only bounded host observation, hashing, parsing,
identity derivation, and review construction. It performs:

- zero Tool executions;
- zero native create attempts;
- zero target-file creation;
- zero repository temporary-file creation;
- zero parent creation;
- zero worktree mutation;
- zero index, HEAD, ref, branch, or history mutation;
- zero Stage, Unstage, or Commit;
- zero model/runtime execution or lifecycle event;
- zero MCP execution;
- zero Process Plugin execution; and
- zero durable authority or ticket persistence.

Hashing, reading, Git status/metadata inspection, and identity observation are
allowed only as non-effectful host observation. If any preparation, admission,
review-size, currentness, or privacy check fails, no ticket exists. A failed
Prepare must not leave a target, parent, temporary repository artifact, or
effectful activity.

## Complete human review contract

The local review returned by Prepare must contain, at minimum, these
backend-derived fields and semantic statements:

```text
operation: repo.create-file
target_count: 1
path: complete logical repository-relative path
path_utf8_bytes: exact byte length
target_absence: currently absent from worktree and filesystem namespace
parent: existing immediate logical parent, ordinary directory, safely contained
git_preconditions: absent from HEAD and index; not ignored; no submodule/sparse ambiguity
expected_post_effect: one untracked regular file
content: complete deterministic escaped content
content_byte_length: exact host-derived length
content_sha256: exact host-derived SHA-256
content_facts: BOM/newline/final-newline/whitespace/control/format facts
file_semantics: regular, non-executable, no caller-selected permissions
effect: one exclusive create-new followed by exact bounded write
protected_non_effects: no overwrite, parent creation, Stage, Commit, index, HEAD, or ref mutation
commit_point: exclusive native create-new/name acquisition
warnings: non-atomic content, partial failure, uncertainty, no retry/replay
```

The review must additionally state:

- existing files will not be overwritten;
- the parent will not be created;
- the operation is one file only;
- creation can acquire the name before complete content is written;
- a write or flush failure can leave an empty or partial file;
- cancellation, timeout, disconnect, or crash is not rollback;
- RAH will not delete a partial result automatically;
- RAH will not retry or replay the operation; and
- RAH will not Stage or Commit the result.

The following remain private backend binding rather than human review fields:

- repository root, native paths, Git executable path, handles, and identities;
- raw HEAD/index/ref bytes and private protected-state sentinels;
- ToolCall ID, raw ToolInput, complete ToolDefinition object if not needed for
  human comprehension, permission list, registry/composition pointer, and
  Effective Authority identity;
- repository/model/profile/connection generation numbers;
- target negative-identity evidence and native parent handles;
- actual ticket value, preparer object, currentness token, and private review
  identity; and
- provider/model metadata, credentials, environment, diagnostics, or raw
  native errors.

The complete source-bearing review is available only in the bounded local
review surface needed for the human’s explicit authorization. It is not a
generic activity payload.

## Ticket and activity separation

The ticket follows the established HostExplicit contract:

- RAH-generated;
- opaque;
- process-local;
- in-memory;
- capability-specific to `repo.create-file`;
- nonserializable as durable authority;
- exact-preparation and currentness-bound;
- single-use;
- valid for an inclusive five-minute TTL boundary; and
- discarded on restart, disconnect, cancellation, expiry, stale state, or
  recomposition.

The ticket binds the exact path/content preparation, complete review identity,
repository and parent/absence evidence, ToolDefinition, ToolInput, registry,
permission, Effective Authority, composition, preparer, repository/model/
profile/connection generations, and relevant Git observations. Confirm accepts
only:

```json
{"ticketId":"opaque-ticket-value"}
```

Cancel accepts only the same ticket identity according to the existing
coordinator contract. It cannot accept content, path, hash, Tool JSON, or
authority fields. A wrong, expired, duplicate, cancelled, stale, or activity-ID
value is rejected and cannot restore or replace the ticket. The coordinator
consumes a valid ticket before asynchronous Confirm revalidation; it remains
consumed on every post-consumption failure.

The generic activity ID is a separately generated RAH value. It is not the
ticket, is not derived from the ticket, cannot Confirm, and cannot Cancel.
The activity ID is correlation metadata only.

Task 263’s value-level privacy correction is mandatory: checking only field
names such as `ticketId` is insufficient. Future tests must place a distinctive
ticket sentinel in the actual ticket value and prove that the value is absent
from activity under alternate keys such as `invocationId`.

## Review privacy model

Complete source content is permitted only in the bounded local Prepare response
and the process-local pending review needed for the human decision. It must not
enter:

- generic `HostActivityEvent` or generic HostExplicit activity history;
- conversation messages, model context, or transcript persistence;
- persisted session text, browser storage, or restart/resume state;
- generic Tool activity or provider metadata;
- logs, tracing, telemetry, crash diagnostics, or live-evidence JSONL; or
- raw error strings.

Generic activity for this route may contain only bounded non-authority
metadata, such as source `host_explicit`, operation name, a separately
generated activity ID, lifecycle state, safe result class, target count, and a
safe logical path or opaque target label where the established presentation
policy permits it. It must exclude the ticket value, content sentinels,
complete content, escaped content sentinels, raw ToolInput, raw ToolOutput,
native/absolute paths, parent native identities, provider diagnostics, and
content SHA-256 if source-sensitivity policy excludes it from generic
activity.

The local review may show the complete logical path and content SHA-256 because
they are required for the human’s bounded decision. That does not authorize
copying them into generic activity or persistence. The frontend renders all
review and result values as untrusted text nodes; it does not infer authority,
construct raw Tool JSON, persist the review, or accept a native path.

## Confirm-time currentness and D2

Ticket-only Confirm follows this exact order:

```text
ticket-only Confirm
 -> consume single-use ticket
 -> creation-specific revalidation
 -> current Effective Authority and eligibility revalidation
 -> D2 exact definition and permission revalidation
 -> HostExplicit Started
 -> authorized_tool_dispatch
 -> ToolRegistry
 -> existing repo.create-file Tool
 -> ADR 0013 RepositoryFileCreationPolicy
```

Before D2 and `Started`, all of these must still match the preparation:

- connected-current selected repository and canonical root identity;
- host-selected Git executable identity;
- complete `ToolDefinition`, including name, description, schema, and
  permission;
- current `PermissionLevel` membership;
- ToolRegistry identity and composition identity;
- Effective Authority identity, source classification, repository binding, and
  capability-specific preparer identity;
- repository, model, Trusted Profile, connection, and relevant repository
  generations;
- review/preparation identity and complete content binding;
- every parent identity, ordinary type, containment, and no-link/no-reparse
  fact;
- target still absent from filesystem namespace, aliases, HEAD, and every
  index form;
- ignore, submodule, and sparse admission; and
- retained HEAD/index/ref/protected-state assumptions.

Name-only equivalence is insufficient. A changed description, schema,
permission, registry, composition, Effective Authority, repository, parent,
target, generation, or content binding fails closed before Tool execution.
No frontend Effective Authority snapshot is trusted as dispatch authority.

D2 must receive the current registry, current allowed permission policy, exact
expected ToolDefinition, exact host-created ToolCall, and existing ToolContext.
It must re-resolve the current public name, compare complete definitions, check
permission membership, and only then authorize ordinary ToolRegistry execution.

There is no direct `Tool::execute`, direct filesystem open/write from Desktop,
generic registry shortcut, frontend-native write path, model/runtime
substitute, or live-test-only mutation substitute.

## Native commit point and effect claims

The native mutation commit point is the final exclusive name acquisition:

- Unix: `openat` with `O_CREAT | O_EXCL` and no-follow parent/target behavior;
- Windows: the semantic `CREATE_NEW` operation, currently implemented through
  handle-relative `NtCreateFile` with `FILE_CREATE` and a non-directory target.

Before the commit point, a refusal can be known to have created no RAH target
only when the native operation was not entered. At the commit point, the target
name may be acquired. Writing, flushing, closing, and verifying the complete
content happen after name acquisition. The complete content operation is not
atomic and is not a crash-atomic publication.

After the commit point, HostExplicit may claim only what is proven by the
identity-backed native and post-observation evidence. It may not claim that a
timeout, cancellation, disconnect, crash, or lost result rolled back the file.

## Exact six result classes

The existing ADR 0013 result set remains exactly:

```text
ok
invalid_target
precondition_failed
create_failed_known
write_failed_known
uncertain
```

The reviewed route must not import `repo.edit-files` result names such as
`failed_known_no_effect` or `partial_effect` into this capability.

| Result | Commit point | Proven effect | Human-safe presentation | Refresh | Ticket |
| --- | --- | --- | --- | --- | --- |
| `invalid_target` | Not reached | No RAH create when proven; malformed DTO/path/content is rejected before ticket | Bounded invalid input/target category and safe logical path only | Not required | No ticket on Prepare failure; consumed if an already-started Tool returns a proven invalid result |
| `precondition_failed` | Not reached | No RAH create when all preconditions are observed to fail before native create | Safe precondition category; do not expose native diagnostics | Optional descriptive observation | No ticket on Prepare failure; consumed after Confirm |
| `create_failed_known` | Not reached/acquisition not obtained | No RAH-created target, proven by native failure plus post-observation/identity evidence; external target is not changed | Known no-effect collision/create refusal; never say that arbitrary I/O failure was harmless | Optional status refresh | Consumed; no automatic retry |
| `write_failed_known` | Reached | This invocation acquired a new target; its identity and bounded partial bytes are proven, while complete write failed | State only proven partial metadata and that the new target is retained; never claim complete content | Required descriptive refresh | Consumed; no delete, cleanup, continuation, or replay |
| `uncertain` | Unknown or possibly reached | Effect may be absent, empty, partial, or complete; identity/result/post-observation is insufficient | Unknown effect; inspect manually; no claim of absence or rollback | Required when connected/current, without upgrading the result | Consumed; no retry, replay, second create, or rollback |
| `ok` | Reached | Exact new regular-file effect verified | One created untracked regular file with exact safe path, length, and hash | Required descriptive refresh | Consumed; no Stage or Commit |

The result classification is capability-specific. Host activity state may map
these classes to `ToolCompleted`, `ToolError`, or
`PossibleEffectUnknown`, but it must retain the six-class meaning in the local
human result and must never present a generic ToolOutput as an authority token.

## Known write failure

`write_failed_known` is allowed only when all of the following are proven:

- the exclusive create-new operation returned successful name acquisition;
- the newly acquired target identity is retained or otherwise identity-backed;
- the observed target is an ordinary regular non-link/non-reparse file under
  the same safe parent/root binding;
- the target is attributable to this one ticket and native attempt, not merely
  a same-named external file;
- the bounded observed bytes are readable and their length is known;
- the observed bytes are only a proven prefix or otherwise proven bounded state
  of the exact requested bytes;
- the relevant parent, root, HEAD, index, refs, and protected observations
  remain valid; and
- no evidence requires a stronger claim than the proven partial state.

The partial file is retained. There is no automatic delete, rollback,
continuation, retry, replay, or second create attempt. Deleting it would
require separate deletion authority. A partial result is not a completed
source publication and must not be reported as `ok`.

The current low-level implementation’s path-only partial verification and
over-broad native error mapping are not sufficient evidence for this reviewed
classification. Future implementation work must add or reuse a proof that
binds the created target identity and distinguishes known no-effect native
failure from unknown native outcome.

## Uncertain outcome

`uncertain` is mandatory for a lost native result, failed post-observation,
contradictory identity, parent/root drift after possible acquisition, timeout,
cancellation, disconnect, crash, write/flush uncertainty, or any state in
which the host cannot prove the exact result.

Unknown effect remains unknown. The route must not infer absence from a missing
path after a lost result, infer success from a matching file without retained
identity, or infer rollback from cancellation or timeout. It must not retry,
replay, delete, continue a partial write, restore state, or issue a second
create attempt. The ticket remains consumed. A descriptive refresh may show
current observations, but it cannot convert an uncertain effect into a new
authorization or silently upgrade it to `ok`.

## `create_failed_known` proof

The class is reserved for a native create failure for which the host proves
that this RAH invocation did not acquire the target. Acceptable proof requires
the native operation to report a no-acquisition outcome and a bounded
post-observation that confirms no target attributable to this invocation was
created, while preserving the external target if a collision existed.

If the native error is generic, the operation’s status is unavailable, the
post-observation cannot distinguish an external target from an RAH target, or
parent/identity state is contradictory, the result is `uncertain`, not
`create_failed_known`. In particular, the current Windows “all failed NT
status equals AlreadyExists” mapping cannot be used as reviewed evidence until
the future implementation supplies this distinction.

## `ok` proof

`ok` requires all of the following after the one native attempt:

- target exists under the retained safe parent/root;
- target identity is the identity acquired by this invocation;
- target is an ordinary regular file and not a symlink, junction, reparse, or
  special entry;
- complete bytes equal the exact retained content;
- exact byte length equals the retained content length;
- exact SHA-256 equals the retained content SHA-256;
- parent and root identity remain safe and current;
- target remains absent from HEAD and index and is observed as untracked;
- raw index bytes, HEAD, symbolic HEAD, refs, and protected unrelated
  observations remain unchanged; and
- no Stage, Unstage, Commit, or other protected mutation occurred.

The host may show the human the safe logical path, exact length, and exact
content hash in the local result. Generic activity remains redacted and does
not carry raw ToolOutput or source-bearing data.

## Repository refresh and Commit invalidation

Any confirmed repository-bound effectful create invalidates existing reviewed
Commit authorization at the HostExplicit `Started` boundary, before ordinary
Tool dispatch. This is conservative and applies even if the owned dispatch
later rejects after `Started` or returns an error. Prepare is zero-effect and
does not create, arm, or serialize Commit authorization.

After `ok`, `write_failed_known`, or `uncertain`, repository refresh is
descriptive reconciliation only. It may update status and file-info and may
show the new untracked path. It must not create a new Commit review, restore a
cleared Commit authorization, Stage the file, or Commit it. The absence of
untracked content from ordinary `git diff` is expected; host hash/length and
file-type verification remain necessary.

For `invalid_target`, `precondition_failed`, and proven
`create_failed_known` before any effect, refresh is optional and must not be
used to alter the pending review or create a replacement ticket. For known
partial and uncertain outcomes, refresh is required when currentness permits,
but it is descriptive and must preserve the partial/uncertain classification.

Fresh review is not Commit authorization. Human Stage/Unstage and the
existing reviewed Commit workflow remain separate authorities.
