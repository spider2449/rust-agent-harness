# Task 187 — RAH v0.15 Directory-Creation Milestone Audit

## 1. Executive conclusion

**PASS — ready for v0.15 release preparation**

The selected v0.15 capability was delivered: `repo.create-directory` creates
exactly one new ordinary directory leaf beneath an already-existing,
validated parent in the host-selected repository. The implementation conforms
to ADR 0019, preserves separate host-owned authority, uses the normal
ToolRegistry and Generic Codex Bridge path, binds Desktop state to repository
generation, revokes reviewed commit authorization after verified mutation, and
has Windows live certification.

No concrete release-blocking defect was found. Several adversarial path cases
are covered by shared validation/native helpers and source inspection rather
than by a directory-policy-specific test for every case; this is recorded as
non-blocking coverage debt because the policy fails closed, the native
operations are bounded, and the required Windows live gate passed.

## 3. v0.15 scope delivered

v0.14 delivered bounded tracked-file rename/move. v0.15 adds the separate
structural worktree effect needed to create one empty directory before a
separate `repo.create-file` or `repo.rename-file` operation. The product
scope is therefore one explicit directory effect and one explicit authority;
it is not tree creation and does not make either later operation implicit.

## 5. Authority/security audit

Directory creation remains distinct from repository read, content mutation,
file creation, file deletion, file rename/move, index mutation, reviewed
commit/history mutation, and Execute. `RepositoryFileCreationPolicy`,
`RepositoryFileDeletionPolicy`, and `RepositoryFileRenamePolicy` do not imply
the directory policy. Execute remains only the outer dispatch permission.

The registry publishes the Tool only when the trusted host supplies the
explicit directory authority. Model requests, provider metadata, Tool
advertisement, frontend state, and Trusted Profile configuration do not
construct or elevate it. No generic filesystem, shell, process, or Git
authority was introduced. No production use of `std::env::set_current_dir`
was found.

## 6. Filesystem/path-security audit

`parse_logical_path` rejects absolute, drive-relative, backslash, colon/ADS,
NUL, traversal, and namespace-like forms. Component checks reject wildcard
forms, trailing dot/space aliases, and reserved Windows device names. Parent
validation rejects links/reparse ancestry, requires an existing directory, and
opens only existing components relative to the selected root. The destination
must be absent as any filesystem object.

Unix uses descriptor-relative `mkdirat` with `O_NOFOLLOW` parent walking.
Windows uses handle-relative `NtCreateFile` with `FILE_CREATE`,
`FILE_DIRECTORY_FILE`, and `FILE_OPEN_REPARSE_POINT`; no generic path-based
mkdir, recursive helper, or subprocess fallback is present. The implementation
does not claim to eliminate all external TOCTOU races. Shared helper/native
coverage and the live gate establish the supported Windows behavior; Linux is
deterministic evidence only.

## 7. Exactly-one-effect / replay audit

The effect boundary is one lease-protected capture, immediate revalidation,
one native attempt, and post-observation. A possible effect is classified
conservatively. There is no automatic retry, replay, alternate fallback,
delete compensation, or rollback. Timeout, cancellation, disconnect, crash,
or lost observation is not treated as rollback. The core attempt counter and
bridge execution counter both prove the relevant one-call cases.

## 8. Git-clean empty-directory audit

The implementation never invokes Git for the mutation, stages, commits,
changes the index, changes HEAD, changes refs, or creates a marker. Git does
not track empty directories, so clean `git status --short` after verified
creation is expected. Filesystem existence, ordinary type, emptiness, and
unchanged Git metadata are the authoritative success evidence. Task 186
recorded empty status, empty cached/worktree diffs, unchanged HEAD/branch/refs,
and no staging or commit.

## 9. Desktop/repository lifecycle audit

Desktop constructs the authority from the selected canonical repository and
stores it with the repository snapshot. Repository replacement increments
`repository_generation`; stale runtime/connection publication and stale turns
remain rejected, and reconnect is required. A fresh connection receives fresh
repository context. The directory authority is root-bound and is not reused
across selection.

Task 185 tests cover authority presence/absence, generation changes, stale
publication, reconnect behavior, and mutation refresh classification. Task
186 independently recorded repository, connection, runtime, and session
generation `1`, all correlated to `D:\rah-task186-live`.

## 10. Reviewed commit authorization audit

Verified directory creation is classified as a repository mutation by Desktop
even when Git status is clean. The generic mutation refresh invalidates the
outstanding reviewed commit authorization and rotates review state. The direct
test `desktop_verified_directory_creation_revokes_reviewed_commit_authorization`
proves this with staged review state and an empty directory creation. Known
precondition failures are not verified mutations; possible-effect uncertainty
remains fail-closed and is not replayed.

## 11. Generic Codex Bridge audit

`host_composed_repo_create_directory_uses_generic_bridge_once` proves absent
authority omits the Tool, explicit authority registers the canonical public
name, and the exact closed schema is preserved. The generic bridge maps the
Tool to private test alias `rah_tool_0`; the alias is not public contract. The
request is forwarded once, the structured JSON result is preserved, permission
checking remains in RAH, and one registry execution is observed.

No `repo.create-directory` special case exists in the runtime-Codex bridge.
No Codex alias grants authority, and no Trusted Profile path manufactures the
authority.

## 12. Deterministic test coverage audit

Actual direct core tests in
`crates/rah-tools/src/repository_create_directory.rs` are:

- `creates_one_leaf_under_root_and_nested_parent`
- `rejects_authority_input_and_path_contract_failures`
- `rejects_existing_objects_and_file_parent`
- `target_race_is_known_no_effect_without_retry`
- `uncertain_postcondition_is_not_replayed_or_deleted`

They directly cover root/nested success, empty output, closed input, path
rejection, missing parent, existing target, file parent, one-attempt race,
uncertainty, and no replay/deletion. Shared path/native tests provide indirect
symlink/link-parent, descriptor anchoring, and exclusive-native evidence.

Composition is directly covered by
`host_composed_repo_create_directory_uses_generic_bridge_once`, including
authority absence/presence, schema, alias mapping, exact routing, one
dispatch, structured result, and permission path. Desktop directly covers
registry inclusion, clean Git status after an empty-directory mutation,
refresh classification, review revocation, repository-generation binding,
and stale/reconnect lifecycle invariants.

Dedicated directory-policy tests for every Windows reparse/junction variant,
case-equivalent alias, nested metadata case, and every native error mapping
are not present. These are classified MISSING as narrowly targeted test
coverage, not as an observed implementation failure: source and shared native
helpers fail closed, and Task 186 supplies the required real Windows success
and metadata-preservation gate. This is NON-BLOCKING coverage debt for future
hardening, not a release blocker.

## 13. Windows live validation audit

fresh disposable fixture outside the checkout, absent target, public
advertisement, private alias `rah_tool_3`, exact non-null request,
Requested/Started/Finished `1/1/1`, `is_error=false`, verified structured

Git status remained clean. This is expected because Git does not track an
empty directory and materially validates the filesystem-versus-Git lifecycle
design. The fixture was preserved. Linux live certification remains
unestablished and is not claimed.

## 14. Documentation consistency audit

ADR 0019 and Tasks 180–186 accurately describe the authority, implementation,
composition, Desktop lifecycle, and live gate. README, ARCHITECTURE, SECURITY,
CHANGELOG, and `docs/RAH_V0.14_RELEASE_GATE.md` remain v0.14/release-facing
documents and do not incorrectly claim that v0.15 is released. Updating

Security claims remain consistent: host authority, separate mutation planes,
no generic filesystem/shell/process/Git authority, no recursive creation, no
replay or rollback guarantee, process supervision is not OS sandboxing,
network isolation is not claimed, and Linux live certification is not claimed.

## 15. Known limitations / deferred work

The following remain intentional non-goals: `mkdir -p`, recursion, multiple
directories per request, directory deletion/rename/copy, overwrite,
symlink/junction/reparse creation, placeholders, implicit files, mode/ACL
mutation, generic filesystem or shell/process authority, Git mutation,
staging/commit, rollback/compensation, retry/replay, and Linux live
certification. Trusted Profile schema expansion and release/version changes
are also deferred to their separately scoped work.
