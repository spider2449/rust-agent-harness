# Task 201 — RAH v0.17 Scope and Authority Roadmap

## Scope

Research the next product milestone after the completed RAH v0.16.0 release and
select one bounded v0.17 direction without implementing Rust, frontend, schema,
provider, runtime, or authority changes.

The starting released baseline is RAH v0.16.0. Task 200 completed the
post-release documentation cleanup. The v0.16 milestone added the Desktop
Effective Authority Review UX while preserving existing host-owned authority,
repository generation, provider-neutral runtime, Generic Tool Bridge, and
reviewed-commit boundaries.

This task is research-only. It does not authorize implementation.

## Current product state

RAH already has the important pieces for a useful local coding workflow:

- a Windows Desktop host with an explicitly selected canonical repository;
- bounded first-party repository observation and authoring capabilities;
- separate file creation, content mutation, deletion, rename/move, directory
  creation, index mutation, and reviewed commit authority planes;
- a Generic Codex Tool Bridge that remains provider-neutral;
- hardened local stdio MCP and Process Plugin adapters;
- Trusted Static Profile v1, including exact MCP and Process Plugin provider
  admission;
- CLI effective Trusted Profile composition with all-or-nothing provider
  publication and provider lifecycle ownership; and
- a v0.16 Desktop Effective Authority panel that already distinguishes
  configured, effective, advertised, stale, reconnect-required, and unavailable
  state for the Desktop-composed inventory.

The most visible remaining composition gap is that MCP and Process Plugin tools
can be safely composed through the CLI Trusted Profile path but are not yet
reachable through the normal Desktop connection path. The v0.16 authority UX
already reserves presentation categories for MCP and Process Plugin sources,
but those sources are not currently part of Desktop composition.

## Candidate directions

The following directions were compared against user value, architectural fit,
new authority required, security surface, implementation size, and how directly
they complete an already established RAH boundary.

| Candidate | Product value | New authority boundary | Main concern | v0.17 decision |
| --- | --- | --- | --- | --- |
| Structured session/workflow checkpoints | Medium | Persistence/recovery semantics | Migration, privacy, crash and replay semantics | Defer |
| Generic build/test command surface | High | New bounded process/command authority | Easily drifts toward shell/process authority | Defer |
| Network MCP / Streamable HTTP | High | Network, endpoint and authentication authority | Credential/network policy is a major new plane | Defer |
| PluginManager / install/restart lifecycle | Medium | Lifecycle/install authority | Broadens provider management substantially | Defer |
| Trusted Profile hot reload | Medium | Dynamic authority replacement | Requires revocation, generation and reload semantics | Defer |
| Desktop Trusted Profile external-provider integration | High | No new authority class if kept within ADR 0011 | Must preserve Desktop repository and lifecycle ownership | **Recommend** |

## Recommendation

RAH v0.17 should close the Desktop external-provider composition gap by making
explicitly host-selected Trusted Profile MCP and Process Plugin tools available
through the ordinary Desktop Codex connection path.

The milestone should remain narrow:

```text
Desktop host-selected first-party authorities
                +
Trusted Profile admitted local external providers
                |
                v
        fresh ToolRegistry
                |
                v
        Generic Codex Tool Bridge
```

This direction is the strongest v0.17 choice because it completes an existing,
already-hardened capability rather than introducing another authority plane.
MCP and Process Plugin adapters already exist; Trusted Profile exact admission
already exists; the Generic Tool Bridge already dispatches arbitrary registered
RAH Tools; and the Effective Authority UI already has the conceptual source
categories needed to explain the result.

## Authority decision

Task 201 does **not** recommend a new ADR or authority class.

The relevant authority remains ADR 0011: an explicitly selected trusted static
profile is a trusted-host authority-composition boundary for already-approved
capabilities and admitted providers. The model cannot select a profile,
executable, provider, repository, permission, or lifecycle action.

RAH v0.17 must preserve these established distinctions:

```text
profile composition != model authority
external provider permission != generic process authority
provider metadata != authorization
Desktop repository selection != profile repository selection
runtime advertisement != unconditional execution authorization
process supervision != OS sandboxing
```

A provider Tool continues to pass normal ToolRegistry and host permission
checks. A provider declaration, discovered schema, Tool description, frontend
state, or Codex request cannot manufacture additional host authority.

## Desktop repository boundary

The Desktop canonical repository remains host-owned and authoritative for the
Desktop first-party repository workflow. v0.17 must not allow a Trusted Profile
repository resource to silently replace or disagree with that Desktop-selected
repository.

The selected canonical repository remains the common binding for Desktop
repository Tools, repository generation, Codex thread workspace context, and
repository-scoped conversation history. Repository switching continues to
invalidate stale runtime context and requires a fresh connection before new
Tool advertisement can become current.

The detailed rule for how Trusted Profile composition coexists with this
Desktop repository boundary is intentionally delegated to Task 202.

## Lifecycle constraints

Any v0.17 implementation must preserve the following high-level rules:

- selecting or inspecting profile configuration while disconnected must not
  start providers;
- provider startup happens only during an explicit effective composition step;
- effective composition is all-or-nothing;
- no partial registry is published after provider admission failure;
- live provider adapters remain owned for at least as long as their registered
  proxy Tools are usable;
- reconnect builds a fresh effective provider composition rather than reviving
  stale children;
- disconnect and application shutdown reap owned provider processes;
- no automatic restart or replay is introduced;
- no profile hot reload or automatic profile discovery is introduced; and
- Effective Authority Refresh remains observational and must not compose,
  reload, spawn, reconnect, execute, or mutate authority.

## Effective Authority UX requirement

The v0.16 Effective Authority panel is part of the v0.17 acceptance boundary,
not a cosmetic follow-up.

When external providers are eventually composed through Desktop, the backend
must be able to present their sanitized public RAH Tool names, provider source
class, host-configured permission, effective/advertised state, and currentness
without exposing private bridge aliases, native paths, environment values,
credentials, stderr, raw endpoints, or other provider internals.

The frontend remains a renderer of backend-owned state. It cannot infer,
grant, broaden, persist, or activate authority.

## Explicit non-goals for v0.17

The recommended milestone does not include:

- network MCP or Streamable HTTP;
- remote endpoints, OAuth, credentials, tokens, or network policy;
- PluginManager, installation, download, update, marketplace, or automatic
  provider restart;
- profile auto-discovery, persistence, hot reload, or background watching;
- profile editing UI;
- generic shell, generic process execution, model-selected executable/argv/cwd
  or environment;
- new generic filesystem authority;
- new Git branch/ref/history/network authority;
- broad build/test command authority;
- rollback or compensation guarantees;
- stronger OS sandbox or network-isolation claims; or
- Linux live certification claims.

## Required follow-up research

Before Rust implementation, Task 202 must define the exact Desktop Trusted
Profile composition contract, including:

1. where shared effective profile composition belongs in the crate graph;
2. whether Desktop accepts a full profile or a narrower provider-only overlay;
3. how the Desktop-selected repository remains canonical;
4. selection, static validation, Connect, reconnect, disconnect, and shutdown
   semantics;
5. atomic publication and provider ownership;
6. Effective Authority source/effect/permission classification for external
   tools; and
7. the conservative repository/review behavior required after an external Tool
   may have produced effects.

Task 202 remains research-only and must prefer the smallest architecture change
that preserves the v0.16 security and lifecycle contracts.

## Task 201 conclusion

**Recommend RAH v0.17 as Desktop Trusted Profile external-provider integration,
with no new authority class and no ADR change unless Task 202 finds contrary
evidence.**

The next task is Task 202 — Desktop Trusted Profile Composition Contract
Research. No Rust implementation should begin before that contract is recorded.
