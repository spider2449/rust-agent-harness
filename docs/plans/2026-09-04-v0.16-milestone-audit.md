## 5. Authority/security assessment

`get_effective_authority_snapshot` takes only host `State` and returns a DTO.
The implementation copies synchronized repository, connection, composition,
and workflow presentation state. It does not grant, revoke, activate,
reload, execute, mutate, reconnect, persist authority, or consume commit
authorization. No DTO field is accepted as an authority token elsewhere.

The ToolRegistry, host permission decisions, repository policies, generation
checks, review authorization, uncertainty handling, and no-replay rules remain
the authority boundaries. `PermissionLevel::Execute` remains only a dispatch
classification and does not grant narrower repository authority.

No new architecture or security decision was introduced beyond the accepted
ADR scope. Task 192 correctly determined that no new ADR is required.

## 6. Backend snapshot assessment

`crates/rah-desktop/src/effective_authority.rs` defines closed snapshot status,
source, effect, authority, unavailable-reason, repository, connection,
configured, Tool, and reviewed-commit presentation types. Composition reads
`ToolRegistry::definitions()`, applies an explicit classification table, keeps
only classified entries, and sorts by public Tool name. Currentness additionally
requires registry/composition agreement.

The command in `crates/rah-desktop/src/main.rs` reuses
`connection_context_is_current` and `connection_publication_is_current`.
Unknown or inconsistent state cannot become `connected_current`; it becomes a
conservative stale, reconnect-required, disconnected, connecting, unavailable,
or no-repository state.

## 7. Desktop UX assessment

The panel in `frontend/index.html`, `status.js`, and `styles.css` is
presentation-only. It contains `Refresh Authority`, which invokes only
`get_effective_authority_snapshot`, plus the passive `Advanced context`
`details` disclosure. The disclosure is not an authority action.

There are no Grant, Revoke, Authorize, Enable, Disable, Connect, Reconnect,
Reload, Execute, or provider-lifecycle controls in this panel. The UI states
that inventory is informational and that model requests remain subject to host
permission and policy checks. It does not say that advertisement is full or
unconditional authorization.

The renderer uses bounded text labels and `textContent`; it does not infer
authority from names, permission values, advertised state, generations, or
frontend state.

## 8. Generation/currentness assessment

Backend currentness is the sole source of the `Current` classification. The
frontend emits `Current` only for `connected_current` and never compares
generation values to infer it. Repository generation, model generation,
connection generation, and runtime publication are distinct and are checked
using the existing lifecycle helpers.

The required transition is preserved:

```text
A current -> select B -> reconnect required / stale -> fresh B publication -> B current
```

Existing deterministic tests cover repository generation changes, independent
model/repository generations, stale connection publication, reconnect
requirements, and connection lifecycle states. Task 196A visually confirmed
that A-to-B selection did not leave the old runtime Current for B and that a
fresh B connection restored Current.

## 9. Tool inventory and classification assessment

The current Desktop registry composes the following 13 public Tools in the
live certified path:

`echo`, `fs.read`, `repo.commit`, `repo.create-directory`, `repo.create-file`,
`repo.delete-file`, `repo.diff`, `repo.diff-staged`, `repo.edit-files`,
`repo.file-info`, `repo.patch`, `repo.rename-file`, and `repo.status`.

Every one has an explicit backend classification. No Tool-name prefix heuristic
is used. Unknown names are omitted from the classified inventory, and the
registry-length/currentness check fails closed if composition metadata drifts.
Names displayed by the panel are public names; private `rah_tool_N` aliases
are not DTO fields.

`GitStageTool` and `GitUnstageTool` exist as host-owned Repository UI actions
(`repository_stage_action` and `repository_unstage_action`), not as entries in
the model-visible Desktop `ToolRegistry` used by this snapshot. They are
therefore intentionally not missing from the effective Tool inventory.

`echo` is retained existing Desktop behavior and is explicitly classified by
the backend as Built-in / Execute / Execute / not repository-bound. v0.16
observes this baseline; removing it is a separate product-cleanup decision,
not a release blocker for this observational milestone.

## 10. Reviewed commit and unavailable semantics

The snapshot exposes reviewed commit as state only. `Authorization revoked`
can therefore coexist with an effective/advertised `repo.commit` Tool: Tool
advertisement is inventory, while authorization for a particular commit request
is a separate one-shot host-reviewed decision. The panel exposes no review ID,
selector, digest, token, handle, or authorization action.

The closed unavailable-reason model includes authority-not-granted,
repository-required, reconnect-required, provider-not-effective,
provider-unavailable, permission-not-configured, review-required, stale-context,
not-configured, and unknown. Deterministic tests and closed mappings cover the
model, including fail-closed unknown values. Task 196 live-observed zero
unavailable entries in its applicable A/B states; it does not claim that every
reason was live-observed.

## 11. Sanitization and privacy assessment

Backend sanitization is the security boundary. The DTO contains no raw
repository path or canonical root, repository-context fingerprint, Codex
executable path, MCP endpoint, token, credential, environment, cwd, provider
stderr, command line, private alias, review selector, review digest, or review
handle. Repository display is limited to a safe final directory component and
Codex source is mapped to a closed label.

Rust serialization tests check field closure, repeat determinism, representative
secret/path/endpoint/stderr/alias exclusion, and expected safe labels. The
frontend consumes only the DTO and does not render raw/debug data. Ordinary
Repository UI may display its selected path by existing product design; that
does not cross the Effective Authority boundary.

## 12. Zero-side-effect assessment

The command and refresh path only read/copy host state. They do not reconnect,
disconnect, increment lifecycle generations, execute Tools, send chat, alter
repository state, grant/revoke authority, consume review, or persist authority.
Refresh orchestration is independent of repository rendering and has no polling
or retry loop.

Task 195 deterministic structural tests establish this isolation. Task 196A
clicked refresh repeatedly with no repository, A disconnected, A current, B
reconnect-required, and B current. No chat prompt was sent and no Tool activity
was visually observed; repository postconditions remained unchanged. No raw
JSONL Tool-event count is claimed because no JSONL evidence was enabled or
present.

## 19. Known limitations and explicit non-goals

- Linux live Effective Authority certification is not established.
- MCP and Process Plugin Effective Authority UX is not currently reachable in
  this Desktop composition path.
- Generation values are optional advanced diagnostics and need not be visible;
  backend status/currentness is the security classification.
- Historical Tool rows may remain visible during reconnect-required/stale state,
  but the panel globally marks the inventory non-current and does not represent
  those rows as current authority.
- `echo` is existing shipped behavior and remains a cleanup candidate.
- The panel does not prove that a request will succeed. Host input validation,
  policy, preconditions, lifecycle, uncertainty, and postcondition proof remain
  decisive.
- No OS sandboxing, network isolation, rollback guarantee, dynamic authority,
  profile reload, network MCP milestone, or authority persistence is claimed.

These are documented scope limits or existing product behavior, not release
blockers for v0.16.
