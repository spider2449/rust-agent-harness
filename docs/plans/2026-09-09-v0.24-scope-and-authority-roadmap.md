## Current product capability inventory

The v0.23 release establishes the exact nine HostExplicit Tools:

```text
fs.read
repo.file-info
repo.status
repo.diff
repo.diff-staged
repo.create-branch
repo.patch
repo.edit-files
repo.create-file
```

The connected-current human flow is therefore:

```text
inspect repository
 -> typed HostExplicit read/branch action where applicable
 -> typed reviewed patch, multi-file edit, or new-file Prepare
 -> complete backend-derived review
 -> opaque ticket-only Confirm
 -> currentness / exact definition / permission / preparer checks
 -> D2 -> HostExplicit Started -> authorized ToolRegistry dispatch
 -> existing narrow Tool authority
 -> strict result handling and descriptive refresh
```

The human can inspect status, file information, worktree diff, staged diff,
and bounded file content; create a local branch; patch one existing file;
edit a bounded set of existing files; create one absent file; use the existing
explicit Stage/Unstage authority; and use the separate reviewed Commit
workflow. The nine-name set is not a generic category: no wildcard,
permission-derived, provider-derived, model-derived, or frontend-derived
eligibility exists.

The most important remaining workflow friction is structural authoring. A
human can create and edit code through reviewed HostExplicit routes but cannot
delete an existing file or rename/move it through the same reviewed Desktop
route. Directory creation is available as an ordinary narrow capability but
is not HostExplicit and is a weak product milestone because Git does not track
an empty directory and `repo.create-file` still requires an existing parent.
The final commit can already be reached through the host-reviewed staged
snapshot and ordinary `repo.commit` model Tool workflow; it is less direct,
but it is not an absent underlying workflow.

## Implementation status versus reviewed Desktop status

The current source provides these concrete ordinary capabilities:

- `RepositoryFileDeletionTool` uses a separate opaque authority, requires one
  clean HEAD-tracked regular file, binds the exact worktree/HEAD blob
  preimage, performs one native delete attempt, and returns
  `deleted_verified`, `known_no_effect`, or `uncertain` in addition to
  `invalid_input` and `precondition_failed`.
- `RepositoryFileRenameTool` uses a separate opaque authority, requires one
  clean HEAD-tracked regular file and an absent destination with an existing
  parent, supports same-directory and same-repository cross-directory moves,
  rejects Windows case-only ambiguity, uses a no-replace native effect, and
  returns `renamed_verified`, `known_no_effect`, or `uncertain` in addition to
  input/precondition errors.
- `RepositoryDirectoryCreationTool` uses a separate opaque authority,
  permits exactly one absent ordinary leaf under an already existing safe
  parent, verifies parent identity and unchanged Git metadata, and returns
  `directory_created_verified`, `known_no_effect`, or `uncertain` in addition
  to input/precondition errors.
- `RepositoryCommitTool` and `RepositoryCommitControl` provide the mature
  reviewed staged-snapshot foundation: exact index/tree/parent/branch/message
  binding, fixed Git configuration and identity, one normal commit attempt,
  and `committed_verified`, `known_no_effect`, or `uncertain` semantics.

The missing layer is capability-specific HostExplicit preparation and review.
`host_kind` and `HostInvocationKind` contain no deletion, rename, directory,
or commit kind; `host_descriptor` has no preparer argument or eligibility path
for them; the coordinator payload has no corresponding prepared variants; and
the frontend has no typed form or review renderer for them. Effective Authority
does classify these ordinary capabilities, but that classification is
observational and does not enable HostExplicit.

## Candidate scoring method

Scores are 1–5 and are positive fit scores: 5 is favorable. For authority
novelty, 5 means a narrow additive boundary that does not broaden existing
authority. For security complexity, privacy impact, failure complexity, and
scope size, 5 means lower cost or lower risk. The score is a release-fit
signal, not a claim that a high-scoring candidate is authorized.

| Candidate | User value | Coding workflow | Authority novelty | Security complexity | Deterministic testability | Windows live-certifiability | Tool/policy reuse | HostExplicit reuse | Privacy fit | Failure fit | Scope fit | Release confidence |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A. Reviewed HostExplicit deletion | 5 | 5 | 5 | 4 | 4 | 4 | 5 | 4 | 4 | 4 | 4 | 4 |
| B. Reviewed HostExplicit rename/move | 5 | 5 | 4 | 3 | 3 | 3 | 5 | 4 | 4 | 3 | 3 | 3 |
| C. Reviewed HostExplicit directory creation | 2 | 2 | 5 | 5 | 5 | 4 | 5 | 4 | 5 | 4 | 5 | 4 |
| D. Reviewed HostExplicit Commit | 5 | 5 | 3 | 2 | 4 | 4 | 5 | 3 | 3 | 2 | 3 | 3 |
| E. Combined delete + rename + mkdir | 5 | 5 | 2 | 1 | 2 | 2 | 4 | 3 | 3 | 1 | 1 | 1 |
| F. Model-selected reviewed authoring | 3 | 4 | 2 | 1 | 2 | 2 | 2 | 3 | 1 | 1 | 2 | 1 |
| G. Provider HostExplicit | 3 | 2 | 1 | 1 | 1 | 1 | 1 | 2 | 1 | 1 | 1 | 1 |
| H. Network MCP / Streamable HTTP | 3 | 2 | 1 | 1 | 2 | 1 | 1 | 2 | 2 | 1 | 1 | 1 |
| I. Session/workflow persistence | 4 | 3 | 5 | 4 | 4 | 4 | 3 | 4 | 3 | 4 | 3 | 4 |
| J. PluginManager/lifecycle management | 3 | 2 | 1 | 1 | 3 | 2 | 2 | 2 | 2 | 1 | 1 | 1 |

Important score drivers:

- A is a one-path destructive operation with an exact preimage already
  captured by the Tool. Its review can be complete and bounded, its result
  vocabulary is small, and its effect does not touch the index or history.
- B has equal user value but two path identities, destination absence, parent
  identity, same-volume/no-replace semantics, Windows case-only rejection,
  and source/destination postconditions. Those are legitimate authority
  costs, not details that can be hidden in a generic rename.
- C is easy to test and safe to keep narrow, but the user-visible value is
  modest: an empty directory can survive while Git remains clean, and it does
  not remove the existing-parent requirement from file creation.
- D reuses the strongest low-level foundation and would remove model
  mediation from the final commit step, but it adds HostExplicit history/ref
  mutation and must review exact tree, parent, branch/ref, identity, message,
  hooks, signing, and detached-HEAD semantics. The ordinary reviewed Commit
  workflow already exists, so its marginal product value is lower than
  deletion.
- E, F, G, H, and J each either combine distinct authority planes or add a
  provider/process/network/install lifecycle whose review and uncertainty
  cannot be made generic safely. I is valuable only as descriptive workflow
  persistence; it must not persist a ticket or authorization capability and
  does not close the structural authoring gap.

## Detailed candidate analysis

### A. Reviewed HostExplicit file deletion

This is the strongest narrow structural-authoring candidate. The product
capability is:

```text
human supplies one logical repository-relative path
 -> zero-effect deletion Prepare
 -> complete backend-derived review of the exact source preimage
 -> ticket-only Confirm
 -> source/repository currentness and D2
 -> existing repo.delete-file Tool through ToolRegistry
```

The existing ADR 0017 and Tool contract answer the deletion-specific research
questions. The eligible target is exactly one existing regular file beneath
the selected repository, tracked by current `HEAD` through one normal stage-0
entry, with the index and worktree equal to the authorized `HEAD` state. It is
not an untracked or ignored file, an intent-to-add entry, staged deletion,
unmerged/conflicted target, submodule/gitlink, directory, special file, or
unsupported sparse/linked/bare repository state. The current Tool also checks
the target identity and requires link count one, reads the exact bytes, and
matches the HEAD blob plus host-provided SHA-256 and byte length.

The future HostExplicit request must remain narrower than the existing Tool
schema: the human supplies only `{path}`. The host derives the existing
`expected_file_sha256` and `expected_file_byte_length` fields and reconstructs
the unchanged canonical Tool input. No Tool schema change is proposed.

The review must be complete enough for a human to authorize destruction of
the exact source. It should show the operation, relative path, regular-file
and HEAD-tracked status, complete bounded deterministic escaped preimage
content or an equally complete bounded byte representation, host-derived byte
length and SHA-256, and all relevant index/HEAD/current-branch identity and
non-effects. It must state that the result is an unstaged deletion, with no
`git rm`, Stage, Unstage, Commit, ref/history change, rename, directory
operation, or recovery. If the complete review cannot fit a fixed bound,
Prepare must fail closed with no ticket; truncation or an ellipsis cannot
authorize deletion. Binary or otherwise unreviewable content must be rejected
or represented by a complete deterministic byte view in the capability-specific
contract research; the HostExplicit route must not silently authorize from a
hash-only preview.

The underlying authority remains ADR 0017. Its filesystem commit point is one
native delete disposition after immediate independent revalidation. A native
success return is not sufficient if the target can still be present or
pending disappearance. The public result vocabulary remains exactly
`invalid_input`, `precondition_failed`, `deleted_verified`, `known_no_effect`,
and `uncertain`; the HostExplicit layer must not rename or merge these classes.
`deleted_verified` requires absence plus unchanged protected Git state. A
failure is `known_no_effect` only when fresh proof shows the protected
preimage remains intact. Contradictory absence, replacement, timeout,
cancellation, disconnect, crash, sharing/filter failure, or lost observation
is `uncertain` unless independent post-observation proves a permitted result.

The operation never restores the file, retries, replays, compensates, removes
an uncertain replacement, stages the deletion, or commits it. A successful
deletion remains an unstaged worktree deletion until a separate human Stage
and reviewed Commit path is used. A partially created file from
`repo.create-file` is not eligible for this deletion authority; cleanup of
that state remains a separate future authority decision.

### B. Reviewed HostExplicit rename/move

Rename is a close second. It would use `{source_path, destination_path}` as
human input, while the host derives the existing source hash and length and
all native identities. The complete review must show the source preimage, the
existing source and destination parents, proven destination absence, source
and destination paths, same-repository/same-volume admission, and the fact
that the index, HEAD, branch, refs, content, and history remain unchanged.

ADR 0018 requires a clean HEAD-tracked regular source, an absent destination
with an existing parent, no symlink/junction/reparse ancestry, no overwrite,
and one native no-replace rename. It explicitly rejects `git mv`, copy-plus-
delete, generic `fs.rename`, and multi-step case-only workarounds. Windows
case-only or equivalent-path moves must fail closed. The reviewed ticket must
bind and revalidate both source and destination identities, source bytes,
destination absence, both parents, repository/index/HEAD/ref state, and
runtime/currentness. `renamed_verified` requires source absence,
destination presence with exact bytes and supported identity proof, plus
unchanged Git state. After a possible native effect, there is no move-back,
retry, or replay.

Rename offers real value, but its two-sided race and platform surface makes it
a lower-confidence first v0.24 HostExplicit milestone. It remains a strong
candidate for a later structural-authoring release or a separately reviewed
follow-on after deletion's evidence pattern is proven.

### C. Reviewed HostExplicit directory creation

ADR 0019 and the current Tool already provide a particularly narrow contract:
one absent ordinary leaf, an already existing safe ordinary parent, no
recursive creation, no placeholder, no file creation, no Git/index/ref
mutation, and one native creation attempt. Parent and target identity,
reparse/traversal rejection, unchanged Git snapshot, and
`directory_created_verified`/`known_no_effect`/`uncertain` are all
deterministically testable.

Its product value is not proportional to its implementation readiness. An
empty directory is invisible to Git and may leave `git status --short` clean;
the next file operation still requires a separate explicit authorization.
The capability is useful for specialized repository layouts, but it is not
the most important Desktop coding friction. It should remain separate and
not be bundled merely to achieve structural symmetry.

### D. Reviewed HostExplicit Commit

The current `repo.commit` foundation is mature at the underlying policy and
ordinary Desktop reviewed workflow layers. It proves or binds the exact raw
index identity, canonical staged-entry digest, `git write-tree` OID, attached
branch, old HEAD parent, fixed host identity, exact message, hook/signing
configuration, and one normal commit attempt. It rejects detached/unborn
HEAD, unsupported index/special Git states, staged gitlinks, and implicit
Stage. Deterministic tests cover exact index/tree/message behavior, stale
review, hooks/config hardening, known-no-effect, and uncertainty. Windows
live evidence exists for the ordinary reviewed Commit path.

HostExplicit still lacks a commit kind, typed Prepare/Confirm route, and
frontend form. A future route would need a human message input and a
complete review of the exact staged tree, parent, attached branch/ref,
identity, message, no-signing/no-hook execution policy, and non-effects. It
must use the current reviewed `RepositoryCommitControl`, not create a second
commit authority. The final sequence would be ticket-only Confirm, exact
review/control revalidation, D2, HostExplicit Started, and existing
`repo.commit` ToolRegistry dispatch. No automatic Stage or Commit may be
added to an authoring route.

The principal concern is authority plane: commit creates Git objects and
advances the current branch ref, so it is history/ref mutation rather than
worktree authoring. Detached HEAD, branch/ref drift, hooks, signing, commit
object versus ref-update proof, and uncertain ref outcomes make the reviewed
HostExplicit boundary substantially more security-sensitive. It is a viable
future milestone, but v0.24 gains more from exposing a missing structural
operation while retaining the existing reviewed-Commit path.

### E–J. Remaining candidates

The combined structural milestone (E) would obscure distinct policies,
reviews, result vocabularies, and live gates. It should be rejected as a
release scope even though each operation can be separately justified.

Model-selected reviewed HostExplicit authoring (F) does not become safe merely
because a human later presses Confirm. Model-generated intent can introduce
prompt/source privacy exposure, confused-deputy behavior, preparation spam,
and ambiguous authority provenance. Preparation itself can expose sensitive
review material and consume coordinator capacity. A separately designed
model-requested preparation boundary would be required; it is not implied by
the current human route.

Provider HostExplicit (G) has no safe generic admission rule. MCP or Process
Plugin metadata cannot grant authority, and provider schemas do not supply a
uniform typed review, lifecycle, endpoint identity, credential, cancellation,
or uncertainty contract. Network MCP/Streamable HTTP (H) adds endpoint and
credential authority, reconnect/replay and uncertain remote effects, and is
not a structural repository-authoring milestone.

Session/workflow persistence (I) can preserve descriptive history and bounded
draft input, but must never serialize or resume a live authority ticket. It
does not solve deletion or rename reachability. PluginManager/lifecycle
management (J) can improve discovery and process lifecycle but does not imply
installation, configuration, executable, or network authority; process
supervision is not a sandbox and it is too broad for this milestone.

## Risk and uncertainty comparison

Deletion has one protected source identity and one filesystem effect. Its
uncertainty is principally whether the named entry disappeared and whether
the protected source/Git state can still be proven. Rename has two path
identities and a destination collision race; an uncertain result can leave
either name state or an externally replaced destination, so no move-back is
safe. Directory creation has no content preimage but has a persistent effect
that Git cannot display; clean Git status is not proof of no effect. Commit
has the highest durable consequence because a successful effect creates
objects and advances a branch ref; postcondition attribution must distinguish
commit-object creation from ref update and must not reset after uncertainty.

Across all candidates, the safe rule is one possible-effect attempt, fresh
post-observation, conservative result classification, and no retry, replay,
rollback, cleanup, or compensation. This is why a smaller deletion boundary
is preferable to a convenience composition.

authority.

## Required v0.24 boundary and evidence shape

The recommendation requires no new underlying mutation authority. ADR 0017's
`RepositoryFileDeletionPolicy` remains the sole deletion authority. A new
capability-specific ADR is required for the reviewed HostExplicit route (a
new ADR 0025 is the natural next number), while ADR 0021 remains the general
coordinator/currentness/D2/ticket/provenance boundary. This Task 279 document
does not create that ADR.

The new reviewed boundary must be:

```text
typed human {path}
 -> zero-effect deletion-specific Prepare
 -> complete backend-derived exact-preimage review
 -> opaque process-local single-use ticket
 -> ticket-only Confirm
 -> deletion preimage/currentness revalidation
 -> D2 exact definition/permission admission
 -> HostExplicit Started
 -> authorized_tool_dispatch
 -> current ToolRegistry
 -> existing repo.delete-file / ADR 0017
```

The host must derive the legacy Tool's expected SHA-256 and byte length; the
human must not supply hashes, native paths, repository roots, index state,
authority fields, Tool JSON, provider/model selection, retry controls, or
Stage/Commit instructions. The route must bind the selected repository/root
and Git identity, runtime and repository generations, exact logical path,
regular-file identity and link count, HEAD/branch/parent, exact stage-0 index
entry, raw preimage bytes/hash/length, complete review identity, current Tool
definition, permission membership, registry/composition identity, and
capability preparer identity. Confirm revalidates all relevant state before
D2 and before Started.

The route must invalidate repository-bound reviewed Commit authorization once
the deletion reaches the established effectful `Started` boundary (including
an owned post-Started rejection where the authoring precedent requires it).
Prepare is zero-effect and does not revoke Commit authorization. Refresh after
the effect is descriptive only.

## Required deterministic evidence

Before any live certification, the implementation sequence must prove through
RAH-owned deterministic tests:

1. Human input is exactly `{path}` and host-derived Tool input contains the
   existing schema fields; no Tool schema or generic JSON route is introduced.
2. Prepare performs zero Tool executions, zero native delete attempts, zero
   filesystem/index/HEAD/ref/history effects, and issues no ticket on failure.
3. The review is complete, bounded, deterministic, text/byte-safe, and free
   of truncation, hidden preimage material, native paths, tickets, raw Tool
   input/output, and private identities on generic activity/persistence.
4. A clean HEAD-tracked regular file succeeds as `deleted_verified`, is absent
   afterward, and leaves its index, HEAD, branch, refs, and unrelated files
   unchanged; the resulting Git state is an unstaged deletion.
5. Dirty, staged, index-divergent, untracked, ignored, intent-to-add,
   unmerged, missing, directory, submodule/gitlink, special, sparse,
   linked-worktree, bare, and unsupported repository states fail closed.
6. Path traversal, `.git`/metadata, aliases, reserved/device names,
   symlink/junction/reparse ancestry, hard-link ambiguity, and unsafe target
   replacement are rejected without following or deleting the wrong object.
7. Source bytes, SHA-256, byte length, FileIdentity, HEAD/blob, stage-0 index,
   repository identity, and relevant refs are revalidated immediately before
   the one native attempt; drift produces no attempt.
8. Native failure is `known_no_effect` only after fresh proof of intact
   preimage. Lost result, pending disappearance, replacement, failed
   observation, timeout, cancellation, disconnect, or crash remains
   `uncertain` unless independent proof establishes a permitted result.
9. `deleted_verified`, `known_no_effect`, `invalid_input`,
   `precondition_failed`, and `uncertain` are parsed strictly; malformed or
   contradictory Tool output is not upgraded to success.
10. A confirmed effect dispatches exactly once through D2, HostExplicit
    lifecycle, `authorized_tool_dispatch`, and the current ToolRegistry;
    duplicate, wrong, expired, or activity-ID tickets cannot execute.
11. Effectful deletion invalidates reviewed Commit authorization, while
    Prepare, cancellation-before-start, and descriptive refresh do not create
    or replace Commit authority.
12. No uncertainty path retries, replays, restores, stages, commits, deletes
    again, or compensates. A partially created file is not silently cleaned up
    by deletion authority.

## Required Windows live evidence

After deterministic closure, one separately guarded Windows connected-current
production-path test must use a fresh disposable repository and one clean
tracked regular file. It must prove:

- backend eligibility is exactly the newly reviewed deletion kind and still
  rejects providers, model turns, stale compositions, and noneligible names;
- human typed path input reaches Prepare, with Prepare Tool/native counts `0/0`;
- ticket-only Confirm performs exactly one Tool dispatch and one native delete;
- result is `deleted_verified`, the target is absent, and its identity cannot
  be confused with an external replacement or delayed Windows disappearance;
- index, HEAD, attached branch, refs, unrelated staged state, and other files
  remain unchanged, with no Stage or Commit;
- HostExplicit activity is distinct from model lifecycle and records no model
  request, model Tool lifecycle, MCP execution, or Process Plugin execution;
- ticket and activity IDs remain distinct, duplicate and activity-ID Confirm /
  Cancel are rejected, and coordinator/chat return to Idle; and
- a host-attested marker records the exact Windows/Codex baseline and final
  repository evidence.

The live gate must not claim model-selected HostExplicit execution, GUI mouse
automation, Linux/macOS production parity, race-free TOCTOU, rollback,
network isolation, or OS sandboxing. A Windows native success return alone is
not sufficient evidence of verified deletion.

## Explicit v0.24 non-goals

The recommended milestone excludes:

- generic `fs.write`, generic delete, wildcard HostExplicit, or broad
  filesystem authority;
- model-selected executable, argv, cwd, environment, or HostExplicit
  preparation/execution;
- provider-metadata-derived HostExplicit, MCP/Process Plugin HostExplicit,
  network MCP, or Streamable HTTP;
- rename/move, directory creation, directory deletion, recursive deletion,
  untracked-file cleanup, partial-file cleanup, overwrite, copy, or restore;
- HostExplicit Commit, automatic Stage + Commit, branch switching, arbitrary
  Git/ref/history mutation, or changing ADR 0016;
- ticket persistence, authority serialization, resume, automatic reprepare,
  retry, replay, rollback, compensation, or recovery journaling;
- changing any Tool schema, widening the v0.23 nine-name eligibility set
  without the separately accepted boundary, frontend behavior in Task 279,
  workspace version, dependencies, release gates, or accepted ADRs; and
- OS sandbox or network-isolation claims.

Task 279 authorizes none of these follow-on tasks:

1. Task 279 — scope and authority roadmap (this document).

## Final recommendation

RECOMMENDATION:
Reviewed HostExplicit File Deletion for RAH v0.24

Why this beats the alternatives: it closes the highest-value missing Desktop
coding operation after v0.23, while its one-source exact-preimage contract is
smaller and more verifiable than rename and less authority-sensitive than
HostExplicit Commit. It preserves the existing explicit Stage and reviewed
Commit boundaries and does not require a generic filesystem capability.

Underlying existing authority: the host-owned `RepositoryFileDeletionPolicy`
and `repo.delete-file` Tool defined by ADR 0017. The existing Tool remains the
sole mutation authority and keeps its closed schema and result vocabulary.

New authority boundary required: no new underlying mutation authority. A new
capability-specific reviewed HostExplicit deletion boundary is required,
with a host-only preparer/review binding around ADR 0017 and reuse of ADR 0021
for currentness, D2, ticket, lifecycle, and provenance.

HostExplicit boundary required: typed human `{path}`; zero-effect complete
preimage Prepare; opaque process-local single-use ticket; ticket-only Confirm;
identity/currentness and shared revalidation; D2; HostExplicit Started;
`authorized_tool_dispatch`; and existing `repo.delete-file` through the
current ToolRegistry. No Tool schema change or eligibility-by-metadata path.

Major failure semantics: one native attempt only. `deleted_verified` requires
post-observed target absence and unchanged protected Git state;
`known_no_effect` requires proof that the exact source remains intact;
contradictory, pending, replaced, timed-out, cancelled, disconnected, crashed,
or unobserved effects are `uncertain`. No retry, replay, restore, rollback,
cleanup, compensation, Stage, or Commit follows uncertainty.

Required deterministic evidence: zero-effect Prepare; complete bounded
preimage review and privacy; exact source/HEAD/index identity and currentness;
clean tracked regular-file success; all dirty/staged/untracked/unsupported
state refusals; symlink/reparse/alias/path hardening; strict result parsing;
exactly-once D2/ToolRegistry/native dispatch; ticket lifecycle; Commit
invalidation after Started; and no replay or recovery.

Required Windows live evidence: a fresh disposable repository, clean tracked
regular target, production connected-current HostExplicit Prepare/Confirm,
`0/0` Prepare and `1/1` Confirm Tool/native counts, verified absence, unchanged
index/HEAD/branch/refs and unrelated staged state, distinct HostExplicit
activity with zero model/provider lifecycle, duplicate/activity-ticket
rejection, Idle termination, and a host-attested completion marker. This is
not model-selected execution or a race-free/rollback/sandbox/network claim.

Explicit non-goals: all items in the v0.24 non-goal section above, especially
generic filesystem authority, model/provider/network HostExplicit, rename,
mkdir, HostExplicit Commit, automatic Stage/Commit, ticket persistence,
retry/replay, rollback, and broad structural filesystem mutation.

Proposed task sequence: Tasks 280–290 as listed above, with task omission
allowed only when an earlier task demonstrably supplies the required reusable
evidence and the milestone audit records why.
