# Task 280 — RAH v0.24 Reviewed File-Deletion HostExplicit Contract Research

## Scope and research status

This document is the Task 280 research-only contract definition for a future
reviewed HostExplicit route to the existing `repo.delete-file` capability. It
does not implement Rust, change Desktop or frontend behavior, change a Tool
schema, change HostExplicit eligibility, create ADR 0025, modify any accepted
ADR, change Cargo or versions, run destructive live certification, or start
Task 281.

The selected route is deliberately narrower than the ordinary deletion Tool:

```text
human {path}
 -> zero-effect deletion Prepare
 -> complete backend-derived destructive review
 -> opaque process-local ticket
 -> ticket-only Confirm
 -> deletion-specific revalidation
 -> D2
 -> HostExplicit Started
 -> authorized_tool_dispatch
 -> current ToolRegistry
 -> existing repo.delete-file / ADR 0017
```

ADR 0017 remains the sole mutation authority. The future capability-specific
ADR may define only this reviewed human boundary around that authority.

## 3. Existing ADR 0017 and Tool contract

### 3.1 Underlying authority

ADR 0017 introduces the separate host-owned
`RepositoryFileDeletionPolicy`. It is not granted by `PermissionLevel::Execute`,
Tool registration, Tool visibility, provider metadata, model output, a
Trusted Profile, frontend state, or human confirmation. The host selects the
repository and constructs the capability.

The accepted ordinary operation is exactly one explicitly named
repository-relative file in one selected repository. The target must be:

- beneath the selected canonical repository root;
- an existing ordinary regular file;
- tracked by the current `HEAD` through one normal stage-0 index entry;
- clean, with worktree bytes, the HEAD blob, and the index entry agreeing;
- not a submodule/gitlink, nested repository boundary, repository metadata,
  directory, special file, link, reparse target, or unsupported sparse state;
- in a supported non-bare, non-linked-worktree repository state; and
- free of the supported identity and alias ambiguities.

The authority does not include directory or recursive deletion, wildcard or
glob selection, generic filesystem deletion, untracked or ignored cleanup,
partial-file cleanup, rename, directory creation, staging, commit, ref/history
mutation, shell/process authority, or network Git.

### 3.2 Current Tool definition and closed input

`RepositoryFileDeletionTool::definition()` currently exposes:

```text
public name: repo.delete-file
permission: PermissionLevel::Execute
description: Deletes one clean HEAD-tracked repository-relative file.
```

The current closed Tool input is exactly three fields:

```json
{
  "path": "repository-relative/logical/path",
  "expected_file_sha256": "64 lowercase hexadecimal characters",
  "expected_file_byte_length": 0
}
```

The current schema has `additionalProperties: false`, requires all three
fields, bounds `path` to 1024 bytes, and bounds the expected byte length to
1 MiB inclusive. The future HostExplicit DTO must not change this schema. It
must reconstruct the two expected preimage fields from host-captured bytes.

### 3.3 Current policy observations

The current implementation captures and checks, as applicable:

- the host-selected canonical repository root;
- the selected Git executable and its `FileIdentity`;
- the `.git` directory and its `FileIdentity`;
- repository-root containment and reparse ancestry;
- the logical target path and canonical path equivalence;
- ordinary regular-file type and supported file attributes;
- target `FileIdentity` and link count exactly one;
- exact worktree bytes;
- the expected SHA-256 and byte length;
- `HEAD` and the attached symbolic branch;
- the HEAD tree entry and blob bytes;
- the exact normal stage-0 index record and tree/index agreement;
- the `H` worktree tag from `git ls-files -v`;
- raw `.git/index` bytes; and
- a fingerprint containing HEAD, branch, tree entry, index entry, and all
  refs.

The current policy rejects detached or unborn HEAD, bare and linked
worktrees, unsupported sparse or index states, metadata targets, symlinks,
Windows reparse points, hard-linked targets, unsupported file attributes,
directories, special files, and unsafe path forms. It uses a fixed Git
executable plus argument vector and the host execution policy for Git reads.

The shared path helper rejects empty, absolute, drive-relative, UNC, verbatim,
device, ADS/colon, backslash, dot-navigation, repeated-separator, and
case-insensitive `.git` components. `FileIdentity` is device/inode/link count
on Unix and volume serial/file index/link count on Windows. The Windows
identity helper obtains a handle with read-attribute access and all three
read/write/delete sharing modes, then calls `GetFileInformationByHandle`.

### 3.4 Current effect and result path

The current Tool has this execution shape:

```text
parse closed request
 -> capture exact protected preimage and Git state
 -> one independent revalidation
 -> exactly one native DeleteFileW/remove_file attempt
 -> post-effect observation
```

`delete_once` calls `DeleteFileW` on Windows and `fs::remove_file` elsewhere.
There is no Git deletion command, `git rm`, index write, Stage, Commit, or
second delete attempt.

The public Tool output is one `ToolContent::Json` object. The exact current
`result()` helper always emits `status` and `uncertain`, and emits `path` only
when a path is supplied by that branch. `is_error` is false only for
`deleted_verified`.

| Tool status | JSON shape currently emitted | `is_error` | Current proof meaning |
| --- | --- | --- | --- |
| `deleted_verified` | `{ "status": "deleted_verified", "uncertain": false, "path": "..." }` | `false` | Native delete returned and post-observation accepted target absence and protected Git state |
| `known_no_effect` | `{ "status": "known_no_effect", "uncertain": false, "path": "..." }` | `true` | Native failure branch and fresh intact-preimage observation accepted no effect |
| `invalid_input` | `{ "status": "invalid_input", "uncertain": false }` | `true` | Closed Tool parse failed before policy capture or native attempt |
| `precondition_failed` | `{ "status": "precondition_failed", "uncertain": false, "path": "..." }` | `true` | Capture or immediate revalidation failed before native attempt |
| `uncertain` | `{ "status": "uncertain", "uncertain": true, "path": "..." }` in the native-failure branch, or `{ "status": "uncertain", "uncertain": true }` after post-observation failure | `true` | Effect or required proof is not established |

The exact JSON object has no other fields. `path` is never a native absolute
path; it is the logical request path when that branch retains it. An
uncertain result can therefore contain the logical path after a native error,
but the post-success observation-failure branch intentionally omits it.

The core semantic rules are retained exactly:

- a native error alone never proves `known_no_effect`;
- `known_no_effect` requires fresh proof that the exact protected preimage
  remains intact;
- `deleted_verified` requires verified target absence and protected Git-state
  invariants; and
- any possible effect or failed proof remains `uncertain`.

The current source has two observations that the future reviewed route must
strengthen at its boundary without changing ADR 0017 or the Tool schema. The
current `intact` helper checks that a fresh capture succeeds and that metadata
can be read, but does not directly compare the fresh target identity to the
captured `Preimage.identity`. The current `deleted_verified` check treats any
failed `symlink_metadata` lookup as absence rather than distinguishing a
confirmed `NotFound` from access, sharing, or I/O failure. Therefore the
reviewed HostExplicit classifier must independently require identity-equal
preimage proof for `known_no_effect` and a specifically confirmed absence for
`deleted_verified`; all other observation failures are `uncertain`.

## 4. Reviewed-route decisions

### 4.1 Exact human Prepare DTO

The final human request is exactly:

```json
{
  "path": "src/module.rs"
}
```

The typed backend DTO is `RepositoryDeleteFilePrepare { path: String }` with
closed deserialization equivalent to `deny_unknown_fields`. Unknown fields,
missing fields, wrong types, non-object input, NUL, and an over-bound
serialized request fail closed and issue no ticket.

The human does not provide any of the following:

- `expected_file_sha256` or `expected_file_byte_length`;
- repository root, native path, parent path, or Git executable;
- HEAD, tree, blob, branch, refs, index, raw index, identity, or link data;
- permission, authority, effect class, `ToolName`, or raw `ToolInput`;
- provider, model, runtime, profile, or connection identity;
- retry, replay, delete-again, recovery, restore, rollback, or cleanup flags;
- mode, Stage, Unstage, Commit, or Commit-message instructions; or
- a ticket, activity ID, or execution control.

The host validates the logical path, captures the exact source bytes, derives
the SHA-256 and byte length, and reconstructs the unchanged canonical Tool
input. `{path}` alone is sufficient because deletion already targets one
existing file and the host can derive every Tool-required precondition from
that file. The ordinary Tool schema remains three fields; the human schema
remains one field.

### 4.2 Complete preimage review policy

Option A is selected: complete strict-UTF-8 text review with a lower
HostExplicit bound.

The reviewed route admits only source bytes that decode as strict UTF-8 and
fit the reviewed raw-byte bound. It rejects non-UTF-8/binary content before
ticket issuance. NUL is also rejected by the reviewed route even though it is
valid UTF-8, because it is not a useful human source-review surface and the
existing reviewed authoring routes already reject NUL. Other control and
format characters are retained in the source bytes and represented by fixed
escapes, subject to the complete review bound.

The review contains the complete source, not a preview. It may not use
truncation, ellipses, hidden collapsed content, a redaction, or a digest-only
substitute. If complete escaped content and metadata do not fit, Prepare
fails with a bounded review-too-large error and issues no ticket.

Option B is rejected because a complete byte-safe representation would make
ordinary binary deletion technically possible but would create a much larger,
less human-readable destructive review and a larger privacy/IPC surface.
Option C is rejected because a digest identifies bytes without letting the
human inspect the complete destructive preimage. Option D is rejected unless
it preserves the same complete bounded mutation-relevant representation; the
selected contract does not need a hybrid.

This is an intentional subset decision:

```text
ordinary ADR 0017 Tool authority: broader, including up to 1 MiB and binary
reviewed human HostExplicit route: narrower, strict UTF-8, complete bounded review
```

### 4.3 Exact bounds

All serialized bounds are inclusive and measured after deterministic JSON
escaping. The raw preimage bound is measured over the exact bytes that the
existing Tool will receive. The private prepared-state bound includes the
bounded review, exact source bytes, canonical Tool input, and private binding
metadata; it is not a frontend or authority payload format.

| Value | Reviewed HostExplicit decision |
| --- | --- |
| Human request serialized bound | 8 KiB / 8192 bytes maximum |
| Logical path | 1 through 1024 UTF-8 bytes, using the existing logical-path grammar |
| Eligible preimage | 0 through 64 KiB / 65536 raw bytes, inclusive |
| Content policy | strict UTF-8, no NUL; no implicit conversion, normalization, newline conversion, or BOM removal |
| Complete serialized review | 256 KiB / 262144 bytes maximum, inclusive |
| Complete escaped preimage | must fit inside the complete review; no clipped representation |
| Opaque prepared representation | 512 KiB / 524288 bytes maximum, inclusive |
| Native attempt count | at most one; successful, failed, timed-out, or lost attempt is never replayed |
| Observation loop | no additional polling loop; one immediate post-attempt observation pass |

The 64 KiB preimage cap is deliberately lower than both the ordinary 1 MiB
deletion cap and the v0.23 new-file content cap. The 256 KiB review cap is
selected because it accommodates a complete deterministic escaped text view
plus required deletion metadata while preserving the established reviewed
authoring review ceiling. The 512 KiB prepared-state cap is private and
bounded; if exact retained state cannot fit, Prepare fails closed with no
ticket. These values are new reviewed-route decisions, not silent changes to
ADR 0017.

### 4.4 Deterministic complete representation

The direct review uses an ASCII-safe deterministic representation. The exact
source bytes remain unchanged in private preparation state and in the
reconstructed Tool input. The display encoding is not a second input.

The representation uses these rules:

- CR is `\\r`;
- LF is `\\n`;
- TAB is `\\t`;
- NUL is rejected before rendering;
- spaces, including trailing spaces, are rendered as `\\u{20}`;
- backslash and quote are escaped;
- other C0 controls and DEL use fixed `\\u{HEX}` escapes;
- bidi, zero-width, and other Unicode format characters use fixed
  `\\u{HEX}` code-point escapes; and
- all non-ASCII scalars use fixed `\\u{HEX}` code-point escapes so visually
  similar glyphs cannot conceal a different scalar value.

The review also explicitly states whether the source is empty, contains a
BOM scalar, contains CR/LF/CRLF, ends with a newline, contains tabs or
trailing spaces, or contains control, bidi, zero-width, or format characters.
No HTML is used for review authority. Frontend rendering must use text APIs.

## 5. Exact direct review object

The future backend-owned direct review is a closed, display-only value. A
representative shape is:

```json
{
  "operation": "repo.delete-file",
  "target_count": 1,
  "path": "src/module.rs",
  "tracked_state": "clean_head_tracked_stage0",
  "file_mode": "100644",
  "file_intent": "permanently remove this existing regular file",
  "preimage_encoding": "complete_utf8_escaped",
  "preimage": "complete escaped source bytes",
  "content_byte_length": 1234,
  "content_sha256": "lowercase sha256 of exact source bytes",
  "bom": "absent",
  "newline_facts": {
    "contains_cr": false,
    "contains_lf": true,
    "contains_crlf": false,
    "ends_with_newline": true
  },
  "content_facts": {
    "empty": false,
    "contains_tab": false,
    "contains_trailing_space": false,
    "contains_control_or_format_escape": false
  },
  "head_blob_relationship": "worktree bytes equal current HEAD blob",
  "index_relationship": "exact stage-0 index entry equals HEAD tree entry and worktree",
  "expected_effect": "one unstaged deletion at the named path",
  "post_delete_git_meaning": "index, HEAD, branch, refs, and history remain unchanged",
  "non_effects": [
    "not Stage",
    "not Unstage",
    "not Commit",
    "does not modify the index",
    "does not modify HEAD, refs, or history",
    "does not rename, move, restore, or delete another path"
  ],
  "warnings": [
    "permanently removes the selected worktree file",
    "no Trash or Recycle Bin guarantee",
    "no restore, backup, rollback, retry, replay, or cleanup",
    "an uncertain result may require manual repository inspection"
  ]
}
```

The exact field contract is:

- `operation` is fixed to `repo.delete-file`;
- `target_count` is fixed to `1`;
- `path` is the validated relative logical path, never a native path;
- `tracked_state` states clean HEAD-tracked stage-0 eligibility;
- `file_mode` is derived as exactly `100644` or `100755` from the HEAD tree
  entry; it is review-relevant because the executable-bit state is part of
  the protected entry, but it is not human-selectable and is not changed;
- `file_intent` states deletion of one existing ordinary regular file;
- `preimage_encoding` and `preimage` provide the complete escaped source;
- `content_byte_length` and `content_sha256` are host-derived over exact
  source bytes;
- BOM, newline, and content facts are host-derived explanatory facts;
- the HEAD/blob and index relationships describe the exact protected
  preimage, not merely a path name;
- `expected_effect` says the worktree path becomes absent and Git reports an
  unstaged deletion;
- `post_delete_git_meaning` says index, HEAD, branch, refs, and history do
  not change;
- `non_effects` explicitly distinguishes deletion from Stage and Commit; and
- `warnings` state permanence, lack of Trash semantics, lack of recovery, and
  uncertainty guidance.

The review does not contain native repository paths, native target paths,
private `FileIdentity` values, raw index bytes, authority tickets, activity
IDs, raw ToolInput, raw ToolOutput, provider/model identity, or permission
fields. A private review identity exists only in the in-memory preparation
binding and is not serialized in the direct review.

The warning must also say that Cancel before `Started` is zero-effect, that
the operation is not Stage or Commit, and that timeout, cancellation,
disconnect, or process failure after possible effect does not prove rollback.
No RAH wording may imply that deletion is undoable by RAH.

## 6. Eligibility and source-state narrowing

The reviewed route retains the ordinary ADR 0017 target and repository
admission rules, then narrows them by complete text review.

Eligible state is one existing clean HEAD-tracked regular file. The target's
worktree bytes, HEAD blob, exact stage-0 index entry, raw index snapshot,
repository identity, and required refs fingerprint must agree. Unrelated
dirty paths may remain when the existing authority permits them; the review
does not copy unrelated content or status into its public surfaces.

The following are rejected before a ticket exists:

- missing, empty, directory, special, untracked, ignored, or partially-created
  targets;
- dirty target bytes, staged target changes, staged deletion, intent-to-add,
  unmerged/conflict stages, or HEAD/index/worktree disagreement;
- submodule/gitlink, nested repository, `.git` or metadata target;
- detached or unborn HEAD, bare or linked worktree, unsupported sparse state,
  malformed/alternate index, or merge/rebase/cherry-pick/revert/sequencer/
  bisect state where the existing policy refuses it;
- symlink, junction, Windows reparse point, mount-like redirect, hard-link
  ambiguity, unsafe parent, or target alias;
- case-equivalent or otherwise ambiguous Windows target names;
- non-UTF-8/binary bytes, NUL, more than 65536 raw bytes, or complete review
  larger than 262144 bytes; and
- any inability to distinguish absence, identity, Git state, or metadata from
  an observation failure.

The future route must keep native path and identity checks private and must
not claim that a lease makes the repository race-free. External editors,
antivirus, Git, sync software, and privileged actors can still race the
observations.

## 7. Zero-effect Prepare

Prepare must perform exactly zero effectful operations before Confirm:

```text
0 Tool executions
0 native delete attempts
0 filesystem mutation
0 index mutation
0 HEAD/ref/history mutation
0 Stage or Unstage
0 Commit
0 model/runtime execution
0 MCP or Process Plugin execution
0 temporary repository mutation artifact
0 durable authority persistence
```

Prepare may perform bounded reads, hashing, path validation, Git observation,
identity capture, review encoding, and in-memory retention. It must not call
`Tool::execute`, `ToolRegistry::execute`, `DeleteFileW`, `remove_file`, or a
replacement/cleanup path. A failed, stale, unsupported, oversized, or
unreviewable Prepare issues no ticket. Prepare does not invalidate reviewed
Commit authorization and does not create an effectful HostActivity state.

The direct Prepare response may contain only the opaque caller-facing
`ticketId` and the complete direct review. The generic Prepared activity is
not allowed to contain either value-bearing ticket or review material.

## 8. Opaque preparation and binding

The future shared deletion preparation is a process-local Rust-owned value,
not a serialized authority DTO. It retains enough private state to
reconstruct and independently prove the existing Tool request, including:

- logical path and canonical/native path privately, with no durable storage;
- exact source bytes, SHA-256, and byte length;
- file mode, regular-file admission, `FileIdentity`, and link count;
- selected canonical repository root identity;
- selected Git executable identity and `.git` identity;
- attached branch, exact HEAD OID, HEAD tree/blob entry, and symbolic HEAD;
- exact normal stage-0 index record and raw index bytes, or an implementation-
  proven equivalent that preserves byte-for-byte protected-state equality;
- refs fingerprint required by ADR 0017;
- repository, runtime, profile, model, connection, and composition
  generations relevant to the current Desktop composition;
- current repository identity and mutation lease identity;
- exact expected `repo.delete-file` `ToolDefinition`;
- current allowed permission membership and permission-policy identity;
- current `ToolRegistry` and composition identity;
- capability-specific preparer identity;
- deterministic complete review identity; and
- the canonical reconstructed ToolInput containing `path`, derived SHA-256,
  and derived byte length.

Private native paths, source bytes, raw index bytes, and identity values are
allowed only in bounded in-memory pending state needed for the one operation.
They are never persisted, placed in URLs, written to logs, placed in generic
activity, or accepted back from the frontend. If the complete private state
cannot fit the 512 KiB bound, Prepare fails closed with no ticket.

The preparation is opaque to the frontend and non-serializable as authority.
The ticket is only a lookup key for this in-memory value; it is not itself a
filesystem capability, permission, or durable authorization.

## 9. Confirm, currentness, D2, and Started ordering

Confirm receives exactly `{ "ticketId": "..." }`. It does not accept path,
hash, length, Tool JSON, repository, permission, provider, model, authority,
or review fields. The intended ordering is:

```text
take and consume ticket
 -> current connected-current composition check
 -> repository/runtime/generation/preparer checks
 -> deletion preparation revalidation
 -> exact current ToolDefinition and permission membership check
 -> D2 authorize_tool_dispatch
 -> invalidate reviewed Commit authorization
 -> emit HostExplicit Started
 -> authorized_tool_dispatch
 -> current ToolRegistry
 -> existing repo.delete-file
 -> strict result classification and descriptive refresh
```

D2 must occur before `Started` and before any mutation can begin. There is no
post-start D2. The route never directly calls the Tool, directly calls
filesystem APIs from Desktop, builds a parallel registry, or uses a generic
JSON console.

Immediately before D2/effect, revalidation must prove:

- the same selected repository, canonical root, Git executable, `.git`, and
  capability-specific preparer;
- the same logical path and exact source bytes/hash/length;
- the same target identity and link count;
- the same mode, regular-file, no-link/no-reparse, containment, and parent
  observations;
- the same HEAD/blob/tree, attached branch, exact stage-0 index, raw index,
  refs fingerprint, and supported repository state;
- the same review identity and canonical ToolInput;
- the same complete ToolDefinition, current permission membership, registry,
  composition, Effective Authority, and relevant generation tuple.

Any drift is stale/precondition failure with zero native attempt. The route
does not refresh the expected source, issue a replacement ticket, or replay.
The user may explicitly begin a new Prepare after a stale failure; that is a
new authorization, not a retry of the consumed operation.

## 10. Ticket lifecycle and privacy

The ticket reuses the ADR 0021/0024 lifecycle:

- RAH-generated, opaque, capability-specific, process-local, in-memory;
- non-serializable as durable authority;
- single-use and exact-preparation/currentness bound;
- valid only while the current connected-current composition remains bound;
- five-minute TTL, with the existing source boundary: elapsed time `< 300`
  seconds is valid and elapsed time `>= 300` seconds is expired, so exactly
  five minutes is rejected;
- no persistence, resume, replacement ticket, or automatic reprepare;
- wrong ticket, expired ticket, duplicate Confirm, activity ID, and malformed
  ticket are rejected without Tool/native execution; and
- Cancel before `Started` consumes the prepared authorization and is zero
  effect.

The authority `ticket_id` and generic `activity_id` are independently
generated. The activity ID is not derived from, equal to, or usable as the
ticket. It cannot Confirm or Cancel. A ticket cannot appear under alternate
keys such as `invocationId`.

Preparation, confirmation, expiry, stale rejection, cancellation, process
restart, disconnect, and Desktop shutdown do not persist or restore authority.
After restart or disconnect, the old ticket is unusable and the operation is
not resumed or replayed.

## 11. Reviewed Commit interaction

Prepare does not invalidate reviewed Commit authorization. Cancel-before-start
does not invalidate it. Stale rejection before `Started` does not imply a
repository effect and does not invalidate it merely because a ticket was
consumed.

Immediately before emitting effectful HostExplicit `Started`, the backend
invalidates any repository-bound reviewed Commit authorization, matching the
existing patch, multi-file, and new-file authoring precedent. This includes
the operation before the owned dispatch task begins; it does not wait for a
successful deletion result. Any post-Started dispatch/runtime failure remains
covered by that invalidation.

After deletion, refresh is descriptive only. It may show the resulting
unstaged deletion, but it may not fabricate a replacement Commit
authorization, Stage the deletion, Unstage it, Commit it, restore it, or
automatically rerun the deletion.

## 12. Windows DeleteFileW observation rule

Task 280 does not redesign the native Tool. The reviewed route requires a
strict classifier around the existing one-attempt path.

### 12.1 Successful native return

`DeleteFileW` returning success is only the filesystem effect commit point. It
is not by itself deletion proof. Windows may mark a file delete-pending while
an open handle with share-delete behavior keeps the directory entry visible.

`deleted_verified` requires all of the following in one immediate,
deterministic post-attempt observation pass:

1. the native delete call returned success;
2. the exact logical target has a confirmed `ERROR_FILE_NOT_FOUND`/
   `NotFound` absence observation, not merely a generic metadata failure;
3. no same-name entry, case-equivalent entry, trailing-dot/space alias,
   symlink, junction, or reparse entry is present at the target;
4. root and parent containment/identity observations remain protected;
5. raw index bytes and the HEAD/tree/blob/branch/refs fingerprint remain
   unchanged; and
6. no contradictory observation, sharing failure, timeout, or lost result
   occurred.

The pre-delete `FileIdentity` cannot be recaptured after true absence. It is
therefore retained as private preimage binding and is used to prove that the
native attempt was prepared against the intended object. The route makes no
race-free TOCTOU or privileged-actor claim. If an entry is recreated and is
observed at post-observation, even if its bytes match, the result is
`uncertain`, not verified deletion of the final path state. If a replacement
is not observed because an external actor races entirely between observations,
the route cannot claim to detect that race; this is an explicit nonclaim, not
permission to weaken the checks.

### 12.2 Open handles and delayed disappearance

If `DeleteFileW` succeeds but the path remains visible because deletion is
pending, the route returns `uncertain`. It does not wait for disappearance,
poll, close another process's handle, or invoke DeleteFileW again. A delayed
disappearance after the one observation is not upgraded to
`deleted_verified`.

If `DeleteFileW` fails, the route may return `known_no_effect` only after a
fresh independent observation proves the exact original identity, link count,
bytes/hash/length, HEAD/blob relation, index relation, and protected Git
fingerprint remain intact. A native error code, sharing violation, or process
exit by itself is never enough. If any part of that proof cannot be obtained,
the result is `uncertain`.

### 12.3 Replacement, aliases, and observation errors

The route performs no second delete and no cleanup. Source replacement before
the native attempt is caught by currentness and is a precondition failure with
zero attempt. Replacement after the native attempt, same-name recreation,
case-equivalent recreation, reparse substitution, or failure to attribute the
observation to the protected operation is `uncertain` unless the exact
permitted postcondition is independently established under the bounded
observation rule.

There is no additional bounded polling duration or count because this route
does not propose polling. The only observation is the existing immediate
post-attempt proof, strengthened to distinguish confirmed absence from an
observation error. That is observation, not a second mutation attempt.

## 13. Strict HostActivity result mapping

The HostExplicit layer does not add a public Tool status. It strictly parses
the existing five statuses and validates `is_error`, exact keys, path, and
`uncertain` value. It independently applies the Windows/protected-state proof
rules above.

The safe generic terminal envelope is status-only and contains no raw Tool
output. A direct explicit caller may see the complete review before Confirm,
but generic activity, transcript, persistence, logs, telemetry, and provider
surfaces do not.

| Condition | HostActivity state | Generic safe result | Effect proof | Refresh | Retry/replay |
| --- | --- | --- | --- | --- | --- |
| `deleted_verified` with exact output and independent absence/Git proof | `tool_completed` | `{ "status": "deleted_verified" }`, `is_error: false` | Deletion verified under the bounded observation contract | Descriptive refresh yes | No |
| `known_no_effect` with exact output and independent intact-preimage proof | `tool_error` | `{ "status": "known_no_effect" }`, `is_error: true` | Exact protected preimage remains; no effect proven | Descriptive refresh yes | No replay; a new human Prepare may be explicit |
| `invalid_input` exact Tool output | `tool_error` | `{ "status": "invalid_input" }`, `is_error: true` | Tool contract says parse failed before native attempt | No refresh required | No |
| `precondition_failed` exact Tool output | `tool_error` | `{ "status": "precondition_failed" }`, `is_error: true` | No native attempt under the Tool contract | No refresh required | No replay; fresh Prepare only |
| `uncertain` exact output, or success/failure without required proof | `possible_effect_unknown` | `{ "status": "uncertain" }`, `is_error: true` | Unknown; not upgraded | Descriptive refresh if current | Never |
| malformed/contradictory ToolOutput | `possible_effect_unknown` | `{ "status": "uncertain" }`, `is_error: true` | Unknown; malformed data is not success/no-effect proof | Descriptive refresh if current | Never |
| dispatch/runtime error after `Started` | `possible_effect_unknown` | `{ "status": "uncertain" }`, `is_error: true` | Possible effect; no terminal Tool proof | Descriptive refresh if current | Never |

The strict parser requires exactly one JSON content item and no extra keys.
For the success class it requires `status`, `uncertain: false`, `path` equal
to the prepared logical path, `is_error: false`, and the independent
post-observation proof. For the four error classes it requires
`is_error: true`, the exact status, and the status-specific `uncertain`
semantics. A native error branch reporting `known_no_effect` is not accepted
without the route-side identity-equal intact proof. A malformed output is
never passed through or presented as raw ToolOutput.

All five status names remain public exactly as ADR 0017 defines them:
`deleted_verified`, `known_no_effect`, `invalid_input`,
`precondition_failed`, and `uncertain`.

## 14. Generic activity and source privacy

The direct review is intentionally source-bearing because the human must
authorize the exact bytes being destroyed. That exception is limited to the
ephemeral direct Prepare response and local review dialog. It is not a
generic activity representation.

Generic Prepared activity is:

```json
{
  "source": "host_explicit",
  "invocationId": "independent non-authority activity ID",
  "tool": "repo.delete-file",
  "state": "prepared",
  "result": null,
  "review": null
}
```

Generic terminal activity uses the same independent activity ID and a
status-only safe result, or no result for a pre-Started rejection. It must
not contain:

- the authority ticket under any key or value;
- complete or partial source text/bytes or source sentinels;
- escaped source sentinels;
- raw ToolInput or raw ToolOutput;
- native repository or target paths;
- private `FileIdentity`, handle, root, parent, Git, ref, or raw index data;
- provider/model/runtime metadata that is not generic status; or
- a complete source-bearing review object.

The source-derived SHA-256 is sensitive/correlatable content metadata. It is
allowed in the direct review only because it helps the human bind the exact
preimage. It is excluded from generic HostActivity, conversation transcript,
persistence, telemetry, logs, evidence, URLs, browser storage, frontend
state after the dialog closes, and provider metadata. The same treatment
applies to content byte length, BOM/newline facts, content sentinels, and
other source-derived facts unless a future policy explicitly proves that a
generic fact is necessary and non-sensitive. The conservative default is
direct-review-only.

Task 263's correction is normative precedent: `ticket_id` and `activity_id`
must be different values, generic activity must not leak the ticket under an
alternate key, and privacy tests must compare actual sentinel values rather
than only prohibited field names.

HostExplicit remains source-distinct from model lifecycle. The route emits no
`AgentEvent::ToolRequested`, `AgentEvent::ToolStarted`, or
`AgentEvent::ToolFinished`, creates no fake model turn, injects no ToolOutput
into conversation, and causes no automatic model continuation.

## 15. Future typed frontend contract

Task 280 does not edit frontend. The future typed UI must provide only:

```text
path input -> Prepare -> complete destructive review -> Confirm or Cancel
```

The form sends `{ path }` only through a named deletion Prepare command.
Prepare returns the caller-only `{ ticketId, review }`; Confirm and Cancel
send `{ ticketId }` only. The review is display-only and rendered with
`textContent`/equivalent text APIs, never HTML authority or interpolated
markup.

The frontend must not compute or submit SHA-256, byte length, FileIdentity,
Git/HEAD/index/ref state, repository root, native path, permission, authority,
ToolName, ToolInput, result proof, retry/recovery controls, Stage, or Commit
instructions. It must not persist the ticket or source review in URLs,
browser storage, transcript, or generic activity.

If the target is binary/non-UTF-8, contains NUL, exceeds 64 KiB, or its
complete review exceeds 256 KiB, Prepare returns the typed bounded error
corresponding to an unreviewable/too-large deletion and no confirmation
dialog with a usable ticket is opened. The UI must say that the route cannot
authorize this file through the reviewed human path; it must not suggest that
the ordinary Tool or a generic filesystem delete should be used instead.

After Confirm, the UI presents only the safe HostActivity state/result. It
must label `uncertain` and post-start runtime failure as requiring manual
repository inspection and must not offer a retry, replay, restore, or
rollback action. Cancel closes the review and reports zero effect only when it
occurred before `Started`.

## 19. Deterministic evidence required before live work

Task 281 and later implementation tasks must prove through deterministic
RAH-owned tests, without paid credentials, internet, live models, or GPU:

1. The human DTO accepts exactly `{path}`, rejects unknown fields, and the
   host reconstructs the unchanged three-field Tool input with derived hash
   and length.
2. Prepare performs 0 Tool executions, 0 native delete attempts, 0
   filesystem/index/HEAD/ref/history changes, and issues no ticket on every
   failure path.
3. Complete strict-UTF-8 escaped review is deterministic, ASCII-safe,
   complete, bounded, and rejects NUL, binary/non-UTF-8, 64 KiB overflow,
   and 256 KiB serialized-review overflow without a ticket.
4. Direct review contains the required deletion warning, mode, preimage,
   length/hash, Git meaning, non-effects, and content facts, while generic
   Prepared/terminal activity contains none of those source-bearing values.
5. The private preparation retains exact source, identity, link count, raw
   index/equivalent protected state, Git fingerprint, definition, permission,
   composition, generation, and preparer binding within the 512 KiB bound.
6. Source, identity, parent, Git, definition, permission, registry,
   composition, generation, review, or canonical-input drift fails before
   D2/Started/native attempt.
7. The exact five Tool statuses, `is_error`, key sets, optional path behavior,
   and `uncertain` values are parsed strictly.
8. A clean tracked 100644 and 100755 regular file can be reviewed and deleted
   exactly once; the resulting state is an unstaged deletion with unchanged
   index, HEAD, branch, refs, and unrelated protected state.
9. Dirty, staged, untracked, ignored, intent-to-add, conflict, missing,
   directory, special, submodule, sparse, linked, bare, malformed, metadata,
   symlink/reparse, alias, hard-link, and unsafe target cases fail closed.
10. Native failure maps to `known_no_effect` only with identity-equal fresh
    intact proof; native error alone maps to `uncertain` when proof is absent.
11. Success plus a confirmed `NotFound` absence and unchanged protected Git
    state maps to `deleted_verified`; access/sharing/I/O observation failure,
    pending visibility, recreation, and contradictory state map to uncertain.
12. There is exactly one native attempt, no polling loop, no second delete,
    no cleanup, no restore, no replay, and no rollback on every uncertainty
    path.
13. Ticket TTL is rejected at exactly five minutes, tickets are single-use,
    process-local, nonpersistent, and distinct from activity IDs; wrong,
    duplicate, expired, and activity-ID Confirm/Cancel calls cannot execute.
14. D2 occurs before `Started`, and one confirmed dispatch reaches the current
    `authorized_tool_dispatch -> ToolRegistry -> repo.delete-file` path only.
15. Prepare/cancel/stale rejection preserve Commit authorization, while
    effectful `Started` invalidates it and refresh remains descriptive.
16. Malformed/contradictory output and post-Started runtime errors produce
    status-only uncertain activity, never raw output or success/no-effect.
17. Value-level privacy tests reject actual ticket, activity alternate-key,
    source, escaped-source, hash, raw-input, raw-output, native-path, and
    identity sentinels from generic surfaces and frontend persistence.
