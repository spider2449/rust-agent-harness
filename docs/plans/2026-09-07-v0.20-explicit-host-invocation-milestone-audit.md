## Milestone definition

The selected v0.20 milestone is the Explicit Host Tool Invocation Workflow.
Its product purpose is to make a bounded set of already-composed first-party
Tools reliably reachable by an explicit human Desktop host action without
depending on model Tool selection.

The architectural invariant is:

```text
host explicit dispatch != runtime/model dynamic dispatch != capability authorization
```

The milestone adds a dispatch route and provenance boundary. It does not add
repository, filesystem, index, history, branch/ref, provider, network,
process, executable, credential, or persisted authority.

## Product problem / result

YES. v0.20 solves the selected product problem:

> Make already-composed selected first-party Tools reliably reachable by an

It does not solve the different problem of making Codex always select Tools.

## ADR 0021 authority boundary

PASS. ADR 0021 remains accurate and is implemented without an observed
boundary collapse.

- Human host action selects only a backend-owned typed operation; it does not
  create the underlying capability.
- Tool visibility and Effective Authority are observational and do not
  authorize execution.
- Frontend state and `PermissionLevel::Execute` do not manufacture repository
  or provider authority.
- Model text, conversation content, provider metadata, and arbitrary frontend
  input cannot trigger HostExplicit dispatch.
- Existing capability authorities remain authoritative, including the branch
  creation authority and repository identity/currentness policy.
- HostExplicit activity is distinct from runtime/model AgentEvent lifecycle.

## D2 dispatch boundary

PASS. `crates/rah-tools/src/authorized_dispatch.rs` provides a neutral,
provider-independent admission and execution primitive.

`authorize_tool_dispatch` and `authorized_tool_dispatch` share the same
admission function. Admission requires the call name to equal the expected
public Tool name, re-resolves the current Tool from the current registry,
requires complete `ToolDefinition` equality including name, description, input
schema, and permission, and requires explicit membership of the current
permission in the host-owned policy. Permission levels are not hierarchical.

Admission rejection happens before execution. The execution primitive invokes
the admitted Tool once and preserves `ToolOutput`; an underlying `ToolError`
is distinct from dispatch rejection. D2 owns neither host eligibility,
capability composition, lifecycle/provenance, result interpretation, retry,
replay, or rollback.

The deterministic D2 tests cover name mismatch, missing Tool, description/schema
changes, permission changes even when the replacement permission is allowed,
empty/denied policy, exact permission membership, one execution, preserved
error output, and no retry.

## Codex bridge equivalence

PASS. The Codex bridge uses shared D2 semantics while retaining Codex-specific
responsibilities outside D2.

Before `ToolStarted`, the bridge checks `authorize_tool_dispatch`. Execution
uses `authorized_tool_dispatch`, which immediately revalidates the current
registry definition and permission before invoking the Tool. A captured
permission change is rejected as a stale definition mismatch even if the new
permission would otherwise be allowed.

The bridge independently retains thread ownership, active-turn ownership,
private alias mapping, call-ID replay/deduplication, cancellation, response
translation, and real `AgentEvent` lifecycle. HostExplicit semantics do not
enter the runtime event stream. Normal successful runtime execution remains
exactly once per admitted call.

## Desktop connected-current composition

PASS. Host commands call `current_host_composition` and use the currently
published connected composition. They do not construct a fresh registry on a
click, silently connect or reconnect, restore Trusted Profile authority, or
activate providers.

The retained composition includes the registry, expected definitions, allowed
permission policy, repository identity, composition identity, and the
repository/model/profile/connection generation tuple. Command-time checks
require a connected state, matching generations, matching selected repository
fingerprint, consistent composition sizes, and the current host definition.
Stale or disconnected state fails closed.

## Permission policy

PASS. `desktop_allowed_permissions` is host-owned and is retained in the
connected composition. The same policy is passed to the Codex bridge and to
HostExplicit D2 admission. External permission entries are accepted only from
validated host Trusted Profile admission records; provider-authored metadata
does not self-grant permission.

Host eligibility may be narrower than the shared permission policy, but it does
not replace D2 permission admission with a Desktop-specific policy.

## Eligibility boundary

PASS. The backend-owned first-release HostExplicit allowlist is exactly:

- `fs.read`
- `repo.file-info`
- `repo.status`
- `repo.diff`
- `repo.diff-staged`
- `repo.create-branch`

`host_kind` and deterministic tests reject `repo.commit`, worktree authoring
Tools, `echo`, fixtures, unknown Tools, MCP Tools, and Process Plugin Tools for
HostExplicit use. External descriptors are classified by host-owned metadata;
provider metadata cannot set eligibility. The frontend consumes the backend
descriptor and has no parallel allowlist.

## Typed input boundary

PASS. The production command surface has no `host_invoke_tool(tool_name,
arbitrary_json)` command and no generic JSON editor.

- `fs.read` and `repo.file-info` accept bounded `path` values.
- `repo.status`, `repo.diff`, and `repo.diff-staged` accept closed empty
  request forms.
- `repo.create-branch` Prepare accepts `name` only.
- Confirm and Cancel accept `ticketId` only.

The backend chooses the Tool for every typed request, and the underlying Tool
parser remains authoritative.

## Branch prepare/review/confirm

PASS. `repo.create-branch` follows:

```text
prepare -> sanitized review -> explicit confirm -> revalidate -> D2 -> Tool
```

Prepare validates the bounded branch name, performs no Tool execution and no
Git effect, and emits a sanitized review stating the local-branch operation,
captured HEAD target, exact effect, non-effects, Execute dispatch category, and
local-branch authority category. Confirm receives only the opaque ticket ID,
revalidates current state, and invokes the ordinary ToolRegistry path.

The live Task 240 result independently verified one created ref at the captured
HEAD OID, the ADR 0020 reflog identity/message, unchanged index/worktree and
checked-out branch, no upstream, preserved review authorization, unchanged
generations, and current connection state.

## Ticket lifecycle

PASS. Tickets are in-memory, process-local, opaque, non-persistent, single-use,
Tool/input/composition/currentness-bound, and expire after five minutes.
Confirmation consumes the ticket before currentness and D2 revalidation. An
unknown, expired, cancelled, or already-consumed ticket cannot dispatch and
does not trigger automatic re-preparation or retry.

## Host/model concurrency

PASS. The shared atomic coordinator has `Idle`, `ModelTurn`, `HostPrepared`,
and `HostRunning` states.

Read HostExplicit work claims the coordinator before `Started`, so it also
participates in exclusion. Host work is rejected during a model turn; model
start is rejected while HostPrepared or HostRunning; a second host action is
rejected; and terminal/error/pre-start cancellation paths release ownership.
The deterministic Task 239 tests and the Task 240 live fixture verify the
relevant exclusions without starting a model turn.

## HostExplicit provenance

PASS. Desktop activity is private, bounded, and labelled `host_explicit`.
The backend emits `prepared`, `started`, `tool_completed`, `tool_error`,
`rejected_stale`, `cancelled_before_start`, or
`possible_effect_unknown` as appropriate. It does not synthesize
`AgentEvent::ToolRequested`, `AgentEvent::ToolStarted`, or
`AgentEvent::ToolFinished`.

Task 240 observed `Started -> tool_completed` for `repo.status` and
`prepared -> Started -> tool_completed` for `repo.create-branch`; each Tool
executed exactly once.

## Cancellation / replay / crash

PASS WITH DOCUMENTED LIMITATION. Prepared, unstarted work can be cancelled
with known no Tool effect. After `Started`, there is no active HostExplicit
abort operation; owned execution proceeds to terminal handling where possible.
The UI may dismiss activity but cannot claim that the underlying effect was
undone.

The accepted semantics contain no automatic retry, replay, compensation,
rollback, ticket persistence, authority persistence, restart resume, or
automatic conversation continuation. A lost result after a possible effect is
not interpreted as absence of effect. The limitation is intentional: there is
no post-start cancellation contract in the first release.

## Conversation boundary

PASS. HostExplicit creates no user or assistant chat message, injects no
ToolOutput into the model conversation, creates no fake model Tool call, and
starts no automatic model continuation. The existing repository-scoped
conversation namespace is not changed by a host invocation. Host activity is a
separate Desktop presentation stream.

## Repository effect handling

PASS. Host result handling reuses the existing strict branch result
classification rather than a second permissive host parser. Safe
`branch_created_verified` with `uncertain: false` preserves review and current
repository state. Malformed, uncertain, Tool-error, or started-without-safe-
terminal paths conservatively invalidate review and refresh only the still
selected captured repository context where applicable.

No path claims rollback, retries an uncertain operation, or applies a result to
a different newly selected repository.

## Reviewed authorization/currentness

PASS. The branch HostExplicit route does not create, arm, serialize, or infer
reviewed commit authorization. The Task 240 live run established a real review
authorization using the production Desktop path, verified safe branch creation,
and observed preserved authorization, no invalidation, no refresh reason,
unchanged repository/model/profile/connection generations, unchanged
conversation namespace, and `Current` connection state.

## Effective Authority

PASS. Effective Authority is an observational backend descriptor. It exposes
host eligibility, typed kind, and bounded unavailable reasons but never grants
dispatch authority. Every command rechecks connected-current state, exact
backend-selected Tool, current definition, permission policy, repository
binding, and capability-specific preconditions.

The frontend does not infer eligibility from Tool name, permission, effect
class, authority category, or advertisement. Its static test explicitly checks
this non-inference and the backend descriptor path.

## Frontend

review, ticket-only Confirm/Cancel, visible `Host action — not Model`
