# Task 262 — RAH v0.22 Deterministic Fault and Privacy Hardening

## Scope and baseline

Task 262 hardens and validates the completed reviewed multi-file HostExplicit
route at `def0b9c6131ce975eda0e5ef62e863caa53ef382`. The checkout was resolved
with `git rev-parse --show-toplevel`; the worktree was clean and
`HEAD == origin/master` at that SHA. The v0.21.0 annotated tag object remains
`aa178f05d12d881745932800e8fc40a7431ce7b9`, with peeled target
`7faa13a16425cc9d3bdb0dc540923eae8685ba90`.

No new capability, authority, permission, Trusted Profile schema, dependency,
package version, ADR, persistence, replay, retry, rollback, Stage, Commit, MCP,
Process Plugin, or live-certification behavior is added. The exact HostExplicit
set remains:

```text
fs.read
repo.file-info
repo.status
repo.diff
repo.diff-staged
repo.create-branch
repo.patch
repo.edit-files
```

## Narrow implementation hardening

`crates/rah-desktop/src/main.rs` now treats `repo.patch` and `repo.edit-files`
as repository-bound authoring for the entire post-`Started` lifetime. Reviewed
Commit authorization is invalidated at the Started boundary, including when
the owned authorized-dispatch recheck rejects after Started. Such rejection
remains stale/unsafe, refresh is descriptive when currentness permits it, and
there is no second dispatch.

`crates/rah-tools/src/repository_multi_file_edit.rs` adds a `cfg(test)`-only,
fixture-root keyed execution counter. It records Tool entry, is not compiled
into production, is not generic, and creates no authority surface.

## Bounds exercised

Existing Task 257 and ADR 0023 bounds remain authoritative and are checked by
the shared parser/preparer tests: one through four targets; one through sixteen
replacements per target; aggregate replacement, path, text, request, file,
postimage, aggregate image, escaped changed-material, unchanged-context,
serialized review, and pending-state limits. Over-limit preparation fails
without a ticket, Tool entry, native attempt, hidden changed material, or
truncated mutation-relevant review. The frontend receives a complete backend
review and cannot bypass `review_too_large` with a hidden panel or generic
editor.

## Privacy sentinels

Distinctive expected-old, replacement, surrounding-preimage, postimage, HTML,
quote, ampersand, bidi/zero-width/control-like, JSON-looking, and Tauri-shaped
strings are permitted only in the bounded source-bearing review surface. The
generic HostExplicit activity serialization and malformed-result path are
asserted not to retain them, along with ticket-shaped field names, raw
ToolInput or ToolOutput, absolute/native paths, and source-bearing errors.
Frontend source content is assigned with `textContent`/text nodes only. No
ticket ID is added to browser storage or resumable conversation state.

### Historical privacy correction recorded by Task 263

Task 262 did not prove that the actual opaque ticket value was absent from
generic activity. Its regression assertion checked prohibited field/key text,
including `ticketId`, but did not use a distinctive ticket value and therefore
missed the same value emitted under `invocationId`. Task 263 Attempt 1 found
that production HostExplicit Prepared activity leaked the ticket through that
field. Task 263 separates the process-local authority ticket from a RAH-
generated non-authority activity correlation ID and adds value-level tests for
`repo.create-branch`, `repo.patch`, and `repo.edit-files`.

## Platform-gated cases and nonclaims

Unix special-file and symlink cases run only where supported. Windows junction /
reparse identity coverage is gated to Windows; no unconditional Windows file
identity assumption is made. This task performs no Windows connected-current
production live certification and makes no model-selected dispatch claim,
external-provider HostExplicit claim, GUI automation claim, rollback claim,
atomicity claim, OS-sandbox claim, or network-isolation claim. Those live and
production claims remain reserved for Task 263. Task 263 is not started here.
