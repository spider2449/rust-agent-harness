# Task 176 — RAH v0.14 Milestone Audit

Audit date: 2026-09-03
Audit scope: bounded repository file rename/move milestone only
Conclusion: **PASS — ready for v0.14 release preparation**

## 1. Executive conclusion

The v0.14 planned product capability was completed: RAH now exposes one
host-authorized `repo.rename-file` operation for one clean, HEAD-tracked,
regular file, with same-directory rename and same-repository cross-directory
move semantics. The implementation conforms to accepted ADR 0018, preserves
separate mutation authorities, and routes through the ordinary ToolRegistry
and Generic Codex Tool Bridge boundaries.

The deterministic core, composition, Desktop, evidence, and lifecycle
validation provide sufficient evidence for the agreed v1 contract. Task 175G
also completed fresh destructive Windows certification using the certified
Codex pair. Linux remains deterministic-only by design. No release-blocking
defect was found. The current README, ARCHITECTURE, SECURITY, and CHANGELOG
remain v0.13 candidate/release documentation; updating them for v0.14 is
properly deferred to release preparation and is not a Task 176 blocker.

## 3. v0.14 scope delivered

Task 168 selected bounded one-file repository rename/move as the v0.14
capability. Tasks 169–175 completed the research, ADR, core authority,
composition, bridge, structured evidence, Desktop lifecycle, and Windows live
certification chain. The operation accepts exactly:

```text
source_path
destination_path
expected_source_file_sha256
expected_source_file_byte_length
```

It moves one clean HEAD-tracked regular file to an absent existing-parent path
within the same selected repository. It preserves bytes, leaves the Git index
unchanged, and does not stage or commit.

## 5. Authority and security audit

Authority remains trusted-host-owned. `RepositoryFileRenameAuthority` is
constructed from host-selected Git and repository resources. Trusted Profile
configuration composes an already supplied authority and cannot manufacture,
select, broaden, or restore it. Model requests, provider metadata, tool
definitions, Execute permission, and Desktop presentation do not grant
rename authority.

The rename plane remains orthogonal to content replacement, creation,
deletion, index mutation, commit/history mutation, and Execute. No generic
filesystem, shell, process, or Git authority was added. Repository selection
and generation remain host-owned. No security workaround from historical
validation was found: Task 175A/175E changed observability and framing only,
and Task 175C hardened lifecycle publication and stale-context rejection.

Current `docs/SECURITY.md` and `docs/ARCHITECTURE_GUARDRAILS.md` continue to
state the required limits: process supervision is not OS sandboxing, network
isolation is not claimed, rollback is not guaranteed, possible effects are
not replayed, and model/provider/frontend state is not authority. Their
headline still describes v0.13; that is release-documentation work for Task
177, not evidence of a v0.14 implementation defect.

## 6. Deterministic validation audit

The core rename module contains nine deterministic tests:

- successful same-directory rename and exact bytes;
- successful same-repository cross-directory move;
- malformed input and destination collision;
- missing parent and directory destination;
- stale hash and dirty source;
- destination race after capture;
- traversal, metadata, wildcard, and reserved-name path rejection;
- source change after capture; and
- uncertain post-observation with no retry.

Generic bridge tests cover host-authority absence, canonical schema and
permission, one effective rename dispatch, duplicate delivery behavior,
stale preimage, and destination collision. Desktop tests cover host-owned
registration, exact result and repository-state preservation, refresh
activity, case-only rejection, stale source, collision, and no retry.

Coverage is direct for the principal v1 success, collision, preimage, path,
single-attempt, result, bridge, and Desktop contracts. Index/HEAD/ref
preservation is directly asserted on successful Desktop/bridge paths and in
live certification; identity-change behavior is implemented through captured
Git/root/index state and tested through adjacent lifecycle/race coverage.
Explicit rename-specific fixtures for every symlink/reparse, permission-denied,
and externally injected HEAD/index race are not all present; shared validators
and the existing authority/lifecycle tests provide indirect coverage. This is
a test-depth limitation, not a demonstrated release-blocking defect.

## 7. Desktop/runtime composition audit

Task 174 binds rename authority to the host-created `DesktopRepository` and
refreshes repository presentation after a verified move. Task 175C and the
current Desktop tests establish that repository selection increments
`repository_generation`, invalidates the old repository/runtime context,
requires reconnect, disables stale Send paths, and rejects stale connection
publication. A stale runtime is shut down rather than published for the new
repository. Fresh threads/sessions use an immutable fresh repository snapshot.

The repository search found no `std::env::set_current_dir` usage in the
implementation. Repository context is passed explicitly and remains
generation-bound; no global process-CWD workaround was introduced.

## 8. Live validation audit

Task 175F non-destructively validated A/B repository-context separation,
repository generation `1 -> 2`, connection generation `1 -> 2`, runtime
generation `1 -> 2`, session generation `1 -> 2`, distinct repository
fingerprints, correct read-only results, zero failures, zero mutation
requests, and parseable raw JSONL (`RAH_JSONL_PARSE_OK`).

Task 175G performed the final fresh destructive Windows certification using
the certified `codex-cli 0.149.0` executable pair. The source disappeared,
the destination existed with exact bytes and SHA-256, the sentinel was
unchanged, index/HEAD/refs were unchanged, no staging or commit occurred,
the lifecycle was Requested/Started/Finished `1/1/1`, the structured result
was `status=renamed_verified` and `uncertain=false`, the marker was observed,
and raw JSONL parsed successfully. No replay or retry occurred.

The initial pre-tool automation failure and later unclassified Chat-failed
observation remain historical observations. They caused no rename effect and
were not rewritten as successful or proven root causes. Windows live
certification is complete; Linux live certification is intentionally absent.

## 9. Evidence and observability audit

Task 175A prospectively added bounded/redacted generic request capture,
dynamic advertisement evidence with canonical public names and actual private
aliases, completion marker detection, and structured result preservation.
Task 175E moved bridge and Desktop evidence writes to the shared process-wide
serialized append helper, preventing the observed intra-process JSONL
concatenation. The evidence writer remains best-effort observability and
cannot grant or expand authority. Paths, prompts, credentials, environment,
authority objects, executable paths, and raw backend errors remain excluded.

The historical Task 175 first-success gaps (`request: null`, missing
advertisement evidence, and `marker_observed=false` despite marker text) and
Task 175D malformed JSONL remain preserved. Task 175F/175G provide corrected
prospective evidence and do not rewrite history.

## 11. Known limitations and deferred work

The following remain intentionally deferred and are not v0.14 defects:

- arbitrary directory or recursive move;
- overwrite/replace;
- Windows case-only rename;
- untracked or dirty-file rename;
- generic `fs.rename`, `fs.write`, or `fs.unlink`;
- generic `shell.exec` or `process.exec`;
- model-selected executable, argv, cwd, or environment;
- generic Git and branch/ref/history mutation beyond existing reviewed commit authority;
- network Git;
- rollback or transaction guarantees;
- OS sandboxing and network isolation;
- cross-volume copy-delete fallback;
- profile hot reload or dynamic authority composition; and
- Linux live certification.
