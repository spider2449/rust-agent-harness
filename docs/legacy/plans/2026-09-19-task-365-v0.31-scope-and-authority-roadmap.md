# Task 365 — RAH v0.31 Scope and Authority Roadmap

Date: 2026-09-19
Status: **RECOMMENDATION — READY FOR TASK 366 CONTRACT RESEARCH**
Task type: research and product scope only

## Decision

The sole v0.31 primary capability is:

**Bounded Repository Discovery / Search**

The product problem is that RAH can safely read and modify repository content
once a path is known, but the agent has no first-party, repository-bounded way
to discover the relevant path or matching code in an unfamiliar repository.
Today the user must supply the path or use an external editor/shell before the
RAH workflow can begin. v0.31 should remove that discovery friction while
preserving the existing host-owned repository and ToolRegistry boundaries.

The intended product loop is:

```text
host-selected active repository
  -> bounded host-owned discovery/search
  -> repository-relative candidate paths or bounded matches
  -> existing fs.read / repo.file-info
  -> existing edit, review, stage, and commit workflow
```

This is one capability, not two co-equal winners. Task 366 may determine
whether the smallest production surface is one closed-mode `repo.search` Tool
or narrowly specified path and text discovery Tools.

## Authority classification

**NARROW EXTENSION.**

Discovery extends existing repository read/observation authority from a known
path to bounded discovery within the active selected repository. It increases
read disclosure breadth, so it is not `NONE`. It adds no new `PermissionLevel`,
mutation authority, executable/process authority, network authority,
credential authority, persistence authority, Git index/ref/history authority,
or cross-repository routing authority.

No new authority ADR is expected for this scope. If Task 366 finds that the
implementation requires a persistent index, an out-of-repository cache,
background scanning, an external executable, network access, or
cross-repository scope, implementation must stop and the authority
classification must be revisited before code is written.

## Authority and privacy contract for the next task

Task 366 must convert this roadmap into an implementation contract, while
preserving these non-negotiable boundaries:

### Selected-root only

When linked worktree A is active, discovery is limited to A's repository
content namespace. A shared common Git directory does not authorize inspection
of the main worktree or sibling B. No Tool input may contain a repository,
member, worktree, or root selector supplied by the model.

### Host-owned identity

The host selects and captures the active repository before dispatch. Model
output, provider metadata, repository content, remembered candidates, and
frontend confirmation cannot grant or retarget discovery authority.

### Bounded disclosure

Task 366 must decide hard limits for candidate entries, matches, files
inspected, per-file bytes, snippet bytes, total ToolOutput, and execution time.
The result must remain useful on a large repository without producing
unbounded model context.

### Deterministic observation

Results must have stable repository-relative lexical ordering, bounded match
presentation, and stable snippet rules. Unknown results must be a deterministic
empty result or a defined bounded status; discovery must not fall back to
unbounded scanning.

### Confinement and private metadata

Traversal must fail closed for symlinks, junctions, Windows reparse points,
nested repository boundaries, `.git`, private linked-worktree metadata, common
Git storage, gitfiles, backlinks, registration data, absolute filesystem
identities, and authority generations. Errors and ToolOutput may expose only
safe repository-relative paths and bounded content required by the contract.

### Point-in-time and uncertainty

Discovery is a best-effort point-in-time observation. It must not claim a
transactional repository snapshot, global filesystem lock, race-free TOCTOU,
rollback, or replay. Enumeration races, cancellation, and timeout must produce
a conservative bounded result or a defined failure without retrying an
external effect.

## Candidate inventory policy

The initial policy candidate for Task 366 is tracked files plus ordinary
untracked, non-ignored files. `.git`, ignored files, build outputs, credential
stores, arbitrary parent directories, and private linked-worktree/common Git
metadata are not part of the default inventory.

This is a research input, not a frozen schema. Task 366 must decide the exact
tracked/untracked/ignored inclusion rules using adversarial fixtures and must
record whether fixed host Git is used for inventory. Filesystem enumeration
must not silently broaden the disclosure policy.

## Candidate decisions

| Candidate | Authority | Product assessment | v0.31 disposition |
|---|---|---|---|
| A. HostExplicit `repo.create-directory` | Narrow extension | Existing ordinary Tool already covers the operation; only direct reviewed invocation is missing. Lower leverage than discovery. | Defer; keep HostExplicit at exactly 11. |
| B. Durable session/workflow continuity | None if descriptive only | Conversation persistence, explicit resume, and remembered candidates already exist. | Defer as UX refinement. Preserve inert restart semantics. |
| C. Network MCP / Streamable HTTP | New authority category | Adds endpoint identity, DNS/TLS, credentials/OAuth, redirects, SSRF, cancellation, and remote-effect concerns. | Defer. |
| D. Plugin lifecycle UX | Narrow extension | Useful for configured process plugins, but not the highest-frequency repository blocker and must not grow into install/download. | Defer. |
| E. Trusted Profile reload | Narrow extension | Useful but profile composition and provider teardown are already explicit. | Defer. |
| F. GUI automation infrastructure | None | Improves release evidence rather than the end-user repository capability. | Defer. |
| G. Git worktree lifecycle | New authority category | `add`, `remove`, `move`, `prune`, and repair mutate worktree/filesystem/shared Git lifecycle state. | Defer. |
| H. Bounded Repository Discovery / Search | Narrow extension | Removes the high-frequency unfamiliar-codebase blocker without mutation, network, persistence, or generic process authority. | **Select as the sole primary capability.** |

## Explicit v0.31 non-goals

v0.31 does not add:

- a new `PermissionLevel` or generic filesystem/read/write authority;
- generic `shell.exec`, `process.exec`, arbitrary Git, or an `rg`/`grep`/`find` shell shortcut;
- network Git, remote MCP, credentials, OAuth, or endpoint configuration;
- worktree add/remove/move/prune/repair/lock/unlock lifecycle effects;
- multiple active repositories, cross-worktree selectors, or a union ToolRegistry;
- persistent executable repository authority, automatic profile hot reload, or
  model-created persistent indexes;
- background indexing, vector/semantic indexing, or an out-of-repository cache;
- HostExplicit discovery or HostExplicit `repo.create-directory` #12.

## Required Task 366 research questions

Task 366 remains research/design only and must decide:

1. The exact closed Tool surface and input/output schemas.
2. Whether path/name discovery and bounded text-match discovery share one Tool
   or use separate narrowly specified Tools.
3. Tracked, untracked, ignored, generated, and nested-repository inclusion.
4. Selected linked-worktree semantics and the treatment of common Git storage.
5. Symlink, junction, reparse, gitfile, and repository-boundary behavior.
6. UTF-8, invalid UTF-8, binary, oversized-file, and NUL handling.
7. Per-file, aggregate, match, snippet, output, timeout, and cancellation caps.
8. Ordering, truncation/status semantics, unknown-result behavior, and errors.
9. Privacy/redaction rules for paths, snippets, metadata, and failures.
10. Whether fixed host Git is needed for inventory and what currentness it proves.
11. Deterministic tests, Windows fixtures, and release-gate evidence.

Task 366 must not write Rust, introduce dependencies, create an ADR, or broaden
the authority classification without contrary evidence.

## Deterministic and Windows evidence target

The later implementation/audit sequence must cover at least:

| Fixture/class | Required evidence |
|---|---|
| Normal and unknown repository results | Bounded path/text discovery and deterministic empty result. |
| Large repository and oversized file | Candidate, inspected-file, output, and time bounds; defined skip/reject behavior. |
| Binary and invalid UTF-8 files | No binary-as-text disclosure and deterministic encoding handling. |
| Symlink, junction, and reparse fixtures | No traversal beyond the selected safe namespace. |
| Nested repository and `.git` | Nested authority boundary and private Git metadata remain undiscoverable. |
| Linked worktrees A/B and common Git storage | Active A can find A content only; B/main/private/common metadata do not appear. |
| Tracked, untracked, and ignored files | Exact inventory policy is exercised, not inferred from platform enumeration. |
| Enumeration race, cancellation, and timeout | Conservative bounded termination with no retry/replay claim. |
| Tool and error output | Only safe relative paths/snippets; no absolute or private paths. |

Windows live certification should use a fresh disposable fixture containing an
ordinary main worktree, linked A/B, tracked source, untracked non-ignored
source, ignored content, nested repository, junction/reparse adversarial case,
oversized/binary files, and result saturation. It must prove that active A's
safe returned path can be consumed by existing `fs.read` while no sibling or
private Git content is disclosed. It must remain host-driven production
evidence and must not claim GUI automation, model-selected dynamic Tool
dispatch, race-free TOCTOU, network isolation, rollback, or OS sandboxing.
