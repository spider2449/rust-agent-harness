## Milestone definition

The v0.19 milestone is bounded local branch creation at the exact host-captured
attached committed `HEAD`. One authorized request may create exactly one absent
ordinary local ref:

```text
refs/heads/<validated-name> -> <host-captured-attached-HEAD-OID>
```

The only permitted secondary effect is Git-owned reflog state for that new ref,
with the fixed host-controlled message and identity. Creation does not switch
branches or change `HEAD`, the index, worktree, tracking, existing refs, tags,
remotes, conversation state, or runtime/provider generations.

Branch switching, checkout, create-and-switch, existing-ref mutation, delete,
rename, tags, tracking/upstream setup, remote Git, arbitrary revision/OID
input, generic Git/ref authority, and shell/process authority are outside this
milestone.

## Authority boundary

Current source confirms that `RepositoryBranchCreationPolicy` remains private
to `crates/rah-tools/src/repository_branch_create.rs`. The only public branch
surface exported by `crates/rah-tools/src/lib.rs` is:

- `RepositoryBranchCreationAuthority`;
- `RepositoryBranchCreationTool`;
- `REPOSITORY_CREATE_BRANCH_TOOL_NAME`.

The model-facing parser accepts exactly one JSON property, `name`, and passes
no repository, executable, OID, revision, ref, force, tracking, checkout,
hook/config, argv, or environment field. `PermissionLevel::Execute` is present
only on the Tool definition; it does not construct authority. Trusted Profile
and provider composition have no path to construct this authority. No branch
specific generic ref or Git bypass was found.

Current source and deterministic tests support PASS for this boundary.

## Mutation boundary

The sole production mutation is a host-built native Git argument vector:

```text
update-ref --create-reflog -m "RAH create local branch"
  refs/heads/<validated-name> <captured-OID> <zero-OID>
```

The zero OID is sized to the captured 40- or 64-character object ID, so the
operation is an expected-absence create CAS. The repository lease, fresh
revalidation, explicit selected-root cwd, cleared/bounded environment, fixed
hooks/config values, timeout, and output limits are host-controlled. There is
one possible mutating process per Tool execution. A CAS race, timeout,
cancellation, lost response, or observer uncertainty is not replayed and is
not rolled back. No checkout, switch, `git branch`, reset, restore, delete,
rename, remote Git, or generic update-ref path is exposed.

Current source, Task 227's 29-test gate, and the Windows live effect support
PASS.

## Name/collision boundary

The closed validator is ASCII-only, 1–128 bytes, at most eight slash-separated
components, and at most 48 bytes per component. It rejects empty, leading or
trailing-invalid, dot, `.lock`, Git-special, whitespace/control, Unicode,
Windows device-alias, and `refs/`-prefixed forms. Git's
`check-ref-format --branch` check is only an additional compatibility check and
cannot widen the host language.

Git-owned enumeration is restricted to `refs/heads/`. It is byte-preserving
for names, folds ASCII case only, detects exact and ancestor/descendant prefix
collisions, covers loose and packed heads, and uses a 4096-head and 512 KiB
stdout bound. Tags and remote-tracking heads do not collide with this local
namespace. Deterministic tests cover Unicode rejection, aliases, exact/prefix/
case collisions, packed refs, byte-safe non-UTF-8 name handling, and both
bounds. This is PASS; the byte-safe test is a parser-level fixture rather than
a platform-dependent real non-UTF-8 repository fixture.

## Repository admission

The current policy admits ordinary non-bare repositories with a real `.git`
directory, attached existing committed `HEAD`, conventional files ref storage,
and ordinary dirty, staged, mixed, shallow, sparse, or alternate-object state.
It rejects detached and unborn `HEAD`, bare repositories, `.git` indirection and
linked worktrees, unsupported ref storage, and merge, cherry-pick, revert,
squash, bisect, rebase, or sequencer markers. Repository and Git executable
identity are revalidated. Deterministic fixtures cover these admission paths.

The accepted scope is intentionally conventional files-backed repositories;
linked-worktree and reftable support remain deferred by ADR 0020. The evidence
does not claim broader special-topology support than the tested admission
contract.

Status: PASS.

## Outcome/uncertainty handling

The exact private/public-sanitized taxonomy is:

`invalid_input`, `precondition_failed`, `known_no_effect`,
`branch_created_verified`, `desired_state_observed_after_uncertain_attempt`,
and `uncertain`.

`known_no_effect` requires fresh proof of both target-ref absence and target
reflog absence, with protected attached `HEAD` state intact. A nonzero process
result alone is insufficient. Verified success requires clean process status,
exact target/OID, unchanged symbolic `HEAD`/current branch/HEAD OID, and the
fixed acceptable reflog entry. Desired-state-after-uncertain requires the
desired ref, OID, protected state, and acceptable reflog evidence but remains
error-like and does not authorize replay. Fully uncertain or incomplete
observation remains conservative. Current tests cover spawn failure, CAS race,
lost result, missing/wrong/ambiguous reflog, and observer uncertainty.

Status: PASS.

## Hooks/config/identity hardening

The policy creates a unique canonical empty hooks directory outside the selected
repository, captures its identity, and revalidates canonical path, identity,
and emptiness before each Git spawn. A hostile repository `core.hooksPath` is
overridden by the host-pinned absolute hooks path. Cleanup removes the directory
only while it is still the captured safe empty object; attacker content is not
recursively deleted. Git executable identity, repository identity, topology,
and ref backend are revalidated. System/global configuration and prompting are
disabled; safe.directory, hooks, reflog behavior, and host identity are pinned.

Deterministic tests cover hostile hooks/configuration, extra content, replacement
directories, executable replacement, repository replacement, and cleanup.
Canonicalization and identity revalidation reduce TOCTOU exposure but do not
claim race-free exclusion from external Git, editors, sync, antivirus, or
privileged processes.

Status: PASS.

## Review/currentness semantics

The Task 228 correction remains in current source. The Desktop branch-result
parser requires one JSON object with exact status-specific keys, matching
`is_error`/`uncertain` semantics, a non-empty name, and a full 40- or 64-character
hex OID where required. Safe exact outcomes preserve reviewed commit
authorization: `invalid_input`, `precondition_failed`, `known_no_effect`,
`branch_created_verified`, and
`desired_state_observed_after_uncertain_attempt`. Malformed or fully uncertain

namespace unchanged. Deterministic Desktop tests and the host-driven live gate
cover these semantics.
