## Result

Diagnosis category: **C. CODEX LOCAL CONFIG DRIFT**.

The certified executable is unchanged, but it does not run in an immutable
environment. The archived `codex-cli 0.149.0` process loads the mutable user
configuration at `C:\Users\spider.tp\.codex\config.toml`. The current file selects
`gpt-5.6-terra` with low reasoning effort and defines a Desktop-managed
`node_repl` MCP/code-mode environment. That environment references mutable
Desktop runtime paths and a current global Codex CLI path.

With that configuration, a fresh certified live `echo` probe advertised its
dynamic tool and successfully created a thread and turn, but the model
completed without a tool request, stating exactly: `Unable to call the echo
tool: code-mode host executable is missing.` The multi-patch gate showed the
same generic failure mode: fresh turns completed without dynamic tool calls and
stated that the RAH repository toolkit was unavailable.

This rules out `repo.patch` as the first failure point. It also rules out the
uncommitted Task 080 release-preparation patch: the clean Task 079 source has
the same behavior, and the Task 074 multi-patch example source blob is identical
at Task 074 and Task 079.

threads, turns, and fixtures. The first two reached `Completed` with no RAH

- `Unable to access the RAH repository toolkit.`

The first event sequence was:

```text

```

The third fresh attempt passed the turn-level marker check but failed the later
fixture postimage assertion, which is additional evidence that the live service

authority change.

The minimal `live_echo_bridge` probe independently reproduced the failure. It
printed its advertised dynamic tool definition, received successful initialize,
thread creation, and turn creation, then completed with zero requested/started/

response. App-server notifications also reported `mcpServer/startupStatus/updated`.

The repository-observer-only probe also failed its marker check. Consequently
the evidence does not isolate the issue to `repo.patch`; a patch-schema probe
would not be informative until generic dynamic tool availability is restored.

## Tool advertisement and restricted authority

The live fixture's real fresh composition contains only `repo.diff`,
`repo.diff-staged`, `repo.file-info`, `repo.patch`, and `repo.status`, all at
the existing `PermissionLevel::Execute`. The private aliases are:

```text
repo.diff -> rah_tool_0
repo.diff-staged -> rah_tool_1
repo.file-info -> rah_tool_2
repo.patch -> rah_tool_3
repo.status -> rah_tool_4
```

The adapter serializes these under `thread/start.params.dynamicTools`; that
request succeeds before `turn/start`, so app-server did not reject the tool
definitions at protocol validation. The bridge still keeps approvals `never`,
sandbox read-only, and Codex shell/file/MCP/web/image/apps capabilities disabled
in its own request configuration. No RAH authority, permission, schema, or
Generic Tool Bridge semantic change is warranted.

## Reproducibility limitation and recommended next task

The current baseline pins only the executable version and SHA. It leaves model
default, reasoning default, user configuration, feature flags, Desktop-managed
MCP/code-mode setup, and service-side behavior mutable. Thus an immutable binary
alone is not a reproducible live gate.

Recommended next task: create a host-controlled, isolated live-gate Codex home
configuration that pins the approved model and reasoning settings, disables all
user MCP/plugins/feature leakage, and supplies authentication without logging
credentials. It should log a redacted configuration fingerprint and exact
effective model/config before the live probe. Validate generic `echo` first,
then the observer profile, and only then rerun the multi-patch gate. This must
not broaden RAH authority or promote `0.149.1`.
