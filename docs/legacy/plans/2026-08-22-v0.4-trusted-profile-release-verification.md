# Task 040 plan: v0.4 trusted-profile release verification

## Objective

Close the remaining trusted-profile release-verification gates without adding
authority, providers, profile features, or a release artifact.

## Actual composition seam

The tested seam is `rah-cli/src/profile_composition.rs::compose`, which is the
same private function invoked by `rah profile validate-effective`. Its fixed
order is built-ins, all MCP providers, then all Process Plugin providers.
The returned aggregate owns MCP and Plugin adapters and shuts down Plugins
before MCP adapters.

## Evidence added

- A mixed static profile loads one `fs.read` capability, one MCP echo provider,
  and one Process Plugin echo provider through the real composer.
- The test proves the final fresh registry has exactly those three tools,
  resolves and executes both external proxies, retains host-assigned `None`
  permissions, and reports both providers as validated.
- A second test stages the MCP provider and then causes a Process Plugin schema
  admission mismatch. The composer returns `ExternalProviderFailed` and has no
  success aggregate from which a registry or effective inventory can be read.

## Remaining release evidence

The current fixture/profile interface does not provide a test-only lifecycle
marker to observe reaping of adapters consumed by a failed mixed composition.
The two tests therefore validate the real atomic return boundary and successful
ownership/use/shutdown call, but do not yet prove provider exit with a
fixture-owned counter. The required opt-in trusted-profile-to-Codex Generic
Tool Bridge live run is also not implemented or executed by this increment.
Accordingly this document does not promote Task 040 to release-ready.

Task 041 supersedes the deterministic lifecycle gap with bounded fixture audit
files and executable-unlock reaping checks; see
`2026-08-22-mixed-composer-verification-matrix.md`. The opt-in Codex live gate
remains unresolved and is intentionally outside this verification increment.
