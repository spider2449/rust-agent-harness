## Milestone capability

The implemented v0.22 capability is exactly **HostExplicit Reviewed
Multi-File Edit Authoring**.

A connected-current Desktop human can enter one bounded typed change-set over
one through four existing clean HEAD-tracked strict-UTF-8 files, inspect a
complete backend-derived review, explicitly confirm with an opaque ticket, and
reach the already-existing `repo.edit-files` Tool. The operation is then
refreshed through descriptive repository observation. Stage, Unstage, and the
reviewed Commit workflow remain separate explicit operations.

The underlying mutation authority remains ADR 0014's private
`RepositoryMultiFileMutationPolicy`. v0.22 adds the capability-specific
HostExplicit workflow, not a new repository mutation authority.

The product flow is:

```text
typed human request
  -> zero-effect Prepare
  -> complete ordered backend review
  -> ticket-only Confirm
  -> shared revalidation and D2
  -> HostExplicit Started
  -> authorized_tool_dispatch
  -> ToolRegistry
  -> existing repo.edit-files / ADR 0014
  -> strict result classification and descriptive refresh
```

This is one confirmed non-atomic change-set, not four independent actions and
not a transaction.

## Prepare, Review, and Confirm contract

### Typed human request

The production human Prepare schema is closed and contains only:

```text
targets[] {
  path
  replacements[] {
    expectedOldText
    replacementText
  }
}
```

Unknown fields are rejected by `deny_unknown_fields`. The human supplies no
hashes, byte lengths, canonical paths, native paths, repository root, Tool
name, Tool input, permission, provider, authority flags, execution order,
execution controls, or model metadata. The host derives all such values.

The semantics are exact literal matching against one original snapshot. No
regex, glob, fuzzy matching, unified diff, range language, normalization,
case folding, or newline conversion is present. Targets are bounded to 1–4;
replacements are bounded to 1–16 per target and 64 total, with the existing
path, text, request, file, aggregate-image, and review limits.

### Zero-effect Prepare and revalidation

Task 259's `RepositoryMultiFileEditPreparer` owns the shared non-effectful
contract. Prepare and revalidation derive canonical host order, target and
parent identities, tracked-clean/index-consistent Git state, strict UTF-8
preimages, exact literal ranges, complete postimages, SHA-256 values and
lengths, canonical existing ToolInput, review identity, and protected
repository observations.

The deterministic and live evidence proves Prepare performs:

- zero Tool executions;
- zero native replacement attempts;
- zero user-visible worktree mutations;
- zero repository-adjacent mutation temporary artifacts;
- zero index, Stage, Unstage, Commit, HEAD, branch, ref, tag, or history
  changes;
- zero model/runtime lifecycle events;
- zero provider activation or provider execution; and
- zero persistent ticket/capability writes.

The effectful ADR 0014 path retains its own repository-adjacent temporary
handling; that is not reused by zero-effect HostExplicit Prepare.

### Complete backend-derived review

The review contains, for every host-ordered target:

- operation `repo.edit-files`;
- total target and replacement counts;
- stable ordinal and canonical logical path;
- replacement count;
- every changed byte range;
- complete escaped old text and complete escaped replacement text;
- preimage SHA-256 and byte length;
- postimage SHA-256 and byte length;
- exact original-snapshot literal matching semantics;
- an unchanged-context statement;
- the intended effect;
- protected non-effects; and
- the explicit non-atomic warning.

Mutation-relevant material is never clipped, ellipsized, or silently
redacted. If changed material or the complete review exceeds its bound,
`review_too_large` fails closed and produces no ticket. The frontend renders
the returned review as text; it cannot replace it with a hidden editor.

### Ticket-only Confirm

Confirm and Cancel receive only `{ ticketId }`. They do not accept or
resubmit source, paths, hashes, lengths, ToolName, ToolInput, permission,
provider, repository, authority, or model data. The ticket is RAH-generated,
opaque, process-local, in-memory, nonserializable as durable authority,
capability-specific, single-use, exact-change/currentness-bound, and has the
inclusive five-minute TTL established by the HostExplicit precedent. Restart,
disconnect, cancellation, expiry, stale currentness, or consumption does not
restore it and no automatic replacement ticket is issued.

The coordinator consumes/reserves the ticket before asynchronous revalidation.
At most one Tool execution can follow one Confirm. Duplicate, expired,
cancelled, stale, malformed, wrong, or activity-ID-as-ticket requests fail
closed. A ticket is never a permission grant or a replacement for the
underlying ADR 0014 policy.

Immediately before `Started`, the backend rechecks the current Tool name and
complete `ToolDefinition`, permission membership, registry/composition
identity, repository identity, repository/model/profile/connection generation
tuple, retained preparer identity, exact retained plan/review identity, and
all target/preimage/index/HEAD/ref/currentness assumptions. Effective Authority
membership is recomputed from the current host composition and exact
capability classification; frontend authority snapshots are not trusted.
Name-only equivalence is insufficient.

The dispatch path is exactly:

```text
authorized_tool_dispatch
  -> ToolRegistry
  -> existing repo.edit-files Tool
  -> ADR 0014 RepositoryMultiFileMutationPolicy
```

There is no direct `Tool::execute` shortcut, parallel live-only mutation route,
generic registry shortcut, model/runtime substitution, or fabricated model
lifecycle.

## Ticket/activity privacy correction

Task 262's original privacy assertion checked prohibited field/key text,
including `ticketId`, but did not place a distinctive ticket value into the
serialized activity. It therefore missed the value-level leak where the
production Prepared activity emitted the ticket under `invocationId`.

Task 263 Attempt 1 B discovered that defect. It stopped before Confirm with
zero production effect and recorded the failure historically. The correction
introduced separate values:

- `ticket_id`: authority-bearing, private, process-local coordinator key;
- `activity_id`: RAH-generated, non-authority correlation metadata.

The activity ID is generated independently, is not derived from the ticket,
cannot Confirm, cannot Cancel, and is never authority. The separation applies
to `repo.create-branch`, `repo.patch`, and `repo.edit-files`.

Current value-level tests use
`RAH_SECRET_AUTHORITY_TICKET_SENTINEL`: serialized activity contains the
activity ID, excludes the actual ticket value, excludes `ticketId`, and
rejects the activity ID for both Confirm and Cancel. Task 263 Attempt 2
repeated those checks in the production Windows run.

No source-bearing content is persisted into generic activity, conversation,
transcript, logs, telemetry, or evidence surfaces. The bounded local review
and pending process-local authorization are the only source-bearing surfaces.

## Six result classes and non-atomic effects

ADR 0014's six result classes remain distinct and are strictly validated:

```text
ok
invalid_target
precondition_failed
failed_known_no_effect
partial_effect
uncertain
```

Malformed, contradictory, wrong-shape, wrong-order, impossible, or
source-bearing output is unsafe/unknown and is never presented as verified
success. `partial_effect` retains only the verified committed prefix and
classifies the remainder only where proven. `uncertain` preserves unknown
effects without an unchanged inference. The consumed ticket remains consumed
in every case.

There is no retry, replay, prefix continuation, rollback, restore-preimage,
compensation, Stage, Unstage, Commit, or atomicity claim. Timeout, cancellation,
disconnect, crash, or lost response does not imply rollback. Repository refresh
is observation and reconciliation only.

## Repository-bound Commit invalidation and refresh fallback

`repo.patch` and `repo.edit-files` are repository-bound authoring operations.
If the reviewed operation reaches `Started`, existing repository-bound
reviewed Commit authorization is invalidated conservatively, including when
the owned post-Started authorized-dispatch recheck rejects. A fresh repository
review is descriptive only and does not reauthorize Commit, create an edit
ticket, or perform Stage/Commit.

Task 263 found a narrow refresh issue: the optional Commit review correctly
rejects an empty staged index, which made a descriptive post-edit refresh fail
even though status and worktree observation were available. The production
correction in `desktop_repository_snapshot_with_review` preserves status and
worktree/staged-diff observation by falling back to the existing staged-diff
observer when the optional Commit review is unavailable. The fallback returns
`NoStagedChanges` for an empty staged state, creates no fabricated Commit
review, and leaves Commit authorization revoked. Genuine status, worktree-diff,
staged-diff, and output-normalization failures still propagate as observation
failures; the fallback is descriptive and does not bypass Commit authority.

This correction is classified as a narrow observation-refresh correction, not
a new authority or a release capability.
