## Decision-only scope

This is a research and design-selection document. Task 290 changes no Rust,
frontend behavior, tests, Tool schema, HostExplicit eligibility, accepted ADR,
Cargo metadata, dependency, tag, or release. It starts no implementation,
certification, or follow-on task.

The recommendation is deliberately limited to one user/product capability.
Existing authority planes remain separate, model output remains untrusted, and
the released v0.24 security model remains the baseline.

## Released v0.24 baseline

The exact production HostExplicit set is:

```text
fs.read
repo.file-info
repo.status
repo.diff
repo.diff-staged
repo.create-branch
repo.patch
repo.edit-files
repo.create-file
repo.delete-file
```

This is an exact host-owned set. It is not inferred from `Execute`, Tool
presence, effect category, Effective Authority visibility, provider metadata,
model output, or frontend state.

The released human workflow can therefore complete, within its bounded
contracts:

```text
inspect repository
 -> create a local branch
 -> review and edit existing files
 -> create files under existing safe directories
 -> delete narrowly reviewed clean tracked files
 -> explicitly Stage or Unstage
 -> use the separate reviewed staged-snapshot Commit workflow
```

`repo.patch`, `repo.edit-files`, `repo.create-file`, and `repo.delete-file`
reach their existing Tools through zero-effect capability-specific Prepare,
complete review where required, an opaque process-local ticket, ticket-only
Confirm, currentness checks, D2, HostExplicit Started, authorized dispatch,
and the current ToolRegistry. The ordinary underlying registry also contains
separate first-party foundations for `repo.rename-file`,
`repo.create-directory`, and `repo.commit`, but those names are not in the
HostExplicit set.

The current source confirms that `RepositoryFileRenameTool`,
`RepositoryDirectoryCreationTool`, and `RepositoryCommitTool` are distinct
host-constructed capabilities. It also confirms that `host_kind` rejects
`repo.rename-file`, `repo.create-directory`, and `repo.commit`, and that the
Desktop HostExplicit composition has no retained rename or directory
preparer. Effective Authority classification of those capabilities is
observational and does not make them eligible.

## Actual product gaps

### What users can finish today

For ordinary repository authoring, the released path covers the common edit
loop: inspect status and diffs, make a bounded edit, create a new file in an
existing directory, remove a clean tracked file, stage/unstage explicitly,
and commit an already reviewed staged snapshot through the separate Desktop
Commit workflow. Branch creation is also bounded and separate from checkout.

The result is a real worktree authoring workflow, not generic filesystem or
Git authority. It deliberately stops at the boundaries of the selected
operation, with no automatic rollback, cleanup, Stage, Commit, or retry after
an uncertain effect.

### Where users still leave the reviewed RAH route

The remaining structural gap is path topology. A human can edit content,
create a file under an existing parent, and delete a tracked file through
reviewed HostExplicit routes, but cannot perform a reviewed HostExplicit
rename/move or create a directory. A user must use another UI/CLI, rely on an
ordinary model/runtime Tool route where configured, or perform those actions
outside the released typed human workflow.

The final history step is a different kind of gap. RAH already has a
host-reviewed Commit authorization and a bounded `repo.commit` foundation;
the absence of a generic HostExplicit commit route is primarily a reachability
and convenience question, not an absent authority foundation.

Session continuity is also not absent: bounded descriptive transcript
persistence and descriptive resume already exist. What is intentionally
absent is durable or resumable authority. That distinction is security
critical.

### Product prioritization

The most frequent missing operation in normal coding/refactoring among the
remaining structural operations is moving or renaming an existing source,
test, documentation, or configuration file. Refactoring commonly changes
path ownership while preserving file bytes. This is not merely symmetry: two
existing file operations are not an equivalent rename, because their effect
boundaries and failure outcomes differ.

Directory creation is a meaningful blocker when a new module, package,
fixture, test, or documentation folder must be created before its first file.
However, one-level directory creation is only one empty leaf per authorization;
Git does not track the empty directory, and `repo.create-file` still needs a
second authorization. Recursive package hierarchies remain multiple explicit
operations.

Commit matters for end-to-end completion, but current Desktop already lets a
human observe the staged review and authorize the exact staged snapshot before
the existing `repo.commit` path. HostExplicit `repo.commit` would reduce
friction, but it would duplicate an existing human-reviewed surface while
adding a direct route to Git objects and the current branch ref.

## Decision matrix scoring

Scores are ordinal from 1 to 5 and are positive release-fit scores:

- 5 means more product value, lower risk/cost, or easier proof;
- 1 means less product value, a larger authority jump, or harder proof; and
- for `authority increase`, 5 means no new underlying authority and only a
  narrow presentation/binding route, while 1 means network, install, durable,
  or dynamic-authority semantics.

The matrix is a prioritization aid, not an authorization. A high product score
cannot override an unacceptable authority delta. The security columns are
intentionally separate from user value.

### Matrix reading

A has the highest product fit because it closes a common refactoring operation
with one coherent filesystem effect and no history/ref mutation. Its security
score is not perfect: two path identities, destination absence, parent
identity, Windows alias/case behavior, same-volume requirements, and
post-effect attribution are materially harder than deletion or creation.

B has the best deterministic and privacy profile, but its product value is
smaller. An empty directory can persist after a later file-creation failure
while Git remains clean. It is a credible second milestone, not a reason to
invent recursive or idempotent semantics.

C has a mature underlying authority, but its authority increase is lower
because HostExplicit would expose a direct human route to durable Git history
and the current branch ref. The existing reviewed Commit workflow already
solves the underlying human authorization problem.

D is attractive as a convenience layer but is not a safe “transaction.”
Existing edit-files is explicitly non-atomic, while create, delete, rename,
and directory effects have different preimages, commit points, and result
taxonomies. One review over a heterogeneous sequence would need to specify
partial effects and ordered invalidation without being able to roll back.

E is useful only when kept descriptive: saved draft inputs and authoring
context may improve continuity, but a prepared ticket or retained authority
cannot be serialized, restored, or replayed. Descriptive persistence does not
close the missing structural operation.

F, G, and H are larger platform/lifecycle milestones. They add trust or
revocation problems unrelated to completing ordinary local repository work.

## Candidate A — HostExplicit reviewed file rename/move

### Product capability

The proposed capability is exactly one human-reviewed movement of one clean,
HEAD-tracked regular file:

```text
human {source_path, destination_path}
 -> zero-effect rename Prepare
 -> complete path/preimage/absence review
 -> opaque currentness-bound ticket
 -> ticket-only Confirm
 -> D2 and exact ToolDefinition/permission checks
 -> HostExplicit Started
 -> authorized_tool_dispatch
 -> current ToolRegistry
 -> existing repo.rename-file / ADR 0018
```

It supports same-directory rename and same-repository cross-directory move.
The destination parent already exists; directory movement, recursive movement,
cross-repository movement, overwrite, and destination creation are excluded.

### Existing ADR and implementation maturity

ADR 0018 is unusually complete for an accepted underlying authority. It
requires a clean HEAD-tracked regular source, exact source bytes and length,
an absent destination, existing and identity-bound destination parent, safe
ancestry, no-replace semantics, supported same-volume behavior, one native
attempt, post-observation, and conservative `renamed_verified`,
`known_no_effect`, `precondition_failed`, `invalid_input`, and `uncertain`
outcomes. It rejects `git mv`, copy-plus-delete, shell/process fallback, and
case-only Windows workarounds.

The current `RepositoryFileRenameTool` implements the separate ordinary
authority and deterministic tests cover same-directory rename, cross-directory
move, malformed/colliding requests, missing parents, destination collision,
stale/dirty source, destination race, aliases, source drift, and no retry
after uncertain observation. The current Desktop registry can compose this
ordinary Tool when the host supplies `RepositoryFileRenameAuthority`.

That maturity is not enough for HostExplicit. The current code has no
rename-specific zero-effect preparer, complete human review DTO, retained
preparation variant, eligibility kind, typed Tauri Prepare/Confirm route, or
frontend review surface. Those are the missing layers, not an invitation to
change the underlying rename policy.

### Capability-specific research still required

Task 291 must settle the reviewed-route contract, including:

- whether HostExplicit restricts the ordinary 1 MiB/binary source surface to a
  complete strict-UTF-8 reviewable subset, as deletion does, or provides a
  bounded complete byte representation;
- complete display of source/destination logical paths, source preimage facts,
  existing parent identities in sanitized form, destination absence, and all
  non-effects;
- host derivation of source SHA-256 and byte length for the unchanged Tool
  input, rather than human-supplied authority fields;
- exact binding of source and destination parent identities and absence
  observations;
- Windows case-insensitive collisions, Unicode normalization aliases,
  trailing-dot/space aliases, reserved names, and explicit rejection of
  case-only rename;
- native no-replace and same-volume proof without assuming that rename is
  atomic on every platform;
- postcondition proof of source absence, exact destination bytes and supported
  identity semantics, unchanged index/HEAD/branch/refs, and no second effect;
- treatment of timeout, cancellation, disconnect, crash, lost result, sharing
  failure, and failed observation as `uncertain` unless independently proven;
- Commit authorization invalidation when effectful HostExplicit Started is
  reached; and
- no automatic copy-delete fallback, move-back compensation, retry, replay,
  cleanup, or rollback.

The source implementation currently uses the platform-specific native
no-replace primitive permitted by ADR 0018. A future HostExplicit route must
not convert that into a generic `fs.rename` promise or a race-free TOCTOU
claim.

## Candidate B — HostExplicit reviewed directory creation

### Product capability

The narrow candidate is exactly one absent ordinary directory leaf under one
existing safe parent:

```text
human {path}
 -> zero-effect directory Prepare
 -> review parent and target absence
 -> opaque ticket
 -> ticket-only Confirm
 -> D2 -> HostExplicit Started
 -> authorized_tool_dispatch -> ToolRegistry
 -> existing repo.create-directory / ADR 0019
```

It is not recursive creation, `mkdir -p`, ensure-directory, idempotent
success, placeholder-file creation, or implicit file creation. It has one
native creation attempt and may leave an empty directory after a later
separately authorized file creation fails.

### Product blocker analysis

One-level directory creation would directly unlock these first-step workflows:

| Workflow | What one leaf unlocks | Remaining explicit work |
| --- | --- | --- |
| New module directory | A new source/module folder under an existing parent | `repo.create-file` is still needed for the module file |
| New package subdirectory | A package leaf under an existing package root | Each deeper missing ancestor needs another explicit directory operation |
| Test or fixture folder | A test/fixture namespace before its first file | File creation remains separate; an empty folder is Git-invisible |
| Documentation folder | A docs/examples/tutorial leaf | File creation and later Stage/Commit remain separate |

This is a genuine blocker for a new hierarchy, but it does not create a whole
subtree in one call. It also does not complete a Git-visible change by itself.
The product value is therefore lower than rename/move even though the
authority and deterministic proof surface are narrower.

ADR 0019 and the current ordinary Tool are mature enough to reuse: existing
parent, destination absence, safe ancestry, reparse/alias rejection, one
native effect, unchanged Git metadata, and explicit no-replay semantics. A
HostExplicit directory route would still need a capability-specific review
and retained-preparer contract. Its clean Git status after success must not be
mistaken for no filesystem effect.

## Candidate C — HostExplicit reviewed Git Commit

### Existing human-reviewed workflow

The Desktop already owns a reviewed staged-snapshot path. It observes the
staged diff, creates a host-derived review selector, and lets a human authorize
one exact snapshot through `RepositoryCommitControl`. The underlying policy
binds the raw index digest, canonical staged-entry digest, `git write-tree`
OID, attached branch, expected parent, host identity, message constraints,
hook path, signing configuration, and one normal commit attempt. It rejects
detached/unborn state and unsupported Git states and classifies
`committed_verified`, `known_no_effect`, and `uncertain` conservatively.

This is an adequate human-reviewed Commit path for the released product
contract. It may have model/runtime reachability or ergonomics that a future
HostExplicit route could improve, but it is not missing authority or review.

### Why not now

HostExplicit `repo.commit` would duplicate the existing review/control surface
while making a generic host action directly advance the current branch ref and
create Git objects. It would need a separate typed message/review route,
exact staged tree and parent binding, commit identity and hook/signing review,
one-shot consumption, ref postcondition proof, and no replay after an
uncertain result. The authority jump is materially stronger than a local
worktree rename.

The milestone must not add automatic Stage or Commit to rename, directory,
edit, create, or delete workflows. Network Git is excluded. At minimum,
HostExplicit Commit would defer push, pull, fetch, remote credentials, merge,
rebase, reset, checkout/switch, stash, tag creation, arbitrary ref mutation,
and all generic Git or shell execution.

## Candidate D — Reviewed multi-operation authoring

The existing `repo.edit-files` capability already supports a bounded,
reviewed, non-atomic change set over existing files. Adding create, delete,
or rename to the same review would not be a harmless convenience:

- create has exclusive-new-file and possible partial-write semantics;
- delete has destructive preimage and absence-proof semantics;
- rename has two path identities, destination collision, and no-replace
  semantics; and
- directory creation can succeed while Git remains clean.

A heterogeneous sequence would need explicit order, per-operation
currentness, partial-effect inventory, ticket consumption, Commit
authorization invalidation, and post-effect proof. RAH cannot promise a
transaction or rollback across these effects. It would also obscure which
authority was used and make a single human review harder to interpret.

The product benefit is real for convenience, but the authority semantics are
not sufficiently clear for v0.25. The safe composition is separate explicit
operations with separate reviews and no implied transaction.

## Candidate E — Session/workflow persistence

Descriptive persistence can safely preserve conversation history, selected
workflow context, or an uncommitted authoring draft that contains no authority
ticket. It may be useful in a later UX milestone, but current persistence
already covers bounded transcript continuity and marks application restart as
a context separator.

Durable authority-ticket persistence is categorically different. A ticket
would need to bind repository identity, ToolDefinition, permission policy,
profile/model/connection generations, currentness, source/destination
identities, and capability-specific preparation across restart. Restoring it
would introduce durable authority, revocation, migration, stale-state, and
crash semantics. It is forbidden by the current HostExplicit contract and
must not be smuggled into a “session persistence” feature.

E does not close the most frequent remaining repository gap, so it is not the
v0.25 milestone. A later descriptive-only task may be independently valuable.

## Candidate F — Network MCP / Streamable HTTP

The current MCP boundary is a host-configured supervised stdio adapter, not a
network transport. Network MCP would add endpoint trust, TLS/authentication,
credential handling, redirects, DNS and proxy behavior, host allowlists,
SSRF controls, tool-set/schema admission, reconnect/retry semantics, and
uncertain remote effects. Process supervision and protocol validation would
not be an OS or network sandbox.

This is a larger authority jump than required to improve local repository
work. It should remain outside v0.25, with no claim that a configured local
MCP or provider Tool makes network access safe by default.

## Candidate G — Plugin lifecycle / PluginManager

The current Process Plugin boundary admits explicitly configured native
executables with pinned identity, schema, permissions, bounded IPC, lifecycle,
and no automatic replay. It is not an installer, package manager,
marketplace, updater, discovery service, or dynamic-library ABI.

A PluginManager would add install/download/package provenance, executable
replacement and update races, restart/rollback semantics, possible network
authority, and new UI trust decisions. Local Process Plugin execution is not
evidence that package installation or lifecycle management is safe. This
candidate is unrelated to the v0.25 repository-authoring gap.

## Candidate H — Dynamic Trusted Profile reload

Current Trusted Profile persistence is inert preference state. Explicit
Restore reads and statically validates a source; explicit Connect/reconnect
activates a fresh composition. Currentness includes profile and connection
generations, and refresh does not reload or dynamically grant authority.

Hot reload would need a defined revocation model for already prepared tickets,
active Tool executions, provider lifecycle, old/new Effective Authority UI,
and in-flight calls. Generation increments alone do not prove safe revocation
of an effect already Started. The product value is lower than closing a local
authoring operation and the dynamic authority semantics are not yet defined.

## Rename versus `repo.create-file` + `repo.delete-file`

The existing create and delete Tools are not an acceptable semantic substitute
for a reviewed rename/move.

| Concern | Composed create + delete | Dedicated rename/move |
| --- | --- | --- |
| Review burden | Two reviews, two tickets, two currentness snapshots, and two user decisions | One review of source, destination, parents, and absence |
| Effect boundaries | Two persistent commit points; partial completion is normal | One native no-replace attempt |
| Intermediate state | Create-first can temporarily duplicate; delete-first can temporarily lose the source | No RAH-created duplicate or intentional source-loss intermediate step |
| Failure | Create success followed by delete failure leaves both names; delete success followed by create failure risks source loss if ordered that way | `renamed_verified`, `known_no_effect`, or `uncertain` for one possible effect |
| Metadata and identity | New-file creation creates a new file and does not preserve source identity/mode semantics as a rename | Native rename preserves the file bytes and platform-supported entry identity semantics |
| Git meaning | Before staging, typically delete plus untracked destination; Git may later detect similarity but that is not semantic rename authority | Leaves index/HEAD/refs unchanged and represents the intended one-entry move at the worktree plane |
| Collision | Destination collision must be checked independently by create and delete; composition cannot safely bypass it | Destination must be absent and no-replace is part of the authority |
| Uncertainty | One uncertain creation plus one delete cannot be safely compensated; source-loss and duplicate states are hard to attribute | One native attempt; no copy-delete fallback or move-back recovery |
| Intent fidelity | Expresses “make these two effects” rather than “move this entry” | Expresses the user's actual path-preserving intent |

ADR 0018 therefore correctly states that creation plus deletion never composes
into rename authority. A later human could intentionally perform two separate
authorizations, but RAH must not present that as a safe or equivalent rename
workflow. A dedicated rename route is materially safer and more truthful.

## Reuse and capability-specific work

### Reuse from released HostExplicit

A rename route should reuse the generic machinery already released and
certified, subject to capability-specific revalidation:

- `HostInvocationCoordinator` and its one-prepared/one-running invariant;
- opaque process-local single-use ticket;
- inclusive five-minute TTL, with elapsed time at or above 300 seconds
  expired;
- distinct activity and ticket identifiers;
- connected-current repository/model/profile/connection generation checks;
- exact ToolDefinition binding and explicit permission membership;
- retained capability-specific preparer identity;
- D2 before HostExplicit Started;
- exactly one dispatch through `authorized_tool_dispatch` and the current
  ToolRegistry;
- generic status-only HostActivity and no raw Tool input/output or native path;
- effectful authoring invalidation of repository-bound reviewed Commit
  authorization at the established Started boundary;
- descriptive refresh only; and
- no replay, retry, rollback, compensation, cleanup, or automatic reprepare.

This reuse preserves ADR 0021 as the generic boundary and avoids an
invoke-any-tool or generic filesystem route.

### New rename-specific preparation and proof

The missing implementation foundation is a `RepositoryFileRenamePreparer`-
style capability-specific, non-effectful preparation contract. Future work
must retain and revalidate at least:

- selected repository, Git executable, root and `.git` identities;
- repository/runtime/profile/model/connection currentness;
- exact source and destination logical paths;
- source regular-file identity and link-count admission;
- source HEAD/tree/blob and exact raw preimage bytes, hash, and length;
- exact normal stage-0 index entry and protected index fingerprint;
- existing source and destination parent identities;
- destination absence, including alias-equivalent and special-object checks;
- supported same-volume/filesystem and platform semantics;
- branch/HEAD/ref observations proving no index/history effect;
- unchanged canonical `repo.rename-file` ToolInput derived by the host;
- exact current ToolDefinition, permission, registry, composition, and
  Effective Authority identities; and
- complete bounded human review identity and retained private state.

Preparation must perform zero Tool executions and zero native rename attempts.
The human supplies paths only; the host derives hashes, lengths, repository,
identity, and Tool fields. Confirm receives only the ticket ID. A future
review contract must choose a complete bounded representation for source
content/format facts; it must not authorize from a truncated preview or a
digest-only hidden source.

## Required authority and ADR implications

The preferred capability requires no new underlying authority. ADR 0018
already fully defines the narrow repository rename/move authority and its
single-effect failure model. The ordinary Tool and policy remain the sole
owners of the filesystem effect.

A new capability-specific HostExplicit ADR is nevertheless required. ADR 0021
is the generic dispatch/currentness/D2/ticket/provenance boundary, but it does
not define rename review, source/destination proof, privacy, result mapping,
or capability-specific Commit invalidation. ADR 0018 explicitly deferred
HostExplicit, Tool registration, Trusted Profile, bridge, Desktop, and live
work. The correct boundary is therefore a new ADR (provisionally ADR 0026),
not an amendment that broadens ADR 0018 and not a new underlying authority.

Task 290 creates no ADR and does not change the current ten-name allowlist.
The allowlist must change only after the future contract, implementation,
deterministic evidence, Desktop review route, and Windows live gate all pass.

## Minimum safe implementation sequence

The minimum safe sequence for the recommended capability is:

1. Capability-specific rename HostExplicit contract research: settle the
   review representation, bounds, exact DTO, identity/currentness binding,
   result mapping, privacy, Windows alias/case behavior, and nonclaims.
2. Accept the new capability-specific HostExplicit ADR (provisionally ADR
   0026), without changing ADR 0018's underlying authority contract.
3. Build a shared zero-effect rename preparation/revalidation foundation in
   `rah-tools`. Prepare must not call the Tool or native rename primitive.
4. Add deterministic Desktop backend integration: typed request/response,
   retained preparer, eligibility, ticket/currentness checks, D2, exact

5. Add the typed Desktop human review surface. It may render the complete

6. Complete deterministic fault, privacy, path-alias, Windows case-only,

10. Publish v0.25 only after exact tag-object and terminal exact-source CI

11. Perform post-release documentation cleanup as a separate descendant, not

The recommended v0.25 milestone explicitly defers:

- HostExplicit one-level directory creation;
- HostExplicit `repo.commit`;
- heterogeneous multi-operation authoring and any transaction/rollback claim;
- recursive `mkdir -p`, directory movement/deletion, overwrite, copy, or
  generic filesystem rename;
- model-selected or provider-selected HostExplicit preparation/execution;
- MCP HostExplicit, Process Plugin HostExplicit, and network MCP/Streamable
  HTTP;
- plugin installation, download, update, restart manager, and package
  provenance;
- dynamic Trusted Profile reload or mid-flight revocation redesign;
- durable ticket persistence, authority serialization, and resume of effectful
  work;
- automatic Stage, Unstage, Commit, restore, cleanup, compensation, retry,
  replay, or recovery journaling;
- push, pull, fetch, remote credentials, merge, rebase, reset, checkout,
  switch, stash, tag creation, arbitrary ref mutation, and network Git; and
- any dependency, Cargo/version, public protocol, provider-neutral core, or
  inference-engine redesign.

## Explicit nonclaims

This roadmap does not claim:

- that the current `repo.rename-file` Tool is HostExplicit eligible;
- that an accepted ADR is implementation or certification evidence;
- that rename is atomic on every supported platform;
- race-free TOCTOU, cross-process exclusion, OS sandboxing, or network
  isolation;
- rollback, compensation, recovery, or safe retry after an uncertain effect;
- semantic Git rename detection or index rename behavior before explicit
  Stage;
- preservation of every platform metadata attribute or source file identity
  where the platform cannot prove it;
- that clean Git status proves a directory effect did not occur;
- that human confirmation, Execute, Tool registration, Effective Authority,
  provider metadata, or frontend state creates authority;
- that conversation/session persistence can carry authority tickets; or
- Linux/macOS production live parity from deterministic tests or Windows
  certification.

## Final recommendation

**Recommend one capability for RAH v0.25: HostExplicit Reviewed File Rename /
Move through the existing `repo.rename-file` Tool.**

It wins because it closes the most frequent remaining structural coding gap,
preserves the user's actual intent in one effect boundary, and adds only a
narrow human review/binding route around an already accepted and deterministic
underlying authority. It materially improves the released workflow without
crossing into Git history/ref mutation, network authority, package lifecycle,
or durable authority.

The runner-up is HostExplicit Reviewed Directory Creation. It has a smaller
security surface and excellent deterministic testability, but one empty leaf
does not create a Git-visible change, does not create a complete subtree, and
still requires a second `repo.create-file` authorization. It is the next
strongest structural candidate, not part of this milestone.

The required authority boundary is:

```text
existing ADR 0018 RepositoryFileRenamePolicy
 + new capability-specific reviewed HostExplicit binding
 + existing ADR 0021 coordinator/currentness/ticket/D2/provenance
```

No new underlying filesystem authority is required. A new HostExplicit ADR is
required because ADR 0018 deliberately does not define the reviewed human
route. The future route must preserve the current Tool schema, current
ToolRegistry dispatch boundary, exact allowlist discipline, opaque
nonpersistent ticket, complete review/privacy contract, one-attempt
uncertainty semantics, Commit invalidation at effectful Started, and all
released nonclaims.

Task 290 is complete only as this decision document. No Task 291 work, Rust
implementation, frontend change, test change, ADR creation, certification,
tag/release mutation, or authority expansion has started.
