## Decision

The evidence supports a narrow new workflow boundary and not a new mutation
policy. The exact proposed flow is:

~~~
inspect
 -> typed human multi-file Prepare
 -> complete ordered exact change-set review
 -> opaque ticket-only Confirm
 -> shared revalidation
 -> D2 preflight
 -> HostExplicit Started
 -> authorized_tool_dispatch
 -> ToolRegistry
 -> existing repo.edit-files / ADR 0014
 -> bounded result classification and repository refresh
 -> existing Stage / Unstage
 -> existing reviewed Commit
~~~

This is one explicitly confirmed change-set, not four independent authoring
actions and not a transaction. It adds exactly one future HostExplicit eligible
name, repo.edit-files, after the later ADR 0023 and implementation tasks have
completed. It does not add that allowlist entry in Task 257.

The contract is sound because every mutation-relevant part can be represented
exactly within bounded limits, the existing authority already defines ordered
per-file commit points and conservative partial/uncertain outcomes, and the
HostExplicit route can bind the exact reviewed set to host-owned currentness.

If a future implementation cannot keep every changed byte understandable within
the bounds below, Prepare must return review_too_large and issue no ticket;
repo.edit-files must remain ineligible.

## 1. Closed human Prepare input

The recommended closed typed DTO is:

~~~
MultiFileEditPrepare {
    targets: 1..=4 [
        MultiFileEditTarget {
            path: String,
            replacements: 1..=16 [
                TextReplacement {
                    expectedOldText: String,
                    replacementText: String,
                }
            ],
        }
    ],
}
~~~

The exact fields are targets, path, replacements, expectedOldText, and
replacementText. Unknown fields are rejected. The human may supply only one
through four logical repository-relative paths and one through sixteen exact
literal old/replacement pairs per target. expectedOldText is nonempty;
replacementText may be empty for literal removal.

The human does not supply ToolName, arbitrary Tool JSON, hashes, byte lengths,
canonical paths, repository roots, native paths or handles, Git parameters,
provider identity, PermissionLevel, authority flags, model metadata, ordering,
or execution controls. There is no regex, glob, line/range, unified-diff,
fuzzy matching, normalization, case folding, or newline conversion. All pairs
resolve against the same original snapshot.

Hard bounds are:

| Item | Bound |
| --- | --- |
| Targets | 1 through 4 existing files. |
| Replacements | 1 through 16 per target and at most 64 in total. |
| Path | At most 1024 UTF-8 bytes; relative, slash-separated, nonempty, no NUL, absolute/drive/UNC path, empty, dot, dot-dot, or .git component; backslash rejected. |
| Text | At most 64 KiB each; old text nonempty; NUL rejected. |
| Serialized request | At most 256 KiB after deterministic serialization, matching the existing policy. |
| File/postimage | At most 1 MiB each; aggregate original/postimage at most 4 MiB. |
| Applicability | Each old string matches exactly once; duplicate, overlap, and equal old/new pairs fail closed. |

The host translates this DTO into the existing closed repo.edit-files ToolInput.
The frontend cannot construct trusted ToolInput.

## 2. Host-derived preparation

A shared capability-specific preparer/revalidator must own all semantics so
review cannot drift from execution. For every target and the complete set, it
derives:

1. Canonical selected repository root, .git, fixed Git executable, repository
   identity, and repository/currentness bindings.
2. Canonical logical repository-relative path, target and parent identities,
   regular-file status, link/reparse/hard-link status, supported mode/attributes,
   and deterministic UTF-8-byte-order position.
3. Non-bare repository observation; existing HEAD; exactly one regular HEAD
   tree blob; exactly one stage-0 index entry; equal HEAD/index target entries;
   supported index flags; and clean worktree status relative to index.
4. Exact bounded raw preimage bytes, including BOM/newline bytes, plus SHA-256
   and byte length.
5. Exact match positions, duplicate/overlap/no-op validation, exact postimage
   bytes, postimage SHA-256 and byte length.
6. Canonical repo.edit-files ToolInput and ToolCall, complete expected
   ToolDefinition, current permission policy, and review identity.
7. Canonical target order: ascending UTF-8 byte order of canonical logical paths.
8. Raw index bytes, HEAD bytes, complete refs observation, target Git entries,
   and all ADR 0014 protected observations needed for revalidation.
9. Composition/registry, Effective Authority, repository/model/profile/
   connection generations, coordinator, preparer, and currentness bindings.

Prepare is zero-effect:

- 0 Tool executions;
- 0 native replacements;
- 0 user-visible worktree mutations;
- 0 index, Stage, Unstage, Commit, HEAD, branch, ref, tag, or history changes;
- 0 provider activation or model/runtime lifecycle events; and
- 0 conversation injection or persistent ticket/capability writes.

Read-only Git observation and bounded in-memory review construction are allowed.
The existing retained multi-file preflight can create repository-adjacent
temporary files before its native commit loop. A future HostExplicit preparer
must not claim zero worktree mutation while doing that: retain postimages in
memory or host-private storage outside the repository, and leave
repository-adjacent temporary creation to the effectful Tool path. Cleanup
ambiguity after a native commit remains ADR 0014 uncertainty, never rollback.

Prepare success is a review snapshot, not future authority. A failed or
oversized Prepare creates no ticket.

## 3. Exact bounded review

The review is backend-derived and display-only. It must show:

- operation repo.edit-files and HostExplicit human provenance;
- total targets and replacements;
- every target path, target count, stable ordinal, and host-determined order;
- exact replacement count per file;
- every original-snapshot byte range, complete escaped old text, and complete
  escaped replacement text;
- same-original-snapshot matching and rejected overlap/duplicate facts;
- preimage and postimage SHA-256/length, plus bounded target identity metadata;
- deterministic BOM, CR/LF/final-newline, trailing-space, control, bidi, and
  zero-width markers. Escaping is display-only and does not normalize bytes;
- a complete derived change representation for every target. A complete
  postimage may be shown when it fits, but exact ranges plus complete old/new
  text are authoritative. Only unchanged context may be omitted;
- exact intended effect: conditional content replacement in the listed files;
- protected non-effects: index, HEAD, branch, refs, tags, remotes, history,
  providers/profile, conversation, model lifecycle, and other files; and
- explicit no automatic Stage, Commit, retry, replay, continuation, rollback,
  restore-preimage, or cross-file atomicity guarantee.

The review must warn that a later native failure can leave a verified committed
prefix or an uncertain effect. It must show host order rather than input order.

Every mutation-relevant changed byte must be complete and understandable. No
ellipsis, clipping, or redaction may remain confirmable. Only unchanged
surrounding context may be omitted and that omission must be stated. Use these
additional bounded Desktop limits:

| Item | Bound |
| --- | --- |
| Escaped changed material | At most 768 KiB across all targets. |
| Unchanged context | At most 32 KiB per target and 128 KiB total. |
| Complete serialized review | At most 1 MiB. |
| Stored review state | At most 2 MiB. |
| Terminal activity/result metadata | At most 32 KiB, redacted. |

If complete changed material or the complete review exceeds its bound, Prepare
returns review_too_large, issues no ticket, and performs no Tool or native
replacement. A generic editor or hidden source panel cannot evade this rule.

## 4. Source-content privacy and provenance

The workflow separates the local review needed for authorization from generic
activity and conversation records.

| Surface | Permitted content | Prohibited content |
| --- | --- | --- |
| Pending in-memory authorization | Full bounded human DTO, exact escaped review, preimage/postimage bytes or derived representations needed for revalidation, hashes/lengths, identities, ToolInput, and currentness bindings. Process-local, bounded, and discarded on consume/cancel/expiry/restart. | Durable storage, generic authority handles, provider credentials, absolute/native paths, or unrestricted source buffers. |
| Frontend review DTO | Backend-derived exact paths, target/replacement counts, order, bounded escaped changed material/ranges, optional bounded context, hashes/lengths, review identity, non-effects, and failure semantics for display. | Trusted preimages, Tool JSON, permission/authority fields, ticket internals, or frontend-controlled execution bindings. The DTO is not accepted back as Confirm input. |
| Generic HostExplicit activity | Operation kind, bounded target count/relative path or opaque target labels, review identity, result class, per-target redacted effect state, order/count metadata, and stale/invalid reason class. | Old text, replacement text, postimages, full preimages, raw ToolInput, ticket ID, absolute paths, temp names, environment, provider stderr, credentials, or raw backend errors. |
| Conversation persistence | No review or effectful HostExplicit content. The route creates no chat message, ToolOutput injection, fake model turn, or resumable operation. | Full or partial source/change content, ticket/capability state, or automatic conversational continuation. |
| Logs/errors/telemetry/evidence | Bounded category, counts, durations, review identity or non-reversible opaque correlation, currentness/result class, and boolean lifecycle counters. | Source/replacement content, postimages, raw preimages, ticket material, absolute/native paths, command lines, credentials, provider output, or content-bearing error strings. |

The user may see full exact changed content only in the local bounded review
surface and its process-local pending state. On Cancel, expiry, Confirm
consumption, disconnect, restart, or terminal completion, full content is
discarded from pending authorization. Redacted result data may remain where
the existing Desktop activity/evidence contract requires it.

## 5. Opaque authorization ticket

The ticket is RAH-generated, opaque to the frontend, capability-specific,
process-local, in-memory, nonserializable, bounded-lived, and single-use. A
five-minute inclusive TTL matches the v0.21 HostExplicit precedent. Restart,
disconnect/recomposition, cancellation, expiry, or terminal consumption
discards it. It is a lookup key, not a permission or mutation authority.

The private ticket binds the exact:

- capability name repo.edit-files;
- canonical ToolInput and ToolCall;
- complete expected ToolDefinition and allowed current permission policy;
- exact complete review and review identity;
- target count, canonical order, target identities and parent identities;
- raw preimage hashes/lengths and exact derived postimages/hashes/lengths;
- repository root/.git/Git identity, protected index/HEAD/refs observation,
  target Git-clean/tracked state, and preparer identity;
- selected repository, registry/composition, Effective Authority,
  repository/model/profile/connection generations, and currentness tuple; and
- relevant coordinator and repository workflow identity.

Confirm receives exactly { ticketId }. It must not receive or resubmit path,
text, hashes, byte lengths, canonical paths, postimages, Tool JSON, permission,
authority, repository, provider, or model data. It must not reprepare from
current files, rewrite expected hashes, or execute the latest version after a
stale review.

## 6. Revalidation immediately before Confirm execution

The shared preparer/revalidator runs without Tool execution or native
replacement and must prove that the ticket still describes the current exact
change-set. Confirm fails closed before Tool execution when any reviewed
assumption no longer holds.

| Changed condition | Classification | Effect |
| --- | --- | --- |
| Unknown, expired, already-consumed, wrong-capability, cancelled, or malformed ticket | Stale authorization | No effect; ticket remains unusable. |
| Selected repository, canonical root, .git, fixed Git executable, repository identity, or repository context changed | Stale authorization if host context changed; invalid target if the target can no longer be safely resolved | No Tool execution. |
| Target path syntax, canonical path, parent identity, target identity, regular-file/link/reparse/hard-link/mode/attribute status changed | Invalid target | No Tool execution. |
| Target absent, special, binary/malformed, untracked, sparse/conflicted, staged, index-divergent, or no longer clean relative to index | Invalid target for target admission; precondition failure for Git/preimage admission | No Tool execution. |
| Target bytes, complete SHA-256, or byte length changed | Precondition failure | No Tool execution. |
| Any old text no longer matches exactly once; pair becomes duplicate/overlapping/no-op; postimage or size bounds change | Precondition failure | No Tool execution. |
| Canonical target set or host-sorted execution order changes | Stale authorization for exact change-set/order binding; invalid target if canonicalization is unsafe | No Tool execution. |
| Raw index bytes, HEAD bytes, complete refs, target HEAD/index entries, or protected ADR 0014 Git observations change | Precondition failure | No Tool execution. |
| Tool missing; public name, description, input schema, or permission differs; current permission membership or Effective Authority differs; composition/registry/preparer changes | Stale authorization / D2 rejection | No Tool execution and no Started. |
| Repository/model/profile/connection generation or connected-current state changes; reconnect required; coordinator is not reserved HostRunning | Stale authorization / busy rejection | No Tool execution and no Started. |

The distinction is intentional. Host route/currentness and authorization drift
are stale; target identity/admission failures are invalid; a still-recognized
target whose exact bytes, applicability, or protected Git preconditions no
longer match is a precondition failure. None authorizes a fresh attempt
automatically.

The revalidator must repeat the relevant ADR 0014 checks for all targets, not
only the first: root/parent/target identity, bytes, modes, strict UTF-8,
tracked-clean status, original-snapshot applicability, host order, retained
plan identity, raw index/HEAD/refs, and repository observation. After any
already-committed prefix, it expects the verified postimage for that prefix and
the original preimage plus clean Git state for every not-yet-committed target.
Any inability to prove the inventory is uncertain, never a reason to replay.

## 7. D2 and HostExplicit sequencing

The exact sequencing is:

~~~
ticket-only Confirm
 -> atomically consume/reserve ticket and enter HostRunning
 -> shared multi-file preparation revalidation
 -> D2 authorize_tool_dispatch preflight
 -> HostExplicit Started
 -> owned authorized_tool_dispatch recheck
 -> ordinary ToolRegistry dispatch
 -> existing repo.edit-files Tool
 -> ADR 0014 all-target preflight/native commit loop/result
 -> terminal HostExplicit activity and repository refresh
 -> coordinator Idle
~~~

Ticket consumption and coordinator reservation are one atomic state transition:
the pending ticket is removed before asynchronous revalidation. An expired,
wrong, stale, or D2-rejected ticket is never restored. A duplicate Confirm sees
no prepared ticket and cannot produce a second execution. A pre-start
cancellation also consumes the ticket and releases the coordinator without
invoking the Tool.

The first D2 preflight checks current public name, complete ToolDefinition
(including description/schema/permission), current permission membership,
current registry/composition, and host-owned inputs before Started. Only after
it succeeds may private HostExplicit activity record Started. The owned
execution task then calls authorized_tool_dispatch, which repeats the
definition/permission admission immediately before ordinary ToolRegistry
execution. No raw ToolRegistry::execute, direct Tool call, generic
ToolName + JSON route, model lifecycle event, or retry is permitted.

One successful Confirm request therefore has a maximum of one Tool execution.
Once Started is emitted, a lost, malformed, timed-out, or uncertain result does
not make the ticket reusable and does not permit a second confirmation.

## 8. Non-atomic result semantics

ADR 0014 remains authoritative. HostExplicit activity and result must preserve
its six statuses and never collapse them into generic success/failure:

| Result | Review/result presentation | Allowed claim |
| --- | --- | --- |
| ok | Every target is committed_verified in host order; exact postimages and refresh are reported. | All reviewed target changes were verified. No atomicity claim is made. |
| invalid_target | No target effect; identify only a bounded invalid-target reason and, where safe, target ordinal/path metadata. | Request rejected before native mutation. |
| precondition_failed | No target effect; identify the bounded precondition class, such as changed bytes, Git state, or applicability. | Reviewed assumptions no longer held; no native mutation was made by this Confirm path. |
| failed_known_no_effect | Native failure was reached for the stop target, but fresh observation proves it unchanged; show that target as unchanged_verified and later targets as not_attempted. | No committed target effect was observed and the stop target is verified unchanged. Do not call this successful. |
| partial_effect | Show the verified committed prefix in deterministic order as committed_verified; show stopped/remaining inventory as unchanged_verified or not_attempted exactly as proven. | Only the displayed committed prefix changed and the rest of the inventory is verified as shown. No continuation or rollback is implied. |
| uncertain | Show every verified committed prefix item, the first unclassifiable target as uncertain, and later targets as not_attempted only when the trace proves they were not reached. | Native effect cannot be conclusively classified. Do not assert unchanged, committed, atomic, or rolled-back state beyond verified observations. |

partial_effect requires a verified committed prefix and a verified original /
not-attempted state for every remaining target. If any inventory cannot be
proven, the result is uncertain. For uncertain, safe text is that the operation
may have had an effect and requires fresh observation; RAH did not retry,
replay, continue, restore preimages, or roll back. A possible effect is never
turned into no-effect merely because the Tool returned an error or the UI lost
the terminal response.

There is no automatic retry, replay, remaining-target continuation, restore
preimage, rollback, Stage, Unstage, or Commit. Repository refresh after a
terminal result is observation and state reconciliation, not recovery.

## 9. Post-effect authorization invalidation and refresh

The edit ticket is unusable as soon as it is consumed/reserved, regardless of
whether D2 rejects it, the Tool is reached, or the result is lost. If an
effectful path reaches HostExplicit Started, all repository-bound reviewed
authorization state that could rely on the prior worktree/Git observation is
conservatively invalidated, including:

- the current edit ticket and any older pending HostExplicit reviewed
  authorizations for the same repository;
- older reviewed repo.patch or future multi-file authorizations for the same
  repository; and
- existing reviewed Commit authorization / RepositoryCommitControl for the
  affected repository.

This invalidation occurs at the effectful-start boundary, not only after a
successful ok, because a later native result may be partial or uncertain. No
invalidated authorization is recreated or automatically reauthorized.

After ok, failed_known_no_effect, partial_effect, or uncertain, Desktop performs
the existing bounded repository refresh and currentness reconciliation. Refresh
may produce a fresh ReadyToAuthorize staged review when the staged snapshot is
still reviewable. It must have fresh observation/review identity and no pending
underlying authorization. Refresh never arms Commit, does not synthesize a
Commit ticket, and does not make the old authorization valid again. Stage/Unstage
and reviewed Commit remain separate explicit human actions.

The workflow must not infer that repository_generation changed solely because
worktree bytes changed if existing Desktop semantics do not increment it; it
must bind and report the actual current observation/generation tuple. A fresh
selector or observation generation proves refresh; it is not permission to
commit.

## 10. ADR 0023 decision surface for Task 258

The research supports creating this narrow ADR in Task 258:

**ADR 0023 — HostExplicit Reviewed Multi-File Authoring Boundary**

It should govern only:

1. repo.edit-files HostExplicit eligibility as exactly one added first-party
   name, subject to host-composed authority, connected-current state, exact
   ToolDefinition, and D2 current permission;
2. the closed typed human Prepare DTO and its bounds;
3. host-derived canonical targets, preimages, applicability, postimages,
   deterministic order, protected Git observations, review identity, and
   currentness bindings;
4. zero-effect Prepare and shared non-effectful revalidation;
5. the complete bounded review, no-hidden-change rule, non-atomic warning, and
   explicit non-effects;
6. opaque process-local single-use ticket and exact-change/currentness binding;
7. ticket-only Confirm, consume/reserve ordering, D2 preflight, HostExplicit
   provenance, exactly-once dispatch, and no retry/replay;
8. stale, invalid-target, and precondition fail-closed behavior;
9. ok, invalid_target, precondition_failed, failed_known_no_effect,
   partial_effect, and uncertain presentation;
10. post-effect authorization invalidation, repository refresh, and separate
    Stage/Commit continuation; and
11. source-content privacy, redacted provenance, activity, persistence, log,
    error, telemetry, and evidence rules.

The ADR must expressly state what it does not do:

- it does not create, widen, or replace RepositoryMultiFileMutationPolicy;
- ADR 0014 remains authoritative for actual multi-file worktree mutation,
  commit points, ordering, preconditions, and partial/uncertain semantics;
- ADR 0021 remains authoritative for general HostExplicit currentness, D2,
  coordinator, provenance, and ticket principles;
- ADR 0022 remains authoritative for the single-file repo.patch workflow;
- no other authoring Tool becomes eligible;
- no generic JSON, filesystem, Git, process, provider, model, Stage, Commit,
  rollback, replay, continuation, or persistence authority is added.

No amendment to ADR 0014, ADR 0021, ADR 0022, permissions, Trusted Profile,
or package/dependency configuration is supported by this research.

## 11. Minimum deterministic test plan for later implementation

The future implementation must add focused RAH-owned deterministic tests before
any live certification.

### Prepare and review

- Closed DTO accepts only the named fields and rejects unknown, authority,
  hash, byte-length, Tool, or provider fields.
- Bounds cover 1/4 targets, 1/16 replacements, aggregate limits, path/text
  limits, file/postimage limits, escaping limits, and review_too_large.
- Prepare performs 0 Tool executions, 0 native replacements, 0 target/worktree
  mutations, 0 index/HEAD/ref changes, and no model/provider lifecycle.
- Exact preimage hashes/lengths, canonical identities, match positions,
  postimages, canonical ToolInput, host order, review identity, and protected
  Git state are host-derived and stable.
- Every target and every exact changed range/text appears in the review; only
  unchanged context can be omitted. BOM, newline, control, bidi, zero-width,
  trailing-space, and final-newline display is deterministic.
- Human input order differs from canonical order and the review/dispatch proves
  the expected order and exact postimages.

### Confirm and currentness

- Success produces exactly one Tool execution, expected order, exact postimages,
  and no second execution on duplicate Confirm.
- Ticket expiry, cancellation, restart/disconnect, wrong ticket, consumed
  ticket, coordinator conflict, and currentness changes fail with no Tool call.
- Target path/identity/link/reparse/regular-file changes, changed bytes/hash/
  length, clean/tracked/index divergence, replacement applicability, order,
  repository identity, HEAD/index/refs, Tool definition, permission,
  composition, Effective Authority, repository generation, model/profile/
  connection generation, and coordinator state each have explicit fail-closed
  assertions.
- D2 rejects before Started; execution rechecks D2 immediately before the one
  ordinary ToolRegistry dispatch; no direct registry shortcut exists.
- Frontend cannot bypass ticket-only Confirm or resubmit trusted bindings.

### Result and privacy matrix

- Deterministically inject invalid_target, precondition_failed, and
  known-no-effect before native commit and prove no target changes.
- Inject a native failure after a deterministic committed prefix and prove
  partial_effect, exact verified prefix, unchanged_verified, and not_attempted
  states, with no automatic continuation.
- Inject an unclassifiable native outcome and prove uncertain, conservative
  wording, consumed ticket, no replay, and no rollback/restore.
- Prove raw/escaped old text, replacement text, preimages, postimages, Tool
  JSON, ticket material, credentials, absolute/native paths, and provider output
  are absent from generic activity, conversation persistence, logs, errors,
  telemetry, and live-evidence records. Redacted result metadata remains
  bounded and sufficient.
- Prove a started success and a started partial/uncertain result invalidate
  edit and older repository-bound reviewed authorizations, refresh the
  repository, and expose only a fresh non-authorized ReadyToAuthorize review.

### Authority regression matrix

- Exactly the v0.21 HostExplicit set plus repo.edit-files is eligible only in
  the later implementation task.
- repo.create-file, repo.delete-file, repo.rename-file,
  repo.create-directory, repo.commit, external MCP Tools, Process Plugin
  Tools, unknown names, generic JSON, and model/runtime paths remain rejected.
- No PermissionLevel, Trusted Profile, repository authority, dependency edge,
  provider composition, or runtime/model authority changes.

## 12. Windows live certification design

The later production certification should be analogous to Task 251 but use one
fresh disposable Windows repository for each attempt. It must not use the RAH
checkout, a preserved prior fixture, cleanup-as-recovery, or GUI mouse
automation.

### Fixture

Create a disposable non-bare repository with four existing clean tracked
strict-UTF-8 files, each containing one or more exact replacements, and one
unrelated protected sentinel. Preserve enough staged/index state to detect any
index mutation, and capture before-state values for raw index, HEAD, branch,
refs/tags/remotes/history, target bytes, identities, currentness generations,
and repository workflow review state.

### Required production observations

Prepare must demonstrate connected-current Desktop composition, HostExplicit
eligibility, zero Tool executions, zero native replacement attempts, exact
complete review, canonical target order, all four target identities/preimages/
postimages, non-atomic warning, and no source content in generic activity.

Confirm must accept only the opaque ticket ID, perform at most one
repo.edit-files Tool execution (one on the successful run), and observe the
expected four native replacements in deterministic order. Verify all four exact
postimages and the unrelated sentinel.

Verify protected state after completion: raw index unchanged, HEAD unchanged,
branch unchanged, refs/tags/remotes/history unchanged, no Stage/Unstage/Commit,
no temporary residue, no unrelated file change, and no provider/profile state
change. Verify connected-current state, expected generation/currentness
bindings, coordinator Idle, chat Idle, no model request or model lifecycle,
MCP providers equal zero, and Process Plugin providers equal zero.

Deterministic fault injection, not a successful live run, must certify
partial_effect and uncertain. The live gate explicitly does not certify
rollback, atomicity, model-selected execution, GUI automation, external
providers, network isolation, OS sandboxing, or any absent rollback/replay
guarantee. A successful live run proves the bounded Windows HostExplicit route
and exact postimages only.

## Final conclusion

**A — REVIEW CONTRACT SOUND — ADR 0023 MAY BE ACCEPTED.**

The existing ADR 0014 capability supplies the required bounded authority and
non-atomic result model. A new ADR 0023 is justified because multi-file
deterministic order, multiple native commit points, verified prefixes, and
uncertainty are materially different from ADR 0022's single-file review, while
the new ADR can remain strictly a HostExplicit workflow boundary. The exact
human DTO, complete changed-material review, private ticket, fail-closed
currentness, conservative result mapping, privacy separation, and later
deterministic/Windows evidence are sufficient to proceed to Task 258.
