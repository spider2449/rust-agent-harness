## Retained preparer composition

The existing first-party Desktop composition now retains one optional
`Arc<RepositoryPatchPreparer>` alongside the registry that owns `repo.patch`.
It is constructed once from the same host-selected Git executable and
canonical repository root used by the Desktop `repo.patch` Tool. A missing or
failed matching preparer makes HostExplicit patch invocation unavailable.
Prepare and Confirm never construct a preparer.

## Eligibility

`HostInvocationKind` recognizes exactly seven backend-eligible Tools:

    fs.read
    repo.file-info
    repo.status
    repo.diff
    repo.diff-staged
    repo.create-branch
    repo.patch

The existing backend source, connected-current, selected-repository,
permission, coordinator, branch-authority, and retained-patch-preparer gates
remain authoritative. Other authoring Tools, `repo.commit`, and external MCP
or Process Plugin Tools remain unavailable.

## Typed Prepare and ticket payload

`host_prepare_repo_patch` accepts only the closed camelCase DTO
`path`, `expectedOldText`, and `replacementText`. It performs coordinator
reservation, current composition/eligibility/definition/permission checks,
D2 preflight using the canonical `repo.patch` identity, then calls the shared
`RepositoryPatchPreparer::prepare`. The response uses the exact shared typed
`RepositoryPatchReview` and an opaque ticket ID. Invalid, stale, no-effect,
unsupported, precondition-failed, or review-too-large preparation returns a
sanitized error, no ticket, and Idle coordinator state.

The in-memory ticket remains process-local, single-use, non-persistent, and
five-minute TTL. Its payload is generalized to `PreparedHostPayload` with the
existing branch review variant and a patch variant containing the exact
`RepositoryPatchPreparation` plus its retained `Arc<RepositoryPatchPreparer>`.

## Confirm ordering and revalidation

The existing ticket-only Confirm consumes the ticket before any execution.
For patch tickets it verifies current generations, repository and composition
identity, current eligibility/definition/permission, and pointer identity of
the retained preparer; calls `RepositoryPatchPreparer::revalidate`; performs
the exact stored-call D2 preflight; clears reviewed commit authorization; and
only then emits HostExplicit `Started`. Execution is owned by the existing
`authorized_tool_dispatch` path with the exact canonical ToolCall.

Pre-start rejection releases the coordinator and has zero Tool execution and
zero replacement attempts. Cancel remains ticket-only and returns Idle with
known zero effect. No retry, replay, reprepare, rollback, or post-start abort
was added.

## Reviewed authorization and terminal handling

Prepare preserves reviewed commit authorization. Pre-start stale or D2
rejection preserves it unless independent current observation already proves
the review stale. Once patch Confirm reaches `Started`, authorization is
cleared before Tool execution. Any terminal patch ToolOutput or ToolError
retains the underlying ToolOutput where one exists and conservatively
reobserves/refreshes only the captured repository generation and identity.
Task 250 owns strict result classification; this task does not infer success
or known no-effect from arbitrary JSON.
