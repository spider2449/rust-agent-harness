## 2. Research conclusion

**Outcome A - MULTI-REPOSITORY BOUNDARY VIABLE.**

RAH can safely represent several explicitly admitted, independently rooted
repositories in one descriptive workspace if v0.26 adopts the following
bounded model:

```text
host-owned descriptive workspace membership
  -> process-local repository handles with fresh host admission
  -> exactly one explicit active repository, or zero during setup/transition
  -> one fresh current composition for that active repository
  -> existing repository-specific Tool, policy, ticket, Stage/Unstage, and
     reviewed Commit authorities
```

Membership is organizational state. Repository identity is the scope of
mutation authority. Workspace membership never grants filesystem, Git,
network, provider, process, or Commit authority.

The selected contract deliberately rejects nested repository co-membership in
v0.26. This avoids making a parent repository's safety depend on a mutable
workspace member list or on circular authority coupling. Independently, every
repository-relative path policy used by a future multi-repository composition
must reject a nested `.git` boundary; the current implementation does this in
the reviewed rename path but not uniformly in every repository-bounded reader
or mutation path. This is an implementation conformance gate for the next
tasks, not permission to weaken the boundary or to auto-discover repositories.

The boundary is therefore viable for an ADR/decision task, but implementation
must not proceed as a registry union or as a workspace-root filesystem
capability.

### 3.3 Important current nested-path observation

`FsReadTool` constructs `WorkspacePolicy` for the selected repository and
resolves any existing descendant path inside that root (`rah-tools/src/fs_read.rs:11-25,
61-64`; `rah-sandbox/src/workspace.rs:43-89`). It does not treat a child
repository's `.git` as an exclusion boundary. The reviewed rename policy has a
specific `reject_nested_repository_boundary` check while walking ordinary
ancestry (`rah-tools/src/repository_rename_file.rs:1686-1723`), but the shared
patch directory validator (`repository_worktree_patch.rs:2057-2093`) and some
creation paths do not provide the same complete nested-member boundary.

This proves that a future workspace object cannot be passed as a broader
`WorkspacePolicy` root and that a claim of universal parent/child isolation
would be false without a bounded lower-level conformance change. The future
contract below rejects nested co-membership and requires all repository-bound
path operations, including reads, to fail closed at nested `.git` boundaries.

## 4. Workspace identity contract

### 4.1 Meaning

A workspace is a host-owned descriptive container for user work. It has no
root directory capability and no direct Tool or authority semantics.

The v0.26 identity is a combination:

1. a process-local opaque workspace handle and activation epoch used only for
   in-memory coordination/currentness; and
2. optional persistent descriptive workspace metadata used to remember the
   user's organization and where the host may ask for fresh admission.

The persistent identity is not an authority identity. Restart creates a new
process-local authority context even when it loads the same descriptive
workspace record.

### 4.2 Safe descriptive fields

If persistence is enabled, the closed schema may contain:

- schema version;
- a random opaque descriptive workspace ID;
- a user-visible workspace name, bounded and control-free;
- a bounded list of descriptive member IDs;
- optional user labels for members;
- an optional user-approved repository location hint, subject to the privacy
  setting; and
- a last-active descriptive member ID.

It may also contain bounded creation/update timestamps for presentation. It
must not contain a canonicalized path as an authority assertion, filesystem
identity, `.git` identity, Git executable identity, authority object, active
registry, currentness proof, ticket, preparation, Commit authorization,
provider credential, runtime connection, or uncertain-effect replay state.

The default privacy posture is to persist a location hint only when the user
has opted into it. A remembered entry is shown as “remembered, not admitted /
not current” until fresh host admission succeeds.

### 4.3 Explicitly rejected workspace interpretations

The following are not workspace semantics:

- workspace root as a broad filesystem capability;
- automatic admission of descendants;
- automatic scanning or nested Git discovery;
- membership implying permission;
- provider, model, MCP, Process Plugin, repository content, or frontend
  metadata adding members; or
- a union of all member Tools or authority objects.

## 5. Repository identity contract

### 5.1 Authoritative identity

An admitted repository receives a fresh process-local opaque repository handle.
The handle is not persisted and is not accepted as model input. Its authority
identity is a host-private tuple containing, as applicable:

- the canonical existing repository root;
- root filesystem identity (Windows volume serial/file index; Unix device and
  inode where available);
- supported `.git` form and `.git` filesystem identity;
- the Git executable path and its filesystem identity where the capability
  requires it;
- supported ordinary-worktree/non-bare classification;
- the host admission epoch and per-repository generation; and
- the capability-specific policy/preparer identities and relevant target
  identities.

The native path is private evidence, not the identity by itself. The
`effective_authority` repository enum and a path-derived conversation hash are
presentation/namespace values, not authority proofs.

### 5.2 Reselection, movement, replacement, and restart

- Reselecting an equivalent path during the same process may identify the same
  physical repository only after fresh host validation proves the same
  canonical root, filesystem identity, supported `.git` form/identity, and
  relevant Git executable identity. It does not revive old tickets.
- Windows case-equivalent spelling, drive-letter spelling, and supported path
  aliases resolve to the same member only when canonical and filesystem
  identity checks agree. A spelling difference never creates a second
  authority member.
- A moved directory is not automatically treated as the old authority. The
  old binding becomes stale. An explicit fresh admission at the new location
  may create a new handle; physical continuity, if observed, is descriptive
  evidence only and does not preserve old tickets or Commit authorization.
- A replaced root or replaced `.git` fails identity revalidation. It is a new
  repository candidate requiring fresh admission, not a silent continuation.
- Restart discards all process-local repository handles, registries,
  generations, tickets, preparations, Commit authorizations, and runtime
  connections. Persistence can suggest where to ask, never answer the
  admission question.

### 5.3 Platform alias and identity rules

On Windows, admission and every capability-specific policy must account for:

- case-insensitive equivalence and drive-letter spelling;
- UNC and supported verbatim forms, with unsupported forms rejected rather
  than normalized into authority;
- junctions, symlinks, and reparse aliases;
- DOS device names, alternate data streams, trailing-dot/space aliases, and
  other path normalization traps;
- canonical path equivalence; and
- volume serial/file-index identity.

The safe v0.26 subset rejects reparse traversal, unsupported UNC/verbatim/device
forms, DOS-device/ADS ambiguity, and reviewed trailing-dot/space aliases. It
does not claim race-free TOCTOU.

On Unix, admission and relevant policies must reject symlink traversal, check
device/inode replacement, observe mount boundaries where supported, and fail
closed on a changed mount or nested mount boundary. The contract does not
promise race-free TOCTOU or universal identity semantics on filesystems that
do not expose the required identity.

## 6. Explicit admission contract

Admission is a host/human operation. A native picker or an equivalent
backend-owned typed request may propose a path, but only the host validates and
admits it. Model output, Tool input, MCP, Process Plugin, repository content,
automatic scanning, nested Git discovery, frontend-derived authority metadata,
and provider metadata cannot admit a member.

The future implementation should extract a shared host admission primitive
from the current `choose_repository` validation path rather than duplicate
slightly different checks. This is a research recommendation, not a refactor
in Task 309. The primitive must establish fresh canonical root, `.git` form,
filesystem identities, Git binding, supported repository state, capability
authority construction, and descriptive membership in one host-owned flow.

The rule for an already-equivalent member is **reject with `already_member`**.
It does not silently focus, activate, or create a second member. Explicit
active selection is a separate host action. Path aliases, case aliases, and
equivalent physical roots are duplicates after host identity comparison.

Admission must not restore an old ticket, retained preparation, registry,
Effective Authority, Commit authorization, or runtime connection.

## 7. Nested repositories

### 7.1 v0.26 decision

Two repository roots that are nested by canonical path are **not both admitted
to the same v0.26 workspace**. Attempting to admit the second root returns a
bounded nested-member rejection and makes no membership or authority change.
This is a deliberate explicit-admission boundary, not automatic discovery.

This rule answers “can both be admitted explicitly?” with “not in the same
v0.26 workspace.” Separate workspaces may describe the two repositories.

### 7.2 Why this is the least coupled safe rule

If both were members, parent Repository A would need a child-member exclusion
set, and every parent-bound Tool would need to consult it. That would couple
ordinary A authority to mutable workspace membership and risk stale exclusion
state. A one-way admission check avoids circular authority coupling. It does
not itself make a workspace root authoritative.

The lower-level path contract remains necessary even when B is not a member:
every repository-bound path operation must reject a nested `.git` directory or
equivalent nested repository boundary in its target ancestry. This includes
`fs.read`, observation, worktree mutation, file creation/deletion/rename, and
index target validation. Existing rename checks are useful evidence but are not
accepted as proof for all Tools. No automatic repository scan is introduced;
the check is a bounded path-policy rule.

If a future implementation cannot apply that common boundary without weakening
an existing mutation ADR, it must stop and return to capability-specific
research. It must not ship an A/B workspace with an unproved parent escape.

## 8. Active repository contract

Exactly one repository is active for ordinary v0.26 execution. Zero active
repositories is valid during startup, an empty workspace, failed admission,
removal transition, and disconnected setup.

Active selection is explicit host/human input. Frontend selection is only a
request. Model, provider, MCP, Process Plugin, conversation text, repository
content, and Tool arguments can never select or grant another repository.

The selected v0.26 lifecycle is:

1. verify the workspace member is admitted and current enough for fresh
   composition;
2. increment active-selection generation;
3. invalidate any prepared HostExplicit state for the old active member;
4. revoke old active Commit authorization and clear executable Stage/Unstage
   selectors;
5. withdraw the old active composition from executable use;
6. require an explicit fresh connection/composition for the new active member;
7. publish only the new member's current first-party registry and Effective
   Authority; and
8. preserve only bounded descriptive labels/status, never old authority.

For simplicity, selection while a model turn or HostExplicit operation is
running is rejected as busy. A prepared, not-yet-started ticket is canceled by
the explicit host selection/removal transaction; this is a known no-effect
ticket invalidation. A running operation blocks selection until its owned
terminal lifecycle completes. Selection never rolls back an effect.

There is no retained per-repository executable registry in the selected
architecture. A switch requires fresh active composition and, where the
current runtime was connected to the old context, explicit reconnect. A stale
old runtime may not serve a new repository.

## 9. ToolRegistry composition comparison

| Option | Composition | Security/currentness | Lifecycle/privacy/test cost | Decision |
| --- | --- | --- | --- | --- |
| A | One current registry for the active repository only; provider registry is merged into that connection but is not repository authority. | A Tool has one fixed repository root. No Tool argument names a repository. Current registry pointer, active member, generations, and repository identity are checked together. Switching withdraws the registry and requires fresh composition. | Smallest retained secret state and easiest fail-closed proof. Requires reconnect UX and two-repository switch tests. | **Selected.** |
| B | Retain a registry per admitted repository and dispatch by a host-selected repository identity. | Every dispatch must resolve a host-owned target, prove the target is active, prevent model/tool repository arguments, and maintain per-registry lifecycle/currentness. A stale dispatch table or selector can become an any-repository router. | More memory, provider/runtime lifetime complexity, more privacy and stale-state cases, and more live proof. No required v0.26 product benefit. | Rejected for v0.26. |
| C | One union registry with repository-qualified Tools or a repository ID in Tool input. | Presumptively unsafe: a model-visible repository selector becomes a confused-deputy surface; same-name Tools and provider composition multiply routing cases. A union UI is not an authority proof. | Highest frontend/model/schema complexity and weakest direct isolation proof. | Rejected. |

The selected Option A guarantees that a Tool call cannot choose or smuggle a
different repository. Existing public Tool inputs remain repository-relative
operation inputs; no `repository_id` field is added. A Tool constructed for A
cannot traverse B because the repository path policy rejects nested boundaries,
the registry is only A's registry, and the active/currentness gate rejects a
non-A composition. Provider Tools are not made repository-bound by membership.

## 10. Effective Authority model

Effective Authority remains observational, not executable. The active member
gets the current repository binding, currentness, current-generation display,
and the current first-party Tool entries. Inactive members may appear in a
descriptive workspace list with user label, basename, remembered/admitted
state, and a stale/not-current reason, but they do not contribute Tool entries,
permissions, tickets, or a union authority object.

The UI may summarize multiple members, but it must never present a UI union as
an authority union. An inactive “authority summary” means “this member can be
selected and freshly revalidated”; it never means executable now. Stale state
must be explicit: remembered, admitted-but-not-active, revalidation required,
identity changed, disconnected, or reconnect required.

Absolute paths and native identities remain outside generic activity and model
state. Explicit repository-management UI may show a user-selected absolute
path under the privacy rules in Section 17.

## 11. Generations and currentness

The design uses independent domains rather than one global invalidation value:

| Domain | Scope | Invalidated by |
| --- | --- | --- |
| Workspace membership generation | Descriptive member list | Add, remove, label/schema membership change. Adding unrelated B does not stale a safe A effect. |
| Active-selection generation | Current active target | A-to-B switch, zero-active transition, active-member removal. |
| Per-repository generation | One member's admitted identity/currentness | Fresh admission/re-admission, root or `.git` identity change, supported Git binding change, removal/revocation, failed identity revalidation. |
| Connection generation | One runtime publication | Connect/disconnect/reconnect and rejected/superseded publication. |
| Model generation | Model configuration | Model selection/configuration change. |
| Profile generation | Trusted Profile intent/composition | Profile selection, restore, forget, or composition change under existing rules. |
| Composition/registry identity | One published active composition | Fresh registry/composition publication; pointer/identity mismatch is stale. |
| Observation generation | One active repository workflow catalog | Status/diff refresh; consumes Stage/Unstage selectors and review snapshots. |

An authority-bearing prepared ticket binds the active member handle, its
per-repository generation, active-selection generation, connection/model/
profile generations, composition/registry identity, exact Tool definition and
permissions, and capability-specific preparer identity. A model turn binds the
same active member and currentness at request start.

Event semantics:

- Adding unrelated B changes membership presentation only; it does not grant
  B to A or unnecessarily stale A's already-running safe operation.
- Removing B revokes B's future reachability, clears B's prepared/reviewed
  state, and does not roll back a running effect.
- Switching A to B changes active-selection generation, withdraws A's
  executable composition, invalidates A tickets/authorization/selectors, and
  requires B's fresh current composition.
- Re-admitting the same physical repository after removal creates fresh
  process-local authority/currentness; no old ticket or Commit state returns.
- Root, `.git`, Git executable, target, parent, mount, alias, or relevant Git
  state drift fails closed in the capability policy and increments/revokes the
  affected repository currentness. A hash match alone is not identity proof.
- Connection, profile, or model changes preserve no stale executable route;
  existing independent generation rules remain in force.
- Restart creates no authority. Descriptive records are reloaded only as
  remembered/not-admitted state.

## 12. HostExplicit tickets

RAH retains one global `HostInvocationCoordinator` and one prepared/running
HostExplicit invariant for v0.26. Parallel effectful per-repository execution
is not a product goal.

Every prepared ticket binds exactly one repository handle/identity or is a
non-repository read ticket where the existing contract permits that case. A
repository-bound ticket additionally binds the exact active member, per-repo
and active-selection generations, current composition/registry identity,
expected Tool definition, permissions, current Effective Authority identity,
capability preparer, and private typed payload. Tickets remain opaque,
process-local, in-memory, single-use, short-lived, nonpersistent, and never
workspace tickets.

The selected behavior is the simplest fail-closed switch rule: an explicit
active switch or member removal cancels/invalidate a prepared A ticket before
the switch commits. A user must prepare again after activating B or returning
to A. A running A invocation blocks switch/removal until its owned terminal
lifecycle finishes. No switch or removal is rollback, and no uncertain effect
is replayed.

## 13. Running operations

The global coordinator continues to serialize all HostExplicit operations and
to exclude model turns. While an operation is Started/running:

- active repository selection is rejected as busy;
- membership removal of the bound repository is rejected as busy;
- descriptive UI may display that a requested selection/removal is pending or
  blocked, but it cannot change executable authority underneath the operation;
- the operation remains bound to its captured repository identity and
  currentness; and
- after terminal handling, normal `uncertain`/possible-effect semantics remain.

A repository can be marked for a later descriptive removal request only if the
host records no authority change until the running operation has terminated.
Removal never claims absence of an effect, never deletes a fixture to recover,
and never cancels by pretending that cancellation is rollback.

## 14. Reviewed Commit authorization

Each member may have descriptive “needs review” or “staged changes observed”
presentation when it is explicitly observed, but v0.26 retains at most one
executable reviewed Commit authorization: the active repository's exact
staged snapshot. Inactive members do not retain an executable authorization or
a reusable review handle.

Switching away from A revokes A's authorization and clears its executable
review/control state. Switching to B does not transfer it. B must be freshly
observed and reviewed. Removal clears the member's authorization. A root, `.git`,
Git, index, branch, identity, model/profile/connection, or repository-generation
change revokes it. Restart destroys it. There is no workspace-wide Commit
authorization and no cross-repository Commit.

## 15. Stage / Unstage workflow

Stage and Unstage remain separate index authorities. A selector binds:

- member handle and repository identity;
- per-repository generation;
- active-selection generation;
- observation generation;
- canonical target path and target filesystem identity; and
- the host-derived Stage or Unstage kind.

The model supplies no repository selector, native path, Git executable, or raw
argv. On A-to-B switch, all A selectors and staged review controls become
invalid. An A action ID submitted while B is active is rejected before any
Git process or native attempt. B action construction uses a fresh B
observation. Status, staged diff, and refresh are similarly one active member
at a time.

## 16. Conversation and session context

The initial v0.26 choice is **separate conversation context per admitted
repository member**, with an optional workspace-level descriptive overview.
This is the least ambiguous starting point among:

- one conversation spanning all repositories;
- separate repository contexts; and
- a workspace transcript with explicit per-message attribution.

An A transcript may influence model reasoning only when A is explicitly active,
freshly admitted/current, and the user explicitly resumes that descriptive
context. It is never authority. B requests do not receive A's history by
default. Each request captures immutable member ID, repository generation,
active-selection generation, model/profile/connection currentness, and the
conversation namespace before it starts. Switching is blocked while the model
turn is active, so later Tool requests from that turn cannot migrate to B.

Persistence stores bounded descriptive transcript data under a member-specific
namespace. User-provided text can contain paths as ordinary content; host-added
native paths, filesystem identities, tickets, registries, authority objects,
and uncertain-effect state are not added. Restart requires fresh admission and
fresh runtime composition before any repository model turn starts.

## 17. Persistence contract

Persistence is descriptive only. It may remember workspace name, descriptive
member IDs, labels, opt-in location hints, and last-active intent. It never
persists or reconstructs:

- HostExplicit tickets, preparations, or retained preparers;
- ToolRegistry or Effective Authority objects;
- `FileIdentity` or any filesystem identity as authorization;
- Commit authorization, D2 result, or currentness proof;
- runtime connection authority, provider credentials, or private provider
  lifecycle state; or
- uncertain-operation replay/rollback/recovery state.

Before re-admission, each persisted member is rendered as remembered but not
admitted/current. Malformed, oversized, unknown-field, duplicate-ID,
path-injection, or unsupported-form entries are ignored or rejected according
to a closed schema; they cannot become authority. No persisted path is passed
directly to a Tool or runtime as a trust assertion.

## 18. Member removal and revocation

Removal is a host/human operation.

- Removing an inactive member revokes its future reachability, clears all
  retained descriptive authority-bound state, removes its persisted membership,
  and leaves active A unchanged.
- Removing active A requires no running model/HostExplicit operation. It
  invalidates A tickets, Commit authorization, Stage/Unstage selectors,
  composition, and repository-specific currentness, then leaves zero active
  until the user explicitly selects another admitted member.
- Removing a member with a prepared ticket cancels/invalidate the ticket before
  membership removal completes.
- Removal during a running operation is rejected/busy. If removal is requested
  after terminal uncertainty, the user may remove it, but the effect's normal
  possible-effect/uncertain semantics remain and no rollback is implied.
- Descriptive transcript data may be retained only under the user's separate
  persistence policy and is never executable or automatically resumed.

## 19. Privacy model

Public/user-management representations may include a user label, repository
basename, admitted/not-admitted state, and an explicitly requested absolute
path. A basename is not treated as unique; the UI uses the descriptive member
ID or an additional user label for disambiguation.

Generic activity, model-visible state, provider metadata, and serialized
authority snapshots do not automatically expose absolute native paths,
filesystem IDs, `.git` paths, Git executable paths, workspace storage paths,
credentials, authority handles, or path hashes. The process-local repository
fingerprint used by live evidence is correlation metadata and is not an
identity or public authority token. Explicit management UI path disclosure is
distinct from generic activity/model disclosure.

Privacy tests must inspect serialized values, not merely property names: use
sentinel absolute paths, `.git` paths, filesystem IDs, ticket strings, and
credentials and assert their values are absent from generic activity,
model-visible state, persisted workspace metadata, and Effective Authority
snapshots under every field.

## 20. Duplicate and alias members

The following behavior is closed and fail-closed:

| Case | v0.26 rule |
| --- | --- |
| Same repository twice | Reject `already_member`; no focus or activation side effect. |
| Windows case/drive/path alias | Canonical/identity-equivalent duplicate; reject. |
| Symlink/junction/reparse alias | Reject unsupported alias at admission; do not make a second identity. |
| Root and child resolving to the same repository | Equivalent duplicate; reject. |
| Root and physically nested different repository | Reject co-membership in one workspace; no automatic discovery. |
| Moved persisted repository | Remembered hint only; stale until fresh host admission at the new location. |
| Replaced root or `.git` | Existing binding stale; fresh admission required. |
| Same `.git` through multiple worktrees | Reject unsupported linked-worktree/gitfile forms; do not expand support for convenience. |
| Malformed or unsupported path form | Fail closed without membership or authority. |

## 21. Provider composition

Trusted Profile, MCP, and Process Plugin composition remains global to one
explicit runtime connection and independent of repository membership. The
first-party registry is rebuilt for the active repository, then the existing
provider registry may be merged with duplicate public names rejected. Provider
metadata cannot admit, select, or create repository authority.

External provider descriptors remain `repository_bound=false`, classified as
external, and unavailable to HostExplicit under the unchanged policy. RAH does
not create one provider Tool instance per workspace member. Provider Tools do
not gain filesystem access to inactive repositories through membership. When a
repository switch changes the runtime workspace/CWD context, explicit
disconnect/reconnect creates the fresh active composition; a provider is not
silently migrated.

## 22. Model-request binding

At request start the host captures immutable active member identity,
per-repository generation, active-selection generation, connection/profile/
model generations, conversation namespace, and runtime session identity. The
model cannot name another repository, add a member, or alter that binding.

Repository selection is blocked while a model turn is active by the global
coordinator and chat lifecycle. If a lower-level currentness change is
observed anyway, later repository-bound dispatch fails closed and the turn is
terminally handled under existing uncertainty rules; it does not migrate to
B. No model context, provider output, or Tool argument is an authority grant.

## 23. Cross-repository operations explicitly rejected

v0.26 foundation does not add or imply:

- cross-repository rename, copy, move, or patch bundle;
- Stage or Unstage across repositories;
- Commit across repositories;
- transaction or rollback across repositories;
- one Tool input containing a repository ID or repository selector; or
- automatic dependency updates or other sibling-repository workflows.

Every existing operation remains one-repository. Future cross-repository
workflows require separate authority research and a separate decision.

## 24. Three complete architecture options

### Option A - admitted membership, one active repository, fresh composition

Host membership stores descriptive entries. One active member is selected by
the host. A fresh first-party registry and composition is built only for that
member; provider composition remains connection-global and external. Switching
invalidates old executable state and requires fresh current connection.

This gives the clearest authority separation and the smallest lifecycle. It
does require reconnect/currentness UI, per-member descriptive persistence, and
explicit nested/alias tests. Tickets and Commit authorization are naturally
single-active-member state. Restart and live certification are straightforward
because no registry or ticket is retained per member.

### Option B - retained per-repository compositions, host-selected dispatch

Each admitted repository retains a registry, preparers, lifecycle state, and
possibly provider/runtime association. A host-selected member ID routes each
operation. This can reduce reconnect friction, but it introduces a dispatch
router that must prove the selected member is active for every call, prevent
model argument selection, revoke inactive registries, isolate provider CWD and
credentials, and handle multiple retained stale/current generations. It
multiplies ticket, Commit, privacy, shutdown, and live-certification cases
without being required for the foundation.

### Option C - workspace-wide union registry

One registry contains all member-qualified Tools. This makes the workspace look
convenient, but the model-visible Tool surface or a repository-qualified input
becomes a repository authority selector. It also creates same-name/provider
collision and confused-deputy risks, and makes “current active repository” a
soft UI concept rather than a structural dispatch boundary. A UI union cannot
prove a safe authority union. This option is rejected presumptively.

### Selection

**Select Option A.** It preserves existing ToolRegistry, policy, Effective
Authority, HostExplicit, Commit, Stage/Unstage, and provider boundaries while
adding only a host-owned descriptive membership/selection layer.

## 25. ADR question and compatibility

A new ADR is required: **Workspace/Repository Identity and
Authority-Composition**. The existing ADR set does not define workspace
membership, persistent descriptive member state, active-selection currentness,
multi-member privacy, or composition isolation. Those are architectural
invariants, not implementation details, and must be accepted before code.

No conflict requiring modification of ADR 0011, 0016, 0018, 0021, or ADRs
0022-0026 was found. They remain authoritative for Trusted Profile
composition, reviewed Commit, repository mutation identity/policy, generic
HostExplicit dispatch, and capability-specific reviewed routes. The new ADR
must wrap those boundaries and must not amend them merely to make a workspace
union convenient. If the future design requires changing their exact
repository or authority contracts, implementation must stop and return to an
explicit ADR conflict decision.

must use two fresh disposable repositories A and B and a fresh workspace. It
must prove:
