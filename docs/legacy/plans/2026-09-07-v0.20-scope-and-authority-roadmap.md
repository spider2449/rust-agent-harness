## Current released capability baseline

v0.19 has 13 edition-2024 packages, all `0.19.0`, with no dependency drift.
Its first-party tools cover `fs.read`, repository observation, bounded
worktree authoring (`repo.patch`, create/edit/delete/rename file, and
create-directory), host-owned Stage/Unstage, reviewed `repo.commit`, and
bounded local `repo.create-branch`.  The latter creates one absent local head
at captured attached HEAD; it does not switch branches, affect index/worktree,
or provide generic Git.

Desktop has host-selected repository context, Codex/llama configuration,
repository-scoped conversations with resume, Effective Authority, and inert
Trusted Profile path persistence with explicit Restore.  External providers
are admitted local stdio MCP and Process Plugin adapters.  Tools converge on
the same RAH-owned `Tool` / `ToolRegistry` boundary.

## Architectural invariants

RAH remains an orchestration system, not an inference engine.  Model/provider
metadata and frontend state are untrusted requests, never authority.  `Tool` /
`ToolRegistry`, capability-specific host policy, selected repository and
currentness checks remain mandatory.  Trusted Profile composes authority but
does not create it; Execute is only the outer dispatch gate.

Observation, content mutation, index mutation, reviewed history, local-ref
creation, checkout/HEAD transition, remote Git, provider lifecycle, network,
and software installation remain distinct planes.  Timeout, cancellation,
disconnect, crash, or lost response is not rollback; a possible effect is
observed, never replayed or compensated.  There is no generic shell/process/
filesystem/Git capability, network-isolation claim, or OS-sandbox claim.

## Candidate A — Tool selection / dispatch

### A1. Runtime/API required-tool or named choice

The certified adapter snapshots the host registry at thread start, translates
definitions to `thread/start.dynamicTools`, and maps a later private alias
back to the snapshot before emitting RAH events.  Its `turn/start` request has
only translated input plus fixed `approvalPolicy: never` and read-only
sandbox policy.  The shipped `0.149.0` schema fixture records experimental
`dynamicTools` on `ThreadStartParams` and only `threadId`/`input` on
`TurnStartParams`; its local generated-schema research found no `tool_choice`,
required-tool, named-tool, or equivalent selector.  The 0.153.4 comparison
was explicitly non-certified and added no such control.

Current upstream documentation describes app-server as a rich-client protocol
and the current source/documentation still describes dynamic tools as the
experimental client-mediated lifecycle; it is not evidence that current main
applies to 0.149.0.  Sources: [Codex App Server documentation](https://learn.chatgpt.com/docs/app-server)
and [current app-server source README](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md).
The version-pinned local schema and Task 207B are the decisive 0.149 evidence.

Conclusion: no certified required-choice contract exists to implement.  A
future version/baseline may be researched independently, but a baseline change
or a prompt trick is not v0.20.  If upstream later supplies a host constraint,
it must be a **host-only dispatch policy** that names only an already admitted
Tool and still requires registry lookup, PermissionLevel, capability policy,
repository/currentness, and review/preconditions.  Dispatch selection is not
capability authorization.

### A2. Explicit host/user invocation

This is the selected direction.  A user can request a concrete, already
visible public Tool operation even when the runtime does not select it.  The
host resolves the exact public Tool from the current Effective Authority
inventory, presents/collects a closed validated input, obtains the normal
capability-specific host checks, and dispatches through `ToolRegistry`.

It is useful product work, not merely diagnostics: all v0.19 first-party
authoring/ref capabilities and admitted external Tools are otherwise only
conditionally reachable through model selection.  It must not become a
parallel arbitrary JSON/debug console.  Task 235 must choose a bounded first
release surface, argument-review model, eligibility policy, cancellation and
activity semantics before any implementation.  The host may reject tools
whose inputs/effects cannot be safely reviewed; visibility never means
host-invokable.

No new model-visible authority is needed.  A new **host-owned dispatch policy
and Desktop workflow contract** is likely needed to distinguish a human
explicit action from a runtime `item/tool/call`, bind the current composition,
and ensure user intent cannot bypass normal authority.  It constructs no
underlying capability authority; existing per-Tool policies remain decisive.

### A3. Diagnostics only

The bridge already has substantial proof: advertised public/alias evidence,
strict alias snapshot mapping, `ToolRequested`/Started/Finished events, and
hardened live fixture checks.  Better display of “advertised but not requested”
would improve explanation and support, but it cannot make a model select a
Tool.  It is supporting work, not the v0.20 product milestone.

## Candidate B — Branch switching

Switching an existing branch is a separate `HEAD`/index/worktree transition,
not an extension of ref creation.  It needs a new host-only authority and a
new ADR: host-selected existing local target; exact current branch, HEAD,
index/worktree snapshot; clean-only admission initially; rejected dirty,
staged, untracked/ignored overwrite hazards, conflicts, submodules, sparse
checkout ambiguity, special states, linked worktrees, and locked/reparse
uncertainty.  No stash, force checkout, discard, automatic switch-back, or
rollback is safe.

It changes HEAD and may change index/worktree and must revoke reviewed-commit
authorization, advance repository generation, refresh state, and define
runtime/conversation currentness.  A timeout/cancel/disconnect/crash after
process start has possible HEAD/index/worktree/lock effects; observe safely
without replay, then mark conservatively stale.  It is valuable, but broader
than the demonstrated reachability bottleneck and should follow a dedicated
contract research task if selected later.

## Candidate C — Create-and-switch

Users often want this workflow, but it is composition of two independent
authorities: existing bounded ref creation and B's transition authority.  It
must be two explicitly authorized steps, not one merged capability.  Create
can succeed while switch fails or becomes uncertain; the new ref remains and
must not be deleted or compensated.  The compound changes refs and potentially
HEAD/index/worktree, invalidates review on the switch phase, and inherits the
same no-replay observation rule.  Convenience does not justify the extra
partial-effect taxonomy, currentness, or rollback temptation.  Defer.

## Candidate D — Branch lifecycle

### D1. Delete

Deletion is a new destructive local-ref authority, not create authority.  It
would require host-bound source ref, exact expected old OID CAS, current-branch
prohibition, merged-only semantics without force-delete, bounded reflog
contract, fresh ref observation, and no replay.  It changes a ref and Git
reflog; it must not change HEAD/index/worktree/history/remote state.  Timeout
or lost result may mean deletion occurred; fresh observation can classify the
desired state but cannot attribute it, and rollback by recreating is forbidden.
High blast radius and moderate product need: defer.

### D2. Rename

Rename is distinct: host must bind source OID, destination absence/collision
rules, source/destination prefix and Windows case-only behavior, and reflog
movement.  Current-branch rename differs materially from inactive-branch
rename and can alter symbolic HEAD metadata; partial source/destination state
is possible.  It changes refs/reflogs and may alter currentness, never index or
worktree by intention.  No automatic reversal after ambiguous execution.
Separate ADR/contract research; defer.

## Candidate E — Network MCP

Streamable HTTP MCP adds endpoint and egress authority, not merely a transport.
It needs host-owned admission for endpoint identity, TLS/certificate handling,
redirects, DNS/effective destination, proxy environment, credentials/auth and
secret persistence, request/response bounds, server identity, reconnect/retry,
provider lifecycle/currentness, and uncertain remote effects.  It can cause
network and remote-provider effects, while `ToolRegistry` can still normalize
resulting tools.  Disconnect or ambiguous response is observable only through
fresh bounded status where the provider supports it; never resend a possibly
effectful call.  Value is high but security, dependency, and live-certification
risk are too broad for the next release.  Defer.

## Candidate F — PluginManager

Convenient discovery/enable/disable is separable from authority to download,
install, update, replace, or execute new software.  Current fixed Process
Plugin composition does not grant the latter.  A manager needs source/provenance
identity, version selection, durable desired/active state, executable identity
and replacement, restart/teardown, update/crash recovery, and an explicit
supply-chain policy.  It changes provider lifecycle and potentially filesystem,
network, executable installation, and persisted desired state; an interrupted
update has ambiguous installed/active versions and no automatic rollback.
Defer; do not casually add installation authority.

## Candidate G — Dynamic profile reload

An explicit human Reload has less risk than automatic detection, but both
replace an active authority composition.  It needs fresh source identity and
validation, provider restart/lifetime ownership, atomic registry publication,
generation/currentness changes, in-flight call treatment, failure retention,
and clear desired-versus-active state.  Automatic hot reload adds unobserved
authority changes and needs a much stronger justification.  It affects provider
lifecycle and active authority but must never restore or grant authority from
persisted data.  Failed/restarted processes and in-flight external calls are
possible effects; no stale call is replayed.  Defer both, with explicit Reload
only a possible later narrower candidate.

## Candidate H — Session / workflow capability

Branch-aware conversations, checkpoints, saved authoring intent, reviewed
operation plans, and explicit continuation can improve usability, but current
repository-scoped persistence already addresses basic conversation resume.
Durable workflow state must remain descriptive and inert: it cannot serialize
a live registry/process/authority or resume a pending possible effect.  Fresh
host authority, repository identity/generation, provider/profile/runtime state,
and preconditions must be revalidated before any new action.  It mainly changes
persisted descriptive state, not capability authority; crash recovery must
report uncertain pending work rather than replay it.  Useful later, but less
demonstrated than reachability.

## Candidate I — Cross-platform live parity

Linux/macOS Desktop live parity is valuable release assurance and can uncover
platform-specific identity, reparse/symlink, executable, and lifecycle gaps.
It introduces no product capability or authority by itself; deterministic CI
is not live Desktop evidence.  It should be a release-quality supporting gate
when a product capability needs it, rather than consume v0.20's sole product
milestone absent an identified platform authority defect.

## Tool reachability decision

**Choice: 3 — MIXED.**  Do not continue adding model-visible capabilities as
the primary v0.20 product path while their certified Codex route may advertise
them but never select them.  Task 207 proves this across external providers;
Task 229 proves it also for a first-party local-ref Tool after Desktop
composition and real host execution were independently certified.  Neither
establishes an RAH-controlled cause, nor establishes a universal model/external
cause.  Pinned 0.149 required-tool support is absent; research-only 0.153.4
does not demonstrate it either.

Continue only with a host-explicit path that uses already composed capabilities
and preserves all normal checks, while Task 235 investigates the exact
dispatch contract.  This makes existing value reachable without claiming that
model selection is fixed.

## Selected v0.20 milestone

### Product capability

**Explicit Host Tool Invocation Workflow.**  A Desktop user can deliberately
request an eligible public, currently composed Tool operation and receive its
normal progress/result state even if Codex does not select the Tool.

### Authority

No new model-visible or capability-specific authority.  A narrow host-owned
dispatch policy is required only to authorize the *route* from explicit human
intent to `ToolRegistry`.  It cannot construct repository, filesystem, index,
history, branch, provider, network, executable, or credential authority.

### Model input

The model continues to request only tools supplied by its existing dynamic-tool
contract; it may not invoke the host-explicit route, nominate a Tool for it,
or convert text into execution.

### Host input

The host owns eligibility, exact public name resolution, selected repository,
current composition/generations, closed input collection/review, all existing
permission and capability-policy checks, lifecycle ownership, and cancellation.
The user supplies only a UI action and bounded inputs accepted by the selected
Tool schema and host review.

### Effect and non-effect

The only possible effect is the selected existing Tool's already authorized
effect.  The dispatch mechanism itself changes no repository contents, index,
HEAD, refs, history, provider lifecycle, network state, executable state, or
persisted authority.  It does not grant generic JSON execution, generic shell,
Git, filesystem, or provider control.

### Uncertainty

After a Tool reaches its possible-effect boundary, its own outcome contract
governs.  UI cancellation, disconnect, crash, timeout, or lost result never
causes automatic retry, replay, compensation, or a claim of rollback.  The
activity must identify this as host-explicit, not model-selected.

### Composition, Desktop, and live gate

Only current, host-composed and policy-eligible public Tools are registered as
host-invokable; normal `ToolRegistry` dispatch remains mandatory.  Desktop
needs a clearly separate explicit action, sanitized capability/effect and
currentness display, bounded argument/review flow, lifecycle activity source,
and conservative unavailable/stale/uncertain state.  Certification requires a
fresh Windows Desktop fixture proving: explicit user route; exact public Tool
and arguments; one normal registry dispatch; all underlying authority and
preconditions; correct requested/started/finished or host-equivalent lifecycle
source; postconditions; terminal state; cleanup; and a marker proving it was
not a model dynamic request.  Model-selection certification remains separate.

## Required authority boundary

`host explicit dispatch != runtime/model dynamic dispatch != capability
authorization`.  The proposed policy may constrain *which already-authorized
Tool* an explicit host action reaches; it must not broaden that Tool, infer a
capability from presence/advertisement, or bypass ToolRegistry, PermissionLevel,
selected-repository checks, review/preconditions, and currentness.  It is
authority-neutral with respect to underlying effects, but it is not a casual
UI shortcut and needs its own contract research.

## Explicit non-goals

- Required-tool prompting, fake lifecycle events, prompt retries, or manual
  calls presented as model-selected execution.
- Generic shell.exec, process.exec, fs.write, Git, arbitrary refs, checkout,
  reset, clean, branch switch/delete/rename, remote Git, or network MCP.
- Automatic rollback, network-isolation or OS-sandbox claims, automatic
  authority restore/reload, or provider metadata authority.
- Codex baseline migration, live re-runs, provider installation/update, and
  automatic selected-milestone implementation in Task 235.

## Recommended implementation sequence

1. **Task 235 — Explicit Host Tool Invocation Contract Research**: identify
   eligible Tool classes, human-intent/input-review semantics, event/source
   taxonomy, concurrency/cancellation, currentness, and external Tool policy.
2. Create an ADR only if that research establishes a genuinely new enduring
   host dispatch authority; do not create one merely to number tasks.
3. Implement the minimal private dispatch foundation and deterministic misuse,
   stale/currentness, cancellation, and no-bypass tests.
4. Add Desktop composition and an explicit, non-debug user workflow.
5. Run a separately authorized Windows host-explicit live gate; keep
   model-selected certification separate.
6. Perform milestone audit, release preparation, and appropriate parity work.
