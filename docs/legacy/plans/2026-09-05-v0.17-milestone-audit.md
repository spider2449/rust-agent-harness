## Architecture audit

RAH remains an orchestration layer, not an inference engine. `Tool` and
`ToolRegistry` remain the extension boundary, and the runtime depends on
RAH-owned neutral contracts rather than concrete providers. `rah-protocol`
remains dependency-bottom. The shared composition crate depends on the RAH
tool/provider adapters and is consumed by CLI/Desktop; it does not make
provider types part of neutral public APIs.

No new authority class or architectural decision was introduced. Existing
ADRs, especially the Trusted Profile composition boundary, remain sufficient;
no new ADR is required.

## Authority/security audit

The implementation preserves the required invariants:

- model output, provider metadata, frontend state, and advertisement are
  untrusted requests rather than authorization;
- missing permissions fail closed and provider metadata cannot escalate them;
- Execute remains an applicable dispatch gate, not generic mutation authority;
- observation, bounded worktree mutation, file creation/deletion/rename,
  directory creation, index mutation, and reviewed commit remain separate;
- timeout, cancellation, disconnect, and crash do not imply rollback or replay;
- provider supervision is not claimed to be OS sandboxing; network isolation
  is not claimed.

The provider-only Desktop profile rejects first-party capability declarations,
keeps the Desktop-selected repository canonical, and admits only the selected
external providers. Static selection is host-only and inert. Provider
activation occurs during explicit Connect/reconnect composition, and failed
admission does not publish a partial registry.

## Trusted Profile/Desktop provider integration audit

The shared composer participates in both MCP and Process Plugin composition.
Mixed-provider tests verify exact admission, host-configured permissions,
fresh registry merge, and owned provider lifetime. Duplicate public Tool names
fail closed during the final merge. Disconnect/shutdown cleanup and executable
renameability demonstrate child reaping in the tested Windows fixture path.
Reconnect uses a fresh composition rather than reviving stale provider
children or proxy Tools. First-party Desktop Tool construction remains
host-owned and is merged with external Tools only after all required host
preconditions are current.

## Configured / effective / advertised / current audit

Desktop keeps these states distinct:

- **Configured** is host intent from the selected profile and its admitted
  descriptors.
- **Effective** is the successfully composed inventory in the current host
  registry.
- **Advertised** is what the connected runtime received for that publication.
- **Current** requires matching repository, model, profile, connection, and
  publication generations for the active host/runtime context.

The Task 206 false-Stale fix is retained. Every registry definition must be
classified as a first-party host Tool or an explicitly admitted external Tool;
unknown definitions fail closed. External entries are host-derived
descriptors, never provider-metadata authority. Refresh Authority remains
observation-only and cannot activate, reload, reconnect, execute, or grant
authority.

## Effective Authority audit

External descriptors expose only bounded host-owned presentation: public RAH
Tool name, MCP or Process Plugin source kind, sanitized provider identity,
Trusted Profile configured permission, External effect class, External
authority category, and `repositoryBound=false`. Private Codex aliases such as
`rah_tool_N` remain internal routing details and are not public authority
identity.

`repositoryBound=false` means RAH does not represent the external Tool as
repository-bounded. It does not assert that the external process cannot affect
repositories, files, or host state. Likewise, `PermissionLevel` describes the
host admission gate and is not proof that ambient external effects are absent.

## Provider security/admission audit

The inherited boundaries remain in force:

- MCP is local stdio only, with exact expected names, normalized schemas,
  explicit host permission, native executable validation/revalidation, bounded
  messages/queues/results/stderr/timeouts, cancellation, shutdown, and no
  automatic restart.
- Process Plugin uses protocol v1, configured identity/version handshake,
  exact names and normalized schemas, explicit host permission, native
  executable validation/revalidation, bounded resources, cancellation,
  shutdown, and no automatic restart.
- Windows native executable rules, script rejection, link/junction/reparse
  hardening, identity revalidation, and child cleanup remain covered by the
  provider fixtures.

No network MCP, generic subprocess, generic shell, or provider-selected argv,
cwd, environment, or resource limits were introduced.

## External-effect lifecycle audit

Deterministic Desktop tests cover the conservative rules:

- ToolRequested alone infers no external effect.
- ToolStarted immediately invalidates reviewed-commit authorization.
- ToolFinished refreshes the selected repository regardless of success/error.
- Started-without-finish is uncertain, refreshes the selected repository, and
  leaves reviewed-commit authorization revoked.
- With no selected repository, no repository state is fabricated.

These rules are deterministic and host-owned. They were not live-certified by
a real model-selected external Tool call in Task 207, so this audit does not
claim live external-effect invalidation or refresh.

admission, composition, effective inventory, dynamic-tool advertisement, and
provider lifecycle ownership. The following remain **NOT ESTABLISHED live**:

- model-selected MCP Tool execution through Desktop;
- model-selected Process Plugin Tool execution through Desktop;
- real Desktop external ToolStarted/ToolFinished lifecycle;
- live external-effect review invalidation and terminal repository refresh;
- full Windows model-driven external execution; and
- Linux external-provider live certification.

Task 207 is therefore **INCONCLUSIVE / EXTERNALLY BLOCKED FOR THE EXECUTION
SUB-GATE**, never PASS. A completed assistant turn or predictable text marker
is not execution evidence.
