## Executive decision

RAH v0.22 should be defined by one capability:

> **HostExplicit Reviewed Multi-File Edit Authoring** — a connected-current
> Desktop user can prepare, inspect, and explicitly confirm one bounded
> change-set over one through four existing clean tracked UTF-8 files through
> the already-authorized `repo.edit-files` capability.

The required new boundary is a **capability-specific HostExplicit reviewed
workflow policy**, not a new generic filesystem or repository authority. The
underlying authority remains ADR 0014's private
`RepositoryMultiFileMutationPolicy`; the HostExplicit route adds only the
typed human Prepare/Review/Confirm binding, exact change-set review, ticket
currentness, and provenance rules needed to reach that existing Tool safely.

The operation is explicitly **non-atomic**. The review must say that the
native replacements occur in deterministic host-owned path order and that a
verified committed prefix can be reported as `partial_effect`. A lost or
contradictory result remains `uncertain`. RAH must not retry, replay, continue
the remaining prefix, restore preimages, or claim rollback.

This is the smallest next product capability that addresses a concrete v0.21
limitation while reusing a mature RAH-owned capability and the proven v0.21
reviewed-authoring route. It does not imply HostExplicit eligibility for any
other Tool.

## Evidence base

The decision is based on the current checkout, not on a redesign of the
architecture.

### Current architecture and authority invariants

`README.md`, `docs/ARCHITECTURE.md`, `docs/ARCHITECTURE_GUARDRAILS.md`, and
`docs/SECURITY.md` establish that:

- RAH orchestrates providers and is not an inference engine;
- `Tool` and `ToolRegistry` are the common built-in/MCP/Process Plugin boundary;
- model output and provider metadata are untrusted requests, never authority;
- Trusted Profile is host-owned authority composition, not model authority;
- `PermissionLevel::Execute` is an outer dispatch permission, not repository
  mutation authority;
- HostExplicit dispatch, runtime/model dispatch, and underlying capability
  authority are separate boundaries;
- fixed subprocesses and supervision are not OS sandboxing;
- RAH makes no network-isolation or race-free TOCTOU claim;
- timeout, cancellation, disconnect, or a lost response does not imply
  rollback; and
- uncertain external effects are never automatically replayed.

The production crate topology remains provider-neutral. `rah-protocol` stays
at the dependency bottom, provider-specific implementation remains behind
adapter edges, and no candidate below requires a dependency or package
version change for this research decision.

### v0.21 product and live evidence

The released v0.21 product flow is:

```text
inspect
 -> typed human repo.patch Prepare
 -> exact bounded review
 -> opaque single-use ticket-only Confirm
 -> existing repo.patch / ADR 0012
 -> inspect diff
 -> existing Stage / Unstage
 -> existing reviewed Commit
```

The exact current HostExplicit set in
`crates/rah-desktop/src/host_invocation.rs` is:

```text

repo.status
repo.diff
repo.diff-staged
repo.create-branch

```

The same file's exact-allowlist test rejects `repo.create-file`,
`repo.edit-files`, `repo.delete-file`, `repo.rename-file`,
`repo.create-directory`, `repo.commit`, external Tools, and unknown names.
`crates/rah-desktop/src/effective_authority.rs` separately classifies those
Tools for observation, but visibility and classification do not make them
HostExplicit eligible.

Task 252's milestone audit records the v0.21 production route as complete.
Task 251's final Windows connected-current certification proved Prepare with
zero Tool executions and zero replacements, followed by Confirm with one Tool
execution and one native replacement, exact postimage, unchanged protected
Git state, no model lifecycle, and no external provider activity. It did not
certify model-selected execution, external-provider HostExplicit execution,
or other authoring Tools.

The remaining user-visible authoring limitation is concrete: one reviewed
`repo.patch` invocation can change only one existing tracked file. A typical
coherent source change can require several files, while the current Desktop
route still requires separate model/runtime authoring or a future manual
workflow for the additional files.

### Existing multi-file capability

ADR 0014 is accepted and the current implementation is present in
`crates/rah-tools/src/repository_multi_file_edit.rs` and
`crates/rah-tools/src/repository_multi_file_preflight.rs`.

The existing `repo.edit-files` contract already provides the important safety
properties needed for a reviewed human route:

- one through four existing clean HEAD-tracked regular strict-UTF-8 files;
- one through sixteen exact literal replacements per target;
- complete file SHA-256 and byte-length preconditions;
- all-target preflight before the first persistent target mutation;
- one shared repository mutation lease;
- canonical path validation and link/reparse rejection;
- deterministic ascending UTF-8-byte-order target commits controlled by the
  host, not by model-supplied order;
- unchanged index, HEAD, refs, and repository metadata as required by ADR 0014;
- result classes `ok`, `invalid_target`, `precondition_failed`,
  `failed_known_no_effect`, `partial_effect`, and `uncertain`; and
- no retry, replay, prefix continuation, rollback, recovery journal, or
  cross-file transaction claim.

The current deterministic tests cover successful ordered edits, preflight
failure, clean/index/HEAD/ref invariants, known no-effect failure, partial
effect, uncertain native outcome, and redacted output. Trusted Profile and the
Generic Codex Tool Bridge already compose the capability through the ordinary
Tool boundary. The missing piece is the reviewed human HostExplicit route,
not a generic write primitive.

## Authority baseline and decision constraints

The following accepted decisions remain authoritative:

| Decision | Current role | v0.22 consequence |
| --- | --- | --- |
| ADR 0012 | Existing bounded one-file `repo.patch` worktree-content authority | Do not widen it to multi-file effects. `repo.patch` remains valid for one-file work. |
| ADR 0014 | Separate bounded `repo.edit-files` multi-file worktree authority | Reuse it as the underlying capability. Preserve deterministic ordering and non-atomic partial/uncertain outcomes. |
| ADR 0021 | General HostExplicit currentness, D2, coordinator, ticket, and provenance boundary | Reuse it; add no generic JSON or direct Tool console. |
| ADR 0022 | v0.21 H1 reviewed HostExplicit workflow for `repo.patch` only | Preserve its host-derived bindings, zero-effect Prepare, exact review, opaque ticket, and no-replay rules. Multi-file semantics need a new documented boundary. |
| ADR 0016 | Separate reviewed staged-snapshot commit/history authority | Keep Stage and reviewed Commit as separate human actions. Do not make multi-file editing imply commit. |
| ADR 0011 | Trusted Profile authority composition | Profile/provider metadata cannot self-enable HostExplicit eligibility. |

The recommended scope therefore adds no `PermissionLevel`, no generic
filesystem authority, no generic Git authority, no provider bypass, no model
authority, and no new dependency edge.

### Matrix conclusion

Candidate 2 is the only serious candidate that simultaneously has:

1. a demonstrated user gap immediately after v0.21;
2. an already implemented and tested underlying capability;
3. a narrow, typed HostExplicit extension rather than a new authority class;
4. a review contract that can represent every possible effect, including a
   partial prefix and uncertainty; and
5. a bounded Windows certification path that does not require a model request,
   external provider, network, or new Git history operation.

The other candidates either duplicate an existing workflow, require a new
authority plane, create external/provider/network lifecycle risk, or are
assurance/operational work rather than a single product capability.

## Selected v0.22 capability and exact authority boundary

### Product capability

The user-facing capability is **HostExplicit Reviewed Multi-File Edit
Authoring**:

```text
inspect
 -> typed multi-file Prepare
 -> complete ordered change-set review
 -> opaque ticket-only Confirm
 -> existing repo.edit-files / ADR 0014
 -> inspect diff/status
 -> existing Stage / Unstage
 -> existing reviewed Commit
```

This is one change-set operation, not four independent clicks and not a
transaction. The user explicitly confirms the complete bounded set before the
first Tool dispatch.

### New boundary

The new authority boundary is a HostExplicit workflow policy with these exact
properties:

- HostExplicit adds exactly `repo.edit-files` to the current first-party
  allowlist. The existing seven eligible names remain unchanged.
- Eligibility requires a connected-current Desktop composition, the selected
  repository, host-composed `repo.edit-files` authority, the current expected
  complete `ToolDefinition`, and current permission membership through D2.
- The human form accepts only a closed typed change-set: one through four
  repository-relative target paths and bounded literal old/replacement text
  for each target. The human does not supply repository roots, native paths,
  Git executables, permissions, Tool definitions, authority handles, or
  model/provider metadata.
- The host derives every target's exact preimage SHA-256 and byte length,
  canonical `repo.edit-files` ToolInput, target identity, postimage evidence,
  review identity, repository identity, and currentness tuple.
- Prepare is zero-effect. It must not call the Tool, perform a native
  replacement, stage, commit, alter refs, activate a provider, inject model
  events, or persist a capability/ticket. Read-only observation and bounded
  in-memory review construction are permitted.
- Review must contain all mutation-relevant changed material for every target,
  all target paths and preimage bindings, host-determined commit order, target
  count, replacement counts, exact effect, explicit non-effects, and the
  statement that the operation is non-atomic. Hidden, clipped, or redacted
  changed content is not confirmable; it fails closed under bounded review
  limits.
- The ticket is opaque, process-local, in-memory, single-use, expiring, and
  bound to the complete change-set, review, preimages/postimages, target
  identities, complete ToolDefinition, permission, repository/Git identity,
  composition, and currentness. Confirm receives only the ticket ID.
- Confirm revalidates the coordinator, connection, repository, composition,
  generation, definition, permission, every target, every preimage, and the
  exact reviewed change-set before HostExplicit `Started`.
- After the pre-start D2 gate, one `authorized_tool_dispatch` reaches the
  ordinary `ToolRegistry` and existing `repo.edit-files` Tool. No direct Tool
  call or generic registry shortcut is authorized.
- ADR 0014 remains responsible for all-target preflight, shared mutation lease,
  host-controlled ordering, native commit points, result taxonomy, and
  post-observation.
- A successful effect refreshes repository workflow state and conservatively
  invalidates old reviewed-commit authorization. Stage and reviewed Commit
  remain separate explicit actions.

### Explicitly authorized effect

Only the existing ADR 0014 effect is authorized: exact conditional content
replacement in one through four existing clean tracked regular strict-UTF-8
files, with the host-controlled deterministic order and existing per-file
bounds. The worktree may contain a verified committed prefix if a later target
cannot be completed.

### Explicitly not authorized

The v0.22 scope does not authorize:

- `repo.create-file`, `repo.delete-file`, `repo.rename-file`, or
  `repo.create-directory` through HostExplicit;
- `repo.commit` through HostExplicit, automatic Stage/Unstage, or automatic
  Commit;
- creation, deletion, rename, directory creation, overwrite, arbitrary full
  file write, binary edit, regex/fuzzy/unified-diff execution, glob/range
  selection, or untracked/staged-file authoring;
- cross-file atomicity, transaction semantics, rollback, compensation,
  restore-preimage, retry, replay, prefix continuation, or recovery journal;
- model-triggered HostExplicit activity, model lifecycle events, conversation
  injection, or provider-selected human authority;
- generic JSON/ToolName invocation, generic filesystem, shell, process, Git,
  branch/ref/history, credential, network, or OS-sandbox authority;
- MCP or Process Plugin HostExplicit eligibility;
- Network MCP or Streamable HTTP;
- Trusted Profile hot reload, automatic restore, PluginManager behavior, or
  durable reviewed-operation/ticket persistence; and
- any race-free TOCTOU, network-isolation, rollback, or process-supervision
  claim.

### New ADR decision

A new ADR is needed before implementation, but it must be created by a later
authorized task. The recommended title is:

`ADR 0023 — HostExplicit Reviewed Multi-File Authoring Boundary`

It should record the HostExplicit eligibility and the capability-specific
review/currentness contract, not create a new mutation policy. A new ADR is
clearer than silently amending ADR 0022 because multi-file editing has a
materially different result model: deterministic multiple commit points,
verified partial prefixes, and explicit non-atomic semantics. ADR 0014 should
remain the underlying capability decision; ADR 0012 should remain one-file
authority; ADR 0021 should remain the general dispatch boundary. Task 256
does not create or modify that ADR.

## Deterministic and live release-gate strategy

### Deterministic gate

The implementation milestone must prove, through RAH-owned interfaces and
local fixtures, at least:

- exact HostExplicit allowlist: the v0.21 seven plus only `repo.edit-files`;
- built-in/repository-host source restriction and provider rejection;
- typed human input with host-derived hashes, lengths, ToolInput, target
  identities, order, review identity, and no authority-bearing frontend fields;
- zero Tool execution and zero native replacement attempts during Prepare and
  revalidation;
- complete, bounded, safely escaped review for all targets, with no hidden
  mutation-relevant content and an explicit non-atomic warning;
- opaque ticket-only Confirm, single-use/expiry/cancellation, coordinator
  exclusion, currentness, repository-generation, composition, definition,
  permission, target-identity, preimage, and Git-state invalidation;
- D2 complete-definition/permission admission before `Started`, exactly one
  ordinary registry dispatch after `Started`, and no fabricated model events;
- successful deterministic target ordering and exact postimages;
- known no-effect, precondition, invalid-target, partial-effect, and uncertain
  result classification with redacted bounded output;
- no automatic retry, replay, continuation, rollback, restore, compensation,
  second confirmation, or inferred success after a lost/malformed result;
- unchanged index, HEAD, refs, history, remotes, protected sentinel files,
  provider/profile state, conversation persistence, and model lifecycle;
- effectful-start reviewed-commit invalidation followed by fresh, not
  automatically authorized, staged review; and
- full source-content privacy in activity, transcript, logs, and live-evidence
  JSONL.

The focused checks should be followed by the repository's milestone sequence:

```text
cargo fmt --check
cargo check --workspace
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
git diff --check
```

Any implementation task must additionally audit that no dependency edge,
Cargo package version, ADR outside the authorized task, or unrelated frontend
surface changed.

### Windows/live gate

Release certification should use the production connected-current Desktop path
on a fresh disposable Windows repository containing four clean tracked UTF-8
files and an unrelated sentinel. The gate must observe:

- Prepare performs zero Tool calls and zero replacements;
- the review shows all four exact changes, host order, preimages, postimages,
  effects, non-effects, and non-atomic semantics;
- Confirm receives only an opaque ticket ID and performs exactly one
  `repo.edit-files` registry dispatch;
- exactly the intended four postimages are present and the sentinel, index,
  HEAD, branch, refs, tags, remotes, and history are unchanged;
- the activity is private HostExplicit activity with no model request,
  ToolRequested/Started/Finished lifecycle, conversation injection, or
  external provider activity;
- stale/currentness and cancellation behavior is fail-closed; and
- a fresh repository is used for every attempt, with no cleanup action treated
  as rollback or recovery.

Deterministic fault injection remains the appropriate evidence for partial and
uncertain native outcomes; a successful live run must not be presented as
proof of atomicity or rollback. The release claim remains Windows-specific
unless a separate platform gate establishes another platform. Ubuntu CI is
deterministic evidence, not Linux Desktop live certification.

The final release gate must check the exact pushed commit, branch, push event,
completed status, successful conclusion, and exact `head_sha`. Missing,
queued, in-progress, or different-head CI is not success. v0.21.0's tag object
and peeled target remain immutable historical evidence throughout v0.22 work.

## Deferred alternatives and why they lose

- **Structural create/delete/rename/directory authoring:** valuable, but each
  is a separate authority and review model. Combining them would turn a
  focused release into a family of destructive and structural workflows with
  different Windows and uncertainty proofs.
- **HostExplicit commit:** the existing reviewed Commit workflow already owns
  the useful review boundary. A second direct route would duplicate durable
  history authority and weaken the distinction between editing, staging, and
  committing.
- **Higher-level editing plans:** a plan can later describe a change-set, but
  it cannot substitute for the underlying typed capability reviews. Persisting
  executable plans risks treating descriptive state as authority.
- **Session persistence/resume:** current in-memory tickets and authorizations
  are intentionally not restorable. Descriptive conversation resume does not
  prove a repository or capability is still current.
- **MCP/Process Plugin HostExplicit:** external schemas and processes need
  provider-specific typed review, effect contracts, and lifecycle proofs.
  Provider composition and permission assignment do not supply those proofs.
- **Network MCP/Streamable HTTP:** this is new network and remote-effect
  authority, not a transport-only upgrade. RAH has no current network MCP
  implementation or isolation claim.
- **Trusted Profile reload:** an explicit reload may be a later operational
  improvement, but it is not the strongest user-facing capability after the
  proven single-file authoring route. Automatic hot reload remains unsafe.
- **PluginManager:** installation/update/lifecycle management is outside the
  current focused adapter and would introduce executable and trust authority.
- **Broader live parity:** valuable release assurance, but it does not answer
  the demonstrated product gap and cannot define v0.22 by itself.
