## Current released product

RAH is a provider-neutral orchestration system, not an inference engine. The
released product has separate host-owned boundaries for:

- observation: fs.read, repo.file-info, repo.status, repo.diff, and
  repo.diff-staged;
- bounded worktree authoring: repo.patch, repo.create-file, repo.edit-files,
  repo.delete-file, repo.rename-file, and repo.create-directory;
- human-owned index mutation: Desktop Stage and Unstage;
- reviewed history mutation: repo.commit through reviewed staged
  authorization;
- local ref creation: repo.create-branch without switching branches;
- external providers: local stdio MCP and Process Plugin admission through a
  trusted host profile.

All six authoring Tools already have capability-specific host policies and are
composed by the current Desktop/profile layers when their host authorities are
available. Their presence is not HostExplicit eligibility.

v0.20 adds a connected-current Desktop HostExplicit plane. Its exact
first-release allowlist is:

    fs.read
    repo.file-info
    repo.status
    repo.diff
    repo.diff-staged
    repo.create-branch

The route is a backend-recognized human action, typed input, current
composition, D2 current-definition/permission admission, and capability-owned
execution. Branch creation uses:

    typed prepare -> zero-effect sanitized review -> explicit confirm
    -> immediate revalidation -> D2 -> existing branch authority

The ticket is opaque, in-memory, process-local, single-use, bounded-lived, and
bound to Tool definition, input, composition, permission policy, repository
identity/generation, and Desktop currentness. HostExplicit does not emit model
Tool lifecycle events, create chat content, or create/restore authority.

Windows live certification proved repo.status and repo.create-branch through
the production connected-current route. The other four read Tools are
deterministic-only release evidence. Linux/macOS live parity and real GUI
mouse automation were not certified.

## Remaining demonstrated workflow gaps

The principal post-v0.20 gap is not a missing backend write primitive. RAH can
already author a bounded source change through capability-specific Tools, but a
human cannot invoke those Tools through the reliable new Desktop HostExplicit
plane.

The desired human workflow is incomplete here:

    inspect -> explicitly prepare/edit -> inspect diff -> Stage -> reviewed Commit

The missing step is explicit, reviewed worktree authoring. Stage/Unstage and
reviewed Commit already exist as separate authority planes. Branch creation is
available, but branch creation does not make a user work on that branch and is
not a substitute for source authoring.

Two older reachability gaps remain evidence-backed but do not justify making
model selection the v0.21 dependency:

- Task 207 did not establish model-selected MCP or Process Plugin execution.
- Task 229 did not certify model-selected repo.create-branch after two bounded
  0/0/0 attempts.

Task 240 deliberately proved HostExplicit success with zero model lifecycle.
That supports expanding the human plane, not claiming Codex selection changed.

## Architectural invariants

The following invariants remain unchanged:

- A model request, model text, provider metadata, Tool advertisement, frontend
  state, Effective Authority presentation, or PermissionLevel is not capability
  authorization.
- Trusted Profile is host-owned composition. A profile entry may select an
  already constructed authority but cannot create, broaden, or self-enable it.
- Tool and ToolRegistry remain the extension boundary. No provider bypasses the
  registry or policy.
- HostExplicit dispatch, runtime/model dispatch, and capability authorization
  remain distinct. D2 checks the current Tool definition and host permission;
  the Tool enforces its own authority.
- Repository observation, worktree content, file entries, directories, index,
  history, local refs, branch switching, providers, network, and conversation
  state are different effect classes.
- The host fixes repository selection, executable identity, working directory,
  environment policy, limits, authority construction, and security-sensitive
  fields. User/model input is bounded request data only.
- A possible effect is not a known no-effect result. Timeout, cancellation,
  disconnect, crash, or lost response does not imply rollback.
- Uncertain effects are not automatically retried, replayed, restored, deleted,
  reset, or compensated.
- No candidate introduces generic shell, process, filesystem-write, Git, or
  arbitrary ref authority as a convenience.
- No candidate claims OS sandboxing, network isolation, or race-free external
  world TOCTOU behavior.

## Candidate A — HostExplicit worktree authoring

### Decision within Candidate A

Candidate A remains the strongest family, but it must not become one
undifferentiated six-Tool allowlist.

- A1 — repo.patch only: selected for v0.21.
- A2 — repo.edit-files plus repo.create-file: valuable but too broad for the
  first authoring contract because it combines multi-file partial effects with
  exact new-content creation.
- A3 — all six authoring Tools: rejected for v0.21 because destructive,
  structural, rename, and multi-file semantics need separate review UX.
- A4 — one higher-level authoring-review workflow: useful later, but it must
  compose capability-specific Tools rather than become a generic write Tool.

The selected A1 capability is one bounded exact conditional text replacement
workflow for one existing clean tracked file. It is an explicit human route to
the existing repo.patch capability, not a new write capability.

### Product value

A1 materially improves the central Desktop workflow: a user can inspect a
selected repository, prepare an exact source edit, review what will change,
confirm it, inspect the resulting diff, and continue to existing Stage and
reviewed Commit flows.

A1 does not claim all source authoring is complete. New files, multiple files,
deletion, rename, and directory setup remain separate workflows. Narrowness is
intentional: one-file patch review can be exact without pretending that all
mutation result taxonomies are interchangeable.

### Authority analysis

| Question | A1 disposition |
| --- | --- |
| New model-visible authority? | No. Normal model-visible repo.patch behavior is unchanged, and HostExplicit creates no model request. |
| New host-only authority? | Yes: typed human Prepare/Review/Confirm dispatch for the already composed repo.patch Tool. |
| New underlying capability authority? | No. ADR 0012 and RepositoryWorktreeMutationPolicy remain authoritative. |
| State that may change | File bytes and ordinary worktree metadata for one authorized target. |
| State that must not change | Git index, HEAD, attached branch, refs, tags, remotes, history, repository configuration, providers, profile state, conversation state, and any other path. |
| First possible effect | Existing patch Tool native replacement attempt after lease and final preimage revalidation. Prepare is zero-effect. |
| Uncertain result | Preserve repo.patch uncertainty; expose bounded possible-effect-unknown activity and refresh/reobserve. |
| Replay | Never automatic. A new attempt requires fresh observation and a new ticket. |
| Rollback | Not promised. RAH does not restore old bytes after ambiguity. |
| Currentness | Ticket binds current definition, permission, composition, repository identity/generation, runtime/profile/connection state, and exact target preimage. |
| Reviewed commit | Effectful route invalidates existing reviewed commit authorization and refreshes presentation. Prepare does not arm commit authorization. |
| Repository generation | Existing first-party mutation handling refreshes workflow state but does not use repository selection generation as a mutation counter. A1 binds current generation and preimage without inventing new generation semantics. |

### Why A1 instead of the other A options

repo.patch has one bounded target, conditional literal replacement semantics,
and a review that can show an exact bounded diff. repo.edit-files has up to four
files, ordered replacement, partial-effect inventory, and more complex review.
repo.create-file has absent-path, parent, exact-content, and partial-write
semantics. A3 would combine destructive and structural operations. Those
differences are authority-relevant, so A1 is the smallest coherent slice.

## Candidate B — HostExplicit reviewed commit

repo.commit already has a human reviewed staged authorization through
RepositoryCommitControl and the Desktop repository workflow. The review binds
repository, branch, old HEAD, raw/staged index state, tree, policy generation,
and one-shot authorization. The commit Tool consumes it; a HostExplicit
confirmation must not synthesize or arm it.

The existing flow is already:

    observe staged review -> human authorize exact review
    -> commit Tool consumes one-shot authorization

A second HostExplicit path would need to decide who prepares the commit, whether
Confirm can arm review (it must not), how a message is bound, and how an index
change invalidates both states. It largely duplicates existing UX and adds a
second route to durable history. B is deferred.

Authority: no new underlying commit authority, but a high-risk host-only
binding. The effect is durable history and current-branch ref movement. Lost
results remain uncertain; no reset or rollback is allowed.

## Candidate C — Local branch switching

Branch switching is genuinely new capability authority. Even a clean-only
contract may mutate symbolic HEAD, current branch, index/worktree materialized
files, reflogs, and checkout state. It is not a refinement of
repo.create-branch.

### C1 — clean-only existing local branch

C1 is the only credible future starting point: normal non-bare repository,
attached HEAD, no merge/rebase/cherry-pick/bisect/special operation, no staged
or unstaged tracked changes, no relevant untracked overwrite, supported sparse
checkout state, target existing local branch, target not checked out in another
linked worktree, exact host Git identity, fixed argv/config, no force, no stash,
no reset, no arbitrary commit/path checkout, one attempt, and post-effect
HEAD/index/worktree observation.

C1 requires a new authority ADR. It must bind current branch, HEAD OID, index
and worktree identity, special-state absence, target eligibility, linked
worktree status, executable identity, and currentness. A switch can partially
materialize files or return an ambiguous result. There is no automatic
switch-back. Reviewed commit authorization must be invalidated on any possible
transition and Desktop currentness refreshed.

### C2 — broader dirty switch

C2 is rejected. Dirty switching needs preservation/discard, untracked
collision, index stage, conflict, stash, and recovery policy. It conflicts with
the no-discard/no-stash/no-rollback invariants.

C1 has future value but is not the smallest response to the current product
gap. It follows a dedicated authority research task.

## Candidate D — Create-and-switch

Create-and-switch is not one safe compound primitive. It should compose:

    existing repo.create-branch authority
    + separate future branch-switch authority

Branch creation may succeed while switching fails. The branch must not be
automatically deleted, and the worktree must not be restored. Partial outcomes
must be observed and reported as two effects with two authorizations. D remains
deferred with C.

## Candidate E — Branch lifecycle

Branch lifecycle is two independent new ref authorities.

### E1 — branch deletion

The narrow possible contract is inactive local branch only, exact old OID
compare-and-delete, no force delete, no current branch, no linked-worktree
target, explicit merged/unmerged policy, and reflog observation. A delete can
be uncertain; RAH cannot recreate the ref or erase its reflog as rollback.

### E2 — branch rename

Rename needs source exact OID, destination absence, current/inactive policy,
prefix-collision rules, reflog movement, case-only Windows behavior, and
partial-effect handling. Current-branch rename is materially different from
inactive rename because symbolic HEAD and user-visible branch identity are
involved.

E has lower demonstrated value and higher ref-state risk than A1. Defer.

## Candidate F — External-provider HostExplicit

Local stdio MCP and Process Plugin Tools are admitted through host-owned profile
composition. They can define arbitrary schemas, ambient effects, provider
lifecycle, secrets, process/network effects, and uncertain disconnect
semantics. Execute permission and provider metadata do not make them safe for
generic human invocation.

A schema-generated arbitrary JSON form would recreate the generic Tool console
rejected by ADR 0021. Each provider Tool would need a host-owned typed form,
effect/review contract, lifecycle owner, secret policy, currentness binding,
and result taxonomy. Provider metadata must never self-enable it.

F changes provider/process state and may have unknown repository or external
effects. Disconnect and lost result are not replayed or rolled back. Defer.

## Candidate G — Network MCP

Network MCP is a new network authority boundary, not merely another transport.
It requires host-owned endpoint admission, TLS/server identity, redirect and
DNS-rebinding policy, proxy behavior, credentials/token/OAuth lifecycle,
bounded requests/responses, egress policy, reconnect/retry rules, cancellation,
provider lifecycle, and uncertain remote-effect handling.

A remote server may mutate external state before RAH receives a response. RAH
cannot claim rollback or replay safety from a disconnected client. G has very
high blast radius and no current workflow evidence requiring it. Defer.

## Candidate H — Trusted Profile reload

### H1 — explicit human Reload

H1 could make a remembered profile active only after fresh read, static
validation, host composition, and atomic replacement. Provider shutdown/start
and failure behavior must be defined. Safe failure retains the prior active
composition when the new one is invalid; it does not silently restore authority.

Reload must exclude active model turns and HostExplicit work, invalidate stale
tickets, increment relevant profile/composition generations, and retain
conversations as descriptive history rather than authority. H1 has operational
value but does not close the main authoring gap.

### H2 — automatic hot reload

H2 is rejected for v0.21. Watchers create TOCTOU, surprise provider
shutdown/start, stale ticket, and authority-review problems. Automatic reload
needs substantially stronger evidence.

## Candidate I — Higher-level authoring/workflow plan

I can add a descriptive operation plan, saved change-set preview, branch-aware
checkpoint, or resumable sequence of explicit approvals without adding a
primitive authority. It must never persist capability authority, opaque tickets,
reviewed commit authorization, provider handles, or assumptions that a prior
repository generation remains current.

I is valuable after A1 establishes a real reviewed authoring contract. A plan
can later compose A1, diff, Stage, and Commit as separately authorized steps.
Defer as the primary milestone.

## Candidate J — Host result to chat

J could let a human select a completed HostExplicit result and attach a
sanitized immutable snapshot to a later user turn. It must create a new
user/context attachment, not fake Tool lifecycle, replay a Tool, grant
permission, or silently continue a model turn.

J is a useful inspection handoff but does not enable authoring. Defer.

## Candidate K — Cross-platform live parity

Linux/macOS HostExplicit live certification is release assurance, especially for
path, Git, and Tauri differences. It is not by itself a new product
capability. It should not be selected merely for completeness.

If A1 is implemented, live evidence should include supported target platforms
that the release claims. Standalone K remains assurance unless platform demand
is the actual product gap.

## Candidate L — Model Tool-selection research

The certified Codex baseline remains 0.149.0 evidence. Task 207 and Task 229
show no actionable RAH-controlled path from the current certified protocol to
reliable model Tool choice. Newer non-certified upstream behavior cannot be
treated as current evidence, and this task does not install or migrate Codex.

L should be revisited only if a stable required/named Tool protocol field that
RAH controls is demonstrated, or a separately authorized baseline migration is
approved. Defer L.

## Candidate M — Post-start host cancellation

v0.20 can cancel prepared-but-unstarted work and has no post-start abort
command. Adding one requires owned task cancellation for first-party Tools,
provider/process child cancellation, effect-boundary classification, and
terminal handling after a cancellation race.

Cancellation after a filesystem or provider effect boundary is not rollback. A
cancelled task may still require observation and end uncertain. No demonstrated
need outweighs A1. Defer.

## Candidate N — Existing HostExplicit live coverage

Live-certifying fs.read, repo.file-info, repo.diff, and repo.diff-staged would
strengthen release assurance. It would not create a new user-visible
capability because these Tools are already eligible and deterministically
covered. N is a validation task, not the primary v0.21 product milestone.

### Common HostExplicit review abstraction

A common lifecycle is appropriate:

    typed request -> capability-specific zero-effect prepare
    -> sanitized review -> opaque single-use ticket
    -> currentness/preimage revalidation -> D2 -> existing Tool

The common parts may be ticket storage, currentness binding, concurrency
exclusion, D2 admission, bounded activity, and no-replay handling. The
abstraction must not erase each Tool's DTO, preimage identity, effect class,
result parser, or review-refresh rule.

### Review UX

- R1, typed form then immediate execution, is insufficient for source mutation.
- R2, generic Prepare/Review/Confirm, is safe only when capability-specific.
- R3, exact bounded diff plus preimage identity plus Confirm, is required for
  A1 and is recommended.
- R4, generic JSON or patch editor, is rejected as an execution console.

### Patch versus edit-files

repo.patch is the first human-review candidate because it has one clean tracked
target and one bounded diff. repo.edit-files has several preimages,
deterministic order, and partial-effect inventory. A human change-set UI can
support it later, but A1 must not treat its result as single-file success.

## New-authority decision

Choice: 2 — NEW HOST-ONLY WORKFLOW/DISPATCH POLICY.

v0.21 does not need a new underlying repository capability authority. It does
need an enduring host-only policy for typed human Prepare, sanitized exact
review, single-use ticket, immediate revalidation, and HostExplicit dispatch of
the existing repo.patch Tool.

“No new underlying authority” does not mean “add a button.” The backend owns
the typed DTO, capability-specific review, ticket, preimage binding, result
classification, invalidation, and currentness checks. Frontend presentation
remains untrusted.

## HostExplicit vs branch-switch decision

YES — HostExplicit should expand before branch switching.

Evidence:

- the blocked workflow is explicit source authoring, not branch navigation;
- repo.patch already has bounded capability, preimage validation, lease,
  post-observation, and uncertainty taxonomy;
- v0.20 already provides the dispatch/currentness/ticket plane;
- branch switching changes HEAD, index/worktree materialization, and user
  context and needs a new capability authority and ADR;
- A1 unlocks Diff, Stage, and Commit without changing refs or HEAD.

Branch switching remains valuable, but follows the smaller authoring extension.

## Selected v0.21 milestone

### Exact name

HostExplicit Reviewed Single-File Patch Authoring

### User capability

A Desktop user can choose one current repository-relative path, specify a
bounded literal replacement, inspect a sanitized exact preimage/change preview,
and explicitly confirm one existing repo.patch operation without model Tool
selection.

### Existing authority reused

- RepositoryWorktreeMutationPolicy and RepositoryWorktreePatchTool;
- repository selection, canonical identity, executable, and mutation lease;
- existing Tool schema/parser and result taxonomy;
- D2 authorized dispatch;
- connected-current composition and currentness generations;
- Desktop repository refresh and reviewed-commit invalidation;
- repo.diff, Stage/Unstage, and reviewed repo.commit as separate steps.

### New authority

No new underlying repository authority. The new enduring policy is a closed
repo.patch HostExplicit eligibility classification and capability-specific
Prepare/Review/Confirm contract.

### Model input

None for the selected HostExplicit route. Model text, model Tool calls,
conversation attachments, provider metadata, and model-generated UI state
cannot prepare or confirm it. Normal model-selected repo.patch behavior is
unchanged.

### Human input

- one repository-relative path;
- one bounded literal expected-old fragment;
- one bounded replacement fragment;
- explicit review acceptance and ticket confirmation.

The Desktop should derive current file hash/length and identity at Prepare
rather than ask the user to copy authority-bearing preimage fields.

### Host input

The host fixes selected repository, canonical root, Git executable,
environment/configuration, Tool name and complete definition, permission,
profile/model/connection/composition identities, repository generation,
mutation lease, limits, and ticket lifetime.

### Prepare/review

Prepare must have zero Tool execution and zero filesystem effect. It must:

1. require connected-current Desktop state and an idle coordinator;
2. validate the closed typed request;
3. resolve the target beneath the selected repository with existing path/reparse
   rules;
4. capture target identity, bytes, SHA-256, length, Git/HEAD, index, branch,
   refs, repository identity/generation, and current definition/policy;
5. require repo.patch preconditions and a unique literal match;
6. compute a bounded sanitized diff without executing repo.patch;
7. create an opaque, nonserializable, single-use, expiring ticket bound to
   exact input, preimage, composition, currentness, and review identity.

The review identifies relative target, bounded old/new content or exact diff,
preimage hash/length, replacement count, effect, and non-effects. It does not
expose absolute paths, executable paths, temporary names, authority handles,
raw backend errors, secrets, or environment data.

### Confirm

Confirm accepts only the ticket ID. It consumes the ticket once and rechecks
coordinator state, composition, Tool definition, permission, repository
identity/generation, target identity/bytes/hash/length, Git state, and reviewed
input immediately before dispatch. Any mismatch fails closed without
re-preparing or executing updated input.

The route calls D2 and ordinary ToolRegistry execution. It does not call the
Tool directly, synthesize model events, arm commit review, or retry.

### Effect

Only the existing repo.patch effect is authorized: one bounded conditional
replacement in one existing clean tracked file using current native semantics.

### Non-effects

No staging, commit, HEAD move, branch switch, ref/tag/remote/configuration
change, directory or new-file creation, provider/network call, profile or
conversation persistence change, or second Tool execution.

### Uncertainty

If the native attempt or observation is ambiguous, report bounded
possible-effect-unknown activity and preserve repo.patch uncertain semantics.
Refresh/reobserve and invalidate reviewed commit authorization. Never retry,
replay, restore, or claim rollback. A later edit requires fresh observation and
a new ticket.

### Currentness

The ticket is stale on expiry, cancel, repository selection/generation change,
composition/profile/model/connection change, disconnection, coordinator
conflict, Tool definition/permission change, repository identity change, or
target preimage change. Ticket and in-flight execution are not persisted or
resumed across restart.

Repository generation is a context identity, not an automatic mutation
sequence. A1 binds it and refreshes workflow state without inventing new
generation semantics.

### Composition

Add repo.patch to the explicit first-party host classification only when the
current published composition contains the expected Tool and host-composed
authority. D2 permission and definition must match. Trusted Profile metadata
cannot self-enable it.

### Desktop

The UX needs a typed patch form, bounded Prepare, safe exact diff review,
ticket-only Confirm, HostExplicit activity, stale/busy/error handling, and
refresh into the existing diff/review workflow. No raw JSON editor or model
text trigger is permitted.

### Live gate

Release certification should use a fresh disposable repository and production
connected-current Desktop path and prove:

- exact eligibility and D2 checks;
- Prepare with zero Tool/native attempts and unchanged file/Git state;
- sanitized review and bounded nonserializable ticket;
- stale, changed-preimage, changed-definition, expired, reused,
  wrong-repository, busy, and permission-denied rejection;
- exactly one Confirm execution and no second attempt;
- exact postimage and bounded repo.diff observation;
- unchanged HEAD, branch, index, refs, tags, remotes, and sentinel files;
- HostExplicit activity only, no fake model Tool events, zero model lifecycle;
- reviewed commit authorization revoked and workflow refreshed;
- conservative uncertain/lost-result handling with no replay/rollback;
- disposable-fixture cleanup without calling cleanup rollback.

Deterministic coverage must cover all supported effect/error classifications and
platform-specific identity/path rules. The Task 229 model fixture is not A1
evidence.

## ADR recommendation

Recommend a new narrow ADR or explicit ADR 0021 amendment before
implementation; do not create it in Task 245.

No new underlying-authority ADR is needed for repo.patch: ADR 0012 and the
implementation already define that capability. But v0.21 adds an enduring
policy that an existing effectful Tool may be reached by a human HostExplicit
Prepare/Review/Confirm route with capability-specific preimage DTO and ticket.
ADR 0021 currently defers worktree authoring until this contract exists.

The follow-on ADR should record only A1 eligibility, human versus host fields,
zero-effect prepare, exact preimage review, ticket/currentness/permission
binding, uncertainty/refresh/review invalidation, and bans on generic JSON,
model-triggered HostExplicit, replay, and rollback. It must not broaden
repo.patch or create a generic mutation abstraction.
