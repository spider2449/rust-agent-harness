# Codex Integration Spike

Date: 2026-08-20

Status: Task 019 research result. No Codex integration or RAH architecture change is included.

## Decision summary

For RAH v0.1, the best available Codex integration boundary is a version-pinned
`codex app-server` subprocess using its stdio JSON-RPC protocol. This boundary is
documented for deep client integrations, supports headless thread lifecycle,
events, approvals, and cancellation, and keeps all Codex implementation types
inside `rah-runtime-codex`.

RAH should not embed the current Codex Rust crates and should not vendor selected
Codex source. The current Rust crates expose usable symbols, but they form a large,
tightly coupled workspace API rather than a supported Rust SDK. OpenAI currently
documents TypeScript and Python SDKs; the Python SDK itself controls a local Codex
app-server process. The process protocol is therefore the clearest supported seam.

This recommendation does **not** establish that a live `CodexRuntime` can yet meet
RAH's tool-security invariant. Codex built-in command, file-change, and MCP actions
are executed inside the Codex runtime rather than being emitted as neutral RAH
`ToolCall` values for `ToolRegistry` dispatch. That mismatch must be resolved before
enabling live Codex tool execution.

## Research baseline

The findings use these exact baselines:

- Local CLI: `codex-cli 0.148.0`.
- Upstream source tag: `rust-v0.148.0`, peeled commit

  `codex app-server generate-json-schema`.

  `AgentEvent`, `ModelBackend`, `ToolRegistry`, and `Sandbox`.

## Answers required by Task 019

### 1. Which Codex crates are required for a headless agent session?

There are three technically possible boundaries:

| Boundary | Direct Codex crates in RAH | Assessment |
| --- | --- | --- |
| Spawn `codex app-server` | None | Recommended. `rah-runtime-codex` owns a child process and translates the versioned JSON-RPC wire protocol. |
| Embed app-server | `codex-app-server` and `codex-app-server-protocol`, transitively including `codex-core` and `codex-protocol` | Headless, but embeds almost the entire application and its transport/runtime assumptions. |
| Embed core session loop | At minimum `codex-core` and `codex-protocol` | `ThreadManager`/`CodexThread` can start sessions, submit operations, and read events, but configuration, auth, provider, persistence, tools, MCP, and sandbox support arrive through a large internal graph. |

`codex-app-server-protocol` is not a lightweight standalone dependency: at 0.148.0
it directly uses several other Codex workspace crates. Using generated or locally
defined wire DTOs at the process boundary is narrower than linking the protocol
crate.

The current 0.148.0 Rust crates are not available as matching releases from
crates.io. A direct Rust integration would therefore require Git dependencies on
the Codex monorepo or vendoring, in addition to accepting the internal API risk.

### 2. Which public APIs appear intended for reuse?

The intended integration surfaces are:

1. The app-server JSON-RPC protocol. OpenAI describes it as the boundary for rich
   clients that need authentication, conversation history, approvals, and streamed
   agent events. It uses JSON-RPC 2.0 semantics but omits the standard `jsonrpc`
   header. Stdio is the default transport and carries newline-delimited JSON;
   WebSocket support is experimental.
2. Version-generated JSON Schema and TypeScript bindings from
   `codex app-server generate-json-schema` and `generate-ts`.
3. The documented TypeScript and Python Codex SDKs. Both offer thread start,
   execution, and resume concepts. The Python SDK explicitly manages a local
   app-server process.
4. `codex mcp-server`, when Codex should appear as a tool inside some other
   orchestrator. This is not equivalent to implementing RAH's `AgentRuntime`.

At the Rust source level, `codex-core` publicly exports `ThreadManager`,
`StartThreadOptions`, `NewThread`, and `CodexThread`. `CodexThread` publicly exposes
submission, event retrieval, shutdown, and thread state operations. These are
source-public APIs, but current product documentation does not identify them as a
supported Rust SDK or give them a compatibility promise.

### 3. Which APIs are internal or unstable?

Treat the following as internal or unstable:

- All direct `codex-core`, `codex-protocol`, `codex-app-server`, sandbox, provider,
  state, rollout, and tool workspace APIs. Rust visibility alone is not an SDK
  stability guarantee.
- Codex internal `Op`, `Event`, rollout, configuration, provider, and sandbox
  representations.
- Experimental app-server fields and methods, including dynamic tools.
- App-server WebSocket transport, which the documentation marks experimental.
- Auto-approval review payloads, which the generated 0.148.0 schema explicitly
  marks unstable.
- Legacy v1 app-server methods. A new adapter should use the documented v2 thread,
  turn, and item APIs and tolerate additive notifications.

The generated schema should be pinned and reviewed whenever the Codex CLI version
changes. Unknown notifications must not crash the adapter.

### 4. How are sessions started and resumed?

The app-server connection starts with `initialize`, followed by the client
notification `initialized`.

- `thread/start` creates a thread and returns its Codex thread identifier.
- `turn/start` supplies user input and begins work in that thread.
- `thread/resume` loads an existing persisted thread.
- A resumed thread does not itself start new model work; a subsequent `turn/start`
  is required for new input.
- `thread/fork` creates a new thread from existing history.

For direct Rust reuse, `ThreadManager::start_thread`,
`resume_thread_from_rollout`/`resume_thread_with_history`, and `fork_thread` expose
the analogous operations.

RAH must keep its own mapping between neutral `SessionId` and Codex thread ID.
There is a semantic mismatch in the current `AgentRuntime::resume(session_id)`:
the RAH call has no new input, while Codex separates loading a thread from starting
a turn. The adapter must not invent input or silently start a turn. Task 019 does
not change this API.

### 5. How are events represented?

App-server models execution as:

```text
thread -> turn -> item
```

JSON-RPC notifications include `thread/started`, `turn/started`,
`turn/completed`, `item/started`, `item/completed`, and item-specific deltas or
progress such as `item/agentMessage/delta`. A completed turn reports a terminal
status such as completed, interrupted, or failed. Items are tagged variants for
messages, reasoning, command execution, file changes, MCP calls, dynamic tool
calls, and other Codex capabilities.

Direct Rust consumers read `codex_protocol::protocol::Event` values from
`CodexThread::next_event`; their payload is an internal, more detailed event model.

The app-server notifications map more safely than direct Rust events because their
wire schema is generated for a particular CLI version. Even so, RAH must translate
only into RAH-owned events and define forward-compatible handling for unknown
Codex notifications.

### 6. How are tool calls represented?

Codex has more than one tool representation:

- Built-in command execution and file changes are first-class turn items, with
  progress/completion notifications and optional approval requests.
- MCP calls are first-class MCP tool-call items and are executed by Codex's MCP
  manager.
- App-server dynamic tools are declared when starting a thread and invoked through
  the experimental server request `item/tool/call`; the client returns success or
  error content.
- Internal Rust protocol types additionally represent custom, dynamic, MCP, shell,
  and other tool calls.

Only the dynamic-tool callback resembles RAH's desired host-dispatch boundary, and
it is experimental. Built-in and MCP actions do not naturally follow RAH's required
path:

```text
ToolCall -> ToolRegistry -> policy -> Sandbox -> Tool -> ToolOutput
```

Consequently, an adapter must not merely translate Codex's post-execution item
notifications into `AgentEvent::ToolRequested`/`ToolStarted`/`ToolFinished`; doing
so would falsely imply RAH authorized and executed the action. Live integration is
blocked until there is a concrete design that either disables Codex-owned action
execution or mediates every actionable request through RAH's registry and policy
boundary.

### 7. How are approvals represented?

App-server sends server-initiated JSON-RPC requests scoped by thread and turn. The
0.148.0 schema includes:

- `item/commandExecution/requestApproval`;
- `item/fileChange/requestApproval`;
- `item/permissions/requestApproval`.

Command and file decisions include accept, accept for session, decline, and cancel;
command approvals may also carry execution-policy or network-policy amendments.
Permission approvals can describe requested filesystem and network grants and
their scope.

This is richer than RAH's current `ApprovalRequest`, which contains one neutral
tool call and a reason. More importantly, `AgentRuntime` currently has no public
method for returning an approval decision. It can emit
`AgentEvent::ApprovalRequired`, but cannot complete Codex's pending JSON-RPC
request through a RAH-owned interface. Automatic denial is representable; an
interactive accept/decline flow is not. This is an explicit contract mismatch, not
an authorization to change the trait in Task 019.

### 8. How is cancellation handled?

App-server uses `turn/interrupt`. A successful interruption is observed through a
terminal `turn/completed` notification whose status is interrupted. Direct Rust
reuse can submit the corresponding interrupt operation and can shut down a thread.

The natural mapping is:

```text
AgentRuntime::cancel(session_id)
    -> resolve active Codex thread and turn
    -> turn/interrupt
    -> wait for terminal interrupted notification
    -> AgentEvent::Cancelled
```

The adapter must own the child-process, reader, pending-request, and event-stream
lifecycle. Dropping a RAH event stream must not detach those resources. Cancelling
an idle thread and losing the app-server process require defined adapter-local
errors rather than fabricated success.

### 9. Which sandbox helpers are coupled to Codex assumptions?

Codex's sandbox and approval policy are separate layers. Its execution stack is
coupled to:

- Codex configuration names and policy enums;
- Codex command/file-change tool implementations and approval protocol;
- per-turn working directory and writable-root rules;
- Codex network policy and proxy behavior;
- platform-native implementations such as Linux Landlock/seccomp, macOS Seatbelt,
  and the dedicated Windows sandbox/helper executables;
- Codex rollout, telemetry, MCP, and process-management lifecycle.

These helpers are not drop-in implementations of RAH's `Sandbox` trait. RAH's
current `ProcessSandbox` represents a direct `program + args` execution boundary,
whereas Codex's sandbox protects commands selected inside its full runtime. Reusing
Codex sandbox crates would import Codex policy types and execution assumptions into
RAH's neutral boundary. The adapter may configure Codex's own sandbox defensively,
but must not claim that this makes Codex-owned tools pass through RAH's sandbox.

### 10. Can model-provider behavior be replaced cleanly?

Not with RAH's `ModelBackend`.

Codex supports configured model-provider records, base URLs, authentication,
headers, and a limited set of wire APIs. That permits some endpoint substitution
inside Codex. It does not expose a documented app-server hook that delegates model
completion to an arbitrary RAH `ModelBackend`, and the Rust provider/client types
are coupled to Codex configuration, auth, request metadata, retry, streaming, and
feature assumptions.

Therefore `CodexRuntime` should be treated as an optional full `AgentRuntime`, not
as a generic implementation of RAH's `ModelBackend`. Provider replacement within
Codex is a Codex configuration feature, not RAH's provider-neutral backend seam.

### 11. What transitive dependency cost is introduced?

The subprocess design adds **no Codex Cargo dependency edge**. It adds an explicit
runtime dependency on a compatible Codex executable, JSON-RPC framing, process
lifecycle management, and a version/schema compatibility policy.

Direct reuse is large. For the 0.148.0 tag, a current Windows Cargo resolution of
normal and build dependencies produced these approximate distinct package counts:

| Root package | Distinct packages | Codex-named packages |
| --- | ---: | ---: |
| `codex-protocol` | 347 | 12 |
| `codex-app-server-protocol` | 566 | 30 |
| `codex-core` | 867 | 76 |
| `codex-app-server` | 910 | 103 |

The measurement used `cargo tree --edges normal,build` and distinct package labels
on `x86_64-pc-windows-msvc`; feature unification, target selection, and future
Codex revisions can change the totals. It is a scale indicator, not a reproducible
lockfile guarantee for RAH.

The graph includes async/network stacks, authentication, keyring support, MCP,
state and SQLite support, image/audio handling, telemetry, configuration, file
watching, platform sandbox crates, and many Codex workspace crates. This would
substantially increase compile time, supply-chain surface, platform complexity,
and upstream-update work for an optional adapter.

### 12. Is direct crate reuse preferable to selective vendoring?

Between those two choices, direct reuse at an exact upstream Git revision is
preferable to selective vendoring because it preserves upstream source identity
and makes upgrades auditable. However, neither is recommended for v0.1:

- direct reuse imports a large, undocumented Rust compatibility surface;
- selective vendoring creates a local fork across tightly coupled crates and moves
  security fixes and protocol evolution onto RAH maintainers;
- selecting only a few files is unlikely to remain buildable because session,
  provider, tool, persistence, and sandbox concerns are cross-linked.

The preferred order is:

1. Pinned app-server subprocess and generated-schema compatibility fixtures.
2. A future official Rust SDK, if OpenAI publishes and supports one.
3. Exact-revision direct crate reuse only if the process boundary proves
   insufficient and the maintenance cost is explicitly accepted.
4. No selective vendoring.

## Mapping to current RAH interfaces

| RAH concept | Codex app-server concept | Mapping status |
| --- | --- | --- |
| `AgentRuntime::start` | `thread/start`, then `turn/start` | Mostly clean. Adapter owns ID mapping and handshake. |
| `AgentRuntime::resume` | `thread/resume`, optionally later `turn/start` | Mismatch: current RAH resume has no input and does not express load-only versus continue-with-input. |
| `AgentRuntime::cancel` | `turn/interrupt` | Clean only for an active turn; completion must be confirmed asynchronously. |
| `AgentEvent::ModelDelta` | `item/agentMessage/delta` | Clean translation with adapter-owned model request IDs. |
| `AgentEvent::Completed` | `turn/completed` plus final agent message | Feasible; final-output assembly rules must be explicit. |
| `AgentEvent::Failed` | failed turn or JSON-RPC/process error | Feasible with adapter-local error classification. |
| RAH tool pipeline | built-in command/file/MCP items | Architectural mismatch: Codex can own dispatch, policy, sandbox, and execution. |
| `ApprovalRequired` | server-initiated approval requests | Payload can be reduced, but RAH has no approval-response operation. |
| `ModelBackend` | Codex provider/client internals | No clean substitution boundary. |
| `SessionStore` | Codex rollout/thread persistence | Separate ownership models; adapter must not expose Codex rollout types. |

## Required constraints for any later implementation

Task 020 and later work should preserve these constraints:

1. All Codex process, protocol, and generated DTO details remain private to
   `rah-runtime-codex`.
2. No Codex crate or type crosses into `rah-runtime`, `rah-model`, `rah-protocol`,
   `rah-tools`, `rah-session`, or `rah-sandbox`.
3. The Codex executable version is discovered and checked explicitly; protocol
   incompatibility fails with a typed adapter error.
4. Stdio framing, request correlation, notification handling, child ownership,
   interruption, and shutdown are adapter responsibilities.
5. Unknown additive notifications are ignored with diagnostics unless they are
   required to preserve lifecycle or security semantics.
6. Tests use captured JSON fixtures/generated schemas and a fake child transport;
   default workspace tests do not require a live model, credentials, or network.
7. Codex-owned tools remain disabled or otherwise non-operational until the RAH
   registry/policy/sandbox path is proven. Post-execution event translation is not
   an acceptable substitute.
8. Approval requests must not be accepted automatically. Until RAH has a response
   path, safe behavior is explicit denial or a documented unsupported-operation
   error.
9. Codex sandbox configuration is defense in depth local to the adapter, not a
   replacement for the RAH `Sandbox` contract.

## ADR and architecture impact

No ADR changes are required by this research task.

- ADR-0001 remains intact: `AgentRuntime` stays RAH-owned.
- ADR-0002 remains intact: Codex remains an optional adapter and no Codex type
  crosses a public RAH boundary.
- ADR-0003 exposes the principal unresolved mismatch: Codex-owned actions do not
  automatically enter RAH through `Tool` and `ToolRegistry`.
- ADR-0004 remains intact: neither the process adapter nor direct reuse would make
  RAH an inference engine.

No architecture deviation or new dependency edge was introduced. The unresolved
tool and approval mismatches are findings that constrain later work; they are not
resolved by this spike.

## Implementation follow-up

Tasks 020 through 024 implemented ADR-0005 without changing this research result.
The v0.1 adapter uses the pinned app-server process boundary, private JSON-RPC
translation, fake subprocess transport, captured schema contract, private session
mapping, and restricted `AgentRuntime` lifecycle described above.

Known Codex-owned tool surfaces are disabled in the restricted configuration.
Server-initiated tool and approval requests are rejected, and deterministic tests
prove that Codex tool-item notifications never produce RAH tool lifecycle events.
No Codex Rust crate dependency was added.
